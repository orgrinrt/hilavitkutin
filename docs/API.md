# hilavitkutin-api: Design

Consumer-facing types, traits, and platform contracts. Downstream
consumer applications depend on this crate to define WorkUnits. The
engine crate (hilavitkutin) also depends on it. `#![no_std]`, no
alloc. All index, count, and size types use arvo newtypes.

Depends on `hilavitkutin-ctx` for its `provider_generic!` /
`provider_generic2!` macros and the `Context<P>` provider-tuple
wrapper. WU execute parameter types and the WU-context accessor
traits are expressed via those macros; see "WU Context providers"
below.

The crate uses `provider` as a single workspace-wide vocabulary.
Two trait families share the noun:

1. The `Provider` trait declared in this section gates registration
   on the SchedulerBuilder. Every value passed to `.with(value)`
   impls it. See `## Provider, the unified registration contract`.
2. The ctx-framework accessor traits (`HasResourceProvider`,
   `HasColumnReader`, etc.) generated by `provider_generic!`
   expose runtime providers on the WU Context tuple. See
   `## WU Context providers` below.

The two families connect: a `Resource<T>` registered via
`.with(Resource::new(value))` becomes reachable in WU Context
tuples through `HasResourceProvider<R>`. Registration is the
build-time half; accessors are the run-time half. Both refer to
the same concept (a thing the scheduler provides), so both wear
the `provider` label.

## Provider, the unified registration contract

`SchedulerBuilder` takes one verb: `.with(value)`. Every type
accepted by `.with` impls the sealed `Provider` trait. The trait
gates registration and routes per-kind typestate updates through
its `Dispatch` associated type.

```rust
pub trait Provider {
    type Init;
    const KIND: ProviderKind;
    type Dispatch: Dispatch;
}
```

The associated `Init` names the construction-time value type. For
stateful wrappers (`Resource<T>`) it is the inner `T`. For the
zero-data wrappers (`Column<T>`, `Virtual<T>`, `LinkedBin<dyn Trait>`)
it is `()`. For unit-struct WorkUnits, Kits, and platform-impl types
it is `Self` (the registration value IS the construction value).

`Resource::new(value)` returns a value-carrying carrier rather than
dropping `value`. The builder moves each registered input onto a
staged value list at `.with`, so a registered store value is retained
until `build()` moves it into the `MemoryProvider`-allocated arena.
The zero-data wrappers (`Column<T>`, `Virtual<T>`) carry no value;
their `Init` is `()`.

`Dispatch` is the per-kind typestate router (next subsection). The
constant `KIND: ProviderKind` is a documentation and debugging aid;
load-bearing dispatch is via `Provider::Dispatch`, not the constant.

The trait carries `#[diagnostic::on_unimplemented]`. The message
points at the constructors a consumer reaches for: `Resource::new(value)`,
`Column::<T>::new()`, `Virtual::<T>::new()`, `LinkedBin::<dyn TraitFamily>::new()`,
plus the unit-struct WorkUnit, Kit, and platform-impl shapes. A type
that does not impl `Provider` cannot reach `.with`; the diagnostic
names the gap directly.

`Provider` is sealed via a private `Token` pattern. Consumer crates
cannot impl `Provider` directly; the substrate mints the trait for
the four router shapes (Unit, Store, Kit, Platform) plus the
consumer-reachable unit-struct shapes (WorkUnits, Kits, platform
impls).

## Dispatch: per-kind typestate routing

```rust
pub trait Dispatch {
    type NextWus<Wus>;
    type NextStores<Stores>;
    type NextPlatform<Platform>;
}
```

Each generic-associated type computes the next typestate accumulator
when a provider of the corresponding kind registers. The four router
structs sit beside `Provider`:

| Router | Routes |
|---|---|
| `UnitDispatch<W>` | Prepends `W` to the `Wus` accumulator. |
| `StoreDispatch<S>` | Prepends `S` to the `Stores` accumulator. |
| `KitDispatch<K>` | Concats `K::Units` into `Wus` and `K::Owned` into `Stores`. |
| `PlatformDispatch<P>` | Prepends `P` to the platform-tuple accumulator. |

For routers that do not affect a given accumulator, the
corresponding GAT is identity. `UnitDispatch<W>::NextWus<Wus> =
Cons<W, Wus>`; its `NextStores` and `NextPlatform` pass `Stores` and
`Platform` through unchanged. `StoreDispatch<S>::NextStores<Stores>
= Cons<S, Stores>`; its other two GATs are identity.
`KitDispatch<K>::NextWus<Wus> = <K::Units as Concat<Wus>>::Out`;
analogous for stores; platform GAT is identity.
`PlatformDispatch<P>::NextPlatform<Platform> = Cons<P, Platform>`;
its other two GATs are identity.

A single blanket impl on `SchedulerBuilder` over `P: Provider` reads
`P::Dispatch` and walks the per-kind GAT. The trait solver fails on
`Provider` directly when a non-`Provider` value is passed to
`.with`, surfacing the right diagnostic at the call site. Per-kind
blankets would route the failure through the wrong trait first (an
error pointing at `WorkUnit` when the user passed a `u32`).
Validated empirically; see
`mock/research/sketches/202605091700-builder-provider-shape/`.

## Store kinds (domain 06)

Five store kinds, one scheduling mechanism. All of them are views over
one `ColumnStorage` (see "Unified columnar storage" below); they differ
in intent and access, not in backing.

```rust
pub struct Resource<T>(PhantomData<T>);                   // singleton, one value
pub struct Column<T, D = Records>(PhantomData<(T, D)>);   // one value per record of D, written in place
pub struct Buffered<T, D = Records, Ch = Differs>(PhantomData<(T, D, Ch)>); // one value per record of D, read as last committed
pub struct Accum<T>(PhantomData<T>);                      // appended during a pass, grown from zero
pub struct Virtual<T>(PhantomData<T>);                    // zero-data, DAG edge only
```

`Column<T, D>` and `Buffered<T, D>` hold one value for each record of the
domain `D` (see "Record domains" below), and `Records` is the domain a
column is in when none is named. `Accum<T>` reserves a capacity at build
and grows from zero as units append during a pass, the populated prefix
being what a drain reads after the pass. `Buffered<T, D>` is described
under "The frame-buffered kind" below.

The scheduler sees StoreId pairs for edge construction. Does not care
about cardinality. `Write<Resource<X>> → Read<Resource<X>>` builds
the same edge as `Write<Column<Y>> → Read<Column<Y>>`. A `Buffered`
store is the one kind that builds no edge between its writer and its
readers, since a reader of it never sees what the writer wrote in the
same pass.

`StoreId` is a dense index assigned at plan time. Wraps an arvo
fixed-point newtype (not raw u16). `AccessMask` is the arvo-bitmask
`Mask64` (<=64 stores) or `Mask256` (<=256 stores). All scheduler ops
= single-instruction bitwise.

`AccessSet` is the api's bound over the type-level list of
`notko-hlist`. `Empty` and `Cons<H, T>` are that crate's types,
re-exported from this crate's root so that a unit's crate names one
crate, and consumer code meets them either directly or through the
`read!` / `write!` macros (which expand to nested `Cons` cells). The
api declares no list of its own: `Contains`, `ContainsAll` and `Concat`
are the shared crate's as well, and `AccessSet` adds the count as a
`USize` and the bound that says a list is made of store markers.
Compile-time store descriptors. Plan phase converts to runtime AccessMask via
monomorphised generic functions (the monomorphised function IS the
type identity, no TypeId, no std::any).

ZST erasure: column marker types constrain the DAG, enforce type
safety, and determine morsel sizes at compile time. Erased to plain
indices by execution time.

### Store wrappers as Providers

`Resource<T>`, `Column<T>`, and `Virtual<T>` each impl `Provider` so
they reach `.with` on the SchedulerBuilder. Their `Dispatch` is
`StoreDispatch<Self>`. `Resource<T>::Init = T` (the wrapper carries
the inner value at construction). `Column<T>::Init = ()` and
`Virtual<T>::Init = ()` (zero-data markers).

Construction at the call site is uniform:

```rust
.with(Resource::new(value))     // stateful wrapper, takes inner T
.with(Column::<T>::new())       // zero-data wrapper, generic turbofish
.with(Virtual::<T>::new())      // zero-data wrapper, generic turbofish
```

`Column` and `Virtual` impl `HasTrivialCtor` (from notko); the
`new()` method on each calls through to the trait's const-callable
zero-arg constructor. `Resource` keeps its inherent
`pub const fn new(value: T) -> Self` constructor because it carries
state; it does not impl `HasTrivialCtor`.

`Buffered<T, D>` and `Accum<T>` register the same way as `Column`
(`.with(Buffered::<T, D>::new())`, `.with(Accum::<T>::new())`), with
`Init = ()` and `Dispatch = StoreDispatch<Self>` on `BuilderInput`, the
trait this section still calls by its earlier name.

## Record domains

A record domain is a set of records with a count of its own and a key
order of its own. Every `Column` and `Buffered` store is in one domain,
named by the marker's second parameter, and one store list may hold
columns of several domains whose counts differ.

```rust
pub trait Domain: 'static {
    type Axes: Grid;  // the axes, first axis outermost
    type Reach: List; // the offsets a neighbour read in this domain may name
}

pub struct Records;                            // one axis, empty reach
pub struct Extent<D: Domain>(PhantomData<D>);  // the run-time shape of D
```

An axis is a marker type, and `Grid` is implemented for lists of axes. A
shape holds one length per axis, a key holds one coordinate per axis, and
`Grid` gives the record count of a shape and the conversion between a
key and a record's position in both directions. The key order is the
sequence of the axes list with the first axis outermost, so that in a
domain of the axes north then east the records of one northing are
adjacent.

`Records` is the domain of one axis that every column is in when no
domain is named, which is every column written before domains existed.
`Column<T>` therefore means what it meant.

Extents are run-time values and arrive as stores. `Extent<D>` is a
singleton store holding the shape of `D`, registered like a resource
with `.with(Extent::<D>::new(shape))`, or `.with(Extent::records(count))`
for `Records`. `build` takes no record count: each column is sized from
the extent registered for its domain, and a store list that holds a
column of `D` and no `Extent<D>` is refused at `build` by the same
membership bound that refuses a unit reading an unregistered store. A
unit may read an extent. No unit writes one, so the count of a domain is
fixed for as long as a built scheduler lives.

A unit iterates one domain, and it does not write which. The domain is
computed from the unit's read and write lists: every `Column` and
`Buffered` member of both names one domain, and a unit whose members
name two is refused where it is declared, with a message that says a
unit iterates one domain and these members are in two. A unit with no
such member iterates `Records`. Resources, extents, virtuals and
accumulators belong to no domain and are free in any unit.

The plan carries a record count for each domain that some registered
unit iterates. A fiber holds units of one domain, and its record range
and morsel window are those of that domain.

## LinkedBin

```rust
pub struct LinkedBin<T: ?Sized>(PhantomData<*const T>);
```

Type-system marker for an extension-loaded provider bin keyed by a
trait family. `LinkedBin<dyn LinterApi>` reserves a slot in the
SchedulerBuilder typestate that runtime instances populate via
`hilavitkutin-extensions`. `LinkedBin` impls `Provider<Init = ()>`
with `Dispatch = StoreDispatch<Self>`. It impls `HasTrivialCtor`
for the `LinkedBin::<dyn TraitFamily>::new()` form.

The wrapper is the type-system anchor only. Runtime instance
population happens in `hilavitkutin-extensions` plus `hilavitkutin`;
this declaration ships the marker so WUs can declare reads and
writes against `LinkedBin<dyn TraitFamily>` and the typestate
proves coverage at `.build()` time.

`?Sized` permits `dyn TraitFamily` parameters. The `PhantomData<*const T>`
field carries no `Send` / `Sync` requirements onto the wrapper
itself; bounds propagate from the consumer-side trait definition.

## ColumnValue trait (domain 05, R4)

```rust
pub trait ColumnValue: Copy + 'static {
 // trait-body default: the fallback every impl inherits
 const BIT_WIDTH: usize = core::mem::size_of::<Self>() * 8;
}

// empty blanket impl: any Copy + 'static type inherits the default
impl<T: Copy + 'static> ColumnValue for T {}
```

Any `Copy + 'static` type is column-storable, reporting a `size_of * 8`
width. Zero friction for consumers. The shape is spec-free: the default
lives in the trait body and the blanket impl is empty, so no
`specialization` (the full feature is forbidden) is involved.

BIT_WIDTH is a future hook for sub-byte bitpacking. The packed width of
an arvo sub-byte type is a storage-layer concern, read from arvo's own
width-reporting traits where bitpacking consumes it, not encoded as a
`ColumnValue` specialisation here. No pack/unpack today: the type IS the
storage (R3, R4).

Every store kind that holds values (`Column`, `Buffered`, `Accum`, and
`Resource` through its own bound) takes any `ColumnValue` at its native
stride. The contract has no sealed value type, no cell every value must
convert through, and no format tag. A store's identity is its marker
type and its `StoreId` is the plan's to assign, so an author declares no
id either.

## The value form (domain 09)

`RecordOp` is the form a unit is written in first. A unit declares the
members it reads and the members it writes, and is a function from the
values of its reads at one record to the values of its writes at that
record.

```rust
pub trait RecordOp: Send + Sync + 'static {
    type Read: ReadList;
    type Write: WriteList + Along<Self::Read>;
    fn apply(&self, read: &Vals<Self::Read>) -> Vals<Self::Write>;
}
```

`Vals<L>` is the shared list crate's product of one value per member of
`L`. A read is `read.get(MEMBER)` and is bounded on the read list holding
that member, so reading a member the unit did not declare does not
compile. The writes are returned by value as one product over the write
list, built in the list's sequence by the `rec!` macro, so a unit cannot
leave a declared write without a value and holds no handle that could be
used twice or kept.

What a member's value is depends on its kind:

| Member | In a read list | In a write list |
|---|---|---|
| a column | its `T`, the record's value | its `T`, the record's new value |
| a frame-buffered store | its `T`, the record's committed value | its `T`, the record's staged value |
| a neighbour read | the neighbour's committed value, or the edge's | not a write |
| a resource | its `T` | not written in this form |
| an extent | the shape | not written |
| an accumulator | not read | a `Maybe<T>`: append the value, or append nothing |
| a virtual | not read | a `Bool`: fire, or do not |

A value-form unit names no engine type. It has no context, sees no
index and no morsel range, and its crate depends on this crate alone.
`apply` must be a pure function of its reads: the engine may call it for
the records of a domain in any sequence, on any thread, and may compose
it with other units.

The api prefers not to break its public face when the plumbing
changes. The preference weighs most for the authors of units and of
data structures and less for the authors of runners, who are still
counted. It is a preference: a break is made where the design is better
for it, and each one is recorded with its reason. A unit in the value
form is what the preference costs least to keep for, since nothing of
the plumbing appears in it.

`ReadList` and `WriteList` are implemented for lists of members of the
kinds the table admits, and give the list of stores the members stand
for (a `Near` read stands for the store it reads). `Along` joins the
domains of the two lists and is what refuses a unit in two domains.

### The two forms and their routers

`WorkUnit` (below) is the block form: a unit handed a context for one
morsel, written where the body needs the whole morsel, a reduction over
it, or the providers directly. The value form is the default and the
block form is the wider one, and both stay.

Which form a unit is in is read off the router it names on
`BuilderInput`:

```rust
impl BuilderInput for Diffuse {
    type Init = Self;
    type Dispatch = RecordDispatch<Self>;   // value form
}

impl BuilderInput for Tally {
    type Init = Self;
    type Dispatch = UnitDispatch<Self>;     // block form, as before
}
```

Both routers append the unit to the builder's unit list. One api trait
says what the plan needs of either form:

```rust
pub trait Declares<W> {
    type Read: AccessSet;       // the stores read
    type Write: AccessSet;      // the stores written
    type Domain: Domain;        // the domain iterated
    type Sched: ScheduleGate;   // when it runs
    type Hint: SchedulingHint;  // how it is priced
}

impl<W: HasSchedule + Plannable<W::Sched>> Declares<W> for UnitDispatch<W> { /* W's Plannable, the domain folded from its sets */ }
impl<U: RecordOp, S: ScheduleGate, H: SchedulingHint> Declares<U> for RecordDispatch<U, S, H> { /* from U's lists */ }
```

The two implementations are on two distinct types, so they cannot
overlap and need no unstable feature. `WorkUnitBundle` and every fold
of the plan bind a unit as `W: BuilderInput` with
`W::Dispatch: Declares<W>`. A runner implements a run trait of its own
for the two router types, which is how the engine runs a value-form unit
(gather the reads of a record, call `apply`, scatter the writes) without
the unit or this crate naming the engine. A runner that implements its
run trait for `RecordDispatch` alone runs value-form units and refuses a
block-form unit at compile time, the block form being bound to the one
runner whose context it names.

A value-form unit's schedule and hint ride on the router as defaulted
parameters: `RecordDispatch<Self>` runs every pass with the default
hint, `RecordDispatch<Self, On<V>>` runs when the virtual `V` fires, and
a third parameter carries a hint other than the default.

### Fusion

Within-fiber linear fusion folds a straight read-after-write run of
value-form maps into one fused unit whose body keeps every intermediate
in a register (dead-store elimination removes the intermediate column
traffic), matching a hand-fused loop. The fold is a compile-time
composition of concrete monomorphised calls, no function pointers and no
dynamic dispatch. In this revision the fold takes a unit whose read
list is one `Column` of `Records` and whose write list is one `Column`
of `Records`; any other unit stays on the per-unit dispatch path. A
block-form unit may implement `RecordOp` beside `WorkUnit` to offer its
map to the fold, as before, and its `apply` then takes and returns
one-member products.

## Neighbour reads

A unit may read a store at a declared offset from the record it is
applied to.

```rust
pub struct Shift<A, const N: isize>(PhantomData<A>);  // N steps along axis A

pub struct Near<C, O, E>(PhantomData<(C, O, E)>)
where
    C: Committed,
    <C::Domain as Domain>::Reach: Contains<O>;

pub trait Edge<V>: 'static {
    const OUTSIDE: V;  // the value read past the extent
}
```

`Near<C, O, E>` is a member of a read list. Its value is the committed
value of store `C` at the record offset by `O`, or `E::OUTSIDE` where
that lands past the extent of the domain. An offset `O` is a list of
`Shift` cells, so an offset along two axes at once is a list of two, and
a unit that reads east, north and up names three `Near` members.

The offset must be in the reach its domain declares, checked where the
type is named, so a read past the declared reach does not compile. The
reach is on the domain because it is the one thing the plumbing must
know for every reader at once. The value past the extent is on the read,
since two readers of one store may want different ones.

`Committed` is implemented for `Buffered` and for no other kind. A
neighbour read of a column written in place would give a value that
depends on the sequence the records are visited in, which the engine
does not promise, so it is refused. The block form has no neighbour
read.

## The frame-buffered kind

`Buffered<T, D>` holds two sides. A read of it, at the record or at a
neighbour, sees the committed side, which is what the store held when
the pass began. A write goes to the staged side. At the close of the
pass the two sides are swapped for every `Buffered` store written in
that pass, and a store no unit wrote keeps its committed side.

A `Buffered` store is written in the value form only. The swap is
sound because the staged side holds a value for every record of the
domain when it becomes the committed side, which a value-form unit
guarantees by returning a value for every record it is applied to and a
block body, free to skip a record, cannot. The block form reads a
`Buffered` store and does not write one.

What counts as a change of the store, when the next pass asks which
units must run again, is declared on the store and is not the
plumbing's to choose:

```rust
pub trait Changed<T>: 'static {}
pub struct Differs;  // changed when a staged value differs from the committed one
pub struct Written;  // changed whenever its writer ran

impl<T: PartialEq> Changed<T> for Differs {}
impl<T> Changed<T> for Written {}
```

It is the marker's third parameter and `Differs` is the default, so
`Buffered<Heat, Plane>` wakes its readers only in a pass after one whose
writer staged a value that differs from the committed one, and
`Buffered<Heat, Plane, Written>` wakes them after every pass its writer
ran in. `Differs` asks that the value type can be compared. A column
written in place keeps the rule it has, that a store counts as changed
when a unit that writes it ran.

For the plan the kind means that the writer and the readers of one
`Buffered` store have no read-after-write edge and no conflict, in
whichever sequence they are registered, and that the kind
has at most one writer. Two units writing one `Buffered` store are
refused at `build`, at compile time. The priority rule that resolves two
writers of any other kind has nothing to resolve here, since the later
writer would replace the earlier writer's staged values whole with no
reader between them.

A `Buffered` store relates to `ResourceSnapshot` (below) as a column
relates to a resource. Both are a read-only view of a committed state
that work may read while the next state is produced: the snapshot for a
resource across a phase, the committed side for a column across a pass.

A unit that reads its own previous value and writes its next one names
the same `Buffered` store in both lists.

## Unified columnar storage (domain 07)

All engine runtime state reaches one storage floor: a column of
column-sized scalars. `ColumnValue` is the scalar unit; `ColumnStorage`
owns columns of those scalars, allocated through `MemoryProviderApi`.
`Resource`, `Column`, `Virtual`, `Field`, `Seq`, and `Map` are
access-and-intent views over that one store, not independent or
arena-backed mechanisms. There is no separate storage for WorkUnit
state versus engine-internal state; the execution plan, the resources,
and the columns all back onto the same `ColumnStorage`.

`ColumnStorage` sits between `MemoryProviderApi` (the raw allocator the
consumer supplies) below and the per-morsel Context accessors
(`ColumnReaderApi` / `ColumnWriterApi`) above. It owns columns and hands
out base pointers the dispatch codegen turns into per-morsel raw reads.

```rust
pub trait ColumnStorage {
    type Error;

    // Reserve column `id` for `len` records of scalar `T`, 64-byte
    // aligned, stride size_of::<T>(). Allocates through the bound
    // MemoryProvider. Re-reserving an existing id resizes it.
    fn reserve<T: ColumnValue>(&mut self, id: StoreId, len: USize)
        -> Outcome<(), Self::Error>;

    // Base pointer of column `id`. Raw, not a slice: a slice borrow
    // alongside a resource pointer from the same context defeats LLVM
    // noalias and forces a per-iteration reload (R6, the T6 bench).
    // Safety: `id` names a column reserved for `T`; the caller proves
    // the record index stays below count(id).
    unsafe fn column_ptr<T: ColumnValue>(&self, id: StoreId) -> *const T;
    unsafe fn column_ptr_mut<T: ColumnValue>(&self, id: StoreId) -> *mut T;

    fn count(&self, id: StoreId) -> USize;        // record count
    fn release(&mut self, id: StoreId);           // advisory, reader-count model
}
```

`Decompose` maps an aggregate type to its scalar column leaves: the
struct-of-arrays expansion. A multi-field struct yields one leaf per
field, recursing through nested structs until every leaf is a
`ColumnValue` scalar. `Field<S>` is the base case the recursion stops
at, so scalar promotion is preserved as the fundamental, not dropped.
`Seq` / `Map` elements expand the same way when the element is not
itself a scalar.

```rust
pub trait Decompose {
    // Cons-list of this aggregate's scalar column leaves (Field<S> per
    // scalar leaf, in field order). Empty for a unit aggregate.
    type Leaves: StoreBundle;
}
```

`Resource` and `Column` differ in intent and access pattern, not
mechanism. `Resource` holds persistent, infrequently-written state
(config, providers, the plan), cardinality one or more; a `Field<T>`
resource decomposes to a length-1 column and is staged stack-local
before the morsel loop with separate pointer provenance from the bulk
columns (domain 19), so it promotes to a register rather than paying a
per-record load. `Column` holds hot per-morsel records accessed via the
raw morsel-offset read / write. Both back onto the same store.
`Virtual` carries no backing (DAG edge only).

The cardinality-1 path is the fast path: the unified floor does not cost
a scalar resource its register. A default arena-backed `ColumnStorage`
impl ships in `hilavitkutin-providers` as the placeholder. Bespoke
per-subsystem arenas are forbidden; see the unified-storage principle.

The persistence boundary (`evict` / `inject`, R2) folds onto
`ColumnStorage` with the resource-resolution / persistence migration; it
is not part of the core contract here.

## WorkUnit trait (domain 09)

```rust
pub trait WorkUnit<Schedule = Always>:
    Provider<Init = Self> + Send + Sync + 'static
{
 type Read: AccessSet;
 type Write: AccessSet;
 type Hint: SchedulingHint = (Immediate, Atomic, Normal);
 type Ctx<'frame>: HasColumnReader<Self::Read>
 + HasColumnWriter<Self::Write>
 + HasResourceProvider<Self::Read>
 + HasVirtualFirer<Self::Write>
 + HasEach<Self::Read, Self::Write>
 + HasBatch<Self::Read, Self::Write>
 + HasReduce<Self::Read, Self::Write>;
 const COMMUTATIVE: bool = false;
 fn execute<'frame>(&self, ctx: &Self::Ctx<'frame>);
}
```

The `Ctx` associated type is a Generic Associated Type (GAT) over a
`'frame` lifetime. The engine instantiates it at dispatch time with the
live frame lifetime so the WU can read borrows into `PoolFrame`-derived
state (progress slots, predicted-wait atomic readers, etc.) without
forcing the consumer's `impl WorkUnit` declaration to carry an
explicit `<'frame>` parameter. Validated by sketch
`mock/research/sketches/202605101036-poolframe-lifetime/`. Dispatch
sites use HRTB: `Wu: for<'a> WorkUnit<Ctx<'a> = SomeCtxFor<'a>>`.

The `Provider<Init = Self>` supertrait carries the registration
contract. WorkUnits register on the SchedulerBuilder via
`.with(MyWu)` (unit struct) or `.with(MyWu::new())` (when the WU
has init data). `Provider::Dispatch` for WorkUnits is
`UnitDispatch<Self>`, appending the WU type onto the `Wus`
typestate accumulator so the carrier type order equals registration
order. The producer-before-consumer registration order this implies
is a provisional constraint: `build()` validates it and a later step
lets the engine auto-apply the cache-optimal order itself.

No NAME const. WU identity is the type itself. Naming is a consumer
concern; they can implement their own trait or use wrappers.

Schedule conditions:
- `Always`: unconditional (default)
- `On<V>`: when virtual V fires

Write-write ambiguity resolved by scheduling hint priority across
three dimensions. Tie-break: most deps first, then deterministic
fallback. This holds for every store kind but `Buffered`, where a
second writer is refused at `build` (see "The frame-buffered kind").

`WorkUnit` is the block form of a unit and `RecordOp` the value form
(see "The value form" above for how the two relate and how each
registers). What this section says of schedules, hints and write-write
priority holds for a unit of either form.

## Plannable trait (domain 09): the runner-agnostic declaration

`WorkUnit` bundles two separable things: a declaration (what it reads,
what it writes, how to price it) and a fiber execution model (`Ctx`
bound on the column accessors, plus `execute`). The declaration names
no runner. `Plannable` is that half, so a consumer whose runner is not
the fiber engine can declare and plan work without adopting the
column-record execution model it cannot honour.

```rust
pub trait Plannable<Schedule = Always> {
    type Read: AccessSet;
    type Write: AccessSet;
    type Hint: SchedulingHint;
}

impl<W: WorkUnit<S>, S> Plannable<S> for W {
    type Read = <W as WorkUnit<S>>::Read;
    type Write = <W as WorkUnit<S>>::Write;
    type Hint = <W as WorkUnit<S>>::Hint;
}
```

`Schedule` is a parameter of `Plannable`, not only of the blanket
impl's bound; that is what constrains it (a schedule-free
`impl<W: WorkUnit<S>, S> Plannable for W` fails E0207). Because the
schedule is in the trait reference, the blanket covers every schedule
including `On<V>` and `OnMeta<V>`, so no existing `WorkUnit` gains an
impl block. A type that is not a `WorkUnit` (a runner that records a
dispatch rather than executing per record) implements `Plannable` by
hand, and the two impls cohere by the orphan rule: only the crate that
owns the local type could make it a `WorkUnit`, and it does not.

The plan stage reads a unit's declaration through `Declares` on the
router the unit names, never `WorkUnit::execute`. For a unit routed by
`UnitDispatch` that declaration is its `Plannable`, so planning stays
generic over `Plannable<S>` for the block form and for a hand-declared
type. For a unit routed by `RecordDispatch` it is derived from the
unit's lists, since a blanket `Plannable` over `RecordOp` would overlap
the one over `WorkUnit`. Coherence and the E0207
constraint are proven by sketch
`mock/research/sketches/202607171733_plannable-declaration-split/`.

The hint's extension slot: `SchedulingHint` stays sealed and gains one
additive arm, the 4-tuple `(U, D, S, X: HintExt)`, where `HintExt` is
an open marker trait a downstream runner implements to carry a fourth,
runner-specific dimension. A 3-tuple and a 4-tuple are different types,
so the arms do not overlap and existing hints are unaffected. The fiber
engine's scheduling is defined over the three built-in axes, so a
4-tuple hint schedules as its `(U, D, S)` prefix would; reading a fourth
dimension is a later gate for whichever runner defines one, not a
mechanism this crate ships. No `HintExt` markers ship here either: the
slot exists so a genuinely new dimension can land additively rather than
by unsealing, and the three axes already cover the known cases (the
divisibility axis expresses whether work can be split or paused).

WU authoring guideline: ≤8 unique columns per WU (register pressure
guideline, not engine constraint).

## WU Context providers (domains 09, 19)

The WU execution parameter is a ctx-framework provider tuple
(`Self::Ctx` on the `WorkUnit` trait) bound by eight accessor
traits declared via `hilavitkutin-ctx`'s `provider_generic!` /
`provider_generic2!` macros. Each accessor carries the relevant
access-set type parameter so compile-time `Contains<S>` checks
can enforce WU-declared access at the call site.

Provider API traits (access-set-aware via ctx parameterised macros):

```rust
trait ColumnReaderApi<R: AccessSet> {
 fn read<'b, C: PerRecord, I>(&self, i: Index<'b>) -> C::Value
 where R: Holds<C>, Self: ResolveColumnRead<C, I>;
}
trait ColumnWriterApi<W: AccessSet> {
 fn write<'b, C: InPlace, I>(&self, i: Index<'b>, v: C::Value)
 where W: Holds<C>, Self: ResolveColumnWrite<C, I>;
}
trait AccumWriterApi<W: AccessSet> {
 fn append<T: ColumnValue, I>(&self, v: T)
 where W: Holds<Accum<T>>, Self: ResolveAccumAppend<T, I>;
 fn len<T: ColumnValue, I>(&self) -> USize
 where W: Holds<Accum<T>>, Self: ResolveAccumAppend<T, I>;
}
trait ResourceProviderApi<R: AccessSet> {
 fn resource<T: 'static, I>(&self) -> &T
 where R: Holds<Resource<T>>, Self: ResolveResource<T, I>;
}
trait VirtualFirerApi<W: AccessSet> {
 fn fire<V: 'static>(&self)
 where W: Holds<Virtual<V>>;
}
trait EachApi<R: AccessSet, W: AccessSet> {
 fn run<F: for<'b> FnMut(Index<'b>)>(&self, f: F); // per-element, fusible
}
trait BatchApi<R: AccessSet, W: AccessSet> {
 fn run<F: for<'b> FnOnce(Block<'b>)>(&self, f: F); // the whole morsel, non-fusible
}
trait ReduceApi<R: AccessSet, W: AccessSet> {
 fn run<A, F: for<'b> FnMut(A, Index<'b>) -> A>(&self, init: A, f: F) -> A;
}
```

`PerRecord` is implemented for the two kinds that hold one value per
record, `Column` and `Buffered`, and names the value type and the
domain. `InPlace` is `PerRecord` narrowed to `Column`. `read` and
`write` are keyed by the store marker, so a block-form unit reads
`Column<Pos>` and a `Buffered` store through the same method, a read of
a `Buffered` store returning the committed value. `write` takes an
`InPlace` store: a block body does not write a `Buffered` store (see
"The frame-buffered kind").

Reads, writes and appends are safe. `Index<'b>` is an opaque position in
the morsel the context is bound to, branded with a lifetime that exists
only inside the closure it is handed to. It has no public constructor,
no conversion to or from a number, no comparison and no arithmetic, and
the higher-ranked bound on the closure keeps it from leaving. An index
therefore always names a record of the unit's domain inside the window
the plan gave this unit, and the plan has already proven that no other
unit writes the unit's write set in that window. `Block<'b>` is the
whole morsel under one brand: it iterates the morsel's indices and
gives their count.

An append takes no index, since it names no record: it lands at the
accumulator's own live length, which the plumbing keeps. A unit appends
from inside its per-record loop or once a frame from outside it, and
both are the same call. What makes the call safe is that the unit
declared the accumulator in its write list, that the plan gives each
accumulator one appender in a window, and that an append past the
reserved capacity is refused as a value (below), so no caller
obligation is left for the body to hold.

The engine mints an index through `Index::mint`, an `unsafe fn` whose
caller asserts that the position is inside the bound window. That and
the `Resolve*` bridges below are where the unsafe of a column access
lives, on the plumbing's side of the contract. The accessor methods
above are provided by this crate over those bridges, so the position
inside an index is read by this crate alone.

The keyed accessors (`read` / `write` / `resource`) resolve the requested
store type `T` over the per-WU projected pointer bundle without
`feature(specialization)`. Each carries an inferred index generic `I` plus a
`Resolve*<T, I>` bridge bound; the scheduler-generated context implements the
bridge by delegating to the bundle index witness (`Selector<T, I>` /
`ColSelector<T, I>`). At a concrete call site the bundle is a concrete
cons-list, so exactly one index applies and `I` infers. The index is never
named at a call site: `T` is pinned by context (`let v: &T = ctx.resource()`)
or by turbofish with the index left to inference (`ctx.resource::<T, _>()`).

```rust
trait ResolveResource<T: 'static, I> {
 fn resolve_resource(&self) -> &T;
}
trait ResolveColumnRead<C: PerRecord, I> {
 unsafe fn resolve_read(&self, i: USize) -> C::Value; // morsel-offset read
}
trait ResolveColumnWrite<C: InPlace, I> {
 unsafe fn resolve_write(&self, i: USize, v: C::Value); // morsel-offset write
}
trait ResolveAccumAppend<T: ColumnValue, I> {
 unsafe fn resolve_append(&self, v: T); // append at the live offset, or refuse
 fn resolve_len(&self) -> USize; // the live length of this binding
}
```

The bridges are implemented by a runner's context and called by this
crate's accessors, the read and the write with the position an `Index`
carries. They stay `unsafe`, since they are the plumbing's half: a read
or a write takes a bare position, and an append asks that its caller
holds the accumulator's one appender slot. This crate's `append` calls
it for a unit that declared the accumulator, and the runner that hands
a unit its context owes the rest: the context reaches one thread at a
time, and a runner that splits a unit over threads gives each thread a
binding of its own.

An accumulator append past the reserved capacity is refused, never asserted
and never written. The engine counts every append the frame asks of the
accumulator beside its live length; once one append through a binding is
refused, every later append through that binding in the same frame is refused
too, and its live length stops. On one thread the accumulator is one binding, so
the records it kept are a prefix of the appends the frame asked of it. Under
`run_parallel` each core appends through its own binding over its own region,
so one core can refuse while another still accepts: the records kept depend on
the worker count, and the `AccumRefused` value does not. `len` returns the live
length of the binding the body appends through. The run concludes on the first refusing accumulator as an
`AccumRefused`, returned under the default `Refuse` or asserted under `Assert`
(see "`AccumRefused` and the run's output" below); the body that appended
learns nothing at the call, and
no caller obligation covers the capacity.

Accessor traits (generated by `provider_generic!` /
`provider_generic2!`):

```rust
provider_generic!(<R: AccessSet> ColumnReaderApi as HasColumnReader => reader);
provider_generic!(<W: AccessSet> ColumnWriterApi as HasColumnWriter => writer);
provider_generic!(<R: AccessSet> ResourceProviderApi as HasResourceProvider => resources);
provider_generic!(<W: AccessSet> VirtualFirerApi as HasVirtualFirer => virtuals);
provider_generic!(<W: AccessSet> AccumWriterApi as HasAccumWriter => accums);
provider_generic2!(<R: AccessSet, W: AccessSet> EachApi as HasEach => each);
provider_generic2!(<R: AccessSet, W: AccessSet> BatchApi as HasBatch => batch);
provider_generic2!(<R: AccessSet, W: AccessSet> ReduceApi as HasReduce => reduce);
```

`Contains<S>` is the shared list crate's compile-time membership
witness, sealed there by its `List` supertrait. Accessing a store not
declared in `Read` or `Write` fails to compile at the relevant
API-trait method's where-clause. It is a `#[marker]` trait, so its head
impl (a cell contains its own head) and its tail impl (a cell contains
what its tail contains) coexist.

Membership lookup walks the list at trait-solver time. Depth
scales linearly with list length; round 202605042200 measured 0.53
seconds at depth 5 with 25 WorkUnits across 13 stores (S1b
finding), well within the rustc default recursion limit.

`AccessSet::LEN` reports the list's cardinality at compile time.
`Empty::LEN = <USize as Identity<Additive>>::IDENTITY`.
`Cons<H, T>::LEN = USize(T::LEN.0 + 1)`.
The recursive impl is this crate's own, over the shared crate's two
types. The shared crate counts through its `Cardinal` property, which
only arvo could implement for `USize`, so the count is not read from
there. It computes correctly at any depth and is callable in const
contexts via the const-arith surface on `arvo::USize`.

`&self` receiver on every provider method is load-bearing: prevents
LLVM noalias metadata that would reorder writes across fused WUs.
The engine proves the ownership discipline of a write at plan time,
and the `Index` a write takes carries that proof to the call, which is
why `read` and `write` are safe to call. An append carries no index and
is safe for the reasons given with it above.

## Foundational primitives for Kit (domain 23, )

The api ships the foundational primitives that `Kit` (in
`hilavitkutin-kit`), `SchedulerBuilder` (in the engine), and the
app-level `replace_resource` API rest on. The api crate documents
the contracts because `WorkUnit` authors, `.build()` callers, and
`Kit` authors all reference them at consumer-API positions.

The contract surface is intentionally thin. Round-4's design (topic
`202605042200_topic_kit_trait_split.md`) reduced the Kit-side
contract surface to four trait shapes plus one opt-in marker. The
old `Buildable<Stores>`, `WuSatisfied<A>`, `BuilderExtending<B>`,
and `BuilderResource<T>` traits are gone (deleted entirely per
`no-legacy-shims-pre-1.0.md`); their roles are taken by
`ContainsAll<L>` plus `WorkUnitBundle::AccumRead`/`AccumWrite`
projections plus the new `Kit { type Units; type Owned }` shape.
Layered enforcement framing per
`202605042200_topic_round_4_layered_enforcement.md`: the
typestate proves correctness; visibility lives in Rust language
rules; `Replaceable` is the only enforced annotation.

### `WorkUnitBundle` trait

```rust
pub trait WorkUnitBundle {
 type AccumRead: AccessSet;
 type AccumWrite: AccessSet;
}

impl WorkUnitBundle for Empty {
 type AccumRead = Empty;
 type AccumWrite = Empty;
}

// R and Wr stand for the unit's declared stores,
// <W::Dispatch as Declares<W>>::Read and ::Write.
impl<W: BuilderInput, T: WorkUnitBundle> WorkUnitBundle for Cons<W, T>
where
 W::Dispatch: Declares<W>,
 R: Concat<T::AccumRead>,
 Wr: Concat<T::AccumWrite>,
 <R as Concat<T::AccumRead>>::Out: AccessSet,
 <Wr as Concat<T::AccumWrite>>::Out: AccessSet,
{
 type AccumRead = <R as Concat<T::AccumRead>>::Out;
 type AccumWrite = <Wr as Concat<T::AccumWrite>>::Out;
}
```

A `WorkUnitBundle` is a list of units of either form with
projected per-bundle `AccumRead` and `AccumWrite` totals. The two
recursive impls accumulate each unit's declared read and write stores,
read through `Declares`, via `Concat`. The accumulator carries duplicates (the same store
appearing in multiple WUs' Read sets shows up once per
occurrence); logical dedup via `#[marker] Contains` makes
duplicates correctness-irrelevant. See the audit M2 investigation
at `mock/research/sketches/202605050800_dedup_concat/FINDINGS.md`
for the cost analysis; physical dedup is deferred to round-5+.

### `StoreBundle` trait

```rust
pub trait StoreBundle {}
impl StoreBundle for Empty {}
impl<H, T: StoreBundle> StoreBundle for Cons<H, T> {}
```

A marker trait for the Kit's `Owned` declarations. Two-impl
recursive shape. No projections; the bundle's content is read by
the engine's `KitDispatch<K>` routing during `.with(MyKit)`, not by
the trait itself. `StoreBundle` carries `Resource<T>`, `Column<T, D>`,
`Buffered<T, D>`, `Accum<T>`, `Virtual<T>`, `Extent<D>` and
`LinkedBin<T: ?Sized>` markers in the list
shape produced by `read!` / `write!` macros from a flat-list syntax.

### `Replaceable` opt-in marker

```rust
pub trait Replaceable {}
```

A marker trait with no methods and no associated types. Per-type
opt-in via `impl Replaceable for Foo {}` declarations from the
kit author. The static `T: Replaceable` bound on
`Scheduler::replace_resource::<T>(value)` (see the engine's
DESIGN) rejects override attempts on non-opt-in types at compile
time, with a high-quality E0277 diagnostic that lists the types
that DO impl `Replaceable`. See sketch S5 at
`mock/research/sketches/202605050615_kit_taxonomy/` for the
empirical evidence.

Replaceability is the only enforced annotation on Owned types.
Visibility is per-kit-crate (whole-kit pub vs whole-kit pub(crate)
in its own crate); not a per-Owned-type axis. See
`202605042200_topic_round_4_layered_enforcement.md` for the full
layered-enforcement framing the doc CL paraphrases.

### `Kit` trait at the api boundary

```rust
pub trait Kit: Provider<Init = Self> {
 type Units: WorkUnitBundle;
 type Owned: StoreBundle;
}
```

The trait is declared in `hilavitkutin-kit`, not in api; the api
documents the contract because consumers (kit authors) and the
engine (`.with(MyKit)` caller) both reference it at their boundary.
`Provider<Init = Self>` is the registration supertrait: Kits reach
the builder via the same `.with` verb as WorkUnits and stores.
`Provider::Dispatch` for Kits is `KitDispatch<Self>`, which concats
`K::Units` into the `Wus` accumulator and `K::Owned` into the
`Stores` accumulator at the type level.
The kit crate's `DESIGN.md` carries the authoring guide and
examples; this section names the shape so neighbouring core
primitives can be read in context.

The trait carries no `Required` member and no `requirements_doc()`
helper. "What a kit requires" lives in prose (the kit author lists
required external Resources in the Kit's rustdoc). The typestate
proves correctness via `ContainsAll<AccumRead>` plus
`ContainsAll<AccumWrite>` at `.build()`; the resulting compile
error names the missing marker on the first inline line of the
diagnostic per the S1b depth-5 sketch outcome.

### `ContainsAll<L>`

`ContainsAll<L>` is the shared list crate's, like `Contains`: a list
holds every member of `L`. Its message cannot name the member that is
missing, so the bounds of `.build()` are written on `HoldsAll<L>`, the
api's walk of `L` that asks `Holds` of each member and so reports the
missing store by type (see "`Contains` diagnostic" below).

Replaces the deleted `Buildable<Stores>` and `WuSatisfied<A>`
traits. Two-impl recursive shape: empty list trivially contained;
non-empty list satisfies when the head is contained and the tail
is recursively contained. The `#[marker]` attribute permits the
overlapping resolution shape Contains relies on. Sealed in the shared
crate by its `List` supertrait; consumers cannot impl it
directly because the only legitimate shape is the recursive walk.

The trait solver's recursion grows with the length of `L`, which
equals the count of distinct Read/Write records across all WUs in
the bundle (with duplicates per the M2 finding). Empirical: a
25-WU bundle at depth 5 with 13 distinct stores produces a
36-element accumulated chain; `.build()` resolves in 0.53s on
nightly rustc per S1b. See
`mock/research/sketches/202605050700_deep_stacking_d5/FINDINGS.md`.

### `read!` / `write!` macros

Consumers declare WU access sets through declarative macros that
convert flat-tuple syntax to the cons-list shape used by
`WorkUnitBundle::AccumRead/Write` accumulation:

```rust
#[macro_export]
macro_rules! read {
 () => { Empty };
 ($T:ty $(,)?) => { Cons<$T, Empty> };
 ($T:ty, $($rest:ty),+ $(,)?) => { Cons<$T, $crate::read!($($rest),+)> };
}
// write! has identical shape.
```

A `WorkUnit` impl writes:

```rust
type Read = read![Resource<Interner>, Column<FileInfo>, Resource<Workspace>];
type Write = write![Column<Diagnostic>];
```

Empty `read![]` yields `Empty`; single-store `read![Resource<X>]`
expands to `Cons<Resource<X>, Empty>`. Both macros live in
`hilavitkutin-api` and are re-exported from the crate root.

### `Depth` trait

```rust
#[allow(private_bounds)]
pub trait Depth: Sealed {
 const D: USize;
}

impl Depth for Empty { const D: USize = <USize as Identity<Additive>>::IDENTITY; }
impl<H, R: Depth> Depth for Cons<H, R> {
 const D: USize = R::D + <USize as Identity<Multiplicative>>::IDENTITY;
}
```

Two impls. No specialization. No marker overlap. Coherence
trivially holds because `Empty` and `Cons<H, R>` are disjoint
shapes.

`Depth` is impl'd ONLY on cons-list shapes. Plan-stage code
consumes engine accumulators (cons-list by construction) and
consumer-declared `Read` / `Write` (cons-list via the `read!` /
`write!` macros), so any value the plan stage counts already
comes from a cons-list source.

`AccessSet::LEN` and `Depth::D` coexist with explicit, distinct
contracts. `LEN` is shape-based (immediate-cell count, always 2
for cons-list cells); `D` is total-element-based (the count after
recursive descent). Both stay documented at their respective trait
declarations.

### `Contains` diagnostic

`Contains<S>` is the shared crate's trait and carries the shared
crate's message, which knows nothing of stores. The api's bounds that
an author or a `.build()` caller can fail are therefore written on
`Holds<S>`, an api trait implemented by one blanket for every list that
`Contains<S>`. `Holds<S>` carries `#[diagnostic::on_unimplemented]` and
its blanket carries `#[diagnostic::do_not_recommend]`, so the
unsatisfied bound is reported on `Holds` with the api's message:

```text
note: store `{Self}` does not contain `{T}`. Register it with
 `.with(Resource::new(value))`, `.with(Column::<T>::new())`,
 `.with(Virtual::<T>::new())`, or install a Kit that owns it via
 `.with(MyKit)`. If `.build()` reports `overflow evaluating the
 requirement`, declare `#![recursion_limit = "1024"]` at your crate
 root.
```

The attribute is purely a DX win; `Holds<S>` holds exactly where
`Contains<S>` does. The annotation lives on the `Holds<S>` declaration
in `access.rs`.

### Diagnostic coverage across the public surface

The following public traits carry `#[diagnostic::on_unimplemented]`
as of round 202605082321 in addition to the previously-shipped
`Contains<S>` and `ContainsAll<L>`:

- Type-level: `Concat<L>`, `WorkUnitBundle`, `StoreBundle`,
  `ColumnValue`, `Replaceable`.
- Sealed substrate axes: `SchedulingHint`, `UrgencyValue`,
  `DivisibilityValue`, `SignificanceValue`, `Depth`. The
  diagnostics on the sealed axes name the available
  substrate-provided ZST markers so consumers see the menu in the
  error trail.
- Capability layer: `Push<T>`, `BulkPush<T>`, `Len`, `Capacity`,
  `BoundedPush<T>`, `Collector<T>`, `DiagnosticSink<E>`,
  `ByteEmitter`.
- Codec: `Encoder<T>`, `Decoder<T>`. The extension traits
  `EncoderExt<T>` / `DecoderExt<T>` are not annotated; their
  default-method default impls rarely surface raw bound failures.
- Platform contracts: `MemoryProviderApi`, `ThreadPoolApi`,
  `ClockApi`, `HasMemoryProvider`, `HasThreadPool`, `HasClock`.
- Provider API: `ColumnReaderApi<R>`, `ColumnWriterApi<W>`,

- WorkUnit: `WorkUnit<Schedule>`.

Each diagnostic carries a one-line `message` plus, where the fix

### `prelude` module

`hilavitkutin_api::prelude` re-exports the consumer-facing

use hilavitkutin_api::prelude::*;

// Now in scope:

### `.build()` where-clause (engine side)

The engine's `SchedulerBuilder::build` carries:

```rust
where Wus: WorkUnitBundle, Stores: AccessSet + StoreBundle
 + HoldsAll<Wus::AccumRead> + HoldsAll<Wus::AccumWrite>
```

This unfolds via the recursive `HoldsAll` impl into the
conjunction of per-store `Contains<...>` proofs against `Stores`.
The recursion impl on `Contains` handles arbitrary-depth
`Stores` accumulators. `build` takes the storage and no record count,
and adds one bound per domain: the store list holds an `Extent<D>` for
the domain `D` of every `Column` and `Buffered` store in it. With `#[marker]` on both `Contains` and
`ContainsAll`, the trait solver picks any matching impl and stops;
duplicates in `Wus::AccumRead/Write` extend traversal length but
do not duplicate proof work.

When a consumer registers a WU via `.with(MyWu)` whose `Read`
mentions a store not added via `.with(Resource::new(value))` /
`.with(Column::<T>::new())` / `.with(Virtual::<T>::new())` /
`.with(MyKit)`, rustc reports the missing membership using the
diagnostic message above, naming the missing store by type. The
inline error leads with the `Empty: Contains<...>` failure on the
first line; the verbose `Cons<...>` accumulator chain follows but
does not bury the marker name.

### Recursion limit

The substrate's typestate machinery walks cons-list recursions at
trait-solver time. Default rustc `recursion_limit = 128`
accommodates apps up to roughly 30 WUs by 30 stores. The
`hilavitkutin-api`, `hilavitkutin`, and `hilavitkutin-kit` crates
declare `#![recursion_limit = "512"]` internally for their own
machinery. Consumer crates approaching the threshold (4+ nested
Kit layers, 30+ flat WUs across the build) declare:

```rust
#![recursion_limit = "1024"]
```

at their own crate root.

Earlier substrate designs proposed shipping a
`recursion_limit_for_kits!()` macro that expanded to the inner
attribute. Current rustc rejects macro-expansion of crate-level
inner attributes ("an inner attribute is not permitted in this
context"); the design retreats to documenting the directive
plainly. The trait diagnostics on `Contains`, `ContainsAll`,
`Kit`, and `WorkUnit` mention the recursion-limit directive in
their notes when the bound failure could plausibly stem from
depth.

When `.build()` reports `overflow evaluating the requirement`, the
fix is the inner attribute above; no other configuration is
needed.

### Marker-trait keystone risk

`Contains` and `ContainsAll` rely on `feature(marker_trait_attr)`
(rust-lang/rust#29864), an unstable feature without an active
stabilisation track. The crate accepts this risk explicitly.
A future rustc that removes or restricts marker-trait coherence
would break the recursive cons-list AccessSet pattern; the planned
response is a bitset-backed AccessSet over a per-app StoreIndex
ConstParamTy, sketched in
`mock/research/marker_trait_attr_bitset_fallback.md`. The fallback
is not built in round-4. Other nightly features the crate
depends on (`const_trait_impl`, `adt_const_params`,
`generic_const_exprs`) have differing stabilisation profiles;
analogous response notes can be written if and when their
role becomes load-bearing.

### Why these live in api, not in kit

`WorkUnitBundle`, `StoreBundle`, `ContainsAll`, `Replaceable`, and
`Depth` are contract-shape artefacts. `WorkUnitBundle` and
`StoreBundle` are referenced in `Kit` associated-type bounds.
`ContainsAll` is referenced at the engine's `.build()` where-clause
and in any consumer-side trait bound that proves a particular
access-set state. `Replaceable` is referenced at the
`replace_resource` call site. `Depth` is referenced by plan-stage
code that walks accumulators. They belong with `AccessSet` and
`Contains` in api. The `Kit` trait in `hilavitkutin-kit` is purely
the consumer-facing declarative shape; the proofs above sit a
layer below it. The `Kit: Provider<Init = Self>` supertrait is also
declared in this api crate alongside `Provider` itself; the kit
crate inherits the registration shape rather than defining its own.

## Scheduling hints (domain 09)

Three axes. Each axis is a sealed trait with a fixed set of ZST
carrier types. Each trait's `VALUE` const is typed as the narrowest
arvo `UFixed<N, 0, Hot>` alias that fits the axis.

| Axis | Alias | Width | Markers | Discriminants |
|------|-------|------:|---------|---------------|
| Urgency | `Urgency = UFixed<2, 0, Hot>` | 2 bits | `Immediate`, `Steady`, `Relaxed`, `Deferred` | 3, 2, 1, 0 |
| Divisibility | `Divisibility = UFixed<2, 0, Hot>` | 2 bits | `Atomic`, `Adaptive`, `Interruptible` | 2, 1, 0 |
| Significance | `Significance = UFixed<3, 0, Hot>` | 3 bits | `Critical`, `Important`, `Normal`, `Opportunistic`, `Optional` | 4, 3, 2, 1, 0 |

`SchedulingHint` trait on tuples: `(U: UrgencyValue, D:
DivisibilityValue, S: SignificanceValue)`. Higher discriminant =
higher priority (ordering derived from `UFixed`'s `PartialOrd`).

Three axes pack into 7 bits; u8-discriminant thinking would take
24 bits. Exact-width primitives are how the stack pays this memory
back at every WU.

## Platform traits (domain 02)

```rust
pub trait MemoryProvider: Send + Sync {
 unsafe fn allocate(&self, len: usize, align: usize) -> *mut u8;
 unsafe fn deallocate(&self, ptr: *mut u8, len: usize);
 unsafe fn protect(&self, ptr: *mut u8, len: usize,
 read: bool, write: bool);
}

pub trait ThreadPool: Send + Sync {
 fn spawn(&self, f: impl FnOnce() + Send + 'static);
 fn worker_count(&self) -> usize;
}

pub trait Clock: Send + Sync {
 fn now_ns(&self) -> u64;
}
```

All consumed via monomorphisation. The Scheduler is generic over the
platform types. Storing `dyn MemoryProvider` would violate the dyn
ban. The os tier ships a `MemoryProvider` and a `Clock`; the no_os tier
ships none. No tier ships a `ThreadPool`: the executor is the
consumer's, or comes from a crate outside the hilavitkutin family.
Consumer overrides via scheduler builder.

Every closure the engine hands `spawn` is no wider and no more
aligned than one pointer, so an executor can move it into a thread's
argument slot without allocating. `OnePointerClosure<F>` names that:
its associated const `FITS` fails the build at monomorphisation for a
wider or over-aligned `F`. The engine forces it at its spawn site, and
an executor may force it in its own `spawn` to hold every caller to
the same width.

Note: `len`, `align`, `worker_count`, `now_ns` parameters and return
types should use arvo newtypes in the final API (e.g. `ByteCount`,
`Alignment`, `CoreCount`, `Nanoseconds`). Exact arvo type mappings
ride the hilavitkutin sweep (#72); this round intentionally does not
retune them.

### `ResourceSnapshot<'phase, R>`

Read-only typed view of a scheduler-owned store, captured at a phase
boundary (Topic 8 axis A). Immutable for the snapshot's lifetime,
which is bounded to the current phase: the view cannot escape across
a phase barrier (lifetime invariance prevents lift-out). A worker
holding one is guaranteed the underlying storage is not written for
the snapshot's lifetime and that its content matches what the store
held at the captured phase.

The committed side of a `Buffered` store is the same guarantee given to
columns across a pass: what a reader sees is what the store held when
the pass began, and nothing writes it until the close. The snapshot
stays the form for a resource at a phase boundary, and neither is built
on the other.

Use case: `AdaptWu` at `ScheduleEnd` observes the snapshot of
`AdaptMetrics` to derive `predicted_wait_ns[]` writes for the next
frame. Pure read.

Status: the concrete signature lands with the data plane
(HILA-RUNTIME-C6). The earlier `Dispatch = ResourceDispatch` /
`R::Owned` form predates the round 202605101036 topic 2 builder
reshape, which replaced per-kind dispatch routers with `StoreDispatch`
and left `BuilderInput` carrying only `Init` and `Dispatch`. The
shipped signature is re-derived against the current `BuilderInput`
contract and the store storage the resource arena exposes.

### `PlanAffecting: BuilderInput + Sealed`

Sealed marker trait. Resources implementing `PlanAffecting` dirty the
plan cache when replaced via `Scheduler::replace_resource`; resources
without it are cheap value-swaps. Default is NOT plan-affecting.

```rust
pub trait PlanAffecting: BuilderInput + private::Sealed {}
```

The dirty bit array is `[AtomicBool; Cfg::MAX_PLAN_AFFECTING_RESOURCES]`
keyed by `PlanAffectingId`, where `Cfg: RunCfg` is the consumer's run
config. Default `RunCfg::MAX_PLAN_AFFECTING_RESOURCES = USize(256)`
(32-byte bitmask, fits one cache line). Consumers override per-app by
writing the const explicitly in their `impl RunCfg` block:

```rust
impl RunCfg for MyApp {
    type Overflow = ...;
    type Out = ...;
    const MAX_PLAN_AFFECTING_RESOURCES: USize = USize(8);  // tight envelope
}
```

The substrate documents the tradeoff (cache-line footprint, dirty-check
scan cost); the consumer picks per-app. Per `arvo-toolbox-not-policer.md`,
the substrate ships sharp tools with sensible defaults, never policy.

### `AccumRefused` and the run's output

`AccumRefused` names the accumulator that refused an append in a frame and by
how much. It carries the accumulator's position among the scheduler's
accumulators in registration order (`accum()`) and a `notko::Exhausted`
(`exhausted()`) whose `wanted` is every append the frame asked of it and whose
`had` is its reserved capacity. Both fields are private and read through
`const fn` accessors. `new` builds a value from its two parts: the engine builds
the frame's own at the close from the counts it kept, and a caller can build one
to compare a run's output against. A value claims nothing beyond its two parts;
what makes the run's output true is that the engine counted it.

At the close every run entry has the frame's verdict, a
`notko::Outcome<(), AccumRefused>`: `Ok(())` when no accumulator refused, `Err`
with the first refusing accumulator, walked in registration order, otherwise.
`wanted` counts what the bodies asked, which does not depend on how the records
were split over workers, so an emitter that asks more than the reserved capacity
gets the same verdict at every worker count.

What the run does with the verdict is the consumer's choice, made at compile
time on the run configuration. `AccumOverflow` names it, and it is a fixed
vocabulary of the engine's, sealed, with two inhabitants:

```rust
pub trait AccumOverflow: Sealed + 'static {
    type Out;
    fn conclude(verdict: notko::Outcome<(), AccumRefused>) -> Self::Out;
}
pub struct Refuse; // Out = notko::Outcome<(), AccumRefused>, the verdict as it is
pub struct Assert; // Out = (), and a refusal panics, naming the AccumRefused
```

`RunCfg` carries the choice as `type Overflow: AccumOverflow<Out = Self::Out>`,
so `RunCfg::Out` is the choice's output and nothing else: every run entry
returns `Cfg::Overflow::conclude(verdict)`. `RunCfg` is sealed and
`DefaultRunCfg<O: AccumOverflow = Refuse>` is its one impl, so `build` keeps the
refusal as a value and a consumer that wants the assert builds with
`build_with::<DefaultRunCfg<Assert>, _, _>`. Under `Assert` the run's output is
`()`, so a consumer of it cannot name `AccumRefused` in what the run returns. The
append path is the same under both: it refuses and counts, and no write passes
the capacity. The assert fires at the close, on the thread that called the run,
after every worker has re-parked, so it never stalls a `run_parallel` join.

A `Buffered` store is under the same choice and has nothing to refuse
today: it has no append, and its committed and staged buffers are both
sized from its domain's record count, so a write to it lands on a record
that exists. A store kind that can be asked for more than it reserved
concludes through `RunCfg::Overflow` and adds no second configuration.

## Resource model (domain 07, R5)

```rust
pub struct Field<T: ColumnValue>(PhantomData<T>); // scalar ≤16 bytes
pub struct Seq<T, const N: usize>(PhantomData<T>); // const-sized array
pub struct Map<K, V, const N: usize>(PhantomData<(K, V)>); // const-sized map
```

No dynamic collections. Allocation size is const generic. Field<T>
is stack-local cached (LLVM promotes to registers). Seq/Map are
arena-allocated. Write resource collections count toward L1 morsel
budget; read-only ride L2 prefetcher.

Resource data is behind pointer indirection to external slab storage.
NOT inline in Context. Writing inline data through `&self` is UB.

`Seq<T, N>` and `Map<K, V, N>` are type-level descriptors, not
containers with a `push` method. Consumers receive items into them
via `Push<T>` (or `BoundedPush<T>` for overflow-aware pushes); see
the contract surface below. The scheduler owns the arena; these
types name the slot, not the storage.

## Virtual flag system (domain 10)

Bit-packed fire flags using arvo-bitmask types. One bit per registered
Virtual type. Packed into arvo words, grouped into Mask64/Mask256.
Hierarchical check: word == 0 → skip. Affinity-ordered bit assignment
at plan time. Epoch-based reset (increment, not memset).

Per-(virtual, consumer) bit tracking. Clear-on-dispatch. Re-fire
during execution → consumer runs again next pass. No lost fires.

## Consumer contract surface (capability / sink / codec)

The modules above cover pipeline execution. A parallel surface covers
the OTHER boundary: API positions that receive or emit items outside
WU execution (a parser's diagnostic stream, a codegen target's byte
output, a serialiser's encoded bytes). That surface lives in three
modules: `capability`, `sink`, `codec`.

Framing: every position that accepts items is a trait bound, not a
concrete container. The trait is the contract; the caller brings the
type. `Vec<T>` never crosses this boundary; neither does `Seq<T, N>`.

### `capability`: the atoms

```rust
pub trait Push<T> { fn push(&mut self, item: T); }
pub trait BulkPush<T>: Push<T> {
 fn push_bulk(&mut self, items: &[T]) where T: Copy {
 for i in items { self.push(*i); }
 }
}
pub trait Len {
 fn len(&self) -> USize;
 fn is_empty(&self) -> Bool { /* default via len */ }
}
pub trait Capacity {
 fn capacity(&self) -> USize;
 fn remaining(&self) -> USize;
}
pub trait BoundedPush<T>: Push<T> + Capacity {
 fn try_push(&mut self, item: T) -> Outcome<(), Full>;
}
pub struct Full;
```

`Push<T>` is the atom: receive one item. `BulkPush<T>` adds slice
push (with a loop default implementors may override for memcpy-style
fastpaths). `Len` / `Capacity` are introspection atoms. `BoundedPush<T>`
is overflow-aware; `try_push` returns `Outcome::Err(Full)` on refusal
and MUST NOT silently drop items.

### `sink`: named composites + combinators

Named traits are bounds over capabilities; blanket impls make them
shorthand:

```rust
pub trait Collector<T>: Push<T> {}
impl<T, S: Push<T> + ?Sized> Collector<T> for S {}

pub trait DiagnosticSink<E>: Push<E> + Len {}
impl<E, S: Push<E> + Len + ?Sized> DiagnosticSink<E> for S {}

pub trait ByteEmitter: Push<u8> + BulkPush<u8> {}
impl<S: Push<u8> + BulkPush<u8> + ?Sized> ByteEmitter for S {}
```

Combinators:

- `NullSink`: unit struct; implements `Push<T>` + `BulkPush<T>` for
 every `T` as no-ops. For tests and dry-run counting.
- `CountingSink<T>`: counts pushes, stores nothing; implements
 `Push<T>` + `Len`. For "how many diagnostics were emitted".
- `TeeSink<'a, A, B>`: fans each push to two downstream sinks.
 Requires `T: Clone` (pushes distribute across both).

Tuple blanket impls ship for arity 2 and 3 so consumers can pass
`(&mut diagnostics, &mut bytes)` satisfying disjoint `Push<T>` and
`Push<u8>` slots via destructured field access. Higher arities land
when a concrete consumer surfaces a need.

### `codec`: encode / decode

Primary form is stateful incremental:

```rust
pub trait Encoder<T> {
 fn feed<B: ByteEmitter>(&mut self, v: &T, out: &mut B);
 fn finish<B: ByteEmitter>(self, out: &mut B);
}

pub trait Decoder<T> {
 fn feed<'a, S: Push<T>>(&mut self, chunk: &'a [u8], out: &mut S)
 -> Outcome<&'a [u8], DecodeError>;
 fn finish(self) -> Outcome<(), DecodeError>;
}

#[non_exhaustive]
pub enum DecodeError { Truncated, Invalid, OverLength }
```

Oneshot adapters as extension traits with blanket impls:

```rust
pub trait EncoderExt<T>: Encoder<T> + Sized {
 fn encode_one<B: ByteEmitter>(self, v: &T, out: &mut B);
}
pub trait DecoderExt<T>: Decoder<T> + Sized {
 fn decode_all<S: Push<T>>(self, bytes: &[u8], out: &mut S)
 -> Outcome<(), DecodeError>;
}
```

Streaming consumers (chunked bytecode loading, paradox save parsing)
call `feed`/`finish` directly. All-at-once consumers use the `Ext`
methods. One trait pair serves both shapes.

### Example: reshape a Vec-return

```rust
// Before the sweep:
fn parse(tokens: &[Token]) -> Result<Ast, Vec<SyntaxError>> {... }

// After the sweep (contracts from this round):

where
 E: DiagnosticSink<SyntaxError>;
```

std feature in tests, a `CountingSink` in "just count" mode, a

- Blanket impls for `Vec<T>` / `Seq<T, N>`. These live in test-helper

- `Flush` / `Fuse` / back-pressure semantics for buffered byte
