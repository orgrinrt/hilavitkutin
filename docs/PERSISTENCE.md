# hilavitkutin-persistence, Design Overview

`#![no_std]`, no alloc. Generic hot-cold storage bridge for the
hilavitkutin ecosystem. All serialisation via rkyv. All memory
from shared `MemoryProvider`. Reusable by any hilavitkutin
consumer.

## Dependencies

- `hilavitkutin-str`, Str type, content hashing
- `hilavitkutin-api`, the shared `MemoryProviderApi` the cold store
  maps and allocates through
- `arvo` and `notko`, the primitive vocabulary at the API boundary

`rkyv` is the archive format the file-backed round takes on (no_std,
no alloc for reads). It is not a dependency yet: the skeleton ships
without it.

Does NOT depend on hilavitkutin engine directly. Operates on
raw column data via the evict/inject pattern (R2). The consumer
provides the ColumnStorage interface.

## Core responsibility

Bridge between hilavitkutin's in-memory columnar hot store and
on-disk rkyv-archived cold store. Consumer-agnostic, knows
nothing about metadata tables, records, or domain schemas.

## Serialisation boundary

Everything crosses hot↔cold via rkyv `Archive` trait.

### Standard types, identity

`ColumnValue` types (`u32`, `i64`, `bool`, fixed-point, float)
archive as themselves. `type Archived = Self`. Zero overhead.

### Str, content hash translation

Str handles are session-specific (runtime IDs), and a const handle holds
only 28 bits of its string's hash. On disk a string is stored as its
content hash at full width, the 64-bit FNV-1a hash of its bytes, stable
across sessions. The runtime API uses arvo_hash ContentHash for the hash
value; the rkyv Archived form is a bare u64 to pin the on-disk byte
layout.

```rust
impl Archive for Str {
 // Disk-layout ABI: the full 64-bit FNV-1a content hash of the bytes.
 // Runtime API uses ContentHash, which has the same width.
 type Archived = u64;
}
```

The width is the point. Truncated to 28 bits, ten thousand distinct strings
collide with a probability of about 17 percent, and a collision on disk
returns the wrong string without any sign that it did. At 64 bits the same
count collides with a probability near 3e-12. The ten-thousand-string test
evicts ten thousand strings through `evict_str` and requires as many distinct
keys, and counts the same keys again at a width narrow enough to collide, so a
counter that cannot see a collision does not pass for one that sees none. Ten
thousand strings seldom collide at 28 bits by luck, so a second test searches
for two strings that share their low 28 bits and requires `evict_str` to key
them apart, which a key cut to 28 bits fails.

Evict: a handle resolves to bytes through the interner (a const handle
through the const table, a runtime handle through the arena), and the bytes
hash to the key. A handle the interner cannot resolve evicts to
`PersistenceError::Missing`, since a const handle alone no longer carries the
key.
Inject: the content hash looks up the string table, interns, returns a
runtime handle.

On inject the const table is consulted first. The candidate const handle
is built from the low 28 bits of the key, and it is accepted only if the
string it resolves to hashes back to the whole key, so a handle that
shares 28 bits with the key and nothing else is not taken for the string.

### Disk-layout types (rkyv ABI)

Every value that crosses the rkyv boundary on disk is specified by
its byte layout, not by its runtime type surface. The Archived
associated type on an impl Archive names the disk form; the
runtime type names the in-memory form.

Current disk-layout types, pinned:

- Str Archived to u64. The full 64-bit FNV-1a content hash of the
 string's bytes; the const and runtime flag does not travel to disk,
 because the key names the string and not the session's handle for it.
- Integer primitive columns archive to themselves (identity).

The runtime API carries the hash value as arvo_hash ContentHash, an
alias for arvo_bits Bits<64, Hot>, the same width as the archived form,
so the rkyv boundary is a plain copy.

ContentHash and the width-refit traits come from arvo-hash and
arvo-refit at the arvo revision the workspace pins. Persistence reads the
crates at that pin and nothing newer, and the hash it computes is
`hilavitkutin_str::const_fnv1a`.

Disk-layout types are exempt from the primitive-vocabulary
discipline. They exist to pin a byte layout across sessions. Giving
them a semantic newtype would add a conversion call at the hottest
serialisation path without changing the on-disk format.

### Extending

Consumer types needing custom serialisation boundary handling
impl Archive directly. Same mechanism, no new traits.

## Cold store

### File layout (per consumer)

```
data_dir/
 manifest.rkyv, table directory, metadata
 tables/
 <name>.rkyv, archived column data per table
 strings/
 runtime.rkyv, runtime string table: content_hash → bytes
```

Consumer extends with domain-specific files (locale overlays,
search indices, warmup manifests, etc.).

### Data flow

**Evict (hot → cold):**
```
column data (raw typed arrays)
 → rkyv serialize (with PersistenceContext carrying interner)
 → Str values: handle → content_hash
 → all else: identity
 → write to.rkyv file via MemoryProvider
```

**Inject (cold → hot):**
```
mmap.rkyv file (via MemoryProvider)
 → rkyv archived data directly accessible (zero-copy)
 → Str columns: content_hash → intern → runtime handle
 → all else: pointer handoff
 → inject into ColumnStorage
```

### Flush coordination

The cold store provides the mechanism. The consumer decides
when to flush:
- `flush(dirty_set)`, serialise dirty data to disk
- `load(table)`, mmap and inject a table
- `snapshot(target)`, copy all files for backup

## SIEVE eviction

`SieveCache` wrapping ColumnStorage. Keyed by
`(TableId, SegmentRange)`, weighted by byte size.

Key invariant: dirty data is flushed before eviction. The
hot store is fully reconstructable from cold store files.

The consumer provides:
- Memory budget (how much RAM the hot store gets)
- Budget phase changes (e.g., game launch → shrink)
- Eviction granularity preferences

## String table persistence

Runtime strings persisted as `(content_hash, string_bytes)`
pairs in `runtime.rkyv`. On load:
1. Const table available from binary (linker section)
2. Load `runtime.rkyv` → intern each pair → sequential IDs
3. Column data `Str` values resolved via content hash lookup

Content hash = stable file-level identity.
Sequential ID = ephemeral session-level identity.

## Manifest

```rust
struct Manifest {
 tables: /* map of table_id → TableMeta */,
 count: ColumnCount,
}

struct TableMeta {
 name_hash: ContentHash,
 version: SchemaVersion,
 record_count: USize,
 column_count: ColumnCount,
 columns: /* column metadata */,
}
```

Domain aliases:

- ContentHash comes from arvo_hash (alias for arvo_bits Bits<64, Hot>).
- SchemaVersion, record_count, ColumnCount, Cardinality,
 BufferOffset, BufferLen, BitWidth, EvictionWeight are
 persistence-local newtypes over USize or raw integer (when the bit
 width is load-bearing, as with SchemaVersion's u32 ordinal).

All rkyv-archived. Consumer extends with domain-specific metadata
(schema versions, migration state, etc).

## Backup

Snapshot = copy the data directory. All files are rkyv archives,
always consistent (complete writes via MemoryProvider). Consumer
wraps in whatever container format they want (ZIP+zstd, custom
container, etc.).

## Design rule

No std. No alloc. No domain knowledge. Consumer-agnostic.
Reusable across hilavitkutin ecosystem.

## Engine integration boundary (round 202605101036)

Per Topic 8 axis C, the runtime engine never depends on this crate's
types directly. Consumers wire the persistence spine via a
`PersistenceProvider` trait registered on the SchedulerBuilder; the
engine's resource resolution path reaches the provider through the
standard `Has...Provider` accessor pattern.

PassEnd WU drain protocol: a substrate or consumer-authored PassEnd
WorkUnit reads accumulator columns and writes through
`PersistenceProvider::commit(...)`. The commit boundary is the
phase-end synchronisation point; persistence writes are ordered after
the phase barrier and before the next phase's morsel dispatch begins.
Cross-thread visibility is guaranteed by the barrier's Release-Acquire
pair (Topic 3 S7 atomic-ordering protocol).

The narrow integration shape preserves the standalone-ecosystem-crate
rule. Substrate consumers (vehje, future loimu) ship their own
provider impls; this crate ships no engine-side glue.
