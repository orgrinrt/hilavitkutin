# hilavitkutin-providers

Default Resource-backed providers for the hilavitkutin scheduler.
Standalone ecosystem crate: consumed by the engine via Kit
installation or via direct `builder.with(Resource::new(...))`
wiring, no reverse dep.

Ships the interner surface and the default `ColumnStorage` backing
(`ArenaColumnStorage`) today: an `InternerApi` provider trait,
`MemoryArena<BYTES, ENTRIES>` inline-storage backing, the
`InternerKit` preset, and `ArenaColumnStorage<M, D>` (the naive
arena-backed store the engine wires in via `CS: ColumnStorage`),
and `StaticBumpMemory`, the memory provider over a buffer the consumer
hands it for the life of the program. Future rounds add the Clock
default and a libc/Unix memory provider per consumer demand.

### `InternerApi`

The provider shape. WorkUnits that handle `Str` (lexers, file
walkers, diagnostic emitters, etc.) declare `HasInterner` in their
`Ctx` tuple bound and call `ctx.interner().intern(s)` /
`ctx.interner().resolve(handle)` from within `execute()`.

The trait carries `'static` so the value can live in a
`Resource<T>`. v0 does not require `Send + Sync` on the provider
because the engine's resource access pattern is sequential during
single-thread morsel dispatch. The Sync arena variant in BACKLOG
tracks the future generalisation.

### `HasInterner`

```rust
pub trait HasInterner {
 type Provider: InternerApi;
 fn interner(&self) -> &Self::Provider;
}
```

The accessor lives in providers, not in api. The platform
contracts in api (memory / threadpool / clock) are the
engine-required surfaces; the interner is an opt-in provider, not
an engine prerequisite.

### `MemoryArena<BYTES, ENTRIES>`

Inline-storage `ArenaInterner` impl. Holds `[u8; BYTES]` bytes plus
an `[Entry; ENTRIES]` table where each entry records `(offset,
len)` for a previously-interned string. Interior mutability via
`Cell` for the cursor and entry count, `UnsafeCell` for the
buffer and table.

Each runtime-interned string gets a sequential 28-bit id (the
entry index). `arena_resolve(id)` looks up the entry and slices
`[offset..offset+len]` from the byte buffer.

Capacity overflow (out of bytes or out of entry slots) returns
sentinel id `u32::MAX` from `arena_intern`. Consumers tune
`BYTES` and `ENTRIES` to their workload.

`MemoryArena` is `!Sync` by default. The eventual
`Resource<StringInterner<MemoryArena<...>>>` will need either a
consumer-supplied Mutex shim or a future SyncArena variant for
multi-thread access. Tracked in BACKLOG.

### `default_interner()` constructor

```rust
pub const fn default_interner<const BYTES: usize, const ENTRIES: usize>()
 -> StringInterner<MemoryArena<BYTES, ENTRIES>>
{
 StringInterner::new(MemoryArena::new())
}
```

Consumers wire it onto the scheduler with
`builder.with(Resource::new(default_interner::<BYTES, ENTRIES>()))`.
Two const generics because byte capacity and entry-count are
independent dimensions a consumer tunes.

### `InternerKit<BYTES, ENTRIES>`

```rust
pub struct InternerKit<const BYTES: usize, const ENTRIES: usize>;

impl<const BYTES: usize, const ENTRIES: usize> Kit
 for InternerKit<BYTES, ENTRIES>
{
 type Units = read![];
 type Owned = read![Resource<StringInterner<MemoryArena<BYTES, ENTRIES>>>];
}
```

The Kit impl is purely declarative per the round-4 Kit shape
(`pub trait Kit { type Units: WorkUnitBundle; type Owned: StoreBundle }`).
It declares no WorkUnits (`type Units = read![]`); it owns one
Resource. The Kit impl never names `SchedulerBuilder`. The v0.1
`BuilderResource<T>` bridge is gone (deleted entirely per
`no-legacy-shims-pre-1.0.md`); the new shape needs no bridge
because Kits no longer call methods on builders.

Usage on the scheduler:

```rust
let scheduler = Scheduler::builder()
.with(Resource::new(default_interner::<4096, 256>()))
.with(InternerKit::<4096, 256>)
.build();
```

The Kit declares the type-level commitment that
`Resource<StringInterner<MemoryArena<4096, 256>>>` exists in
`Stores`. The actual instance is supplied by the app via
`builder.with(Resource::new(...))`; the api has no
`Kit::default_resources()` association. See BACKLOG for the
auto-wiring follow-up.

Equivalent to the direct form
`Scheduler::builder().with(Resource::new(default_interner::<4096, 256>())).build()`
when there's only this one kit. The Kit form becomes valuable
once a consumer bundles several Resources / Columns under one
named preset; for the single-resource interner case the gain is
consistency more than ergonomic savings.

### Replaceable opt-in for the Interner Resource

The `Resource<StringInterner<MemoryArena<...>>>` does not impl
`Replaceable` by default. Apps that need test-fixture replacement
(for example, a deterministic interner for unit tests) impl
`Replaceable` themselves on the relevant alias type. This matches
the workspace's "tools, not policies" rule: the crate ships
the Resource without forcing override semantics on consumers that
do not want them.

### `ArenaColumnStorage<M, D>`

The default backing for the unified columnar store
(`hilavitkutin_api::ColumnStorage`). A naive arena placeholder: the
engine stays generic over `CS: ColumnStorage`, and consumers (and the
engine's own tests) wire this in as the concrete store. The columnar
engine replaces it later without touching any `CS: ColumnStorage`
consumer.

```rust
pub struct ArenaColumnStorage<M: MemoryProviderApi, D: Capacity = Dim<256>> {
    // M: the allocator. D: caps the distinct-column count (Dim<256>
    // matches the engine's Mask256 store ceiling). A fixed slot table
    // D::Array<Maybe<ColumnSlot>> records each column's base / bytes /
    // record count, indexed by StoreId.
}
```

`reserve<T>` allocates `count * size_of::<T>()` bytes 64-byte aligned
through the bound `MemoryProvider`, recording the slot; a resizing
re-reserve frees the prior block first. `column_ptr` / `column_ptr_mut`
return the recorded base cast to the scalar type (raw, not a slice, per
R6). `count` reads the slot. `release` is a no-op (the reader-count
reclamation is a columnar-engine concern). `Drop` deallocates every
live slot through the provider, passing `CACHE_LINE_ALIGN` back so the free
layout matches the reserve layout. Every column is reserved at that 64-byte
alignment because the canonical design requires it, and a free that assumed
anything narrower would be undefined behaviour under a layout-taking
allocator.

Correctness, not performance: the slot table is a flat scan and each
column is a separate provider allocation. The point is a working
`ColumnStorage` behind the contract while the columnar engine matures.

### `StaticBumpMemory`

A memory provider over one buffer the consumer hands it, which is the
provider's alone for as long as the provider lives.

```rust
pub struct StaticBumpMemory {
    // base and capacity of the buffer it was built over, and an atomic
    // cursor: the offset of the first free byte.
}

impl StaticBumpMemory {
    pub const fn new(buffer: &'static mut [MaybeUninit<u8>]) -> Self;
    pub const unsafe fn from_raw_parts(base: *mut MaybeUninit<u8>, len: USize) -> Self;
}

unsafe impl MemoryProviderApi for StaticBumpMemory { /* ... */ }
```

`allocate(len, align)` rounds the address of the first free byte up to
`align` (the address, not the offset, so a buffer of any alignment gives
aligned blocks) and moves the cursor past the block by compare-exchange,
so callers on several threads get disjoint blocks without a lock. A block
that would pass the end of the buffer, or an `align` that is not a power
of two, returns null and leaves the cursor where it was. `deallocate`
and `protect` do nothing: no block is handed back before the buffer is,
and its pages are not the provider's to change.

`new` takes a buffer borrowed exclusively for `'static`, which nothing
can release, and is the safe case. `from_raw_parts` takes the buffer as
a pointer and a length for a consumer whose buffer is not `'static`, a
heap block a bench frees when its scheduler is done, and the caller
promises what the borrow proves for `new`: the `len` bytes at `base` are
valid for reads and writes, nothing but the provider reads or writes
them, and they stay so until the provider is dropped. `new` is
`from_raw_parts` over the borrowed slice.

It keeps every promise `MemoryProviderApi` asks of an implementer. The
buffer's address is not the provider's, so no move of the provider moves
a block, and the buffer outlives the provider (forever under `new`, by
the caller's promise under `from_raw_parts`), which is all promise 2
asks; the compare-exchange keeps live blocks apart. A consumer without an
operating system builds it over a `static` buffer; the engine's tests
build it over a leaked one.

## What this crate deliberately does not ship

- **`M: HasMemoryProvider` parameter on `MemoryArena`.** The
 original 2026-05-01 task description named `MemoryArena<M, BYTES>`
 parameterised over a runtime memory provider. The crate uses
 inline storage at the type level instead. Reintroducing the M
 parameter needs allocate-at-builder-time plumbing the engine
 does not yet have. Tracked in BACKLOG.
- **Clock and libc/Unix memory provider defaults.** Per crate scope:
 interner, the `ArenaColumnStorage` backing and `StaticBumpMemory`
 at this stage. The Clock default and a memory provider over the
 operating system's pages each land in their own round when consumer
 demand surfaces.
