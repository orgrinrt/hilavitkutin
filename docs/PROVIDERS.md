# hilavitkutin-providers

Default Resource-backed providers for the hilavitkutin scheduler.
Standalone ecosystem crate: consumed by the engine via Kit
installation or via direct `builder.with(Resource::new(...))`
wiring, no reverse dep.

Ships the interner surface and the default `ColumnStorage` backing
(`ArenaColumnStorage`) today: an `InternerApi` provider trait,
`MemoryArena<BYTES, ENTRIES>` inline-storage backing, the
`InternerKit` preset, and `ArenaColumnStorage<M, D>` (the naive
arena-backed store the engine wires in via `CS: ColumnStorage`),
`StaticBumpMemory`, the memory provider over a buffer the consumer
hands it for as long as the provider lives (forever through `new`, by
the caller's promise through `from_raw_parts`), `StaticFreeListMemory`,
the provider over such a buffer that takes blocks back, and the adapt kits
`StandardAdaptKit` and `OffAdaptKit` with their per-axis metrics
resources. The default clock and the operating-system memory provider
are not here today; the engine's `os` feature carries `OsClock` and
`OsMemoryProvider`.

## Features

Every implementation here sits behind a cargo feature the consumer turns
on, and a build on default features carries the contracts alone. A
feature is named for what its implementations rest on, and the name means
the same in every crate of the family:

| Feature | Rests on | Carries |
|---|---|---|
| `static` | memory the consumer hands in, with no operating system | `StaticBumpMemory`, `StaticFreeListMemory` |
| `portable` | the contracts alone, on any target | `ArenaColumnStorage`, `MemoryArena` with `default_interner` and `InternerKit`, `AdaptWu` with the EMA helpers and `StandardAdaptKit` and `OffAdaptKit`, the per-axis metrics resources with `MetricsKit` |
| `os` | the operating system's services | not in this crate; the engine carries `OsMemoryProvider` and `OsClock` under it |

The two contracts this crate declares, `InternerApi` and `HasInterner`,
are not behind a feature. A consumer that wants a store over its own
buffer turns on `static` and `portable` together, since
`ArenaColumnStorage` is the store and `StaticBumpMemory` the provider
under it.

### `InternerApi`

The provider shape. WorkUnits that handle `Str` (lexers, file
walkers, diagnostic emitters, etc.) declare `HasInterner` in their
`Ctx` tuple bound and call `ctx.interner().intern(s)` /
`ctx.interner().resolve(handle)` from within `execute()`.

The trait carries `'static` so the value can live in a
`Resource<T>`. v0 does not require `Send + Sync` on the provider
because the engine's resource access pattern is sequential during
single-thread morsel dispatch. The Sync arena variant in BACKLOG
tracks the future generalisation.

### `HasInterner`

```rust
pub trait HasInterner {
 type Provider: InternerApi;
 fn interner(&self) -> &Self::Provider;
}
```

The accessor lives in providers, not in api. The platform
contracts in api (memory / threadpool / clock) are the
engine-required surfaces; the interner is an opt-in provider, not
an engine prerequisite.

### `MemoryArena<BYTES, ENTRIES>`

Inline-storage `ArenaInterner` impl. Holds `[u8; BYTES]` bytes plus
an `[Entry; ENTRIES]` table where each entry records `(offset,
len)` for a previously-interned string. Interior mutability via
`Cell` for the cursor and entry count, `UnsafeCell` for the
buffer and table.

`arena_intern` keeps the interning law of the `ArenaInterner`
contract: it first scans the entries held for one of equal length
and equal bytes and returns its id, so a string interned twice
gets one id. Only a string not held is appended, and it gets the
next sequential 28-bit id (the entry index). The scan is linear in
the entries held, once per runtime intern. `arena_resolve(id)`
checks the id against the live entry count, then looks up the
entry and slices `[offset..offset+len]` from the byte buffer; an
id at or past the count is not read. A handle another arena issued
is not told apart from one of its own.

Capacity overflow (out of bytes or out of entry slots) returns
sentinel id `u32::MAX` from `arena_intern`. An id of 2^28 or more is
the arena's refusal under the `ArenaInterner` contract, so
`StringInterner` answers the sentinel with `Maybe::Isnt` and builds
no handle from it; the caller sees that its string was not
interned. An id the arena did not issue, which a handle from another
interner can carry, is still answered with the empty string, so
`evict_str` stores the hash of `""` where the persistence design asks
for `Missing`; that waits on a resolve that can say it holds nothing
(ticket `evict_str_turns_an_unresolvable_runtime_str_into_the_hash_of`).
An arena of `ENTRIES` entries issues ids below `ENTRIES`, and its
refusal is `u32::MAX`, so an `ENTRIES` of up to 2^28 keeps every
issued id inside the 28-bit field and below the refusal; an `ENTRIES`
past 2^28 fails the build at `MemoryArena::new`.
Consumers tune `BYTES` and `ENTRIES` to their workload.

`MemoryArena` is `!Sync` by default. The eventual
`Resource<StringInterner<MemoryArena<...>>>` will need either a
consumer-supplied Mutex shim or a future SyncArena variant for
multi-thread access. Tracked in BACKLOG.

### `default_interner()` constructor

```rust
pub const fn default_interner<const BYTES: usize, const ENTRIES: usize>()
 -> StringInterner<MemoryArena<BYTES, ENTRIES>>
{
 StringInterner::new(MemoryArena::new())
}
```

Consumers wire it onto the scheduler with
`builder.with(Resource::new(default_interner::<BYTES, ENTRIES>()))`.
Two const generics because byte capacity and entry-count are
independent dimensions a consumer tunes.

### `InternerKit<BYTES, ENTRIES>`

```rust
pub struct InternerKit<const BYTES: usize, const ENTRIES: usize>;

impl<const BYTES: usize, const ENTRIES: usize> Kit
 for InternerKit<BYTES, ENTRIES>
{
 type Units = read![];
 type Owned = read![Resource<StringInterner<MemoryArena<BYTES, ENTRIES>>>];
}
```

The Kit impl is purely declarative per the round-4 Kit shape
(`pub trait Kit { type Units: WorkUnitBundle; type Owned: StoreBundle }`).
It declares no WorkUnits (`type Units = read![]`); it owns one
Resource. The Kit impl never names `SchedulerBuilder`. The v0.1
`BuilderResource<T>` bridge is gone (deleted entirely per
`no-legacy-shims-pre-1.0.md`); the new shape needs no bridge
because Kits no longer call methods on builders.

Usage on the scheduler:

```rust
let scheduler = Scheduler::builder()
.with(Resource::new(default_interner::<4096, 256>()))
.with(InternerKit::<4096, 256>)
.build();
```

The Kit declares the type-level commitment that
`Resource<StringInterner<MemoryArena<4096, 256>>>` exists in
`Stores`. The actual instance is supplied by the app via
`builder.with(Resource::new(...))`; the api has no
`Kit::default_resources()` association. See BACKLOG for the
auto-wiring follow-up.

Equivalent to the direct form
`Scheduler::builder().with(Resource::new(default_interner::<4096, 256>())).build()`
when there's only this one kit. The Kit form becomes valuable
once a consumer bundles several Resources / Columns under one
named preset; for the single-resource interner case the gain is
consistency more than ergonomic savings.

### Replaceable opt-in for the Interner Resource

The `Resource<StringInterner<MemoryArena<...>>>` does not impl
`Replaceable` by default. Apps that need test-fixture replacement
(for example, a deterministic interner for unit tests) impl
`Replaceable` themselves on the relevant alias type. This matches
the workspace's "tools, not policies" rule: the crate ships
the Resource without forcing override semantics on consumers that
do not want them.

### `ArenaColumnStorage<M, D>`

The default backing for the unified columnar store
(`hilavitkutin_api::ColumnStorage`). A naive arena placeholder: the
engine stays generic over `CS: ColumnStorage`, and consumers (and the
engine's own tests) wire this in as the concrete store. The columnar
engine replaces it later without touching any `CS: ColumnStorage`
consumer.

```rust
pub struct ArenaColumnStorage<M: MemoryProviderApi, D: Capacity = Dim<256>> {
    // M: the allocator. D: caps the distinct-column count (Dim<256>
    // matches the engine's Mask256 store ceiling). A fixed slot table
    // D::Array<Maybe<ColumnSlot>> records each column's base / bytes /
    // record count, indexed by StoreId.
}
```

`reserve<T>` allocates `count * size_of::<T>()` bytes 64-byte aligned
through the bound `MemoryProvider`, recording the slot. `column_ptr` / `column_ptr_mut`
return the recorded base cast to the scalar type (raw, not a slice, per
R6). `count` reads the slot. `release` gives the slot's block back
through the provider at the 64-byte alignment it was reserved at and
empties the slot, so the id reads as unreserved with a count of zero
until it is reserved again; a release of an unreserved id, or of one
past the cap, does nothing. Whether the block is reused is the
provider's: `StaticFreeListMemory` hands it out again, `StaticBumpMemory`
does not. A re-reserve gives the old block back the same way before it
takes the new one, and copies no record across. A reserve refused for
its arguments, `IdOutOfRange` or `LengthOverflow`, changes nothing, so
a live column stays live; one whose block the provider refuses,
`Exhausted`, leaves the id unreserved with a count of zero, since the
old block went back first. `Drop` deallocates every
live slot through the provider, passing `CACHE_LINE_ALIGN` back so the free
layout matches the reserve layout. Every column is reserved at that 64-byte
alignment because the canonical design requires it, and a free that assumed
anything narrower would be undefined behaviour under a layout-taking
allocator.

Correctness, not performance: the slot table is a flat scan and each
column is a separate provider allocation. The point is a working
`ColumnStorage` behind the contract while the columnar engine matures.

### `StaticBumpMemory`

A memory provider over one buffer the consumer hands it, which is the
provider's alone for as long as the provider lives.

```rust
pub struct StaticBumpMemory {
    // base and capacity of the buffer it was built over, and an atomic
    // cursor: the offset of the first free byte.
}

impl StaticBumpMemory {
    pub const fn new(buffer: &'static mut [MaybeUninit<u8>]) -> Self;
    pub const unsafe fn from_raw_parts(base: *mut MaybeUninit<u8>, len: USize) -> Self;
}

unsafe impl MemoryProviderApi for StaticBumpMemory { /* ... */ }
```

`allocate(len, align)` rounds the address of the first free byte up to
`align` (the address, not the offset, so a buffer of any alignment gives
aligned blocks) and moves the cursor past the block by compare-exchange,
so callers on several threads get disjoint blocks without a lock. A block
that would pass the end of the buffer, or an `align` that is not a power
of two, returns null and leaves the cursor where it was. `deallocate`
and `protect` do nothing: no block is handed back before the buffer is,
and its pages are not the provider's to change.

`new` takes a buffer borrowed exclusively for `'static`, which nothing
can release, and is the safe case. `from_raw_parts` takes the buffer as
a pointer and a length for a consumer whose buffer is not `'static`, a
heap block a bench frees when its scheduler is done, and the caller
promises what the borrow proves for `new`: the `len` bytes at `base` are
valid for reads and writes, nothing but the provider reads or writes
them, and they stay so until the provider is dropped. `new` is
`from_raw_parts` over the borrowed slice.

It keeps every promise `MemoryProviderApi` asks of an implementer. The
buffer's address is not the provider's, so no move of the provider moves
a block, and the buffer outlives the provider (forever under `new`, by
the caller's promise under `from_raw_parts`), which is all promise 2
asks; the compare-exchange keeps live blocks apart. A consumer without an
operating system that never gives memory back builds it over a `static`
buffer; the engine's tests build it over a leaked one. A consumer that
gives blocks back and wants them again builds `StaticFreeListMemory`.
`allocate_zeroed` keeps the trait's default, since a buffer handed over
as `MaybeUninit` bytes is not known to be zero.

### `StaticFreeListMemory`

A memory provider over one buffer the consumer hands it, as
`StaticBumpMemory` is, that takes blocks back and hands them out again.
It is for a consumer that keeps a store between rebuilds and reserves
its columns again each time, or keeps an arena whose live peak is far
below what it allocates over a run.

```rust
pub struct StaticFreeListMemory {
    // the buffer it was built over, the head of the free list, the bytes
    // handed out, and the one-flag lock over the list.
}

impl StaticFreeListMemory {
    pub const fn new(buffer: &'static mut [MaybeUninit<u8>]) -> Self;
    pub const unsafe fn from_raw_parts(base: *mut MaybeUninit<u8>, len: USize) -> Self;
    pub fn used(&self) -> USize;
    pub const fn capacity(&self) -> USize;
}

unsafe impl MemoryProviderApi for StaticFreeListMemory { /* ... */ }
```

The two constructors and what they ask of the buffer are
`StaticBumpMemory`'s, and both providers hold the buffer through one
private type that carries the constructors and that reasoning once.

Free space is a list of free blocks in address order, and each free
block holds its own list node, its length and the next free block, in
its first bytes, so the provider keeps no table of its own. Every
block's start and length are multiples of a grain, the size of that
node (two machine words, a multiple of its alignment), so any piece a
split leaves can hold a node. The usable span is the buffer's grain-aligned interior,
which at first is one free block.

`allocate(len, align)` rounds `len` up to the grain, a zero length
taking one grain, and walks the list for the first free block that holds
that length at `align`, or at the grain where `align` is smaller. The
space before the block, which is a multiple of the grain, and the space
after it stay on the list as free blocks. No block that fits, or an
`align` that is not a power of two, returns null and changes nothing.
`deallocate(ptr, len, align)` rounds `len` the same way, puts the block
back in address order, and merges it with the free block before it and
the one after it where they touch, so space given back in any order
comes together again. `protect` does nothing, as for the bump provider.

The list is changed by several threads through the trait, and the stack
has no lock, so the provider keeps a one-flag spin lock over it: taken
by an acquire compare-exchange, given back by a release store, so every
change one holder makes to the list and its nodes happens before the
next holder reads them. The count behind `used()` is relaxed and read
as a count only, never to order a block's bytes. Allocation happens
at build and between frames, never in the morsel loop, so the spin is
short; a lock of the stack's own replaces it (ticket
`the_stack_has_no_lock_so_a_provider_keeps_a_spin_flag_of_its_own`).

It keeps every promise of `MemoryProviderApi`. A block is cut from free
space inside the buffer at an address rounded up to its alignment, which
is promise 1, and the buffer outlives the provider and moves with
nothing, which is promise 2. A block is on the list or handed out and
never both, and merging joins only free blocks that touch, which is
promise 3. Every change of the list happens under the lock, which is
promise 4. `allocate_zeroed` keeps the trait's default, since a block
given back and handed out again carries what its last owner wrote, and
that keeps promise 5. `used()` is the bytes handed out and not given
back, grain padding included, and `capacity()` the buffer's length.

## What this crate deliberately does not ship

- **`M: HasMemoryProvider` parameter on `MemoryArena`.** The
 original 2026-05-01 task description named `MemoryArena<M, BYTES>`
 parameterised over a runtime memory provider. The crate uses
 inline storage at the type level instead. Reintroducing the M
 parameter needs allocate-at-builder-time plumbing the engine
 does not yet have. Tracked in BACKLOG.
- **Clock and operating-system memory provider defaults.** The
 engine's `os` feature carries both today, `OsClock` and
 `OsMemoryProvider`. A default of this crate's own lands in its own
 round when consumer demand surfaces; its scope until then is the
 interner, the `ArenaColumnStorage` backing, the two providers over a
 consumer's buffer (`StaticBumpMemory` and `StaticFreeListMemory`) and
 the adapt kits.
