# hilavitkutin, Design

Morsel-driven pipeline execution engine. Takes WorkUnit declarations
(from hilavitkutin-api), analyses them into phases/trunks/fibers,
compiles dispatch programs, and runs them on a pre-allocated thread
pool. `#![no_std]`, no alloc. All index/count/weight types use arvo
newtypes.

The consolidation topic (202603181200) is the authoritative design
source. This document maps domains to engine modules.

## Plan stage (domains 11-16)

Pure analysis, no runtime state. Takes WU declarations (Read/Write
AccessSets, scheduling hints, COMMUTATIVE flag) and produces a
complete execution plan:

1. Build DAG from AccessMask overlap (arvo-bitmask). DependencyGraph
   uses CSR backing (`row_offsets` + `col_indices` + `edge_kinds`)
   per Topic 9 axis B, bench-locked canonical at every N (no threshold).
   It converts to a bidirectional CSR (forward adjacency plus a
   pre-computed transpose) to feed the arvo-sparse structural steps
   (5-6). RAW edges are order-independent: for any unit pair where one
   writes a store the other reads, the writer sorts before the reader,
   regardless of which was registered first. WAW conflicts serialise
   deterministically by input index (the lower index first). WAR
   anti-dependencies are a tracked plan-chain follow-up.
2. Topological sort + node renumbering (arvo-graph). A registration
   whose units form a cyclic data dependency (each reads what another
   writes, transitively back to itself) cannot be linearised; the runner
   rejects it as `PlanError::Cycle`.
3. Upward rank → critical path (arvo-graph)
4. Waist detection → phase boundaries (arvo-graph)
5. RCM reordering → renumber permutation on `ExecutionPlan`, feeding arena layout now and fiber grouping order later (arvo-sparse)
6. Block diagonal → connected-component partition projected to per-phase
 trunk skeletons (one trunk per block; sets `Phase` id, `Trunk` id, trunk
 count). Dulmage-Mendelsohn fine decomposition, dead column elimination,
 and the phase-alignment check layer on in later rounds (arvo-sparse).
 Consumes `core_class: [CoreClass; MAX_CORES]` from heterogeneous-core
 detection per Topic 6 axis E.
7. Spectral partitioning → spectral `FiberGrouping` via an engine-local
 symmetric Laplacian over arvo-spectral's k-way partitioning, run over
 the live-node-count-aware (loose-CSR-correct) Laplacian. Step 8's
 width-gate consumes it for wide blocks (arvo-spectral).
8. Fiber grouping → per-block fiber formation projected onto
 `Trunk.components`. Each block (trunk) forms its fibers within the
 block's units in topo order, so fibers nest within trunks. A width-gate
 picks the former per block: wide blocks (unit count above the
 threshold) use the spectral former, narrow blocks the greedy one.
 `TrunkComponent::Fiber` entries carry id and units; columns, head+tail,
 and dispatch shape fill in at later steps (arvo-comb).
9. Per-fiber morsel sizing (write-only formula, domain 12). Output
   includes `micro_morsel_interval: USize` alongside `morsel_size: USize`
   per Topic 7 amendment. Default `MICRO_MORSEL_INTERVAL = 64` records.
   Adapt sidecar cache footprint subtracted from `l1_write_budget`
   per Topic 5 M10 amendment.
10. Per-phase adaptive configs (MAX_FUSE / BALANCED / MAX_SPLIT)
11. Column classification per fiber (internal / input / output)
12. Dirty propagation masks for incremental skip (arvo-bitmask)
13. FiberShape classification per Topic 3 amendment (Topic 4 axis D):
    typed projection over the unique fiber shape set (K, not 2^N).
    Codegen-emitted; informs per-core dispatch monomorphisation.

Plan recomputes on `Scheduler::run()` entry when the dirty bit is set
(Topic 1 axis 4). Dirty bit is keyed per `PlanAffecting`-bound Resource
(Topic 8 axis B); resources without that marker are cheap value-swaps.

Plan recompute is single-threaded in v1 (sequential through steps 1-13).
Parallelisation deferred until consumer pipelines push beyond ~256 WUs.

## Dispatch codegen (domain 17)

Turns the plan into executable code. Codegen is shaped by Topic 4 axes:

- Sealed `trait DispatchCodegen<Cfg: RunCfg>` with TAIT
  `type CoreDispatch = impl Fn(...)`. Single shipped impl
  `StandardCodegen` lowers to closed-form arithmetic, zero `blr`.
- Per-fiber-shape generic monomorphisation: `fn run_fiber<S: FiberShape>(...)`
  over the sealed `FiberShape: Sealed` marker carrying `type WuTuple` +
  `const SHAPE_ID`. Combinatorics K (unique shapes), not 2^N.
  Sealed-trait dispatch measured free vs hand-written direct calls
  per `mock/benches/dispatch_static_n*_findings.md`.
- Codegen-wrapped via `#[inline(always)] fn invoke_<wu>_in_fiber_<n>`
  shim fns; LLVM elides the shim layer.

The fused-pipeline pattern within a fiber:

1. Cache resources to stack-local array
2. Read fiber-input columns at morsel start
3. Pure function pipeline with locals (no intermediate stores)
4. Fiber-internal columns → register-to-register (DSE)
5. All output stores grouped at end (store-buffer friendly)

The concrete Context a WorkUnit's `execute` receives is a per-WU
`EngineCtx<'frame, R, W>` the engine constructs at the monomorphised
dispatch call site, scoped to that WU's declared `Read` / `Write`. It
holds only the projected pointers for those stores (a WU cannot reach
an undeclared store, since its Context does not carry that pointer),
implements the eight `HasX` accessor traits with `Provider = Self`,
resolves resources from the arena, reads and writes input columns over
the per-frame column buffers, appends to accumulator columns, and
iterates the morsel. The WorkUnit's
`Ctx<'frame>` stays a `HasX`-bounds declaration; only the engine names
`EngineCtx<'frame, W::Read, W::Write>`.

The sequential walk that constructs each unit's `EngineCtx` and runs
`execute` over a fiber's WorkUnit sequence is `RunFiber`, a monomorphic
trait over a value-carrying unit list: `WuCons` cells carry a unit
instance plus the tail, `WuNil` terminates, following the `PtrCons` /
`PtrNil` cell convention. The free `run_fiber_walk` entry drives it. Per
unit it projects that unit's `EngineCtx` from the shared arena through
`EngineCtx::project`, runs `execute` via the `invoke_wu_in_fiber` shim,
and recurses on the tail; the per-unit projection index is carried as a
parallel witness list and inferred at the call site, no caller turbofish.
This is the pre-codegen dispatch core, pure Rust generics with no LLVM,
and is distinct from the per-fiber-shape `run_fiber<S: FiberShape>`
monomorphisation above (the codegen-emitted path). `RunFiber` itself
stays resource-only: it is the slice-1 sequential primitive, retained
with its test, and it does not carry the column projection a column-
bearing unit needs. Column-bearing units dispatch through `Scheduler::run`
(the `CollectFiber` path described next), which projects columns from the
bindings alongside resources.

`Scheduler::run` dispatches the WorkUnit instances the builder retained at
registration (see the scheduler builder section) in the plan's topological
order, windowing the record range into morsels of `RunCfg::MORSEL_SIZE`
(guarded to at least one record) and dispatching each unit once per morsel
(unit-outer: a unit completes its record range before the next unit runs).
The per-fiber, phase-sequential morsel loop is a later arc. It
materialises one type-erased dispatch slot per retained unit through
`CollectFiber`, the sibling of `RunFiber` that records a `FiberSlot` (an
erased instance pointer plus a per-unit shim) instead of running the unit
inline, then walks the phase-sequential dispatch order `build` derived (the
plan flattened `phases -> trunks -> fibers -> units`, a topological order
grouped by the plan's locality structure) and dispatches each unit's slot. The shim casts the erased pointer back to its
concrete WorkUnit, projects the unit's `EngineCtx` from the bindings
(resources via `Project`, columns via `ColProject` over the Read and Write
sets, fully-qualified as `EngineCtx::project` does it), and runs `execute`. A
column-reading unit registered ahead of its writer runs after it, because the
plan reorders them so the writer's column write lands first. Windowing the
record range into multiple morsels with micro-morsel sync points (the
morsel-loop split) is a later round; `run` covers all records in one morsel.

Per-core compiled dispatch: each physical core gets a monomorphised
`CoreProgram<...>` encoding its phases, record ranges, morsel
boundaries, and sync points. Worker entry receives
`Pin<&'frame CoreProgram<...>>` per the Topic 6 axis C lifetime
contract (validated by the PoolFrame lifetime sketch).

Progress counters: `AtomicUsize` per fiber, monotonic record index.
Plain store (Release), not RMW; cheapest atomic per the
`atomic_ordering_cost` bench (Relaxed beats Acquire/SeqCst by 3-4x
on aarch64). Lock-free by construction.

`DispatchApproach` shipped in v1 (`#[non_exhaustive]`):
- `ScheduleMega`: approach A.
- `TrunkMega`: approach B (within margin of A per bench).
- `IndirectPerFiber`: approach D + E. Single-target indirect dispatch
  per fiber; BTB-warm above N≈256 per the `dispatch_dynamic` bench
  (volatile fn pointer converges to baseline once warmed).

Selection driven by record count + per-fiber shape entropy. Codegen
emits `dmb st` (aarch64) / `sfence` (x86_64) between final FiberOutput
non-temporal `stnp` writes and progress-counter Release store
(Topic 3 invariant S3).

ExpandedLto pragma (domain 03, hilavitkutin-build) REQUIRED for
devirtualisation.

## select_approach base heuristic

`select_approach(record_count, fiber_count) -> DispatchApproach`
returns one of `IndirectPerFiber`, `TrunkMega`, `ScheduleMega` per
the three-variant codegen contract. Base body ships a three-branch
heuristic over `(record_count, fiber_count)` using typed `USize`
thresholds. The two cutovers live as named constants:
`SCHEDULE_MEGA_THRESHOLD: USize = USize(10_000)` and
`SINGLE_FIBER_CUTOVER: USize = USize(1)`. The function body
compares `record_count` and `fiber_count` against the typed
constants directly (`PartialOrd` on `USize`), so the bare-primitive
literal lives at one declaration site instead of every call site.

- `record_count >= SCHEDULE_MEGA_THRESHOLD` returns `ScheduleMega`.
  At high record counts LLVM's whole-pipeline optimisation window
  outweighs the indirect-call overhead.
- Otherwise, if `fiber_count <= SINGLE_FIBER_CUTOVER` returns
  `TrunkMega`. Single fiber means the mega function fits the
  working set without the per-fiber dispatch split.
- Otherwise returns `IndirectPerFiber`. Per-fiber indirect call is
  the lowest-overhead split at small record counts with many
  fibers.

The `10_000` threshold matches the `<10K target` named in the type
doc comments on `DispatchApproach` and `select_approach`. The
tiebreaker between `TrunkMega` and `IndirectPerFiber` uses a coarse
single-fiber cut. Benchmark-tuned thresholds (both the size cutover
AND the fiber-count cutover) land in the follow-up; see BACKLOG.

## Resource handling (domain 19)

Stack-local resource caching: snapshot accessed resources to stack
before morsel loop, redirect res_ptr. LLVM proves stack doesn't alias
heap column data → promotes to registers. Zero resource memory ops in
hot loop. Write back mutable resources after loop.

Pointer separation: resource storage and column storage at separate
provenance. Both through `&self` receiver (load-bearing: prevents
noalias UB when WUs are fused within a fiber).

Convergence accumulators: each head+tail thread gets its own stack-
local accumulator. Merged after convergence (addition for additive,
sequential fallback for non-commutative).

## Threading (domain 20)

Locked shape from Topic 6 (round 202605101036). Pre-allocated thread

### Executor trait

Open `trait Executor: Sealed`, monomorphised. Default impl
`HybridExecutor` ships in this crate. `Scheduler<'frame, Cfg, E: Executor = HybridExecutor>`
propagates the type so consumers can swap in custom executors.
Sealed bound enforces Topic 3 S7 cross-thread atomic-ordering protocol.

### Three-tier parking

Per-OS atomic-wait primitives (Topic 6 axis B):

- Linux: `futex(2)` `FUTEX_WAIT_PRIVATE` / `FUTEX_WAKE_PRIVATE`.
- macOS: `__ulock_wait2` / `__ulock_wake`.
- Windows: `WaitOnAddress` / `WakeByAddressSingle`.

Tier selected by per-phase `predicted_wait_ns` slot in `PoolFrame`
(Topic 6 axis J):

- `< 2µs`: spin-only (skip middle + park tiers).
- `2µs to 50µs`: spin budget exhausted → futex/ulock/WaitOnAddress.
- `> 50µs`: skip spin, park immediately.

Thresholds in `WakeStrategy`. Per-CoreClass spin defaults: P=128, E=32
(Topic 6 axis K; subject to bench validation in follow-up).

### Phase barrier

Centralised atomic counter + futex-wake-all (Topic 6 axis I). Worker
on phase exit: `phase_arrived.fetch_add(1, Release)`. If value < N:
futex-wait on the address. Last arriver (value == N): reset counter,
futex-wake-all. Tree-barrier deferred to follow-up if 32+ core bench
shows ping-pong on the centralised counter.

### Heterogeneous-core awareness

Per-OS P/E classification ships in v1 (Topic 6 axis E):

- x86_64: CPUID leaf 0x1A.
- Linux: `/sys/devices/system/cpu/*/topology/cluster_id` + cpufreq.
- macOS: `sysctlbyname("hw.perflevel0.physicalcpu")`.
- Windows: `GetSystemCpuSetInformation`.

`CoreAssignment` (existing) extends with `core_class: [CoreClass; MAX_CORES]`.
P-cores get critical-path trunks + larger morsels. E-cores get
branches/leaves + proportionally smaller ranges.

Head+tail convergence: two threads process same commutative fiber
from opposite ends. Every commutative fiber gets ~2x parallelism
(Topic 3 axis E).

Pipeline parallelism between phases: phases overlap via `progress_slots[]`
atomic counters. Phase N+1 starts when N produces enough records
for one morsel.

### Shutdown protocol

`PoolFrame.shutdown: AtomicBool`. Workers Relaxed-load after each morsel
boundary; on shutdown=true, exit mainloop cleanly. `Scheduler::Drop`:

1. Stores `true` into `shutdown`.
2. Calls futex/ulock/WakeByAddressAll on every parked worker.
3. Joins each ThreadHandle.

Per Topic 6 axis G. No thread cancellation primitives used.

### Work-stealing

NOT in v1 (Topic 6 axis D). Deterministic morsel assignment (pre-
partitioned at plan time) covers v1's workloads. `Executor::try_steal`
deferred to v2 behind a `work-stealing` feature flag.

## assign_cores base implementation

`assign_cores` maps plan trunks to concrete cores once per pipeline,
returning a `CoreAssignment<MAX_LANES>`. The assignment is reused
across phases: each phase reuses the same per-core trunk mapping,
so the parallel-dispatch width is bounded by the phase with the
most trunks.

The base body lands in HILA-RUNTIME-C4 as a round-robin assignment.
`width = min(max_trunks_per_phase, core_count, MAX_LANES)`. Then
`trunk_index[i] = USize(i)` for `i in 0..width` and `NO_TRUNK` for
the rest. `assigned_count = width`. `fiber_assignments` stays
`FiberId::ZERO` and `morsel_size_multiplier` stays `USize(100)`
(1.0x). Both wait for follow-up slices that populate fiber-to-trunk
maps and heterogeneous-core-aware weighting.

### Heterogeneous-core follow-up

CoreClass-aware assignment lands in a follow-up once `classify_cores`
returns non-stub data on at least one platform. The follow-up
prefers P-cores for the first `width` slots and sets
`morsel_size_multiplier[i] = USize(200)` for P-core slots,
`USize(100)` for E-core slots. Today every `detect_into` stubs out,
so the heterogeneous path is a no-op against the base assignment.

### Per-phase trunk-index alignment assumption

The pipeline-wide round-robin assignment assumes phase-local trunk
indices align: trunk `i` in phase A is logically the same trunk as
trunk `i` in phase B. The dispatch stage that consumes
`CoreAssignment` drives the same core through different phases by
reading `trunk_index[core_idx]` once and feeding it into each
phase's local trunk slot. If a future plan stage reorders trunks
per-phase (so phase A's trunk 2 is logically distinct from phase
B's trunk 2), this assumption breaks and assign_cores would need
the heterogeneous-core follow-up to gain per-phase awareness.
Today the plan stage produces aligned trunk indices; the
assumption holds.

dispatch programs, firing meta-virtual phase boundaries, and
draining ResourceSnapshots through persistence. The runtime
megaround punted the body to a follow-up because the real loop

`Cfg::Out::default()`. A method-level `where Cfg::Out: Default`

this method only to RunCfg impls with a defaultable Out, so
`Scheduler::builder`, `replace_resource`, `replace_value`, and

- No morsel loop walk.
- No per-core dispatch program invocation.
- No adapt subsystem metric flow.
- No meta-virtual `PlanStage / ScheduleReady / PassStart /

- No `ResourceSnapshot` persistence drain.

All of the above land in the follow-up entry
`Scheduler::run real morsel loop body` in `BACKLOG.md.tmpl`. The

The transitional body is honest about its state: consumer crates
can call `Scheduler::run` without panic, but the runtime executes

## Plan dimensions: `PlanDims`

The plan, thread, and dispatch structures size their fixed arrays by
thirteen capacity dimensions: units, stores, edges, phases, trunks,
trunks-per-phase, fibers, lanes, columns, components-per-trunk,
units-per-fiber, columns-per-fiber, and cores. Earlier these were
individual `Cap` const generics threaded through every plan signature
(`ExecutionPlan` carried ten, `compute_execution_plan` twelve). A `Cap`
const generic feeds `[T; cap_size(N)]`, and that `cap_size` in array-
length position leans on `generic_const_exprs`, which overflows the
moment the dimension is threaded from generic scheduler code (the
`cap_size(cap(K))` round-trip). The engine bundles the dimensions into
one trait whose associated types are each an arvo `Capacity`:

```rust
pub trait PlanDims {
    type Units: Capacity;
    type Stores: Capacity;
    type Edges: Capacity;
    type Phases: Capacity;
    type Trunks: Capacity;
    type TrunksPerPhase: Capacity;
    type Fibers: Capacity;
    type Lanes: Capacity;
    type Columns: Capacity;
    type ComponentsPerTrunk: Capacity;
    type UnitsPerFiber: Capacity;
    type ColumnsPerFiber: Capacity;
    type Cores: Capacity;
}
```

`DefaultPlanDims` is the engine's default budget (each dimension a
`Dim<N>` at the current default size). Plan, thread, and dispatch
structures take one `D: PlanDims` parameter and project
`<D::Units as Capacity>::Array<UnitMeta>` and the like. Because the
dimension is a TYPE and the array length is a literal inside `Dim<N>`,
no `cap_size` expression sits in type position, so `generic_const_exprs`
never runs over capacity arithmetic and the scheduler can thread `D`
through generic code with no overflow. The dimension is the budget; the
live count (how many units exist now) stays a runtime `USize` bounded by
the dimension's `CAP`. `PlanDims` and `DefaultPlanDims` live in the
engine: the api carries no plan dimension and already declares an
unrelated `Capacity` introspection trait, so the bundle and its arvo
`Capacity` bound sit cleanly in the engine. The `Scheduler` gains
`D: PlanDims = DefaultPlanDims` to thread the budget into plan
computation.

The `PlanDims` dimensions size the plan's flat columns: `D::Phases` the
phase array, `D::Trunks` the flat trunk pool, `D::Fibers` the flat fiber
pool, `D::Units` the unit arrays. The live count (how many phases,
trunks, or fibers a plan actually forms) is a runtime `USize` bounded by
each dimension's `CAP`; the dimension is the ceiling, not a worst-case
nested allocation.

## Flat execution plan

The plan-stage output is flat, not a nested tree. A nested const-array
`ExecutionPlan` over `DefaultPlanDims` measured 11 MB, dominated by the
`phases` field: `[Phase; 32]` embedding `[Trunk; 32]` embedding
`[TrunkComponent; 32]` of ~256-byte fibers, the worst-case `32 x 32 x 32`
nesting reserved regardless of how many fibers a real plan forms. Every
leaf of the tree is already a `ColumnValue` arvo scalar (`FiberId`,
`UnitId`, `TrunkId`, `PhaseId`, `USize`, `StoreId`, `Bool`, small repr
enums), so the bulk was array nesting, not non-scalar data.

The phase / trunk / fiber structure flattens CSR-style. `ExecutionPlan`
holds three flat arrays sized by the plan-wide dimensions: `phases`
(`D::Phases`), a flat `trunks` pool (`D::Trunks`), and a flat `fibers`
pool (`D::Fibers`). Each `Phase` carries a `(trunk_offset, trunk_count)`
range into the flat `trunks` pool; each `Trunk` carries a
`(fiber_offset, fiber_count)` range into the flat `fibers` pool; each
`Fiber` carries its units inline. The dense `Phases` x `TrunksPerPhase`
x `ComponentsPerTrunk` nesting (32768 reserved fiber slots at the default
budget) collapses to the `D::Fibers` flat pool (64 slots), so the plan
measures kilobytes, not megabytes, and its footprint tracks the
plan-wide caps rather than the product of the per-aggregate caps.

`compute_execution_plan` runs the step chain into the flat arrays. The
fiber-formation step (`project_fiber_components`) writes the flat
`trunks` and `fibers` pools with running plan-wide ids, and the runner
assigns the per-phase CSR ranges. The step functions keep their analysis
logic; only the assembly target changes, from nested arrays to the flat
pools.

Unifying the plan onto the scheduler's columnar store is the next step
in the unified-storage arc. A follow-on round moves the flat plan
columns into a scheduler-owned columnar store (each column reserved by
live count), turning `ExecutionPlan` into a small handle over those
columns and realizing the heritage design (domain 09: the plan as a
data-plane meta-Resource, not a const-array field). That migration
carries the cross-crate wiring (the scheduler's store parameter, the
Send/Sync lifecycle, the provider-backed arena); see `BACKLOG.md`.

`SchedulerBuilder<Wus, Stores, Platform, StoreValues>` accumulates
typestate across each registration call. Initial state on
`Scheduler::builder()` is `SchedulerBuilder<Empty, Empty, Empty, SvEmpty>`.
The first three parameters are type-level accumulators (the WorkUnit
bundle, the store access set, the platform tuple). The fourth,
`StoreValues`, is a value-carrying cons-list aligned with `Stores`:
`.with` routes each registered value through a `RouterKind` tag on its
dispatch router and a `Place` view, so store carriers (a
`StagedResource<T>`, a `Column<T>`, a `Virtual<T>`) are retained on
`StoreValues` in registration order. WorkUnit values are retained too,
on a parallel WorkUnit-value list (the value-carrying unit cons-list the
run walk consumes): the WorkUnit placement kind prepends each registered
unit instance, so the unit's runtime value (including any `.with`-time
configuration it holds in its fields) survives into the built scheduler.
Platform and run-config values are still dropped (their type stays
tracked in the typestate). The single `.with` verb is unchanged.

`build(storage, record_count)` walks `Stores` and `StoreValues` in
lockstep, reserves a one-record column per `Resource<T>` through the
supplied `ColumnStorage`, writes the staged value into the column, and
records a `ResourcePtr<T>` derived from the column base pointer. It returns an
`Outcome` because reservation can fail. Resource values are
`ColumnValue` (`Copy + 'static`); a zero-sized resource records a
dangling pointer and reserves no column. `Scheduler` gains `Stores` and
`CS: ColumnStorage` parameters and owns the store; the store frees every
resource block on its own `Drop`, so the scheduler runs no resource
destructor and needs no `Drop` of its own. The engine ships a
`NullColumnStorage` as the default `CS` for the bare `Scheduler` type,
so a no-store scheduler needs no concrete store wired. `build` also carries the
retained WorkUnit-value list into the `Scheduler`, which gains a
WorkUnit-value-list parameter alongside its store and provider
parameters. Before draining the store arena, `build` computes the execution
plan from the registered bundle and derives the phase-sequential dispatch
order on the scheduler by flattening the plan's phase structure
(`phases -> trunks -> fibers -> units`); a dependency cycle returns
`BuildError::PlanFailed` without allocating. After draining the resource columns, `build` reserves the plan's
flat CSR pools (phases, trunks, fibers, per-unit metadata, per-fiber morsel
sizes, the RCM renumber) as columns in the same `ColumnStorage`, at a `StoreId`
namespace continued past the resource columns, and keeps a `Copy` `PlanHandle`
(base id plus live counts) so the plan persists in the store for the dispatch
consumer instead of being dropped after `build`. `build` / `build_with`
take the frame record count as the column-reservation dimension: they feed
it to the plan computation in place of the zero placeholder, and the
`Column<T>` drain arm reserves a real column sized by the record count at a
`StoreId` continued past the resource columns, recording the real
`ColumnPtr<T>` and count in the `ColumnBinding` (no longer a dangling
placeholder). The `Accum<T>` drain arm reserves a column the same way
(capacity sized to the record count this round) and records the
`ColumnPtr<T>` plus a `Cell` live-length in the `AccumBinding`; the
live-length starts at zero and a WorkUnit advances it by appending during
the frame, with a later PassEnd drain reading the populated prefix. An
append saturates at the reserved capacity: once the live-length reaches the
capacity the append is dropped, so it never runs past the reserved buffer. `run`
then dispatches the retained units in that topological
order, projecting each unit's `EngineCtx` (resources and columns) from the
bindings and calling `execute` once per morsel as it windows the record
range into morsels of `RunCfg::MORSEL_SIZE`.
Per-fiber column classification and the dirty masks stay off the store for
now (their columnar form and their consumers are later rounds), as do
accumulator columns (records appended during the frame, drained at PassEnd
with the persistence spine) and Kit-contributed units (a Kit hands the
builder unit types, not instances).

The builder takes one verb: `.with(value)`. Every type accepted by
`.with` impls the sealed `Provider` trait declared in
`hilavitkutin-api`. The trait routes per-kind typestate updates
through its `Dispatch` associated type; see the api crate's
`## Provider, the unified registration contract` section.

Example call site:

```rust
Scheduler::builder()
    .with(MyMemory::new(4096))           // platform: memory
    .with(MyThreadPool::new(8))          // platform: threads
    .with(MyClock)                       // platform: clock
    .with(Resource::new(GameState::default())) // store: stateful
    .with(Column::<Player>::new())       // store: zero-data
    .with(Virtual::<Tick>::new())        // store: zero-data
    .with(LinkedBin::<dyn LinterApi>::new()) // store: extension bin
    .with(InternerKit)                   // kit: declarative bundle
    .with(SpawnerWu)                     // workunit
    .with(PhysicsWu)                     // workunit
    .build()
```

Method signature:

```rust
impl<Wus, Stores, Platform> SchedulerBuilder<Wus, Stores, Platform>
where Wus: AccessSet, Stores: AccessSet,
{
 pub fn with<P: Provider>(self, _provider: P) -> SchedulerBuilder<
     <P::Dispatch as Dispatch>::NextWus<Wus>,
     <P::Dispatch as Dispatch>::NextStores<Stores>,
     <P::Dispatch as Dispatch>::NextPlatform<Platform>,
 >;
}

impl<Wus, Stores, Platform> SchedulerBuilder<Wus, Stores, Platform>
where
 Wus: WorkUnitBundle,
 Stores: AccessSet + StoreBundle
 + ContainsAll<Wus::AccumRead>
 + ContainsAll<Wus::AccumWrite>,
{
 pub fn build(self) -> Scheduler<Wus, Stores, Platform>;
}
```

The single `.with` method routes each registration through
`P::Dispatch`. A `WorkUnit` provider (kind `WorkUnit`) carries
`Dispatch = UnitDispatch<Self>`, which prepends `Self` onto the
`Wus` accumulator. A store provider (`Resource<T>`, `Column<T>`,
`Virtual<T>`, `LinkedBin<T>`) carries `Dispatch = StoreDispatch<Self>`,
which prepends onto `Stores`. A `Kit` provider carries `Dispatch
= KitDispatch<Self>`, which concats `K::Units` into `Wus` and
`K::Owned` into `Stores`. A platform provider (memory, thread pool,
clock) carries `Dispatch = PlatformDispatch<Self>`, which prepends
onto the platform tuple. Each kind's GAT is identity for the
accumulators it does not touch. The blanket impl on
`SchedulerBuilder` reads `P::Dispatch` once per call and the trait
solver computes the next typestate via the GAT walks.

Kit registration is type-driven: the Kit instance flows through
`.with(MyKit)` purely so `Self` participates in
`Provider::Dispatch` resolution; the engine reads `K::Units` and
`K::Owned` at compile time. Unit-struct Kits register zero-cost.
Stateful Kits (rare) construct via `.with(MyKit::new(args))` and
the constructor body computes whatever runtime data the Kit needs;
the typestate accumulation is the same.

The v0.1 Kit shape (`pub trait Kit<B> { type Output; fn install(self, B) -> Self::Output }`)
is gone. The new declarative `pub trait Kit { type Units; type Owned }`
shape (in `hilavitkutin-kit`) lets the engine accumulate
without invoking an install method. The v0.1 `BuilderExtending<B>`
sealed trait that bounded `K::Output` is therefore also gone; the
new shape has no `Output` to bound.

`.build()` carries `Wus: WorkUnitBundle, Stores: ContainsAll<Wus::AccumRead> + ContainsAll<Wus::AccumWrite>`
from `hilavitkutin-api`. The accumulator is computed once at the
type level via the recursive `WorkUnitBundle for Cons<W, T>` impl;
the proof unfolds via the recursive `ContainsAll` impl into
per-store `Stores: Contains<Tᵢ>` proofs. With `#[marker]` on both
`Contains` and `ContainsAll`, overlapping resolutions are
permitted; duplicates in `Wus::AccumRead/Write` extend traversal
but do not duplicate proof work.

When a registered WU's `Read` mentions a store that was not
registered, `.build()` fails to compile with a pointed error. For
example, a WU with `type Read = read![Resource<Interner>]` and no
`.with(Resource::new(interner))` or `.with(InternerKit)` triggers
the `Contains` `#[diagnostic::on_unimplemented]` message:

```text
note: store `Empty` does not contain `Resource<Interner>`. Register it with
 `.with(Resource::new(value))`, `.with(Column::<Interner>::new())`,
 `.with(Virtual::<Interner>::new())`, or install a Kit that owns it
 via `.with(MyKit)`.
```

The error names the missing store directly, by type, on the first
inline line of the diagnostic. The verbose accumulator chain
follows but does not bury the marker name. Empirically validated
to depth 5 with 25 WUs and 13 stores; see
`mock/research/sketches/202605050700_deep_stacking_d5/FINDINGS.md`.

The engine declares `#![recursion_limit = "512"]` at its crate
root. This accommodates `.build()` against 50-WU by 50-store apps
without trait-solver overflow. Consumers whose apps exceed this
scale should bump the limit at their own crate root; see the
`hilavitkutin-api` "Recursion limit" subsection.

Static composition (R6): all WUs registered at compile time. No
runtime registration. Plan parameters adapt; composition does not.

Kit composition: see `hilavitkutin-kit/DESIGN.md`. A Kit is a
declarative bundle: `type Units` (cons-list of WorkUnits) plus
`type Owned` (cons-list of stores). Kits chain freely with each
other and with raw builder calls; each `.with(MyKit)` (or
`.with(MyKit::new(args))` for stateful kits) accumulates `K::Units`
into the bundle and `K::Owned` into the stores via `KitDispatch<K>`
typestate routing. Order matters for the `ContainsAll` proof at
`.build()`: a Kit whose WUs read from another Kit's Owned state
must come after the owning Kit in the builder chain (or after the
relevant `.with(Resource::new(value))` / `.with(Column::<T>::new())`
calls).

### `Scheduler::replace_resource`

```rust
impl<Wus, Stores> Scheduler<Wus, Stores> {
 pub fn replace_resource<T: Replaceable>(&mut self, _new: T)
 where
 Stores: Contains<Resource<T>>;
}
```

App-level method to swap the existing `Resource<T>` instance in
the scheduler's data plane. The static `T: Replaceable` bound
rejects override attempts on types that did not opt in via
`impl Replaceable for T {}`. The `Stores: Contains<Resource<T>>`
bound proves the resource exists in the registered stores.

Replaceable opt-in is the only enforced annotation on
Owned types (per audit C2/M4 plus the S5 visibility-axis
finding); see `hilavitkutin-api::Replaceable` and
the design notes.

When a consumer attempts `scheduler.replace_resource(NotReplaceable)`,
rustc emits an E0277 with a high-quality diagnostic that names
the offending type, lists the types that DO impl `Replaceable`,
and points at the bound declaration. See
`mock/research/sketches/202605050615_kit_taxonomy/FINDINGS.md`
for the empirical evidence.

`replace_resource` is app-only. Called between `.build()` and
`scheduler.run()`. Not a hot-path operation; the typestate change
is logical only (the `Resource<T>` slot's value is replaced; its
type-level identity in `Stores` is unchanged).

Self-hosting meta pipeline: PlanStage → ScheduleReady → PassStart →
ScheduleEnd. Meta resources: Dag, ExecutionPlan, LaneAssignment,
SchedulerMetrics. Irreducible kernel ~50 lines.

Version stamps: parallel arrays (SoA), capture-before + compare-after.
Changed stores = bitmask. Increment only on completion.

Error handling (R7): execute() → (). Abort on failure. Errors via
data flow (error columns/virtuals). Fiber failure → freeze progress
→ poison dependents → independent fibers continue. PipelineResult:
per-fiber status (Completed / Failed / Poisoned).

R2 APIs: evict/dump + inject/import for column persistence.
hilavitkutin owns generation counters; consumer owns storage.

## Platform implementations (domain 02)

os tier (default): raw mmap/munmap for MemoryProvider, raw
pthread_create/clone for ThreadPool, clock_gettime for Clock. Direct
syscalls, no libc where possible.

std tier (fallback): std::alloc, std::thread, std::time::Instant.
catch_unwind available but abort preferred (R7).

no_os tier: trait contracts only. Consumer provides all impls.
