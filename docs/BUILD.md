# hilavitkutin-build, Design

Shared build-dependency crate. Every hilavitkutin crate but this one,
and every consumer crate that builds through it, writes
`hilavitkutin_build::script!` in its build script. Independent of
the hilavitkutin runtime, it optimises how code is compiled, not what
it does. A build-dependency only, it never links into a binary.

## Entry point

```rust
// a consumer's build script, at whatever path the consumer keeps it:
fn main() {
    hilavitkutin_build::script!(Default);
}
```

`script!` is the whole of a script that only configures, and one line
of a script that does more. It expands, in the script's own std
context, to two things: the named prototype's directives, written
straight to standard output with no text kept in memory, and the
wiring the next section states. The directives are the ones the call
below prints, less its warning, since `script!` looks at the wiring
before it says anything:

```rust
let mut out = String::new();
hilavitkutin_build::configure(|key| std::env::var(key).ok().into(), &mut out)
    .expect("a String takes every write");
print!("{out}");
```

That call is also what a script written by hand uses, and it does
nothing about the wiring. It takes the `Default` prototype. A crate
with pragmas of its own calls `configure_as::<P, _, _>` the same way,
with a `Prototype` it names. A crate whose own code must not take fast
float math names `Deterministic`, whose sets hold no `FastMath`, which
keeps the `arvo_fast_math` cfg off for that crate. kaski's
deterministic simulation crates do this. The cfg reaches the
configured crate alone: arvo's `Float` is resolved in arvo's own
build, which no consumer's build script reaches, and takes fast float
math only from a build that passes `--cfg arvo_fast_math` to every
crate. That is the binary builder's choice, and a deterministic
simulation never makes it.

The crate is `no_std` and does not allocate, like every hilavitkutin
crate, so it touches neither the environment nor the filesystem. The
build script owns both: it passes a closure that reads one variable,
and the crate reads `PROFILE`, the `CARGO_CFG_TARGET_*` values and
`RUSTC_WORKSPACE_WRAPPER` through it, resolves the `BuildConfig`, and writes the `cargo::` directives
into the `core::fmt::Write` the script supplies, which the script
prints. `BuildConfig::from_env`, which reads through the closure,
`BuildConfig::from_cargo`, which takes the values already read,
`write_directives` and `write_wrapper` are the parts `configure`
composes, public for a script that needs one alone. `write_directives`
is generic over the set it writes and takes the set's `Site`, and
`Profile::name` is the profile as cargo spells it.
Does NOT do live CPUID/sysctl detection, hardware topology
(L1 sizes, core counts, P/E ratio) is a runtime concern of
hilavitkutin's thread module, whose `classify_cores` reads it through
the platform's own interfaces without std.

## Prototypes and the wiring a workspace takes

A build script is its project's. A consumer keeps one per crate, or
one file that several crates name with `package.build`, or anything
else cargo takes, at whatever path it chooses, and this crate asks
nothing about where. What the crate gives is the body. A `Prototype`
is a type that names one set of pragmas per profile, as its associated
types `Dev`, `DevOpt`, `Release`, `Profiling` and `Ci`, and
`script!(<prototype>)` is the one line that runs the chosen one. The
crate's own are three unit types: `Default`, `Deterministic`, which is
`Default` with no `FastMath`, and `Workspace`, which is `Default` with
the pragmas that reach the whole workspace, for the one script that
claims it (the section on reach below). `script!(Default)` names one
of the three by its bare name. A consumer writes a prototype of its
own in a crate among its build-dependencies and names it by its path,
`script!(my_build::Sim)`, or writes it in the script's own file and
names it `script!(crate::Sim)`: a bare name is always one of this
crate's. A script that does more than configure
writes that line and goes on with its own work. Nothing a prototype
does is written out in a consumer, so there is nothing in a consumer
to drift.

The expansion holds one `const` item per profile's set that asserts
over the set, so a set that breaks a requirement is refused by a check
at the script's line, before any script runs.

Taking the crate is two lines the consumer writes: the workspace's
dependency on `hilavitkutin-build`, spelled over ssh while hilavitkutin
is private (git over https waits for a credential nobody gives), and
the `[build-dependencies]` line of each crate that builds through it.
Everything after that follows from the first build with nothing done
by hand. Each time the script runs, `script!` asks cargo for the
workspace root (`cargo locate-project --workspace`, from
`CARGO_MANIFEST_DIR`) and keeps the wiring there: the wrapper at
`.cargo/hilavitkutin-rustc-wrapper` with the text of `write_wrapper`
and its executable bit, and the `build.rustc-workspace-wrapper` line in
`.cargo/config.toml`. A wrapper whose text differs from `write_wrapper`
is written again, also in a workspace long since wired, so a consumer
keeps no test of its copy. A `config.toml` that exists without the line
is left as it is, and the script's warning names the line to add.

Three roots are not this build's to write into, and nothing is written
there and nothing said. A root under `CARGO_HOME` is a checkout cargo
fetched for a dependency. A root that holds `Cargo.toml.orig` is a
crate cargo unpacked, which is what `cargo package` builds when it
verifies, and that build fails when a script adds a file to it. The
third is a root other than the one cargo's wrapper sits in: where
`RUSTC_WORKSPACE_WRAPPER` names a `hilavitkutin-rustc-wrapper` outside
the root's `.cargo/`, the workspace is wired from somewhere else, a
`config.toml` in a directory above it, and a second copy inside it
would serve nothing. A wrapper is named by its file name, here and in
a `config.toml`: a path that only ends with the same letters is
somebody else's.

A host that is not unix is written nothing either. The wrapper is a
POSIX `sh` script, and a `config.toml` naming one on a host that cannot
run it stops every build after the first. There the script says, where
the crate has flags, that they are dropped on this host, and the
consumer builds as it would without this crate.

One root that is not this build's cannot be told apart, and is written
into. A path dependency that is a member of another workspace has that
workspace as its root, and cargo names no workspace wrapper to the
script of a crate outside the workspace it was run in, wired or not.
The script sees exactly what the first build of the dependency's own
workspace would show it, and wires that workspace. That is the
consumer's own tree, never a fetched one, and the files are the ones
its own first build would write. A workspace wrapper reaches the
members of the workspace cargo was run in and nobody else, so the
dependency takes no flags from the outer build, and its script says so
with the warning for dropped flags whenever it runs.

Cargo reads its configuration when it starts, so the build that writes
the wiring runs without the wrapper. The script that writes the config
file says so in one `cargo::warning`. In a workspace of several members
the scripts run side by side, one of them writes the file and each of
the others finds it there with no wrapper named, which is also what a
script sees when cargo is started outside the workspace. Those say that
cargo was started without the wrapper and the flags of this build are
dropped, in words that hold for both. Two scripts that find nothing at
the same moment both write, each to a file of its own that is then
moved into place, so neither reads half of the other's and the config
file is never one a script wrote over.
`RUSTC_WORKSPACE_WRAPPER` decides only what is said: nothing where it
names the wrapper or `clippy-driver`, and that the flags are dropped
where the wiring is in place and cargo names nothing or something else.
A build of the workspace after that one runs through the wrapper, which
changes how cargo names every member's artifacts, so the members and
their scripts are built again and take the flags.

The script asks to be rerun when either file of the wiring changes
(`cargo::rerun-if-changed` on both paths, which it knows once it has
the root), and when `RUSTC_WORKSPACE_WRAPPER` changes in cargo's own
environment. A wrapper edited by hand or left behind by an older
version of the crate is therefore written again by the next build, and
a `config.toml` that gains the line stops the warning. The script
cannot help where the wrapper is deleted, or loses its executable bit,
in a workspace whose `config.toml` names it: cargo runs the wrapper
before any script and stops there. Both files are committed, so the
writing happens once per workspace and a fresh clone has them.

The crate stays `no_std`: which file holds what text, and when it is
written, is decided by functions of this crate that write into a
`core::fmt::Write`. The reads, the writes and the question to cargo
are the script's, in the code `script!` expands there.

That code reaches the crate through public items, since a macro's
expansion sees only what a consumer could name. `Tree` is whose the
root is and whether the host runs the wrapper, decided by `Tree::of`
from what the script found, each finding a type of its own so two
cannot be swapped: `Unpacked`, `Placed` and `Host`, and `Flags` for
whether the crate has flags to hand over.
`WrapperFile` and `ConfigFile` are what the script found on disk, the
second read from a config file's text by `ConfigFile::read`. `plan`
takes those and answers a `Plan`: whether each file is written, and
the `Notice` to print. `write_cargo_config`, `write_notice` and
`write_watch` are the texts of the config file, of a notice and of the
two rerun lines, and `WRAPPER_NAME` is the wrapper's file name. They
are public for the macro and for a script that wants the same wiring
with its own pragmas, and every one of them is a function of what the
script hands it, with nothing of the host in it.

A script that writes a `cargo::rerun-if-` line gives up cargo's own
rule of running it again whenever a file of the package changes, and
`script!` writes three. A script that does more than configure, and
reads files of its own, names those files itself.

## Four-part build configuration model (T4 §Q1)

**1. hilavitkutin-build (this crate):** reads the cargo env values
through the build script's closure, and writes the cfg flags and the
crate's rustc flags as directives for the script to print. Runs in
every crate's build.rs. It chooses the LLVM codegen flags; the wrapper
applies them.

**2. No custom cargo features (T4 §Q2):** the compiler already
provides everything needed. ISA capabilities via `target_feature`.
Vendor identity via `CARGO_CFG_TARGET_VENDOR`. Architecture via
`CARGO_CFG_TARGET_ARCH`. Cache/topology is runtime detection.
`compile_error!` guards for any future mutually exclusive feature
groups.

**3. RUSTC_WORKSPACE_WRAPPER:** the mechanism that puts the LLVM
flags on the command line. The flags of a crate follow from the set
its prototype names for the profile cargo passes the script as
PROFILE: each pragma of the set writes its own, and `configure` writes
them as
`cargo::rustc-env=HILAVITKUTIN_BUILD_RUSTFLAGS=<flags>`. Cargo sets a
`rustc-env` variable on the rustc process of that crate alone. The
wrapper is a fixed POSIX shell script that appends the variable to
rustc's arguments:

```sh
#!/bin/sh
# Written by hilavitkutin-build: appends the flags a crate's build script chose for it.
set -f
exec "$@" $HILAVITKUTIN_BUILD_RUSTFLAGS
```

`set -f` keeps a flag from being expanded as a pattern against the
directory rustc runs in.

Where the variable is unset (a build script's own compilation, cargo's
`rustc -vV`, a crate with no build script) the wrapper is rustc
unchanged. Cargo runs the wrapper before the first build script, so
the build that writes it cannot use it: `script!` writes it at the
workspace's `.cargo/hilavitkutin-rustc-wrapper`, executable, with the
text `write_wrapper` owns, and the builds after that one run through
it. It is plain `sh` because
cargo runs it for every rustc call before anything else is built, so
it needs a host with a POSIX `sh`; Windows waits on the backlog entry.

The same call writes the workspace's `.cargo/config.toml` where there
is none, a path with a slash being relative to the directory holding
`.cargo`:
```toml
include = [{ path = "hilavitkutin-build.toml", optional = true }]

[build]
rustc-workspace-wrapper = ".cargo/hilavitkutin-rustc-wrapper"
```

The first line takes the generated file of the section on reach, and
is no error where that file is not there.

Only affects workspace crates, not dependencies, and of those only the
crates whose build script builds through this crate. Cargo finds
`.cargo/config.toml` from the directory it runs in, not from the
manifest, and walks up from it, so the one at the repository root
reaches cargo run anywhere in the repository. Where a
crate has flags to hand over and cargo names no wrapper, or one whose
file name is not `hilavitkutin-rustc-wrapper` (a compile cache set as
the workspace wrapper), a `cargo::warning` says the flags are dropped:
`configure` writes it for a script written by hand, and `script!`
prints it once it has seen that the wiring is in place. Under
`cargo clippy` cargo names `clippy-driver`, and nothing is said: a
check generates no code, so the flags it does not get cost it nothing.

**4. Generated config file:** pragmas that are cargo configuration
write to `.cargo/hilavitkutin-build.toml`, which the workspace's
`config.toml` takes by one `include` line. The section on reach says
which script writes it.

## cfg flag emission

hilavitkutin-build emits NO custom cfg flags for hardware detection.
The compiler provides `target_feature` and `CARGO_CFG_TARGET_FEATURE`
natively. arvo detects hardware capabilities in its own build.rs
via `CARGO_CFG_TARGET_FEATURE`, not custom flags from this crate.

The only cfg this crate emits:
- `arvo_fast_math`, when the FastMath pragma is active, with its
 `cargo::rustc-check-cfg` declaration. Code in the configured crate
 gates its own fast-math float operations on it. It reaches no other
 crate, arvo included.

Beside it the script asks cargo to rerun it only when
`RUSTC_WORKSPACE_WRAPPER` changes, `cargo::rerun-if-env-changed`. That
is the one input it reads which can change between two builds of one
profile and target. It names no file, since a script naming a file the
crate does not have is rerun on every build.

## Pragma system (T4 §Q4f)

A pragma is one build choice, a unit type, and a set of them is a
tuple of types. What a pragma requires of the set it is in is checked
before any build script runs.

```rust
pub trait Pragma {
    const NAME: &'static str;
    const BIT: u64;
    const REACH: Reach = Reach::Crate;
    const UNMET: &'static str = "";
    const NEEDS: &'static [&'static Tool] = &[];
    type Group: Group;
    type Requires: Requirement;
    fn admitted(target: &Target) -> Maybe<&'static str> { Maybe::Isnt }
    fn write_rustflags<W: Write>(with: &Written, out: &mut W) -> fmt::Result { Ok(()) }
    fn write_cfgs<W: Write>(out: &mut W) -> fmt::Result { Ok(()) }
    fn write_cargo_config<W: Write>(with: &Written, out: &mut W) -> fmt::Result { Ok(()) }
}
```

`NAME` is the pragma's name in every sentence said about it. `BIT` is
its place in a set's mask, given by the crate in one list, and a test
holds every two of them apart. `REACH` is the next section's. `UNMET`
is the sentence for a set that does not meet `Requires`. `NEEDS` is the
rows of the tools table the pragma waits on, every program its text
names, and the first is the one whose path its writer is handed.
`admitted` answers with
the sentence of a refusal where the target cannot carry the pragma.
The three writers are the routes a pragma's text takes: a flag the
wrapper appends, a cfg, and lines of the generated cargo file. A
linker's argument is a flag like any other, `-Clink-arg=`, and goes
through the wrapper; the script prints no `cargo::rustc-link-arg`.
`Written` is what a writer is handed: the profile's name as cargo has
it, the target triple, the path of the pragma's tool where it has
one, and a `Shared` that says whether the keys its group shares across
profiles are still owed or already written. No function returns a
collection; the crate does not allocate.

Each route has one form of text, so a set's text is its members' texts
one after another. A pragma's rustc flags are separated by single
spaces with none before the first or after the last, and the set puts
one space between two pragmas that wrote any. Cfgs are one to a
line. Cargo configuration is whole lines in dotted keys
with no table header, `profile.release.lto = "fat"`, since two pragmas
write keys of one table and TOML takes a header once.

A `Requirement` is read as three masks, `ALL`, `ANY` and `NONE`.
`All<(A, B)>` asks that every one of the list is in the set,
`Any<(A, B)>` that at least one is, `Not<(A, B)>` that none is, and
`()` asks nothing. A `Group` is a choice a set holds one value of at
most, a type with a `BIT` and with `CLASH`, the sentence for a set
that holds two of it; `Free` is the group of a pragma that is one
value of no choice. A group whose keys belong to no profile, the link
driver's and the C compiler's, says so in `SHARED`.

`Set` is implemented for the flat tuples of pragmas, arities zero
through sixteen. It folds its members into constants: `MASK`, every
member's bit, `GROUPS`, every member's group, `SHARED`, the bits of the
members whose group is shared, `REACH`, the widest reach among them,
and `VERDICT`, the first thing wrong with the set (a pragma named
twice, a group held twice, a requirement unmet) as that pragma's or
group's own sentence, or the empty string. A mask is a `Mask` and a
name or a sentence is `Words`, the two aliases the constants are
written in. `checked::<S>()` is a `const fn` that panics with the
verdict where there is one, and `crate_reach::<S>()` one that panics
where the set holds a pragma of workspace reach. `script!` calls both
in a `const` item per profile, which a check evaluates, so the refusal
arrives at the line that names the set. `Set` also walks its members:
`Set::each` hands every member, as a type, to a `Visit`, and the four
writers, `admitted` and the tools are each one visit. What a walk is
handed is a `Site`: the profile, the target triple and the tools the
script found, each a `ToolPath` of a tool and where it is, from which
the walk makes every member its `Written`. `each_tool` is the walk
that hands over every member's tool, and `writes_flags` asks a set at
its site whether any member writes a flag, which is what the wiring's
notices turn on. `write_set_config` is the walk that writes the cargo
configuration of every member of one set at one site.

`PragmaSet` is the folded value of a set, the mask a `BuildConfig`
carries, built by `PragmaSet::of::<S>()` and read by `contains::<P>()`.
Nothing changes one: a set is changed by naming another type.

## Reach

A pragma reaches one of two things. `Reach::Crate` is the crate whose
script names the set: the flags the wrapper appends to that crate's
rustc, the linker's among them, and its cfg.
`Reach::Workspace` is cargo configuration, which cargo reads before
any script runs and applies to every crate it builds, the
dependencies and the build scripts among them. No one crate's set can
hold such a choice for the others, so the workspace's pragmas are
named once, by the one script of the workspace written
`script!(<prototype>, workspace)`. Every other script asserts
`crate_reach` over its sets, and naming a pragma of workspace reach
there does not compile.

The script that claims the workspace writes the generated cargo file,
`.cargo/hilavitkutin-build.toml`, beside the wrapper and with the same
care: under a name of its own first, and never into one of the roots
the wiring leaves alone. Where there was no file it is placed by a
hard link, which refuses where a file is already there, so of two
scripts that both found none one places its file and the other reads
whose it is. Where the file is this crate's and holds another text it
is moved into place. `write_generated`
writes its text: a first line that names the crate it was written for,
then every key the workspace's pragmas write, for the `dev` and the
`release` profile, each set's through `write_set_config`. A caller
that builds without the generated file, a bench of the build itself,
hands the same lines to cargo one by one as `--config`, since a dotted
key with its value is the form that option takes. A key that belongs to no profile is in the file
once: the pragma that writes it is told through its `Shared` when a
profile before this one has written it, and one key twice is a file
cargo cannot read, which stops every build before any script runs. So
the sets of a prototype that claims the workspace hold the same pragma
of a shared group in every profile, and `claimed::<P>()`, the `const
fn` the claiming script's `const` item calls, refuses a prototype
whose sets differ there. A script that finds the file holding another text
for its own crate writes it again. A script that claims the workspace
and finds the file written for another crate writes nothing and fails
the build with a `cargo::error` that names both crates, since two
crates claiming one workspace is a mistake only its author can
resolve; `Claim` is what the script found (no file, its own, another
crate's by name) and `claim` reads it from the file's first line.
`Notice` has the two things said about this file: that it was written
and the next build takes its keys, and that `config.toml` lacks the
`include` line, which `includes_generated` reads from its text.

The claiming script asks to be run again when the generated file
changes, so one edited by hand is written again by the next build.

A key in the file is read by cargo before any script runs, so the file
is written only where the build can carry every key in it. Before it
writes, the claiming script looks at every pragma of workspace reach
in the `dev` and the `release` set, whichever profile is being built:
the target has to admit it and the machine has to have every tool it
needs.
`write_uncarried` writes one `cargo::error` for each that fails, with
the profile it is in, and where it wrote any the file is left as it
was and the build fails. A file written while a tool was there, whose
tool has since gone, is beyond the script: cargo hands the key to a
rustc that cannot follow it before the script is built.

The key of a link driver is `target.<triple>.linker`, for the target
of the build that wrote the file. A build for another target writes
the file again for that one, so a workspace built for two targets in
turn has the file written at every turn, and the build that wrote it
is, as ever, not the one that takes it.

Cargo takes the file by the `include` line of `config.toml`, which is
the constant `INCLUDE_LINE`.
`write_cargo_config` writes that line with the wrapper's, so a
workspace the first build wires has both. A `config.toml` that exists
without the line is left as it is, and the notice names the line to
add, as with the wrapper's. The build that writes the generated file
runs before cargo has read it, and the next one takes its keys, which
the script says in one `cargo::warning`.

The three custom profiles get no table: cargo tells a script only
`debug` or `release`, and a table for a profile the consumer's
manifest does not define is an error.

One thing is not checked. A requirement holds within one set, so
between a pragma of one script and a pragma of another nothing is
enforced: `DylibDomain` in one crate and an LTO pragma in the
workspace's set are each accepted, though LTO does not cross a dylib
edge.

## The target and what it admits

`Target` is the target's facts as the crate reads them from
`CARGO_CFG_TARGET_OS`, `CARGO_CFG_TARGET_ENV`, `CARGO_CFG_TARGET_ARCH`
and `CARGO_CFG_TARGET_FEATURE` through the script's closure: an `Os`,
an `Env`, an `Arch`, the `ObjectFormat` that follows from the three,
and an `Isa`, the widest instruction set among the features. Each is
an enum with `Other` for a value the crate has no name for, and
`Target::from_cargo` reads them. `BuildConfig` carries the `Target`.
The enum of the target's environment is named in full, `target::Env`,
since the crate's root has the closure's trait under that name.

What a target admits is a requirement like the ones between pragmas,
known only when the script runs. `Mold`, `Wild` and `Bfd` admit an ELF
target only. `Cranelift` and `DylibDomain` do not admit wasm. Where
`admitted` answers with a sentence, `configure` writes
`cargo::error=` with the pragma's name, that sentence and the remedy,
and the build fails. Nothing falls back to another value in silence.
The same line is written for a pragma that needs a local build and
whose `Site` holds no path for it, which is what a script written by
hand gets where it names such a pragma: only `script!` provisions.

`Bolt`, which is ELF only, is not held to this: it is in the release
set of every prototype and writes nothing yet, and refusing it would
fail every release build on macOS. It says so when it gains a hook.

## Tools

A pragma that needs something the toolchain does not bring names it in
`NEEDS`, rows of `TOOLS`, one for every program its text names: a
machine that has one and lacks another is refused by the crate, with
the command that brings the missing one, and not by rustc or by a
build script further on. `Wild` needs wild and clang. `GccCc` needs
gcc, g++ and ar, and `ClangCc` clang, clang++ and llvm-ar, the three
programs each puts under `[env]`. Every other pragma needs one tool or
none. A `Tool` has a name, a pinned version, a
`Source` and a `Proof`. A `Proof` is a `Line`, what the tool's version
line has to start with or hold, or that the tool is found in the
toolchain's sysroot, and for a linker the mark it leaves in `.comment`.
The version line is the first two lines a tool prints when asked for
its version, joined by a space: an llvm-ar built with no vendor name
prints `LLVM (http://llvm.org/):` first and its version on the second.

| Tool | Version | Source | Proof |
|---|---|---|---|
| mold | any the package gives | `Source::Package("mold")` | version line starts `mold `, mark `mold ` in `.comment` |
| wild | 0.10.0 | `Source::LocalBuild("wild-linker")` | version line starts `Wild 0.10.0`, mark `Linker: Wild` in `.comment` |
| clang | any the package gives | `Source::Package("clang")` | version line holds `clang version` |
| gcc | any the package gives | `Source::Package("gcc")` | version line starts `gcc ` |
| clang++ | any the package gives | `Source::Package("clang")` | version line holds `clang version` |
| llvm-ar | any the package gives | `Source::Package("llvm")` | version line holds `LLVM version` |
| g++ | any the package gives | `Source::Package("g++")` | version line starts `g++ ` |
| ar | any the package gives | `Source::Package("binutils")` | version line starts `GNU ar ` |
| cranelift | the toolchain's | `Source::Component("rustc-codegen-cranelift-preview")` | the component is in the sysroot |
| the plugins and profile tools of the thirteen older pragmas | none | `Source::Awaited` | none |

A package is taken from a trusted package manager and a local build is
kept for what none carries. wild's pin moves to 0.11.0 when the
toolchain pin reaches a rustc it builds on. A pragma whose tool is
`Source::Awaited` writes what it can without it and is not refused,
which is what those pragmas do today.

`tools_home` decides where locally built tools live, and answers a
`Home` or nothing:
`HILAVITKUTIN_BUILD_TOOLS_HOME` where the builder sets it, else the
per-user cache, `$XDG_CACHE_HOME/hilavitkutin-build/tools`, else
`$HOME/.cache/hilavitkutin-build/tools`, and on macOS
`$HOME/Library/Caches/hilavitkutin-build/tools`. `write_tool_dir`
writes the directory of one tool under it,
`<home>/<host triple>/<name>-<version>`, so a home is shared by every
clone and worktree on the machine and survives `cargo clean`.

`provision` answers what a script does about one tool, from what the
script found, as a `Provision`: use the one on the path, where its
version line passes the proof; use the one in the home; build it into
the home; or refuse, with the command that brings it. Only a local
build is built. A package and a component are refused where they are
missing, `apt-get install mold` and
`rustup component add rustc-codegen-cranelift-preview` being a
machine's setup and outside what a build script may do.

The `script!` expansion does the work on disk. It provisions the tools
of every pragma in the set it runs, in a crate's script and in the
workspace's alike. Where the answer is to build, it prints a
`cargo::warning` that the tool is being built, runs
`cargo install --locked --version <pin> --root <dir> <crate>`, and
then removes every `<name>-<version>` directory beside the new one
whose version `older` says is below the pin, so a pin that moved up
leaves no old version behind. A newer version beside it is another
clone's pin and stays. So does an older one whose lock the script
cannot take at once: a clone that pins it is building it now. Nothing
of it is done by hand. The build that
needs a tool waits for it once per machine. Scripts of one workspace
run side by side, so the one that builds holds a lock on a file beside
the tool's directory, `<name>-<version>.lock`, and the others wait for
the lock and then find the tool built. The lock is the operating
system's and goes with the process that holds it, so a build that is
interrupted leaves nothing to clear. The lock files themselves stay,
those of removed versions too: a script that removed one could take it
from under a script waiting on it, and each is an empty file. The child cargo is given a target directory of its own under
the tool's, and none of the outer build's wrapper or flags. Where the
answer is to refuse, the script prints the text of `write_refusal` as
a `cargo::error`.

## The linker of a set

A set is linked by one linker, and the crate answers which.
`linker_of::<S>()` answers a `Linker`: `Linker::Toolchain` where the
set holds no pragma of `LinkerGroup`, else `Linker::Named` with the
pragma's name and the mark its tool leaves in `.comment`, the `mark`
of the first row of its `NEEDS`, which is nothing for `Bfd`: GNU ld
leaves none. `linker_named` answers the same from a name, `toolchain`
or a pragma's name, and nothing for any other. It is for a reader that
has a recorded name and no type. `Linker::name` is the name
`linker_named` takes back.

`Linker::leaves` says whether a mark read from an executable is that
linker's. A named linker with a mark leaves a text that starts with
it. A named linker with none leaves nothing. The toolchain's own
leaves exactly the mark the caller worked out for it and hands in.

The toolchain's own linker differs by target, and rustc says which in
its description of the target, the text `--print target-spec-json`
prints. `ToolchainLinker::of` reads that text:
`ToolchainLinker::RustLld` where the linker flavor is an lld one and
`link-self-contained` names the linker, else `ToolchainLinker::Other`
with the flavor as the text has it. The crate reads the two fields it
needs by searching the text and parses no JSON. `rust_lld_mark` takes
the first line `rust-lld` printed for `--version` and answers a
`RustLldMark`, which displays as `Linker: ` and the version with the
LLVM commit it was built from, or nothing where the line is not
lld's. For any other toolchain linker the crate has no mark, and a
caller that needs one refuses.

The running of rustc and of `rust-lld` stays the caller's, as every
looking does.

## LLVM pass plugin (T4 §Q4c)

A ~40-line C++ file compiled against LLVM headers. Registers passes
at two extension points in the LLVM pipeline:

**VectorizerStartEP (before vectorizer):**
1. IRCE, bounds check elimination
2. LoopPredication, guard hoisting
3. SimplifyCFG, dead branch cleanup after IRCE/Predication
4. LoopInterchange, fix nested loop order for sequential access
5. LoopDistribute, break dependent loops for partial vectorization

**OptimizerLastEP (after vectorizer):**
6. LoopDataPrefetch, prefetch the vectorized access pattern
7. SeparateConstOffsetFromGEP, CSE of column base pointers
8. LoopFusion, fuse adjacent loops (conditional: only when
 LoopFusion pragma is active)

The IR cleanup pipeline (passes 1-3) runs BEFORE Polly to make Rust
IR Polly-friendly (remove bounds checks, panic branches, dead code).
Callback registration order at VectorizerStartEP determines execution
order, cleanup callbacks register before Polly's callbacks.

**Platform constraint:** `-Z llvm-plugins` only works on Linux
(dynamic LLVM). macOS/Windows ship static LLVM, no plugin loading.
Dev builds on macOS use `-C passes=` and `-C llvm-args=` (built-in
passes, no plugin). Release builds use the container workflow.

## Flag ownership by pragma

Every flag has exactly one owner pragma:

Of these, the flags a pragma writes today are the ones whose mechanism
the pinned toolchain carries and the build script needs nothing else
for. The rest wait on a tool or a profile the build script does not
yet find, and their pragmas write nothing meanwhile:

| Pragma | Writes today | Waits on |
|---|---|---|
| `LoopOptimization` | the five `-C llvm-args` flags below, which need no plugin | `polka-passes.so` for its plugin passes, the awaited row of `TOOLS` its `NEEDS` names |
| `FastMath` | the `arvo_fast_math` cfg | nothing |
| `ParallelCodegen<N>` | `-Zthreads=N` | nothing |
| `SharedGenerics` | `-Zshare-generics=y` | nothing |
| `MathPeephole`, `Polly` | nothing | their plugins |
| `Pgo`, `Bolt`, `Profiling` | nothing | merged profiles, `llvm-bolt` |
| `ExpandedLto` | its profile keys, in the generated cargo file of the script that claims the workspace | nothing |
| `BuildStd` | nothing | the consumer's Cargo profile |
| `ChecksumFreshness` | its one key, in the generated cargo file or as a `--config` line | nothing |

**LoopOptimization:**
- `-Z llvm-plugins=<path>/polka-passes.so` (once found)
- `-C llvm-args=-enable-loop-distribute`
- `-C llvm-args=-enable-loop-versioning-licm`
- `-C llvm-args=-enable-interleaved-mem-accesses`
- `-C llvm-args=-loop-prefetch-writes`
- `-C llvm-args=-enable-histogram-loop-vectorization`

**MathPeephole:**
- `-Z llvm-plugins=<path>/math-peephole.so`

**FastMath:**
- `--cfg arvo_fast_math`, as a `cargo::rustc-cfg` directive

LLVM no longer has a global unsafe-fp-math option (the pinned rustc
refuses `-enable-unsafe-fp-math` as an unknown argument). Fast float
math is chosen per operation, and the cfg is what selects it, in the
configured crate's own code. arvo's `Float` takes it only from a
whole-build `--cfg arvo_fast_math`; whether a crate should choose it
for arvo per crate is the ticket
`arvo_should_a_crate_choose_fast_float_math_per_crate`.

**Polly:**
- `-Z llvm-plugins=<path>/libPolly.so` (or `-C llvm-args=--polly`)

**ExpandedLto:**
- `lto = "fat"` (in generated config)
- `codegen-units = 1` (in generated config)

**Pgo (when profiles exist):**
- `-C profile-use=<path>/merged.profdata`
- `-C llvm-args=-loop-vectorize-with-block-frequency`
- `-C llvm-args=-split-machine-functions`
- `-C llvm-args=-profile-guided-section-prefix`

**ParallelCodegen<N>:**
- `-Zthreads=N`

**SharedGenerics:**
- `-Zshare-generics=y`

No flag is always on. A native target CPU makes a binary that runs
only on the machine that built it, so it is no default.

Cargo profile settings (`panic = "abort"`, `strip`, `opt-level`)
remain in the consumer's Cargo.toml. NOT pragma-controlled.

The variable's name is a `const` string, `RUSTFLAGS_VAR`.
`no-bare-static-str` keeps such text out of release binaries; this
crate is only ever a build-dependency and reaches none, so it carries a
`lint:allow` naming the ticket
`no_bare_static_str_does_not_know_a_build_dependency_only_cra` until
the lint knows a build-dependency-only crate. The wrapper's text is
written with `write!` and is no `const`, and the five option names are
a `[&str; 5]`, which the lint does not read.

## PGO + BOLT workflows (T4 §Q5)

**Release build 1 (no profiles):**
1. Cargo builds → binary produced
2. Post-build hook: static BOLT runs immediately (seconds, Linux ELF,
 reorders blocks/functions with static heuristics, 3-5% gain)
3. Background: runs benchmarks with PGO instrumentation + perf record.
 Generates `.profraw` + `perf.data`. Merges profiles.

**Release build 2+ (profiles exist):**
1. The build script finds `merged.profdata` and tells `configure()`
 it is present → `configure()` adds `-C profile-use=...` and
 PGO-complementary flags to the generated config text
2. Cargo recompiles with PGO (10-20% branch/inline improvement)
3. Post-build hook: profile-guided BOLT (additional 5-10%)
4. Background: re-profiles with optimised binary

**Profile staleness:**
- Profiles in `target/hilavitkutin-build/pgo/` (gitignored)
- `cargo clean` deletes them
- The commit hash is recorded when profiles are generated; the build
 script reads it and HEAD's distance from it and passes the distance
 to `configure()`
- If HEAD diverges >50 commits, `configure()` writes
 `cargo:warning=stale profiles` among its directives
- Never refuses to build; stale profiles degrade gracefully

**Optimisation tiers (additive, automatic):**

| Tier | What | Benefit |
|---|---|---|
| Stock | nothing extra | baseline |
| Plugins | LLVM pass plugins via wrapper | loop optimization |
| Static BOLT | post-build reorder (Linux ELF) | 3-5% layout |
| PGO | profile-use from benchmarks | 10-20% branch/inline |
| Profile-guided BOLT | BOLT with profiling data | additional 5-10% |
| Machine function split | compile-time flag (all targets) | partial BOLT for macOS |

BOLT is Linux ELF only (no Mach-O). macOS gets
`-C llvm-args=-split-machine-functions` as partial alternative.

## Five profiles (T4 §Q3)

| Profile | Backend | Opt | Key settings |
|---|---|---|---|
| dev | LLVM | 0 | debug=1 (line-tables), incremental, fast iteration |
| dev-opt | LLVM | 2 | + LoopOptimization. For testing MIR/LLVM behaviour |
| release | LLVM | 3 | Full pragmas. strip=symbols |
| profiling | LLVM | 3 | + debug info (line-tables). Runs benchmarks post-build |
| ci | LLVM | 3 | ExpandedLto, as release, without the profile-guided pragmas |

Cargo tells a build script only `debug` or `release` in `PROFILE`, by
which of the two built-in profiles the one being built inherits from.
`debug` resolves to `Profile::Dev` and `release` to `Profile::Release`;
anything else falls back to `Profile::Dev`. The three custom profiles
are design until the build script can tell them apart.

## Container workflow (T4 L596-663)

`-Z llvm-plugins` requires dynamic LLVM (Linux nightly only).
Dev builds on macOS: no plugins, use `-C passes=` and `-C llvm-args=`
for built-in passes. Release builds: Apple Container (Apache 2.0,
macOS Virtualization.framework, boots <1 second) running minimal
Debian with rustup nightly. Runs aarch64-linux natively on Apple
Silicon. No VM overhead, no Rosetta, no cross-compilation.
