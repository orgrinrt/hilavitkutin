## The decision (op, 2026-07-02)

Go with the **hybrid**. Op's stated reasoning: it is more future-proof, it performs just about the
same as the pure blob (the bench put V4 within +-1.7% of V1 on every scalar arm across both runs
and tied on B/C/E), so it carries only upsides. The one thing the bench listed against V4, the
backcast machinery and type-erasure round-trip burden, is a complexity-versus-simplicity concern,
and that axis is an anti-axis in this workspace: it is not counted against a design. With the only
downside ruled out and a future-proofing upside in hand at parity cost, the hybrid wins.

## What the hybrid is, precisely

The bench's axis-A and axis-D findings (snapshot the scalar `Field` members before the morsel
loop; live-stream `Seq`/`Map` collection members, never snapshot-copy) are about the value ACCESS
PATTERN and hold regardless of how the value bytes are ADDRESSED. The V1-vs-V4 question was only
about addressing: native monomorphised direct access (blob) versus erased static-shape access
(backcast through a shape descriptor). The hybrid takes V1's access discipline AND V4's erased
addressing into one model:

- **Value layout:** a one-record contiguous blob on the arena (bench-decided; NOT decomposed per
  member, NOT shape-bound shared).
- **Addressing:** erased static-shape (backcast via a shape descriptor), so a resource value can
  cross a cdylib/wasm plugin boundary and interoperate with builtin resources near-natively. This
  is loimu's reason for the erased-shape model. The bench measured this addressing at parity with
  native monomorphised on every axis, so it carries no in-process penalty.
- **Access discipline:** scalar `Field` members stack-snapshotted before the morsel loop; `Seq`/
  `Map` collection members live-streamed from their column (the snapshot copies only the scalars
  and the collection ptr+len, never the elements).
- **Handle + noalias:** `Resource<T>` is a handle (R5); the handle store never aliases the value
  columns (separate provenance); scalars snapshotted before the loop stay in registers across it.

## The per-resource-vs-global sub-question, resolved to global-capable

The v4-plugin-interop topic left open whether the erased boundary is per-resource (only resources
that cross a plugin boundary go erased, the rest stay native blobs) or global (every resource uses
the erased addressing). Op's two stated criteria settle it:

- **"More future-proof"** selects global-capable: if every resource uses the erased static-shape
  addressing, any resource can be shared across a plugin/wasm boundary without a per-resource
  design change or a typestate migration. A per-resource split requires knowing at design time
  which resources cross the boundary, and later additions are a change.
- **Parity** removes the only reason to keep in-process resources on the native-monomorphised path:
  there is no measured latency gain from native addressing, so nothing is lost by making every
  resource erased-addressed.
- The only argument left for the per-resource split is reducing the erasure surface on in-process
  resources, which is the complexity-versus-simplicity axis op explicitly ruled out.

So the erased static-shape addressing is the uniform resource value model: every resource is
plugin-capable, at parity cost. This is a call derived from op's stated criteria, not from an
explicit op instruction on the sub-question; it is cheap to narrow to a per-resource opt-in if op
prefers on review (no code exists yet), but nothing in op's reasoning points that way.

## Impact on the drift-fix and downstream

The drift-fix on the shipped `DrainStores` blob is still additive, now with the erased-addressing
path included: (1) add the scalar stack-snapshot before the morsel loop, (2) wire live-streamed
`Seq`/`Map` access, (3) state the noalias invariant, (4) route value access through the erased
static-shape descriptor rather than a monomorphised concrete-type pointer. Item 4 is the erased
addressing; because the bench showed parity, it does not regress in-process access, and it is what
buys the plugin-crossing capability. `CollectionBytes`/`ResourceFootprint` (#163/#164) supplies the
collection-bytes term for the A3b L1 morsel formula (blob-stride + collection-bytes fold), unchanged
by the addressing choice. 6d/6e and the rest of the roadmap sequence are unaffected.

The layout is now fully settled: no open storage-model fork remains for op.
