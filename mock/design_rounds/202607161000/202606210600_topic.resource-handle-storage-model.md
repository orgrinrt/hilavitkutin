# Topic: Resource is a handle, not an inline-value store

**Date:** 2026-06-19
**Phase:** TOPIC
**Round:** 202606210600
**Source topics / canonicals:** consolidation spec R5 (`mock/design_rounds/202604200055/202603181200_topic.hilavitkutin-design-consolidation.md` lines 535-566, 1682-1710); loimu unified-storage model (`~/Dev/loimu/mock/discussions/2026-02-17_unified-storage-model-discussion.md`); A3 re-chart `mock/research/202606210000`; the shipped impl `mock/crates/hilavitkutin/src/resource/bindings.rs`.

## The realization

A `Resource<T>` is a **handle**. It does not store its value inline. `T` decomposes
per-member: each `Field`/`Seq`/`Map` member becomes its own column in the **unified,
type-erased columnar store**, keyed/shared by **shape** (stride), so a `Field<u32>`
appearing in many resources collapses to one shape-bound column rather than a
type-unique column per concrete `T` (type-unique is too wide and explodes the column
count). The resource record itself holds only the **pointers** (or pointer + index)
to its members' columns, in a **separate handle store keyed by resource id**, with
separate pointer provenance from the value columns. The resource has **no private
value arena**.

`Seq`/`Map` values: a pointer-to-first-element plus a length (count of strides), the
elements stored consecutively without gaps per one `Seq`/`Map`, in the type-erased
stores.

When a morsel runs and needs the resource, the handle pointers become **stack-local**.
That stack-local hoist, with the handle store's separate provenance, is the source of
the LLVM-noalias win the spec measured (1.28-1.40x): LLVM can prove a column store does
not alias a resource read because the pointers originate from distinct provenance, so
it keeps resource members in registers across the morsel loop instead of reloading.

## Why this is the canonical model (R5 read correctly)

Spec line 1689 states it directly: "All behind pointer indirection to external slab
storage. NOT inline in the context struct." The "separate arena / separate pointer
provenance" (566, 1695-1704) is the **handle store** being distinct from the value
columns, which is what earns the noalias win. It is not a resource-private inline-value
domain. Read this way, every clause of R5 that a casual reading takes as "resources are
a separate storage island" is in fact the handle model expressed in storage-engine terms.

## What the shipped impl got wrong (drift)

`DrainStores` (bindings.rs:22) reserves a **one-record opaque column per `Resource<T>`**:
the whole value moved in as a blob behind a single `ResourcePtr<T>`. That is NOT the
canonical model. Canonical: the members decompose into per-member shape-bound columns,
and the resource is a handle of their pointers/indices. The blob impl is the drift to
fix; it is also what manufactured the morsel-size "dissonance" (the heterogeneous
bare-RunCfg-vs-Resource-vs-Column type-fold). Once every value is a shape-bound column
with a known stride and the resource is a handle, per-store size is uniform (column
strides) and the type-fold problem disappears.

## Downstream

A3 (per-fiber morsel-window sizing) rides on this: the write-byte sum is over shape-bound
column strides. The `CollectionBytes`/`ResourceFootprint` work (#163/#164) becomes the
const size source for `Seq`/`Map` member columns.
