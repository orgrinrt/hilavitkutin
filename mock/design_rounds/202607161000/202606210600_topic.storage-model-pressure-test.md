# Topic: pressure-test the resource storage model before locking it

**Date:** 2026-06-19
**Phase:** TOPIC
**Round:** 202606210600

The handle model (sibling topics) is the canonical intent and the amendment would lock it.
Before that, pressure-test the concept itself. Three reasons it is worth questioning rather
than rubber-stamping:

1. **Underspecified even originally.** R5 never spelled out the per-member shape-bound
   decomposition or the handle-of-indices shape (see `202606210600_topic.r5-underspecification.md`).
   A model this load-bearing should be stated and defended, not inferred.
2. **Largely unbenched.** The only measured win is the pointer-provenance / stack-local
   noalias finding (1.28-1.40x, spec 1698) — and that is a small slice of the whole model.
   Shape-bound column sharing, per-member decomposition vs blob, the morsel-window-internal
   fetch vs stack-local cache fork, the column-count behaviour: none benched.
3. **Old concept against a moved design.** R5 was distilled early; the rest of the engine
   (waist-based grouping, the const-gated flattener, the self-hosting meta pipeline, the
   per-fiber morsel arc) has since shifted and reshaped. This corner may simply be due an
   update, or may still be objectively strong. We do not know without testing it.

## What the pressure-test must produce

A set of independent domain-expert analyses (each a durable `.md` in `mock/research/`,
never context-only), plus this agent's own analysis, covering:

- Is the handle + per-member + shape-bound + unified-store model the best design for the
  engine's goals (no_std, no_alloc, monomorphised dispatch, const-known sizes/strides,
  morsel locality, the noalias win, consumer ergonomics for viola/saalis/loimu/polka-dots)?
- The open forks: morsel-window-internal member fetch vs stack-local handle cache; shape-bound
  sharing vs type-unique columns vs a hybrid; how `Seq`/`Map` ptr+len interacts with morsel
  windowing and resize/replace; how the handle store is keyed (resource id -> member column
  ids) and resolved const-vs-runtime; aliasing/soundness under the unified store.
- Concrete **impl paths** for the chosen shape (how `Resource<T>`, the bindings, `DrainStores`,
  `ColumnStorage`, and the ctx accessors change), with the drift-fix sequencing.
- **Alternative approaches** if an expert sees a better one (e.g. a different decomposition,
  a different handle representation, a different store layout), argued against the same goals.

## Process

Dispatch experts in parallel; each writes its deliverable as a durable research `.md`. This
agent also writes its own analysis as a research `.md`. Synthesise into one research doc
citing all deliverables. Then spitball with op via AskUserQuestion to confirm/decide the open
forks. Only after that does the amendment (sibling topic) get treated as locked and the
drift-fix arc + A3 downstream proceed. Nothing here pre-commits the answer; this topic frames
the question.
