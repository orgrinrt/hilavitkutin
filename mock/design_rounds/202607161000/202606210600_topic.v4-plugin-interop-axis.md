# Topic: V4 erased-shape carries a plugin/dynamic-loadability win the bench never scored

**Date:** 2026-06-20
**Phase:** TOPIC
**Round:** 202606210600
**Relates to:** `202606210600_topic.bench-decision.md` (frozen) + `mock/research/202606210600_storage-bench-findings.md`. This topic adds the axis that doc omitted; it does not edit it.

## The omission

The six-variant bench scored V4 (type-erasure-via-shaping) as "matches the blob on locality and
column-count, no per-call gain" — true on the LATENCY axes (A/B/C/D/E), which are all the bench
measured. It missed a strategic axis: **dynamic loadability across a plugin boundary.**

A type-erased boundary with a **statically-known shape** lets dynamically-loaded plugins (wasm,
cdylib) cross the boundary and interoperate with builtin variants near-natively. A monomorphised
blob (V1) has a layout fixed at the builtin's compile time; a separately-compiled plugin cannot
share that layout. A type-erased shape descriptor it CAN agree on. **This is why loimu chose the
erased-shape model: it makes wasm-loaded plugins almost as efficient as Rust dylibs/cdylibs**
(op, 2026-06-20).

## Why it is load-bearing for hilavitkutin

The engine ships a plugin-host layer (`hilavitkutin-linking`, `hilavitkutin-extensions`,
`hilavitkutin-extensions-macros`), viola loads cdylib plugins, and the arbitrary-time-linking
invariant requires any extension to load/run/drop independently. If consumer plugins must
**define or access resources that cross the dylib/wasm boundary**, the erased-shape model
(V4) enables it where a monomorphised blob cannot. The bench's per-call parity for V4 then reads
as a feature (erasure is free per call) plus an extensibility upside the bench never scored.

## Decision impact (for run-2 judgment, next week)

The decision is NOT simply "blob wins." The likely answer is a **hybrid**:
- blob + scalar stack-snapshot for builtin / in-process resources (the latency winner, V1);
- a type-erased static-shape boundary for resources that must cross a plugin/wasm boundary (the
  extensibility winner, V4 / loimu shape).

Weigh the plugin-interop requirement explicitly with the run-2 numbers + op. Do not lock "blob"
as if the latency axes settled it. Open question to resolve: do hilavitkutin's target consumers
(viola plugins, future clause extensions) actually need plugin-crossing resources, and if so, is
the boundary per-resource (only plugin-shared resources go erased) or global?
