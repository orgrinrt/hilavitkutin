# Project a WorkUnitBundle into PlanInputs

The plan stage (`compute_execution_plan`) takes a `PlanInputs` (per-unit read/write access masks, commutative flags, unit count, record count) and produces the `ExecutionPlan`. Today `PlanInputs` is hand-built in tests only; nothing projects it from the registered work units. The scheduler holds its work units as a type-level `WorkUnitBundle` (a cons-list of `WorkUnit` types) and its stores as a type-level `AccessSet`, but it never turns those into the runtime `PlanInputs` the plan stage consumes. So `Scheduler::run` cannot compute a plan: it is a transitional no-op.

This round adds the missing projection. It is the foundational step that lets the scheduler compute its plan from what the consumer registered, which every execution path (the later interpreted single-thread tier and the eventual compiled tier alike) depends on.

## The shape

The projection reuses the engine's existing frunk-style index-witness pattern (the `Here` / `There<I>` witnesses and the disjoint head-vs-tail recursion that `dispatch::engine_ctx`'s `Selector` / `Project` already ship). That pattern turns a type-level cons-list member into a position without the coherence wall a const-carrying `IndexOf` would hit, and the witness infers at the call site.

Three engine-local traits plus one free function, all in a new `plan::project` module:

1. A peano-value trait giving each `Here` / `There<I>` witness its runtime `USize` index. The existing `Selector` / `Project` never needed the numeric index (they pull pointers by recursion); the mask projection does, to pick which bit to set.

2. `Locate<Target, Index>`: a pure type-level "the list contains `Target` at position `Index`" witness over the api `AccessSet` cons-list (`Cons` / `Empty`). Disjoint head (`Here`) and tail (`There<I>`) impls let the solver infer `Index` for a `(StoresList, Target)` pair. Unlike `Selector`, it is driven by the list type alone, with no runtime value.

3. `MaskProject<Stores, Indices>`: walks an access set and, for each member, sets the bit at that member's located index within the global `Stores` list, building an `AccessMask`. `Indices` is the parallel witness cons-list, inferred at the call site exactly as `Project<R, Indices>` infers its indices.

4. `plan_inputs_from_bundle`: walks the `WorkUnitBundle` cons-list and, per work unit, projects its `Read` and `Write` access sets into `PlanInputs.reads[i]` / `.writes[i]`, sets `access[i]` to their union, copies the unit's `COMMUTATIVE` flag, and counts the units via `AccessSet::LEN`. `record_count` stays a runtime argument (it is not a property of the bundle).

The same-store-same-bit property is what makes the masks useful: when one unit writes a store another reads, both land on the same bit (the store's position in the global list), so the plan stage's dependency-edge derivation sees the overlap. The feasibility sketch at `mock/research/sketches/202605300626_plan-inputs-locate-witness/` validated the kernel (`Locate` + `MaskProject` with an inferred witness list) compiles and holds that property under the pinned toolchain.

## What stays out of scope

This round produces `PlanInputs` from the registered `(Wus, Stores)`. It does not store the resulting plan on the scheduler, does not change `Scheduler::run`, and does not add the interpreted execution path. Those are the following round. The witness types are reused from `dispatch::engine_ctx` rather than duplicated; if the plan-depends-on-dispatch direction wants tidying, a future shared-witness module is the move, tracked separately.
