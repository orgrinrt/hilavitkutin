# panic-aborts-on-a-worker

**Date:** 2026-11-14
**Phase:** TOPIC
**Scope:** job 3 of `mock/research/202611140100_engine-path-plan/PLAN.md`; ticket 144; the question ticket `a_unit_panic_aborts_behind_a_no_unwind_boundary_in_hilavitku` under its provisional stamp; the task ticket `hilavitkutin_engine_design_keeps_fiber_failure_poisons_depen` for the split of a poisoned fiber from an aborting panic

## What is wrong

A unit that panics on a `run_parallel` worker stalls the frame for good. The worker thread is the executor's; the unwind ends that thread, the engine's worker never reaches its done arrival, and the thread that called `run_parallel` parks in `frame_await_done` (`crates/hilavitkutin/src/thread/frame.rs:88-111`), which has no way out. The design says so as though it were the intended behaviour (`crates/hilavitkutin/DESIGN.md.tmpl:685-688`): "A panic inside a unit's own body on a worker is not caught or reported ... Catching it is the executor's".

The ratified row `execute_returns_nothing_and_a_failing_unit_aborts_because_abort_gives_better_llvm_codegen` (`mock/registry/tenet/units.toml:361`) says failure aborts, and that on the no_os and os tiers panic is abort already. That premise does not hold in a build that unwinds: `mock/Cargo.toml` sets no `panic = "abort"`, and every test build unwinds. The hang is the gap between the row and the build.

## The stance this round builds on

Op: "Abort stays, fix hang only" (clause-dev `.data/op-responses/202611131716_op-on-okay-so-while-we-wait-any-commentary-or.md:121-127`; the options were to redesign now, to redesign after the api revision, or this). The plan's two seats refused the three options of the open question (an executor catching the unwind and reporting a poisoned arrival, requiring units never to panic, a clock timeout) and chose a fourth: the body runs behind a boundary that cannot unwind, so a panic aborts the process whatever the build's panic strategy. That choice is the question ticket `a_unit_panic_aborts_behind_a_no_unwind_boundary_in_hilavitku`, provisionally stamped by the coordinators while op is away. It is not ratified, and this round says so where it cites it.

## The sketch

`mock/research/sketches/202611140545_no-unwind-worker-boundary/` builds both mechanisms against a generic entry over one raw pointer, as `worker_main` takes, with `panic = "unwind"`, and runs each in a child process whose worker thread panics. Both abort: the child dies of SIGABRT with no exit code, inside the 10 s bound. The control, a plain Rust entry, lets the thread die and the child exit 0, which is the engine's case. The `extern "C"` entry is taken: the compiler accepts it generic over the scheduler's parameters, it needs no `std`, the abort is the language's at a non-unwinding ABI edge, and it marks the call `nounwind`, which is what the abort row asks of failure for codegen.

## Where the boundary goes

The plan says the boundary goes "on the body wherever it runs". Every unit body the engine runs goes through one shim, `invoke_wu_in_fiber` (`crates/hilavitkutin/src/dispatch/wu_fn.rs:37-44`), whatever the entry and whatever the thread: `run`, `run_fused` and the workers of `run_parallel` all reach `execute` through it and nowhere else (the only `execute(` call in `crates/hilavitkutin/src`). The shim calls `execute` through an `extern "C"` function, so a panic in any unit body aborts at the unit.

The worker entry `worker_main` (`crates/hilavitkutin/src/scheduler/worker.rs:60`) becomes `extern "C"` as well. A unit panic never reaches it any more, but the worker's own code between units can still panic (an index, a debug assertion, an overflow in a debug build), and on a worker that hangs the frame the same way. The entry boundary closes that class, at no cost on the hot path, since it is crossed once per worker lifetime.

The caller's thread keeps unwinding outside unit bodies. The assert configuration's refusal is a panic by design, raised in `conclude` on the caller's thread after the frame (`crates/hilavitkutin-api/src/accum_overflow.rs:56-62`), and `tests/overflow_is_a_value.rs:421-435` holds it as `should_panic`. No worker waits on the caller there, so it hangs nothing.

## A poisoned fiber is not a panic

The ratified row `a_unit_signals_failure_through_data_flow_by_writing_an_error_column_or_firing_an_error_virtual` (`units.toml:394`) and the design's error-handling line (`crates/hilavitkutin/DESIGN.md.tmpl:1619-1622`) keep a second kind of failure: a unit signals it as data, the scheduler poisons the dependents, independent fibers continue. That path is not built; the pipeline result surface is charted into the completion arc (`mock/registry/tenet/future.toml:225`). The design states the split: a failure a unit reports is data and poisons; a panic is no report and aborts. Nothing of the poisoning path is built here.

## The check

A child-process test in `crates/hilavitkutin/tests/`: two workers through `FixedWorkers::<2>`, a carrier of two independent writer units in the first phase and a reader of both in the second, where the second writer panics. Trunks are owned round-robin, so the second writer's trunk is core 1's. The parent re-runs the test binary as the child and asserts it died by SIGABRT inside a bound. The case that must fail: on today's tree the child hangs, the bound trips and the parent kills it.

Each arm is shown alone: with the shim boundary taken out and the worker entry kept, the test still passes, and with both taken out it fails on the bound.
