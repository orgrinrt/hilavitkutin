# overflow-is-the-consumers-choice

**Date:** 2026-11-13
**Phase:** TOPIC
**Scope:** the run configuration in `hilavitkutin-api` (`src/run_cfg.rs`, a new `src/accum_overflow.rs`), the verdict at a run's close in `hilavitkutin` (`src/scheduler/verdict.rs`, `builder.rs`), both crate designs, the root README, and the overflow tests.

## Op's ruling

Asked through the coordinator whether an append past an accumulator's capacity should be a refusal as a value, with the options [a refusal as a value everywhere | the assert stays the default, refusal is a provider's opt-in | configurable by the consumer: a const, generic or trait parameter on the run configuration picks refuse or assert, default refuse], op answered, verbatim: "Configurable by the consumer".

The intent: the consumer picks, at compile time and on the run configuration, whether an over-capacity append comes back as a value or stops the run with a panic, and the refusal as a value is the default.

## Current state

Round 202611130402 built the refusal only. `RunCfg` is sealed, `DefaultRunCfg` is its one impl, and `RunCfg::Out` is `notko::Outcome<(), AccumRefused>` there. Every run entry ends in `frame_verdict`, which builds `Cfg::Out` from the frame's verdict. A consumer picks a configuration by type through `build_with::<Cfg, _, _>`; `build` takes `DefaultRunCfg`.

## Changes proposed

1. A sealed `AccumOverflow` names the choice, with two inhabitants, `Refuse` and `Assert`. Each fixes the run's output type and turns the frame's verdict into it: `Refuse` hands the verdict back as `notko::Outcome<(), AccumRefused>`; `Assert` returns `()` and panics on a refusal, naming the `AccumRefused`. The set is the engine's own fixed vocabulary, two behaviours of one branch, not content.
2. `RunCfg` gains `type Overflow: AccumOverflow<Out = Self::Out>`, so `Out` differs by the choice and nothing else can set it apart from it. `DefaultRunCfg` becomes `DefaultRunCfg<O: AccumOverflow = Refuse>`, so `build` keeps the refusal and `build_with::<DefaultRunCfg<Assert>, _, _>` takes the assert.
3. The append path does not change under either choice: it refuses and counts. The assert fires at the close, on the thread that called the run, after every worker has re-parked. `dev` asserted inside the append, so under `run_parallel` the panic hit a worker and the join stalled (fault H2). Asserting at the close keeps op's intent, a run that stops on an over-capacity append, without bringing that stall back, and no write passes the capacity under either choice.
4. Tests: the overflow suite runs under the default unchanged; under `Assert`, `run_parallel` at 1 worker and at `MAX_CORES` panics with the refusal in its message, and a compile-fail pair shows that under `Assert` the run's output is `()` and cannot be named as an `Outcome<(), AccumRefused>`.
5. Both designs and the README state the two choices and the default.
