# Topic: single-core dispatch completion (morsel-outer, phase/fiber-structured)

**Date:** 2026-06-05
**Scope:** hilavitkutin engine (`mock/crates/hilavitkutin`), `Scheduler::run` and the plan/dispatch surface it walks. GATE 1 of the engine runtime frontier: the single-core runtime to completion, then benched in its completed form.
**Source topics:** the dispatch-build-plan memo (`mock/research/202605282100_engine-dispatch-build-plan.md`, Phase C/D/E); the morsel-loop-windowing topic (`mock/design_rounds/202606041609`, the unit-outer increment this round supersedes); the consolidation spec (`202604200055/202603181200_topic.hilavitkutin-design-consolidation.md`, the fiber/trunk/morsel vocabulary); a neutral `feature-dev:code-architect` read (agent a81e51cf9c95770db) on the dispatch shape and order reconciliation.

## What this round is, and the honest state it starts from

`Scheduler::run` (`scheduler/mod.rs:591`) today is a correct but transitional single-core dispatch. It builds the column-capable per-unit dispatch slots (`CollectFiber` / `FiberSlot`, real, exercised by the engine-vs-std bench), then walks the plan-derived flat dispatch order (`derive_phase_dispatch_order`, #647) unit-outer: each unit completes its whole record range across every morsel before the next unit runs. The morsel-loop round (`202606041609`, #343) chose unit-outer deliberately, because it is correct for every plan (a downstream unit always sees the full output of an upstream unit, whether the dependency is element-wise or crosses record indices), and it named the transition: when the phase/fiber tier lands, only the outer loop is restructured to phase-then-fiber, while the per-morsel body, the morsel-size handling, and the windowing carry forward.

That transition is this round. Unit-outer is correct but it is the slow form: it materialises every intermediate column at full record count, which is exactly the cache cost the engine-vs-std bench measured (2 to 4x slower than a fused std loop, the gap attributable to intermediate materialisation, not to the dispatch machinery, which the bench's gap decomposition showed runs at parity). The designed cache-friendly form is morsel-outer per fiber: one morsel runs the fiber's whole WorkUnit sequence before the next morsel, so a fiber's intermediate columns stay resident across its stages. That is the form a completed single-core engine must dispatch, and the form the GATE-1 exit bench measures.

The reason morsel-outer was deferred, not the reason it stays deferred: morsel-outer is correct only when every cross-unit dependency inside a morsel-grouped run is morsel-local (record i of a downstream unit depends only on record i of an upstream unit). Establishing that safely is what the phase and fiber structure is for. Phases (waist barriers) separate runs where a dependency crosses record indices (a reduction feeding a broadcast, a gather): the downstream phase does not start until the upstream phase has completed every record. Fibers group units whose internal dependencies are morsel-local, so morsel-outer within a fiber is sound. Single-core needs no thread barriers for this: phase ordering is just sequential execution, and the "barrier" is free.

## The shape: walk the real plan, morsel-outer per fiber, runtime-ordered through the local slice

The dispatch keeps the existing column-capable local-slice path (`CollectFiber` builds one `FiberSlot` per unit; each slot's `fiber_shim` projects the unit's full `EngineCtx`, resources and columns and accumulators alike, and runs `execute`). That path is already column-capable and proven; its fn-pointer is a local array entry, the devirtualizable form the memo's R2 note distinguishes from a call through a stored `FiberDispatch.body` field (the 12.6x pathology). The pure-generics `RunFiber` tuple walk (`fiber_walk.rs`) is the resource-only sibling and is not the target here: a compile-time tuple-order walk dispatches in registration order, which equals the correct topological order only by coincidence, so it cannot serve as the general single-core oracle. The plan computes a topological (later RCM-reordered) dispatch order precisely because registration order is not guaranteed topological; honoring that runtime order requires the runtime-indexed slice. The architect read converged independently on the same conclusion.

`run()` is restructured to walk the plan's real structure rather than the pre-flattened order: `plan.phases[0..phase_count]`, each phase's trunks (`trunks[trunk_offset .. +trunk_count]`), each trunk's fibers (`fibers[fiber_offset .. +fiber_count]`), the same nesting `derive_phase_dispatch_order` already contains. Per phase, sequentially; per fiber, morsel-outer: window the fiber's record range into morsels of `max(Cfg::MORSEL_SIZE, 1)` and, for each morsel, dispatch the fiber's units in order (indexing the local slot array by `fiber.units[u].index()`) before advancing to the next morsel. The flat `topo_order` permutation loses fiber boundaries, so the new loop reads the structured plan, not `topo_order`.

The structured plan is store-backed (#655), not retained inline on the scheduler. The round resolves how `run()` reaches the phase/trunk/fiber pools: read them back through the existing `PlanHandle` (the store is the canonical home, consistent with #655), versus retain the `ExecutionPlan` (it is `Copy`) on the scheduler. The read-back path keeps the data plane unified and avoids duplicating a large structure; the retain path is fewer moving parts. Decided in the doc CL.

## The morsel-locality guard: correct everywhere, fast where provable

A fiber is dispatched morsel-outer only when its units are provably morsel-local; otherwise that fiber falls back to unit-outer. Both are correct; morsel-outer is the fast path for the common element-wise case. This makes the round correct for every plan from the first slice, rather than shipping a morsel-outer contract that holds only for element-wise plans (the failure mode the morsel-loop round named).

The morsel-local signal is structural. The Context per-record API (`each` / `read(i)` / `write(i)`) yields morsel-relative indices and adds `morsel.start` internally, so a plain column-transform WorkUnit is morsel-local by construction: it cannot read a record other than the one it is handed. The only cross-record surface is the accumulator path (`reduce` / accumulator writes), which is already a distinct kind in the type-level Write AccessSet and already carries dedicated plan machinery (`AccumSlot`, `Fiber.head_tail: Maybe<HeadTailConvergence>`, the `AccumProject` projection). So "this fiber is morsel-local" reduces to "no unit in this fiber writes an accumulator." Surfacing that bit into the runtime plan, so the dispatch guard can read it per fiber, is an open question for the doc CL (a per-fiber flag set at fiber formation, versus deriving it from the fiber's column set and the accumulator column classification).

## Slice breakdown (sequential rounds on this one branch)

1. Morsel-outer phase/fiber dispatch with the morsel-locality guard. Restructure `run()` to walk `plan.phases -> trunks -> fibers`; per fiber, morsel-outer when the fiber is morsel-local, unit-outer otherwise. Resolve plan access (read-back vs retain). Surface the per-fiber morsel-local bit. This is the slice that makes the bench measure the designed form: the bench's element-wise chain forms one fiber, which is morsel-local, so it dispatches morsel-outer. Correct for all plans via the unit-outer fallback.
2. Widen the fast path: real `arvo_graph::waist_detect` for phases (the current out-degree-zero heuristic over-segments) and fiber-formation refinement so accumulator boundaries become fiber or phase boundaries rather than forcing a whole fiber to unit-outer. This is where more of a general plan becomes morsel-local-by-formation.
3. Re-bench the completed single-core engine against optimal std (the GATE-1 exit), interpret, decide whether any further single-core work (stage fusion, the codegen tier) is needed before GATE 2, which is op's call informed by the number.

The slice count is provisional; sequential rounds on one branch absorb whatever the implementation reveals.

## Out of scope (later, by sequencing not by deferral)

- The dispatch codegen tier: `codegen_fiber` / `codegen_core`, the rust-pipe monomorphised body, per-core programs, the hilavitkutin-build LLVM flag emission (Phase D, #340). These are the optimization layer; correctness does not depend on them. Whether single-core needs the fusion they enable is the GATE-1 exit-bench decision.
- The parallel runtime: the spawn-once parking pool, phase thread barriers, trunk-to-core assignment, inter-fiber micro-morsel sync (#342). That is GATE 2, gated on a completed and benched single-core engine.
- Adapt (#341), plan caching (#345), spectral trunk balancing (a parallelism concern, not single-core).

## Open questions to resolve in the doc CL

- Where the per-fiber morsel-local bit lives: a flag set at fiber formation, versus derived at dispatch from the fiber's accumulator column membership.
- Whether a fiber's record range is the full `[0, record_count)` (the chain-over-all-records reading) or a per-fiber slice from `morsel_sizes` (the record-partition reading); the consolidation spec's "records within a fiber are independent" and the morsel-loop round's full-range windowing point to the full range single-core, with `morsel_sizes` being the per-fiber morsel granularity once the Phase C formula lands. Confirm against the fiber semantics before the dispatch loop commits.
