## Current state

The merged GATE-1 engine walks a single flat value-carrying WorkUnit list. `hilavitkutin-api::work_unit_values` ships `WuCons<W, Tail>` / `WuNil` (the per-fiber unit sequence) plus `WuAppend`. `hilavitkutin::dispatch::fiber_run::RunFiber<A, Witnesses>` walks that list: per unit it projects the unit's `EngineCtx` through `EngineCtx::project` and runs `execute` via `invoke_wu_in_fiber`, recursing on the tail, with the per-unit projection-index quad `(RIdx, RCIdx, WCIdx, WAIdx)` carried as a parallel witness cons-list inferred at the call site. The walk devirtualises under fat LTO (no stored function pointer). `Scheduler::run` drives it over one morsel.

Per the canonical hierarchy (`:74`) a fiber is one level below a trunk: `trunk → fiber`. The flat list the engine walks today is the degenerate single-trunk-single-fiber collapse. There is no type for "a trunk = a list of fibers" and no walk that runs a trunk's fibers in sequence. The plan stage already computes the trunk/fiber grouping (`group_fibers`, `block_diagonalise`, `compute_waists`), but dispatch ignores that structure and walks one flat list.

## Changes proposed

Add the trunk nesting level, the level directly above the shipped `RunFiber`:

1. **Carrier (api crate).** `FiberCons<F, Rest>` / `FiberNil` in `hilavitkutin-api::work_unit_values`, mirroring `WuCons` / `WuNil`. A `FiberCons` cell carries one fiber (itself a `WuCons` unit list) plus the tail of remaining fibers. The carrier lives in the api crate for the same reason `WuCons` does: the scheduler builder constructs it (at G2-0c; this round adds only the type, hand-constructed in tests). No `FiberAppend` yet; carrier construction from the plan is G2-0c.

2. **Walk (engine `dispatch/trunk_run.rs`).** `RunTrunk<A, WL>`: a monomorphic walk over `FiberCons` / `FiberNil`. `WL` is a cons-list whose head is one fiber's witness list and whose tail is the rest, so the whole nest is a 2-deep witness cons-list inferred with no turbofish (proven by 061400). `RunTrunk for FiberNil` is the no-op base; `RunTrunk for FiberCons<F, Rest>` requires `F: RunFiber<A, FW>` and `Rest: RunTrunk<A, RestWL>`, delegating each fiber to the unchanged `RunFiber::run` then recursing on the rest. Single-core, sequential: the fibers run one after another, exactly the order a flat concatenation of their unit lists would. At N cores (stage G2-N) each trunk, not each fiber, is the core-pinned unit; this round does not touch that.

The output-equivalence contract: a `RunTrunk` walk over `FiberCons[fiber_a, fiber_b]` produces the same column state as a `RunFiber` walk over the flat concatenation `fiber_a ++ fiber_b`, because `RunTrunk` only sequences `RunFiber` calls and `RunFiber` is unchanged. This is the test premise (TDD, fail-first): the trait does not exist, so the test referencing it fails to compile until the walk lands; once it lands, the two paths must agree bit-for-bit, and the trunk walk must carry no indirect call (ASM checklist, the GATE-1 devirt discipline extended to the new level).

`Scheduler::run` is NOT re-pointed onto the nested carrier in this round; that is G2-0c (build the `PhaseCons<TrunkCons<FiberCons<WuCons>>>` carrier from the plan and replace the flat walk). G2-0a adds the trunk level and proves it in isolation against the shipped `RunFiber`, so G2-0b (the phase level + waist barrier) and G2-0c (the plan-driven carrier) build on a landed, tested trunk walk.

## Why this slice and not the whole nest

The full three-level carrier built from real plan structures is the genuinely-new integration (G2-0c), gated by sketch A which is already proven. Landing the levels bottom-up (trunk, then phase, then plan-driven construction) keeps each round small and each test sharp: this round's test exercises only `FiberCons` + `RunTrunk` against `RunFiber`, so a regression localises to the trunk level. Per `branch-pr-flow.md` sequential rounds on one branch is the canonical shape; G2-0b and G2-0c follow on this same branch.
