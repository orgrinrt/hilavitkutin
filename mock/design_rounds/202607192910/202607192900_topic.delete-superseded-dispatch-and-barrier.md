# Topic: delete the superseded nested-carrier dispatch and its barrier

**Date:** 2026-07-19
**Phase:** TOPIC
**Scope:** `dispatch/phase_run.rs` entire, its re-export, its test, the design paragraph describing
it, and the `phase_barrier_*` family in `thread/barrier.rs`.
**Grounded on:** A1 registry item 3 (`202606111400:184-185`); op's direction that chart-the-path
exists to remove redundancy, YAGNI rot and drift.

## The test that was being used, and why it was wrong

Earlier passes in this arc kept both of these on the signal "something still references it": a test
exercises `phase_run`, a design paragraph names it, a BACKLOG note promises to wire the phase
barriers. That signal is worthless here. It is satisfied by exactly the artefacts that describe the
superseded mechanism, so it will always vote to keep drift alive.

The test that matters is **supersession**. Has a later design decision replaced this? If so the code
goes, and the test and the doc paragraph go with it, because they document the thing that lost.

## `phase_run` is superseded

A1 registry item 3 states it without ambiguity: "r4 (`202606070700`) replaces r3's G2-0c
**nested-carrier type construction** with the const-eval grouping + const-gated DCE mechanism."

`RunPhase` and `RunPipeline` are that nested-carrier type construction: `TrunkCons` / `PhaseCons`
nests walked by witness recursion. The replacement shipped and is what `Scheduler::run` uses. The
engine reaches `phase_run` only through `pub use` at `dispatch/mod.rs:41`, and its sole exerciser is
`tests/phase_pipeline_dispatch.rs`, which asserts the superseded walk matches the flat walk.

That test is not coverage of a live contract. It is a tether keeping a replaced mechanism compiling,
and its passing is what made the module look reachable in an earlier trace.

`phase_run`'s local `waist_barrier` (`:105`) is a spin-only third barrier implementation. It goes
with its module, which resolves the "three barriers" finding without needing its own decision.

## The `phase_barrier_*` family is drift on shared state

`phase_barrier_arrive` / `_reset` / `_observe` implement an arrive-plus-separate-reset protocol on
`pool.phase_arrived`, the same word the live sense-reversing `waist_barrier` drives with a different
reset discipline. Nothing calls them.

An earlier conclusion in this arc was that canon names no runtime barrier shape, so both should stay
with a clarifying doc note. That was the same preservation reflex. Canon's silence does not make two
incompatible protocols on one word acceptable; it makes the shipped one the answer and the other one
drift waiting for someone to wire it and corrupt the live path.

`DESIGN.md.tmpl:231` promises `phase_barrier_arrive` will be "wired in a following round". That
promise is what should be deleted, not honoured.

## What stays, and on what grounds

`core_phase_mask`. Not because a test names it, but because `core_mask.rs:3-4` records the mask form
as op's chosen mechanism and `trunk_dispatch.rs:83` cites it as the rule the live inline threading
implements. It specifies a shipped mechanism rather than a replaced one, so supersession does not
apply to it.

## Out of scope

`core_phase_mask` and `grouping_arrays`. The live `waist_barrier`. The D1 install revert, which is
its own correction.
