# Lift the engine's 64-node waist cap onto `D::Units`

## Current state

`compute_waists` (step 3 of the plan chain, `plan/steps.rs`) builds the
dependency adjacency as a `BitMatrix<Bits<64, Hot, Unsigned>, D::Units>` and runs
`arvo_graph::waist_detect::<D::Units, Bits<64, Hot, Unsigned>>` over it. The row
word is hardcoded to `Bits<64, Hot, Unsigned>`, a 64-bit mask. The node index a
row bit addresses is the unit's position, so the matrix can only carry edges for
nodes `0..64`. Above 64 units the column bit overflows the 64-bit word and edges
are silently dropped, corrupting waist detection. The step's doc comment states
this outright: "arbitrary node counts above 64 are a separate arc."

arvo #663 generalised `arvo_graph::waist_detect<C, B>` over the row word `B`
(bound `B: BitSequence + BitAccess + BitLogic + Copy + Default + Identity`), and
arvo's own `tests/generic_width.rs` proves concrete wide rows (`Bits<128>`,
`Bits<256>`) compile and run through `waist_detect` / `components` /
`upward_rank`. The substrate side of the cap lift already landed. The engine
still calls the 64-wide instantiation, so the engine caps at 64 regardless.

`D::Units` (the unit capacity dimension on `PlanDims`) can be `Dim<128>`,
`Dim<256>`, or any consumer budget. The engine's default is `Dim<64>`, an exact
fit for the old hardcoded row, which is why the cap went unnoticed.

## Why the inline-derive shape does not work

The obvious fix, deriving the row word from the capacity inline as
`Bits<{ cap_size(<C as Capacity>::CAP) as u16 }, Hot, Unsigned>`, does not
compile. arvo's `Bits<const N: u16, S, Sign>` resolves its storage container by
per-concrete-N const-tag projection (`Picker: Project<N_TAG, ...>`), and the
trait solver discharges that projection bound only for a concrete `N`. A symbolic
`generic_const_expr` over the capacity never reduces to a literal during
bound-checking, so `Bits<{that expr}>` is not even `Sized`. Sketch
`202606101000_d668-cap-width-row-word` records the wall (E0277, 19 errors, all
the same root cause) and proves the resolution below compiles and runs clean.

The same wall blocks the cleaner arvo-side fix (a `Capacity::AdjRow` associated
type) because `impl<const N: usize> Capacity for Dim<N>` is itself generic over
`N`, so `type AdjRow = Bits<{N as u16}>` hits the identical symbolic-N projection
wall in the impl. A truly capacity-generic row needs an array-of-words row
representation that is `Sized` for any symbolic N, a larger separate arvo effort.

## Changes proposed

Carry the row word as a concrete associated type on `PlanDims`, pinned at each
impl. Add to the trait:

```rust
/// The bit-matrix row word for waist / adjacency analysis. Concrete per impl,
/// sized to cover `Units` node indices. The "covers `Units`" relation is a
/// documented contract, not type-enforced, matching how arvo's own wide-width
/// tests pin concrete row widths.
type AdjRow: BitSequence + BitAccess + BitLogic + Copy + Default + Identity;
```

`compute_waists` uses `D::AdjRow` in place of the two hardcoded
`Bits<64, Hot, Unsigned>` occurrences. `D::AdjRow` is concrete at every
instantiation, so the container projection resolves; the cap becomes whatever
the `PlanDims` impl's `AdjRow` width covers.

`DefaultPlanDims` and every test `PlanDims` impl set `AdjRow = Bits<64, Hot,
Unsigned>` (all current dims are `<= 64` units, so the 64-wide row covers them
and behaviour is unchanged). A new test pins `Units = Dim<128>` with
`AdjRow = Bits<128, Hot, Unsigned>` and asserts a waist at a topo position past
64, proving the cap is lifted: the old hardcoded `Bits<64>` would drop the
high-index edges and misplace the boundary.

The step doc comment's "arbitrary node counts above 64 are a separate arc" text
is rewritten: this round is that arc on the engine side.

Per pre-1.0 no-shims discipline, the trait gains no associated-type default
(`associated_type_defaults` is forbidden), so every impl specifies `AdjRow`
explicitly. That is the mechanical rehab cost and is correct: the
`AdjRow`-covers-`Units` relation is per-impl.
