### Heuristic

Per `dispatch/approach.rs` doc comments:
- `IndirectPerFiber`: lowest-overhead for small record counts with many fibers
- `TrunkMega`: small record counts where a trunk dominates
- `ScheduleMega`: large record counts where LLVM's whole-pipeline optimisation window outweighs indirect-call overhead

The base body:
- If `record_count >= 10_000`: return `ScheduleMega`.
- Otherwise (small record count):
  - If `fiber_count <= 1`: return `TrunkMega` (single fiber, mega fn fits the working set).
  - Otherwise: return `IndirectPerFiber` (many fibers, per-fiber indirect call is the lowest-overhead split).

The `10_000` threshold matches the `<10K target` named in the existing doc comments on `DispatchApproach` and `select_approach`. The tiebreaker between TrunkMega and IndirectPerFiber in the small-record-count path uses `fiber_count <= 1` as a coarse cut; the benchmark follow-up refines both the size threshold and the fiber-count cutover.

### Tests

Four tests cover the heuristic:
1. `large_record_count_picks_schedule_mega`: 50_000 records, 8 fibers → ScheduleMega.
2. `small_records_single_fiber_picks_trunk_mega`: 1_000 records, 1 fiber → TrunkMega.
3. `small_records_many_fibers_picks_indirect_per_fiber`: 1_000 records, 8 fibers → IndirectPerFiber.
4. `threshold_boundary_picks_schedule_mega`: exactly 10_000 records, 8 fibers → ScheduleMega (the boundary is inclusive for ScheduleMega per the heuristic).

### Follow-up
