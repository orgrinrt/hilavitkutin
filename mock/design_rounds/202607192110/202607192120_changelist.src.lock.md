## CHANGE: `tests/gate2_run_parallel.rs` GAINS a five-producer phase under core surplus

File: `mock/crates/hilavitkutin/tests/gate2_run_parallel.rs`

Two more column-disjoint producers, `ProducerD` and `ProducerE`, and a test that builds with one
record so that on an eight-core machine only core 0 passes the participation guard at
`scheduler/mod.rs:966`. It asserts all five producers wrote.

**The test was written expecting to fail, and it passes.** The prediction was that a producer whose
trunk rank maps to a core with an empty record slice would be stranded, since participation is
decided by record slice and dispatch ownership by rank. That does not happen, because a single-trunk
phase takes the N-way branch, which dispatches the whole-phase mask rather than per-trunk: every
participating core runs every unit in the phase, so no unit depends on a specific core being awake.

So the branch this round set out to delete is doing a second job nobody had written down. It is not
only a record split; it is also what makes participation and dispatch ownership safe to disagree.

The test ships green, as a regression. It pins a property that holds today for a reason R1 removes,
and it is the case that flips to failing the moment the branch goes without the ownership change
landing first. Deleting it as "a test that did not find anything" would throw away the only guard on
the transition.

Verification: `cargo test -p hilavitkutin --test gate2_run_parallel` reports five passing cases.

## No catalogued red, and why the earlier plan for one was wrong

An earlier revision of this changelist specified this case as `#[ignore = "catalogue: ..."]`,
asserting a live defect: that trunk owners with empty record slices already drop their work. That
claim was written from reading the two ownership models against each other, before running anything.
Running it disproved it.

Nothing is catalogued here because there is no gap to catalogue. Writing the red anyway, on the
strength of an argument that had already failed its own test, would have put a confident false
statement into the audit trail in the one place designed to be trusted.
