# Doc changelist: stop calling the N-way split convergence

**Date:** 2026-07-19
**Phase:** DOC
**Topic:** `202607192100_topic.n-way-record-split-is-not-convergence.md`

The design prose names the canonical mechanism and then defines it as the drifted one. That has to
be corrected before the source changes, because the prose is what a future reader checks the source
against, and today it would confirm the drift.

## CHANGE: `hilavitkutin/DESIGN.md.tmpl` single-trunk paragraph

The passage at `:299-303` currently reads "The head+tail convergence branch (a single-trunk
waist-bounded phase split by record range across cores) keeps its record-slice ownership and the
scalar window". Two problems: it calls an N-way split head+tail convergence, and it documents a
carve-out for a branch that is being removed.

It becomes a statement of what canon requires and what the engine does today: single-trunk phases
get head+tail convergence, two threads from opposite ends of a commutative fiber, and that mechanism
is not yet built, so such phases currently run serially. The A4 carve-out sentence goes with the
branch it describes.

## CHANGE: `mock/DESIGN.md.tmpl` domain-20 row

The `thread` row lists "head+tail convergence" among domain 20's mechanisms without qualification,
which reads as shipped. It gains the same not-yet-built marker the other unbuilt mechanisms carry,
so the table does not assert a mechanism the engine lacks.

## CHANGE: `hilavitkutin/DESIGN.md.tmpl` accumulator-region paragraph

The passage at `:553-557` says core c appends at offset `lo_c`, "the same head+tail record-slice
start the morsel-local path uses (`per = ceil(total/ncores)`, ...)". That sentence is where the two
mechanisms got welded together, and it is worth being precise about which part is wrong.

The accumulator regioning is canonical. `202606111800:452-456`: "each core gets an exclusive region
of the accumulator ... the cores append into their regions in parallel, and the main thread merges
the regions after the workers rejoin, preserving append order." That is N-way by design, one region
per core, and it is correctly implemented.

The dispatch record split is not canonical, and it is 2-way by design. The two happen to share the
formula `ceil(total/ncores)`, and the prose reads that shared formula as evidence they are the same
mechanism. They are not: one partitions an output buffer among all cores, the other partitions input
records between exactly two threads walking toward each other.

The paragraph is rewritten to describe the accumulator regioning on its own terms, citing the
accumulator canon rather than the convergence canon, and without claiming the offset is a head+tail
slice.

## The finding that changed this round's scope

Tracing the formula before editing turned up a third site, `scheduler/mod.rs:960`, in the worker
entry itself. It computes the same ceil slice and uses it for two things: the accumulator region,
and `run_this = lo < hi`, the participation guard that makes a core with an empty slice return
early and run nothing.

So the N-way record split is not confined to the dispatch branch. It also decides which cores
participate in a frame at all. Deleting the dispatch branch alone would leave cores opting out by
record slice while dispatch fell back to trunk-rank ownership, and any core with an empty slice
would silently never run the trunks it owns. That is a correctness bug, introduced by a change
whose stated purpose was removing drift.

The source deletion is therefore **not in this round**. It needs a sketch establishing how
participation is decided once record-slice ownership is gone, and the roadmap item needs splitting.
The doc corrections stand on their own: the prose is wrong today regardless of when the code changes,
and leaving it would keep confirming the drift to anyone who checks.

**Then the trace went one step further and found the bug is already live.** `worker_count()` returns
the machine's online processor count, and the parallel fixtures use four records, so `ncores > total`
holds on any ordinary development machine today. With `per = ceil(4/8) = 1`, cores four and up get
an empty slice and return before dispatching. They are still trunk-rank owners. Any phase with more
trunks than `min(ncores, total)` therefore drops the trunks owned by those cores, silently, in a
frame that reports success.

No existing test has enough trunks to reach a core in that range, which is the only reason the suite
is green. The src changelist adds the case, and it is expected to fail against current source.
