## The vehicle

A pragma is a unit type implementing `Pragma`: its name, its bit, its group, `type Requires`, its reach, what a target must be for it, the tool it waits on, and functions that write its text into a `core::fmt::Write`. A set is the flat tuple the canon spells. Requirements between pragmas are `All<(A, B)>`, `Any<(A, B)>` and one per group, folded into one constant of the set that a `const` item in the script asserts over, so a broken set is refused by a check at the line that names it, in the pragma's or the group's own sentence (sketch `mock/research/sketches/202611192110_a-flat-tuple-set-refused-under-cargo-check/`, after `202611191545_pragma-requirements-as-bounds`, where any-of as a trait bound refused a set that met it twice). `PragmaSet::coherent` goes.

A prototype becomes a type as well: a `Prototype` names one set per profile, and `script!` takes its path. `Default` and `Deterministic` are the crate's own, and a consumer writes its own beside them in a crate of its build-dependencies.

The seven choices are groups, one pragma per value that differs from the toolchain's own, and a group with no pragma in the set leaves the choice to the toolchain. They split by reach, which the sketches settled. A linker reaches the crate whose set holds it, as a link argument its script prints (`202611191600_a-link-flag-reaches-the-final-crate-alone`), and the dylib edge form reaches the crate that is the dylib, through the wrapper (`202611191830_where-prefer-dynamic-has-to-reach`). LTO, incremental, the backend, the link driver and the C compiler are cargo configuration that reaches every crate of the build (`202611191615_cargo-keys-for-driver-backend-and-cc`, `202611191735_lto-and-incremental-are-profile-keys`), so they are the workspace's and no one crate's.

The workspace's pragmas are named by one script of the workspace, the one that says so: `script!(<prototype>, workspace)`. Any other script whose set holds a pragma of workspace reach is refused at compile time. The workspace's script writes one generated file, `.cargo/hilavitkutin-build.toml`, which the `config.toml` takes by one `include` line (`202611192125_cargo-takes-a-generated-config-by-include`); the file names the crate that wrote it, and a second crate claiming the workspace is refused in words and writes nothing. This is the canon's generated configuration, moved from a file under `target/` that nothing read to a file cargo reads.

What a target admits and what the machine has are known only when the script runs. Both are requirements all the same: the crate reads the target's facts from the `CARGO_CFG_TARGET_*` values, each pragma states what it needs of them and which tool it waits on, and a pragma that fails either is refused by a `cargo::error` naming the pragma, the fact and the remedy. Nothing falls back in silence.

Tools are one table: name, pinned version, source (a package, a toolchain component, a prebuilt release, a local build) and proof. The crate writes the path a tool has under the tools home; the home is `HILAVITKUTIN_BUILD_TOOLS_HOME` where the builder sets it and the per-user cache where not. The workspace's script does the work on disk: it takes a tool from the path where the proof passes, builds a local-build tool into the home where it does not, and removes the directories of other versions of that tool.

The three axis enums go. Tier and passes restate what the set says and nothing computes from them; the target axis becomes one of the target's facts.

The bench's `build-call` and `build-fixture` read the target's facts, the linker's mark and the profiles from the crate, and a `link-static` arm is a type over its linker pragma and its quantity (tickets `build_call_s_target_spec_reading_linker_mark_and_cargo_flags`, `a_link_static_arm_carries_its_linker_and_quantity_in_a_type`). The move of `build-call` waits on the job `build-bench-rerun` landing its rows.
