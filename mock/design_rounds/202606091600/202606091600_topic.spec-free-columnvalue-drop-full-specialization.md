# Topic: spec-free ColumnValue, drop the full `specialization` gate

**Date:** 202606091600
**Phase:** TOPIC
**Scope:** `hilavitkutin-api` only (`ColumnValue` in `column_value.rs`, the crate-root feature gates in `lib.rs`, and the `DESIGN.md.tmpl` / `BACKLOG.md.tmpl` passages that describe the trait).
**Source design:** workspace rule `unstable-features.md` (full `specialization` is FORBIDDEN, known unsound, no prospective fix; `min_specialization` is the allowed subset); task #631 (spec-free `ColumnValue::BIT_WIDTH`). op directive 202606091600: full `specialization` must be removed wherever still enabled; `min_specialization` stays fine.

Full `specialization` is forbidden across the workspace (structurally unsound, will not stabilise). One enabled gate remains in the stack: `hilavitkutin-api/src/lib.rs` carries `#![feature(specialization)]` solely for `ColumnValue::BIT_WIDTH`, whose blanket impl uses a `default const` overridden by three sub-byte arvo impls. That `default const`-overridden-by-concrete shape is exactly what `min_specialization` rejects, so the full gate was kept. This round removes it: `ColumnValue` becomes spec-free, and the forbidden gate leaves the crate root.

## Why this is removable now with zero functional regression

`ColumnValue::BIT_WIDTH` is dormant. A repo-wide search finds no functional consumer: the dispatch column reservation in `engine_ctx.rs` sizes columns by `size_of::<T>()`, and its two comments name `T::BIT_WIDTH` only as the future sub-byte-bitpacking hook, not as a value read today. The only references to `BIT_WIDTH` outside its definition are documentation. So the three sub-byte overrides (`UFixed<1,0>` to `BIT_WIDTH = 1`, and the 2-bit / 4-bit siblings) carry width information that nothing currently reads.

That makes the spec-free shape a near-trivial collapse. The trait keeps `BIT_WIDTH` with the byte default moved into the trait body; the blanket impl becomes an empty `impl<T: Copy + 'static> ColumnValue for T {}` that inherits the default. Any `Copy + 'static` type still auto-qualifies as a column value (the zero-friction property is preserved). The three sub-byte impls are deleted; those types still satisfy `ColumnValue` through the blanket, now reporting `size_of * 8` instead of their packed width. Because nothing reads the width, the deletion changes no behaviour.

When bitpacking lands (a future feature), the sub-byte storage width is sourced from arvo's own width-reporting traits (the type already knows its bit width through arvo), wired at the storage layer where it is actually consumed, not re-encoded as a `ColumnValue` specialization. That is the correct home for the width anyway: storage width is a storage-engine concern, not a marker-trait const that needs an unsound feature to vary.

## Why a trait-body default plus an empty blanket impl is spec-free

A trait-body default const is the ordinary fallback an impl uses when it does not state the const. The empty blanket `impl<T: Copy + 'static> ColumnValue for T {}` states nothing, so it takes the default `size_of::<Self>() * 8`. No `default` keyword appears, so no `specialization` (full or min) is invoked. A sub-byte type cannot add its own `impl ColumnValue for UFixed<...>` (it would overlap the blanket, E0119), which is precisely why width specialization moves out of the trait and into the future storage layer rather than staying here behind a forbidden gate.

## Changes proposed

1. `column_value.rs`: move the `size_of * 8` default into the trait body; replace the `default const` blanket with an empty blanket impl; delete the three sub-byte `UFixed` specialisations; rewrite the module doc to describe the spec-free shape and the deferred bitpacking-width source.
2. `lib.rs`: remove the `#![feature(specialization)]` gate and its FORBIDDEN-feature exception comment. Confirm no other `specialization` use remains in the crate (grep: only `column_value.rs`).
3. `DESIGN.md.tmpl`: rewrite the `ColumnValue` section to the spec-free shape (trait-body default, empty blanket, no `default const`, no "sub-byte types specialise"); note that sub-byte storage width is a future bitpacking concern sourced from arvo widths.
4. `BACKLOG.md.tmpl`: replace the "ColumnValue specialisation coverage" note with the bitpacking-width-from-arvo follow-up framing.

## Out of scope

- Bitpacking itself (the consumer of sub-byte width): a future storage-layer feature; this round only stops pinning its width to a forbidden-feature specialization.
- `min_specialization` use elsewhere: allowed, untouched. This round removes only the FULL `specialization` gate.
