# Topic: select_adapt_config decision logic (R5, adapt keystone)

**Date:** 2026-06-19
**Phase:** TOPIC
**Scope:** `hilavitkutin` engine (`Scheduler::select_adapt_config` + an `adapt_reconfigure` trigger)
**Source topics:** spec domain 22 (adapt trigger), the shipped EMAs (phase_ema, idle_ns, pass_duration), the adapt-performance-contract catalogue

## Current state

The adapt subsystem now samples its signals: per-frame pass-duration EMA,
per-phase EMA (`phase_ema`), per-core idle (`idle_ns`), throughput numerator,
change rate. Nothing consumes them yet. `select_adapt_config` is the tuning
logic that reads the metrics and decides whether to reconfigure; it is the
keystone the seven catalogued performance contracts pin (an adaptive run must
improve / never degrade, which requires this decision to fire correctly).

The spec frames the trigger as a cheap dirty-bitmask comparison ("if phase
balance shifted, re-select per-phase configs"). The first decision this round
ships is the phase-imbalance trigger: when one active phase's EMA dominates the
least active phase's, set a reconfigure trigger. The actuation that ACTS on the
trigger (re-selecting per-phase configs, re-chunking morsels) is the follow-up;
this round ships the DECISION, unit-tested in isolation, with actuation pending.

## Changes proposed

1. `Scheduler` gains `adapt_reconfigure: Cell<Bool>`: the phase-imbalance
   reconfigure trigger. (One trigger now; it widens to a small bitmask when the
   second tier-trigger lands. No premature bitmask.)
2. `Scheduler::select_adapt_config(&self)`: scan `phase_ema`, treat slots with a
   nonzero EMA as active phases, and set `adapt_reconfigure` iff there are at
   least two active phases and the max active EMA exceeds `BALANCE_FACTOR` times
   the min active EMA. `BALANCE_FACTOR` is a tunable const default (the substrate
   ships a default, the consumer tunes; per the caps-are-defaults rule). Pure
   `&self` logic over existing engine state, no clock, no dispatch tap.
3. `run` calls `select_adapt_config` once per frame, after the per-phase EMA
   fold, so the trigger reflects the frame just observed.
4. White-box test accessors: `__set_phase_ema(p, ns)`, `__select_adapt_config()`,
   `__adapt_reconfigure()`, so the decision logic is unit-tested deterministically
   (set an imbalanced / balanced `phase_ema`, run the decision, assert the
   trigger) without depending on wall-clock timing.

## Edge cases (catalogued as tests)

- imbalanced (`max > FACTOR * min`, >= 2 active phases): trigger set.
- balanced (`max <= FACTOR * min`): trigger clear.
- single active phase: trigger clear (no imbalance with one phase).
- zero active phases (no per-phase timing, e.g. parallel/fused path): trigger
  clear.
- the make-or-break "select_adapt_config reduces the bottleneck phase_ema"
  contract (`tests/adapt_perf_contracts.rs`) stays catalogued-red until the
  ACTUATION lands; this round only ships the decision that sets the trigger.

## Not in scope

The actuation (re-selecting configs / re-chunking morsels on the trigger); the
bitmask generalisation to multiple tier-triggers; parallel/fused-path decisions
(those paths do not populate `phase_ema` yet).
