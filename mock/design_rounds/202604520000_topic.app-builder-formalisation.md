## Background

The Scheduler builder shipped in 202604200117 (`hilavitkutin/src/scheduler/mod.rs:50-92`) provides chainable methods: `.add::<WU>()`, `.resource::<T>(init)`, `.resource_default::<T>()`, `.column::<T>()`, `.memory(provider)`, `.threads(pool)`, `.clock(clock)`, `.build()`. Each method takes the builder by value, returns it. Const-generics `<MAX_UNITS, MAX_STORES, MAX_LANES>` cap the registered set sizes.

What the builder does NOT do today:
1. Validate at compile time that registered providers satisfy WorkUnit Ctx bounds. `.add::<WU>()` accepts any type matching the WorkUnit trait, regardless of whether the registered provider tuple satisfies WU's seven Ctx accessor traits (`HasColumnReader`, `HasColumnWriter`, `HasResourceProvider`, `HasVirtualFirer`, `HasEach`, `HasBatch`, `HasReduce`).
2. Offer a unit of "register a related set of Resources/Columns/access-trait projections in one chain step". Every reusable provider that wants to ship onto a consumer's scheduler currently has to be wired Resource-by-Resource by the consumer, ad-hoc.

This round formalises both gaps so:
- `hilavitkutin-providers` (task #253) can ship the InternerKit (and future kits) using one cohesive trait.
- Consumer apps (viola, vehje) get compile-time guarantees that their scheduler is correctly wired before `.build()` returns.

## Decisions

### 1. Vocabulary: "Kit"

The unit-of-registration noun is **Kit**. Considered and rejected:
- **Bundle**: feels foreign in this stack (Bevy/Specs idiom; user pushback).
- **Preset**: collides with viola.toml v2 lint-preset inheritance.
- **Package**: collides with Cargo packages.
- **Module**: collides with Rust `mod`.
- **Extension**: collides with hilavitkutin-extensions (dylib host).
- **Composition**: descriptive but heavy.
- **Nippu** (Finnish, "bundle/packet"): matches stack's Finnish-named crates; viable but Kit reads more universally.

Chosen: **Kit**. Trait name: `ProviderKit`. Concrete impls: `InternerKit`, `<future>Kit`.

### 2. ProviderKit trait shape: consume + emit

```rust
pub trait ProviderKit {
    fn install<const MU: usize, const MS: usize, const ML: usize>(
        self,
        builder: SchedulerBuilder<MU, MS, ML>,
    ) -> SchedulerBuilder<MU, MS, ML>;
}
```

Rationale:
- The Kit consumes the builder, calls regular builder methods on it (`.resource()`, `.column()`, etc.), returns the mutated builder.
- Same builder API everywhere — Kits can register Kits using the same chain (`.install(other_kit)` inside their own `install`).
- No new ABI surface; the builder method `.install(kit)` is sugar for `kit.install(builder)`.
- Const-generic method (not const-generic trait) keeps the trait object-friendly enough for future flexibility while not requiring the Kit to know `MU/MS/ML` at definition time.

Considered and rejected:
- Descriptor-style (associated types declaring resources + access traits). More abstract; less flexible for Kit-internal allocation patterns like `MemoryArena<M, CAP>`.
- Trait-object-friendly (`fn install_dyn(&self, b: &mut dyn SchedulerLike)`). Violates no-dyn principle; reinvents the heap for "stored heterogeneous Kits".

### 3. Builder method: `.install(kit)`

```rust
impl<const MU: usize, const MS: usize, const ML: usize> SchedulerBuilder<MU, MS, ML> {
    pub fn install<K: ProviderKit>(self, kit: K) -> Self {
        kit.install(self)
    }
}
```

Sugar for `kit.install(builder)`. Choice of `install` over `add_kit` / `with` / `wire` / `register`:
- `install` reads as imperative + complete (a Kit installs onto the builder, becoming part of it).
- `add_*` family is taken (`.add::<WU>()` for WorkUnits).
- `with` is overloaded across builder ecosystems; less precise.
- `register` reads as bookkeeping; `install` is more substantial.

Kits can call any builder method inside their `install`, including `.install(other_kit)` for nested composition. No new vocabulary at chain sites.

### 4. Compile-time validation: type-state accumulator

The `SchedulerBuilder` carries type-level sets that track:
- **Demand**: union of all registered WorkUnits' `Ctx` bound requirements (each `WU::Read` and `WU::Write` access set, plus the seven Has-trait projections).
- **Supply**: providers exposed by `.memory()` / `.threads()` / `.clock()` and Resources/Columns introduced by `.resource()` / `.column()` / `.install(kit)`.

`.add::<WU>()` advances Demand. `.resource()` / `.column()` / `.install(kit)` / platform setters advance Supply. `.build()` requires `Demand ⊆ Supply` at compile time; mismatches surface as trait-bound errors at the `.build()` call site.

Mechanism (final naming + sealing in the doc CL):
- A type-list construct (sealed marker traits over tuple-shaped types).
- Builder gains type parameters representing the demand list and supply list.
- Each chain method advances exactly one of those lists by appending to its tuple.
- `.build()` is gated on a sealed `SatisfiedBy<Supply>` impl for `Demand`.

Considered and rejected:
- Plain trait bound on `.build()`: same compile-time guarantee, harder to give clear error messages.
- Runtime panic on `.build()`: violates substrate's no-runtime-discovery principle.
- Skip validation in v0: defers the hardest part; viola Tier 3 would land on incomplete substrate.

The type-state machinery is non-trivial. The substrate already enables `adt_const_params` + `generic_const_exprs` + `specialization` (`hilavitkutin-api/src/lib.rs:11-15`); the type-list construction can use those features.

### 5. App macro: deferred entirely

No `app!` / `define_app!` macro in this round. Consumers call the chain directly:

```rust
let scheduler = Scheduler::<8, 16, 4>::builder()
    .memory(OsMemoryProvider)
    .threads(OsThreadPool::new())
    .clock(OsClock)
    .install(InternerKit::<_, 65536>::new(OsMemoryProvider))
    .resource::<ViolaConfig>(parse_config())
    .column::<Diagnostic>()
    .add::<LoadConfig>()
    .add::<RunRunner>()
    // ...
    .build();
```

Rationale: macros earn their keep when chain readability degrades. With the type-state accumulator giving compile-time guarantees, the chain itself stays clean; mistakes surface at the wrong-method site, not deferred to runtime. If chain length becomes painful for big apps later, a `define_app!` macro lands in its own round.

### 6. Module placement

- Trait `ProviderKit`: lives in `hilavitkutin-api`. Precedent: `HasMemoryProvider` and friends already in `hilavitkutin-api/src/platform.rs:84-95` (contracts crate).
- Builder `.install` method: lives in `hilavitkutin` engine crate, alongside the existing `SchedulerBuilder` impl (`hilavitkutin/src/scheduler/mod.rs`).
- Type-state machinery: split across both — type-list traits in `hilavitkutin-api`, the builder type-state advancement in the engine.

## Out of scope

- App macro (`define_app!` / `app!`). Deferred. Possible follow-up round.
- Provider catalogue beyond what already ships. Catalogue extensions (InternerKit, others) live in `hilavitkutin-providers` (#253).
- Validation error message customisation. Default trait-bound errors are acceptable for v0; custom diagnostics via `#[diagnostic::on_unimplemented]` etc. are a follow-up polish round.
