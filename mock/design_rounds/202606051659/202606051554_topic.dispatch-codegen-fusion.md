# Dispatch codegen: within-fiber fusion and devirtualization

This round opens Phase D, the dispatch-codegen keystone. The single-core engine is designed to match or beat an optimal hand-fused std loop (0.95x to 1.02x). The `#664` perf gate measures the distance and is red now: the engine runs 2x to 6x slower than std across the three gate workloads. The audit memo traced that gap to two mechanisms the engine does not yet have, both of which live here. This round is where they get built, and the perf gate going green (or measurably moving toward green) is the success criterion.

The first mechanism is within-fiber stage fusion. Today every WorkUnit in a fiber writes its output column to the arena and the next unit reads it back, so a four-stage element-wise chain streams five columns where an optimal fused loop streams two and keeps the three intermediates in registers. Fusion means a fiber's internal columns never reach memory: only the fiber's true outputs are materialised. The second mechanism is dispatch devirtualization. The current hot path dispatches each unit through a type-erased function pointer collected into a runtime-walked array, which is the milder form of the stored-fn-pointer pattern the consolidation benches measured at a 12.6x penalty (risk R2). A monomorphised per-fiber body removes the indirect call entirely.

Both mechanisms hinge on one structural tension that this round must resolve: the plan computes fiber grouping and topological order at runtime, while monomorphisation is a compile-time fact about the statically-registered WorkUnit set. The whole point of "monomorphisation is the dispatch" is that each fiber body is a distinct compiled function, but the engine does not know which units form which fiber until the plan runs. How to map the runtime plan onto compile-time-monomorphised fiber bodies is the load-bearing design question, and it is the reason this is a keystone round rather than a mechanical one.

## Current dispatch reality

The design memo's "current state" predates the dispatch that shipped through PR #129, so the round is grounded in the live code rather than the memo. The plan chain (`plan/`) produces a real typed `ExecutionPlan`. `Scheduler::run` walks the plan's per-fiber `FiberDispatch` descriptors and, per fiber, dispatches each unit's `fiber_shim` function pointer from a local live array (morsel-outer when the fiber writes no accumulator, unit-outer otherwise, per PR #129). Each shim constructs that unit's `EngineCtx` and calls `execute`; column reads and writes resolve through the arena column buffer (`dispatch/engine_ctx.rs`). The `RunFiber` / `WuCons` type-level cons-list fold in `dispatch/fiber_walk.rs` already monomorphises and inlines a fiber's unit sequence with no function pointer, but it is resource-only: a column-reading or column-writing unit does not satisfy its bound. `codegen_fiber` and `codegen_core` (`dispatch/mod.rs`) are empty skeleton stubs that `run()` never calls.

So the pieces that fusion and devirtualization need are partly present: a working plan, a working per-unit Context construction, and a proof-of-concept type-level cons-list walk that devirtualizes. What is missing is a column-capable fused walk whose fiber-internal columns are register-backed, and the mapping from the runtime plan to whatever compile-time shape carries it.

## The open design question (resolved by the architect read plus a sketch, recorded in the DOC CL)

Candidate shapes, to be evaluated on the real surface before the DOC CL commits to one:

1. Scratch-backed internal columns. Fiber-internal columns are backed by morsel-sized stack scratch buffers in the Context rather than arena columns; each WorkUnit keeps its `execute(ctx)` shape with its own internal `each` loop; adjacent morsel loops plus the small fixed scratch rely on LLVM loop-fusion and dead-store elimination under fat LTO to collapse the intermediates. Only Output columns hit the arena.
2. Type-level fused fiber walk. Extend the `RunFiber` / `WuCons` fold to be column-capable so a fiber monomorphises into one inlined body with no stored function pointer (R2), combined with scratch-backed internal columns (fusion). Requires mapping the runtime fiber grouping onto a compile-time WU cons-list.
3. Per-record loop inversion. The engine owns the morsel loop and each WorkUnit exposes a per-record transform; the engine pipelines per-record across the fiber keeping intermediates in registers. Changes the WorkUnit contract.
4. Whole-schedule monomorphisation. The entire registered WU cons-list dispatches as one monomorphised body in plan-topo order for the single-core single-fiber case, internal columns scratch-backed.

The criteria are: how each shape maps the runtime plan onto compile-time monomorphisation, whether it removes the stored-fn-pointer pathology (R2), whether it actually fuses the intermediate-column traffic, the GAT/lifetime/aliasing soundness exposure (R3), the trait-solver feasibility under the pinned nightly, the blast radius on the `WorkUnit` / `EngineCtx` / `classify_columns` / `run()` surface, and preservation of the no-dyn no-TypeId static-composition rules.

## Discipline

This is a keystone with trait-solver and GAT risk, so it follows the keystone discipline: a neutral domain-expert read on the codegen surface (dispatched), then a sketch in `mock/research/sketches/` that compiles the load-bearing trait-solver question for the chosen shape under the pinned nightly before any shipping source changes, then the DOC CL, then the SRC CL test-first. Algorithm and threshold forks (morsel size, the approach selector, scratch sizing) are bench decisions resolved against the `#664` perf gate and the existing bench harness, not asked. Each SRC increment must move the perf gate measurably; when the gate goes green on the workload matrix, Gate-1 (`#661`) is done by the design's own standard.
