# DOC CL: single-core dispatch as a column-capable inline walk

This changelist edits `mock/crates/hilavitkutin/DESIGN.md.tmpl` to describe the corrected single-core dispatch shape that the SRC CL implements. The TOPIC framed four candidate shapes and an order-handling question; this round records the resolution. Two neutral architect reads plus a trait-solver sketch plus the ideal-design synthesis converged on it.

The doc edits are scoped to the single-core `Scheduler::run` dispatch description. The multi-variant mega-dispatch design (`DispatchApproach`, `select_approach`, `codegen_fiber` / `codegen_core`, per-core compiled pipelines) is forward design for the parallel path (GATE 2) and is left untouched.

## Current state (what the docs claim today)

`DESIGN.md.tmpl` (the `RunFiber` paragraph at lines 129-145 and the `Scheduler::run` paragraph at 147-179) describes single-core dispatch as:

- `RunFiber` is the monomorphic inline cons-list walk over a fiber's WorkUnit sequence, but it "stays resource-only": a column-bearing unit does not satisfy its bound.
- Column-bearing units therefore dispatch through `Scheduler::run` via `CollectFiber`, "the sibling of `RunFiber` that records a `FiberSlot` (an erased instance pointer plus a per-unit shim) instead of running the unit inline."
- `run` walks the runtime phase-sequential dispatch order (the plan flattened `phases -> trunks -> fibers -> units`) and dispatches each unit's erased slot through the shim.
- Line 176-177: "A column-reading unit registered ahead of its writer runs after it, because the plan reorders them so the writer's column write lands first."

This is the per-unit type-erased function-pointer dispatch. The ideal-design synthesis (`202606052000` audit, section 4 T6 matrix) measures this dispatch class at 12.6x slower than hand-fused std: an indirect call per unit through a runtime-walked slot array that LLVM cannot devirtualize. Intermediate columns are materialized to arena memory and read back. Both load-bearing single-core perf mechanisms (devirtualization, fusion) are absent.

## Changes proposed (the corrected shape)

The single-core dispatch becomes a column-capable inline cons-list walk, with no stored function pointer and no per-unit erased slot array. The dispatch order, the plan's RCM-reordered topological order, is realized as the compile-time order of the cons-list rather than as a runtime index into a slot array (the indirect anti-pattern).

1. **Devirtualization by an always-inline walk.** The dispatch walk is extended past resource-only to project a unit's read and write columns alongside its resources (the `ColProject` / `AccumProject` projection the sketch confirmed normalizes), so a fiber's unit sequence monomorphises into one straight-line body with no stored function pointer. The release-ASM check in the sketch FINDINGS confirms the walk devirtualizes (no dispatch symbol survives, zero indirect branches in the dispatch region). `CollectFiber`, `FiberSlot`, and the per-unit `fiber_shim` are deleted; the column-capable walk is the only single-core dispatch path.

2. **Dispatch in the plan's RCM-reordered topological order.** Per the canonical design (consolidation spec Step 5 "RCM reordering -> fiber grouping order + arena layout" and Step 8 "Process WUs in RCM-reordered topo order"), RCM's row reordering is the WU execution order. `group_fibers` (step 8) processes units in that order, so each fiber's unit sequence is in RCM-reordered topological order, and the walk runs that sequence. The order stays topological (every unit after its dependencies), but among units at the same topological depth that a naive topo sort would order arbitrarily, RCM picks the order maximising column reuse between adjacent units. The walk runs the fiber's unit sequence as a compile-time-known cons-list, which is what devirtualizes; a unit whose dependencies admit no topological order is a build-time `BuildError`. (This corrects an earlier framing in this round that had dispatch run in plain registration order with RCM unused. That framing came from intermediate design rounds and a current-code punt comment, both of which strayed from the canonical spec; see the Basis.)

3. **RCM is consumed by dispatch, not arena-layout-only.** RCM produces two orderings, both computed at plan time: the row reordering (the WU execution order, fed to fiber grouping and therefore to dispatch) and the column reordering (`rcm_order`, the arena layout co-locating co-accessed columns). The within-equal-depth row ordering is a real single-core cache effect, not a parallel-only concern: the Approach-E sketch measured a reproducible ~2% between two valid topological orders of the same fan-out. The phase and trunk grouping is parallel-scheduling structure (a phase is a cross-core sync barrier, a trunk is a core assignment): on a single core the barrier and core assignment collapse to program order, but the phase sequence and the within-fiber RCM order are preserved, because both encode dependency and cache-locality structure that holds on one core too. The current code computes `rcm_order` and leaves it unused (the audit's "computed and then unused, the only intended consumer is the dispatch codegen that does not exist"); consuming the row order into `group_fibers` so the fiber sequence is RCM-ordered, and realizing that as the compile-time dispatch order, is the work this arc lands.

4. **Within-fiber stage fusion via scratch-backed internal columns.** A fiber-internal column (written and read entirely inside one fiber) is backed by morsel-sized stack scratch in the Context rather than an arena column, so dead-store elimination collapses the intermediate traffic under fat LTO. Only a fiber's true output columns reach arena memory. This needs the real `classify_columns` Input / Output / Internal split (it marks every store Internal today). This fusion is the mechanism that moves the `#664` perf gate.

5. **Per-fiber morsel-locality is preserved.** The walk dispatches each fiber on its own `morsel_local` bit (morsel-outer when the fiber writes no accumulator, unit-outer otherwise), unchanged from the shipped per-fiber dispatch. The column-capable walk per fiber respects that fiber's morsel-locality choice.

## Basis

- Architect read 1 chose the column-capable inline walk over the fn-pointer-plus-LTO, per-record-transform, and whole-schedule-over-fusing alternatives.
- A trait-solver sketch (`202606051601_column-capable-runfiber-walk`) compiled and ran the column-capable inline walk against the real engine crates (a three-deep heterogeneous column chain, correct), and a release-ASM disassembly confirmed devirtualization.
- Architect read 2 evaluated the order handling and, reasoning from a current-code punt comment (`rcm_order` "is arena layout, not the dispatch order") and the intermediate RCM-wiring and phase-sequential rounds, concluded dispatch should run in plain registration/topological order with RCM unused single-core. That conclusion strayed: the canonical consolidation spec (Step 5 / Step 8) states RCM's row reordering IS the WU execution order, fed to fiber grouping. The intermediate rounds and the current-code comment drifted from the spec; the canonical design is authoritative. Claims 2 and 3 are stated on the canonical position. See the workspace rule `canonical-design-outranks-intermediate-rounds.md`.
- A second sketch (`202606060500_approach-e-schedule-mega`) extended the first from a linear chain to the full single-core shape and confirmed it at bench scale (131072 records): a branching diamond plus a two-column join in one phase, a second phase reading the first phase's output, dispatched morsel-outer with a compile-time morsel constant. Release-ASM disassembly of the whole-schedule body showed zero indirect calls, zero surviving dispatch-helper symbols, the morsel constant baked as an immediate, indexed column loads, and a spill-free auto-vectorized inner body. This is the end-to-end devirtualization confirmation for the multi-phase, morsel-outer walk the SRC CL implements. The phase boundary holds as a single-core sequence point (the cross-record dependency that defines it persists in program order; only the cross-core barrier semantics collapse), matching the phase-sequential dispatch contract. The sketch also benched two topologically-valid within-depth unit orders of the same fan-out and measured a reproducible 2% delta; this is exactly the canonical RCM row-reordering effect (Step 5: "for wide DAGs with fan-out, RCM determines which of those equal-depth WUs get grouped first"), confirming that RCM's row order is a real single-core dispatch-order win, not an arena-layout-only or parallel-only concern.
