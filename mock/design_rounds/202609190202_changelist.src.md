## CHANGE: the one-pointer closure FROM a runtime assert in the test executor TO a gate the api names and the engine forces

Files: `mock/crates/hilavitkutin-api/src/platform.rs`, `mock/crates/hilavitkutin-api/src/lib.rs`, `mock/crates/hilavitkutin/src/scheduler/run_parallel.rs`, `mock/crates/hilavitkutin-api/tests/one_pointer_closure.rs` (new).

`OnePointerClosure<F>` carries `const FITS: ()`, two asserts: `F` no wider than `*const ()`, and no more aligned. `run_parallel` hands the worker closure to `spawn_one_pointer`, a private generic helper that forces `OnePointerClosure::<F>::FITS` and then calls `spawn`, so the closure the engine builds is checked when `run_parallel` is monomorphised. `ThreadPoolApi::spawn`'s rustdoc states the promise and names the gate.

The refusal is a monomorphisation error, so `cargo check` never reports it, and a trybuild fixture, which only checks, compiled both refused closures without complaint when tried. The two refusals are `compile_fail,E0080` doctests on `OnePointerClosure` instead, which build in full: two captured `usize`s (wider), and a zero-sized capture aligned to 64 (no wider, over-aligned). A third doctest shows the one-capture shape building. `tests/one_pointer_closure.rs` pins what the gate admits: a captureless closure, one reference, one pointer-sized value, a value narrower than a pointer, and a zero-sized value, each forced and then run.

Negative controls:
- A second capture added to the engine's worker closure (`core::hint::black_box(widen)` with `widen = c`): `cargo test -p hilavitkutin --test gate2_run_parallel --no-run` fails with `E0080`, "the closure handed to ThreadPoolApi::spawn is wider than one pointer", once per monomorphisation of `run_parallel`. A `let _ = widen;` does not capture under disjoint captures and built clean, which is why the control uses `black_box`.
- The width assert made `true || ...`: the wider-closure doctest fails (it compiles). The alignment assert made `true || ...`: the over-aligned doctest fails. Each assert is therefore the one its doctest depends on.

## CHANGE: the worker count `run_parallel` runs on FROM `worker_count()` as reported TO clamped into `1..=MAX_CORES`

Files: `mock/crates/hilavitkutin/src/thread/class.rs`, `mock/crates/hilavitkutin/src/thread/mod.rs`, `mock/crates/hilavitkutin/src/scheduler/run_parallel.rs`, `mock/crates/hilavitkutin/src/thread/barrier.rs` (comment), `mock/crates/hilavitkutin/tests/gate2_worker_count.rs` (new).

The design was silent; the doc changelist gave it the sentence. `runnable_worker_count` is a `pub const fn` in the thread module, re-exported beside `MAX_CORES`. Its zero and one are arvo's `Identity<Additive>` and `Identity<Multiplicative>` constants on `USize` rather than bare literals, so the function carries no `lint:allow`. `run_parallel` stores the clamped value in `gate2_ncores`, and every later reader (the frame await, the accumulator merge, the worker-side barriers, `Drop`'s exit await) reads that stored value, so all of them agree with the number of closures handed out. The two comments that said the worker count can exceed `MAX_CORES` now say the clamp holds it there. `run_parallel`'s rustdoc described an inline single-threaded form that no longer exists; it now says what the method does, the clamp included.

`gate2_worker_count.rs` tests the clamp at 0, across the range, past the ceiling up to `usize::MAX`, and in a `const`. Three stub executors that report 257, 0 and 1 workers run the fan-in fixture for two frames each; every record of both frames is checked, and so is the number of closures each executor was handed (256, 1, 1).

Negative control: `run_parallel` reading `pool.worker_count()` unclamped. The 257 case dies with `SIGSEGV`: the index past `worker_ctxs` panics while 256 workers already hold pointers into the scheduler the unwind frees. The 0 case fails `frame 0, record 0`: the frame returned with the output column still poisoned.

## CHANGE: `ColdStore` FROM stubs with no tests TO `FIXME:`-marked stubs, tests for what works and catalogued contracts for what does not

Files: `mock/crates/hilavitkutin-persistence/src/cold_store.rs`, `mock/crates/hilavitkutin-persistence/tests/cold_store.rs` (new).

`open`, `flush`, `load` and `snapshot` each carry a `// FIXME:` naming the gap and the BACKLOG section that closes it. Five tests hold what stays true once the file-backed round lands: a store opened over a context that flushed nothing has no tables, an empty string table, resolves no content hash, has nothing to load (`Missing`), and hands back the context it was opened with. Three `#[ignore = "catalogue: ...; tracked: #35"]` contracts state the design's promises: a flushed store is loaded by the next open over the same context, `open` reads the manifest a flush wrote, and a snapshot opens as the store it copied. The first asserts directly; the other two need API the skeleton lacks (a table registration, a snapshot target) and are `unimplemented!` with the contract, the shape `hilavitkutin/tests/adapt_perf_contracts.rs` set. Run with `--ignored`, all three fail. `#35` is the engine round BACKLOG names as what the file-backed I/O waits on; no tracked id of its own exists for the persistence gaps.

Negative control: `load` returning `Ok(())`. `a_fresh_store_has_nothing_to_load` fails.

## CHANGE: `ProgressCounter` FROM untested TO a two-thread publication test

File: `mock/crates/hilavitkutin/tests/progress_counter.rs` (new).

A writer thread stores each record's payload Relaxed and then publishes the count with `ProgressCounter::store`; the reader checks every newly covered payload after each `load`, and that the count never goes back, over 4096 trials of 4096 records. Three smaller tests pin the start value, the default and that a store replaces the value.

Negative control: both orderings in `progress.rs` made Relaxed. On this aarch64 host the publication test failed six runs of six in the debug profile and five of five in release; at 64 trials the debug profile caught it only some of the time, which is why the count is 4096. On a strongly ordered host such as x86_64 the test cannot tell the two apart, and its header says so.

## CHANGE: `BuildConfig::target` FROM `Option<TargetAxis>` TO `Maybe<TargetAxis>`

Files: `mock/crates/hilavitkutin-build/src/config.rs`, `mock/crates/hilavitkutin-build/tests/bootstrap.rs`.

## CHANGE: the `lint:allow` comments in `barrier.rs` FROM moved off their lines by the commit hook's formatter TO back on the lines they govern

Files: `mock/crates/hilavitkutin/src/thread/barrier.rs`, `mock/crates/hilavitkutin/src/thread/class.rs`.

Staging `barrier.rs` for its comment change ran the pre-commit rustfmt over the whole file, which moved six trailing allows (four on fn signatures after `(`, two on `if ... {`) onto lines of their own, and split one `store` call. Each of the four fns now carries `#[rustfmt::skip] // keeps ... the allow ...`, the convention `plan/access.rs`, `graph.rs` and `dirty.rs` already use, and the file is otherwise byte-identical to its `origin/dev` shape apart from the bounds-guard comment. The same hook's clippy fix turned `CoreClass`'s manual `Default` impl into a `#[derive(Default)]` with `#[default] P`; that stays, merged into the one derive line.

Verification: `git grep -nE '^\s*// lint:allow' HEAD -- 'mock/crates/*.rs'` returns nothing, and `grep -c '^#\[rustfmt::skip\]' mock/crates/hilavitkutin/src/thread/barrier.rs` returns 4.
