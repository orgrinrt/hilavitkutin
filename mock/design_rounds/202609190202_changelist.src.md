## CHANGE: the one-pointer closure FROM a runtime assert in the test executor TO a gate the api names and the engine forces

Files: `mock/crates/hilavitkutin-api/src/platform.rs`, `mock/crates/hilavitkutin/src/scheduler/run_parallel.rs`, `mock/crates/hilavitkutin-api/tests/trybuild.rs`, `mock/crates/hilavitkutin-api/tests/trybuild/wide_closure_fails_one_pointer_gate.rs` (new) and its `.stderr`, `mock/crates/hilavitkutin-api/tests/one_pointer_closure.rs` (new).

`OnePointerClosure<F>` carries `const FITS: ()`, an assert that `F` is no wider and no more aligned than `*const ()`. `run_parallel` spawns through a private generic helper that forces `<OnePointerClosure<F>>::FITS` before calling `spawn`, so the closure the engine builds is checked at its monomorphisation. `ThreadPoolApi::spawn`'s rustdoc states the promise and names the gate.

## CHANGE: the worker count `run_parallel` runs on FROM `worker_count()` as reported TO clamped into `1..=MAX_CORES`

Files: `mock/crates/hilavitkutin/src/thread/class.rs`, `mock/crates/hilavitkutin/src/scheduler/run_parallel.rs`, `mock/crates/hilavitkutin/tests/gate2_worker_count.rs` (new).

`runnable_worker_count` is a `const fn` in the thread module. Every later use of the count reads the stored, clamped value, so the frame await, the exit await in `Drop` and the worker-side barriers agree with the number of closures handed out.
