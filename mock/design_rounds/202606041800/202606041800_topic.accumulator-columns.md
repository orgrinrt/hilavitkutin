# Topic: accumulator columns (append surface through dispatch)

**Date:** 2026-06-04
**Phase:** TOPIC
**Scope:** hilavitkutin engine (`mock/crates/hilavitkutin`) + the accessor contract in `hilavitkutin-api`. Round 2 of the column-data-plane arc on branch `feat/hilavitkutin-accumulator-columns`.
**Source topics:** dispatch-build-plan memo (`mock/research/202605282100_engine-dispatch-build-plan.md`, §2 + §5.1 accumulator drain); op's locked input-vs-accumulator model; the column-data-plane round (`202606041631`); the de-risk sketch (`mock/research/sketches/202606041800_accumulator-append-selector/`).

The column-data-plane round landed INPUT columns: buffers sized to a build-time record count, populated before the frame, read and written by index. This round lands the second half of op's locked model: ACCUMULATOR columns. An accumulator is written by APPEND during the frame, growing from zero toward a capacity; a later PassEnd drain reads the populated prefix into persistence. op chose this two-kind surface deliberately rather than a single global record count.

The append must work under the engine's `&self` accessor discipline (accessors never take `&mut self`, so LLVM does not reorder writes across fused WorkUnits), which means the per-accumulator live-length counter advances through interior mutability, not a mutable borrow.

## The locked decisions

Two design questions were resolved with a neutral domain-expert read (`feature-dev:code-architect`, agent ac4b8a73015e46b8d) plus a trait-solver and lifetime sketch (`mock/research/sketches/202606041800_accumulator-append-selector/`, verdict WORKS). Both converged on the same four answers.

**Kind representation (A1): a distinct `Accum<T>` marker.** Sibling of `Resource<T>` / `Column<T>` / `Virtual<T>`, with its own binding node, selector, projection, and accessor. The alternative (a role or mode of `Column<T>`) collapses two semantically distinct operations (indexed random-write vs ordered append) onto one marker, making the `Contains<...>` membership proof ambiguous (read vs write vs append) and forcing a runtime flag or a forbidden specialization. The engine already has three parallel per-kind markers; `Accum<T>` is the fourth on the same pattern.

**Live-length mechanism (B): a `Cell<USize>` in the accumulator binding.** The `&self` append accessor reads the current live count, writes the record at that offset, and advances the count. Writing through a pointer derived from a shared reference requires `UnsafeCell`; `Cell<USize>` satisfies that, is `no_std`, has no allocator dependency, and is non-atomic (correct for single-core-first). Multi-core swaps it for an atomic in a later round.

**Projection bundle (C): a fourth `EngineCtx` bundle with a parallel `AccumSelector` / `AccumProject`.** Mirrors `ColSelector` / `ColProject`. The wrinkle the sketch de-risked: a resource or column projection copies a `Copy` pointer and retains no borrow, but an accumulator projection yields a reference to the live-length cell, retaining a `'frame` borrow of the bindings. The accumulator bundle therefore projects from the same `bindings: &'frame A` source the resources use (already `'frame`-tied in `EngineCtx::project`), via a GAT `AccumProject` trait (`type Out<'s>`); the column source can stay a shorter borrow. The sketch confirms the three selectors resolve unambiguously over the interleaved bindings and the borrowed-cell projection composes with the copy-pointer projections from one `&'frame bindings`.

**Capacity source (D): reserve to the build-time record count this round.** An accumulator reserves `record_count` records at build (the same `ColumnStorage::reserve` path as an input column); the live-length grows from zero as WorkUnits append, and the PassEnd drain reads `[0, live_length)`. A distinct per-accumulator capacity dimension is deferred (the same deferral the column round made for the capacity-versus-live-count split). Failure mode to document: a frame appending past `record_count` saturates at capacity (a checked bound), acceptable single-core-first.

## Round changes (accumulator append through dispatch)

1. **`Accum<T>` marker** in `hilavitkutin-api/src/store.rs`: sibling of `Column<T>`, `#[repr(transparent)] PhantomData<T>`, `Copy`, `BuilderInput` (`Init = ()`, `Dispatch = StoreDispatch<Self>`), `HasTrivialCtor`.

2. **`AccumBinding<T, Tail>`** in `resource/bindings.rs`: holds the reserved buffer `ColumnPtr<T>` + a `Cell<USize>` live-length; one new `BindingsFor` arm (`Sv<Accum<T>>` to `AccumBinding`) and one new `DrainStores` arm reserving `record_count` records (bound `T: ColumnValue`), recording the real `column_ptr_mut::<T>(id)` at a continued `StoreId`; zero-record/ZST handled like the column arm.

3. **`AccumSelector` + `AccumProject`** in `dispatch/engine_ctx.rs`: `AccumSelector<T, Here>` on `AccumBinding<T>`, `There<I>` pass-through across all node kinds; `AccumSelector` `There` pass-through added to the existing node kinds; a GAT `AccumProject<Set, Indices>` (`type Out<'s>`) mirroring `ColProject`, recursing the `Accum<T>` members of the Write set. A fourth `EngineCtx` bundle (the write-set accumulator bundle) projected from the `'frame` bindings; one new `project` generic + bound.

4. **`AccumWriterApi<W>` + `ResolveAccumAppend<T, I>` + `HasAccumWriter`** in `hilavitkutin-api/src/context.rs`: `append<T, I>(&self, v: T)` bounded `W: Contains<Accum<T>>` + `Self: ResolveAccumAppend<T, I>`, and a `len<T, I>(&self) -> USize` reader; the `provider_generic!` accessor alias. The `EngineCtx` impls them by resolving the accumulator bundle's `AccumSelector` witness, reading the live count, writing at the buffer offset, advancing the count.

5. **`CollectFiber` / `fiber_shim`** in `dispatch/fiber_codegen.rs`: project the accumulator bundle alongside the resource and column bundles (one more index in the per-unit witness tuple); a WorkUnit with no accumulators in its Write set infers an empty accumulator bundle and dispatches exactly as before.

## Test plan (red-first)

A WorkUnit declares `Accum<T>` in its Write set and appends K values during `execute`; the test builds the scheduler with a record count covering K, runs it, and reads the accumulator buffer back (through a hidden accessor on the binding, or a consumer WorkUnit) to assert the K values landed at indices `[0, K)` in append order and the live-length equals K. Red first: a WorkUnit appending to an `Accum<T>` cannot satisfy the current dispatch bound (no accumulator projection exists), so the file does not compile; once the bundle is projected but before the drain reserves a real buffer, the append writes through a dangling placeholder. Both precede the green round-trip.
