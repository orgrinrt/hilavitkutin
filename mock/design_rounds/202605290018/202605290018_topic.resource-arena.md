# Topic — resource arena, the data-plane keystone first slice (Phase B / B2a)

**Date:** 2026-05-29
**Phase:** TOPIC
**Scope:** route store values onto a `Stores`-aligned `StoreValues` list under the single `.with` verb; build a `ResourceArena` from registered `Resource<T>` values via the consumer `MemoryProvider`; reshape `Scheduler` to own the arena and deallocate on `Drop`. Resources only (Column buffers are B2b).
**Source:** the validated design in `mock/research/202605282319_phase-b-data-plane-design.md` (corrected B2 section) and the compiled feasibility sketch `mock/research/sketches/202605290002_builder-kind-dispatch.md`.

This is the data-plane keystone's first real slice. B1 made the builder retain a registered store value instead of dropping it; B2a moves that value into scheduler-owned memory so a future Context (B3) can hand a WorkUnit a real reference. The build order is dependency-forced: storage exists before anything reads it.

Two design questions were resolved and validated this arc. First, the staged value list and the `Stores` access set are not aligned (every `.with` adds to the staged list; only store inputs add to `Stores`), so the value drain cannot walk them in lockstep, and searching the heterogeneous staged list for a typed carrier is coherence-incoherent without specialization. The fix preserves the documented single `.with` verb: a `RouterKind` tag on each dispatch router plus a `Place<P>` view keyed on the tag routes store carriers onto a `Stores`-aligned `StoreValues` list at registration time, with workunit and platform values dropped (their type stays tracked in `Wus` / `Platform`). The mechanism compiles on stable Rust (the sketch proves it). Second, the `MemoryProvider` is supplied as an explicit `build(memory_provider)` argument rather than extracted from a list, because the platform accumulator is type-level only and a list search for a maybe-present provider needs negative trait bounds that stable Rust lacks.

The drain then walks `Stores` and `StoreValues` in lockstep (same order, same length, no search), allocating one block per `Resource<T>` and recording a `ResourcePtr<T>`. The `Scheduler` owns the arena and the provider, and deallocates every block on `Drop` after running each value's destructor.

Resources are the whole of B2a. Column buffers need a record count that the plan phase produces, so column allocation is B2b; B2a leaves column and virtual arena nodes as no-allocation placeholders.

## Current state

- `mock/crates/hilavitkutin/src/scheduler/mod.rs`: `SchedulerBuilder<Wus, Stores, Platform, Staged: StageList>` (B1) retains every registered value on `Staged`; `build()` drops `Staged` and returns `Scheduler<DefaultRunCfg>` (a `{ _cfg, plan_dirty, plan_cache }` struct).
- `mock/crates/hilavitkutin/src/scheduler/stage.rs`: B1's `StageList` / `StageEmpty` / `Stage<H, T>` (all-values list).
- `mock/crates/hilavitkutin-api/src/builder_input.rs`: `BuilderInput { type Init; type Dispatch; }`; routers `UnitDispatch` / `StoreDispatch` / `PlatformDispatch` / `RunCfgDispatch` (and `KitDispatch` in the kit crate). No kind tag yet.
- `mock/crates/hilavitkutin-api/src/store.rs`: `StagedResource<T>(T)` with `into_inner`; `Resource<T>` / `Column<T>` / `Virtual<T>` markers.
- `mock/crates/hilavitkutin/src/resource/provenance.rs`: `ResourcePtr<T>` / `ColumnPtr<T>`.
- `mock/crates/hilavitkutin-api/src/platform.rs`: `MemoryProviderApi` (`allocate` / `deallocate` / `protect`).
- No arena exists; the builder discards store values at `build()`.

## Changes proposed

1. api `builder_input.rs`: add `RouterKind { type Kind; }` with disjoint tags `StoreKind` / `UnitKind` / `PlatformKind` (Kit and RunCfg routers tagged for drop in B2a), impl it for each router. Add a `Place<P>` view keyed on the tag (`type Next<L: StoreValues>`, `fn place`) with non-overlapping per-tag impls.
2. New `scheduler` store-value list: `StoreValues` sealed cons-list (`SvEmpty`, `Sv<H, T>`) holding store carriers in `Stores` order. Replace the B1 `Staged` builder parameter with `StoreValues`; `.with` routes via `RouterKind`/`Place` (store carriers retained, others dropped). Update B1's `builder_retains_registered_value` test to read `StoreValues`.
3. New `resource/arena.rs` (engine crate): sealed `ArenaFor<S: AccessSet> { type Arena; }` mapping `Stores` to an arena cons-list (`ArenaTail`, `ArenaResourceNode<T, Tail>`, `ArenaColumnNode<T, Tail>` placeholder, `ArenaVirtualNode<T, Tail>`); a sealed `DrainStores` walking `Stores` + `StoreValues` in lockstep to allocate resources via `MemoryProviderApi` and record `ResourcePtr<T>`; a sealed `DropArena` walk. `BuildError::AllocationFailed`.
4. `Scheduler<Cfg, Stores, M>`: add `Stores` (bound `AccessSet + ArenaFor`) and `M: MemoryProviderApi` params, `arena` and `memory_provider` fields, a `Drop` impl (`drop_in_place` each resource value then `deallocate`). `build<M>(self, memory_provider: M) -> Outcome<Scheduler<DefaultRunCfg, Stores, M>, BuildError>`. `type BuiltScheduler<Stores, M>` alias for explicit namers.
5. Tests (engine, with a stack-backed counting test `MemoryProvider`): `resource_arena_round_trip`, `resource_arena_drop_deallocates`, `resource_arena_multiple_resources`, `resource_arena_drop_runs_destructor`.

Outcome: a registered `Resource<T>` value lives in scheduler-owned memory after `build()` and is reachable via its `ResourcePtr<T>`; every allocation is paired with a deallocation on drop, with the value's destructor run first. The single `.with` verb is preserved. B2b adds column buffers; B3 builds the per-WorkUnit Context over the arena.
