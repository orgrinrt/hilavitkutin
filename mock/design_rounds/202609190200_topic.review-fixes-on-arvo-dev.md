## The findings, and what each is held to

### One: the one-pointer closure is a promise nothing checks at compile time

`mock/crates/hilavitkutin/DESIGN.md.tmpl`, Platform implementations, says the engine hands the executor one pointer-sized closure per worker, so an executor can carry it without allocating. `OsThreadPool` used to enforce that with an associated-const assert at monomorphisation; it was deleted with the std tier, and `ThreadPoolApi::spawn` takes any `FnOnce() + Send + 'static`. The only check left is a runtime assert inside the test executor. The design's sentence is a contract between the engine and every consumer executor, so it belongs in the api as a named compile-time gate, forced by the engine at its one spawn site, in the pattern of `UnitsFitGate2`. Putting it in the api rather than privately in the engine lets an executor force the same gate on its side and lets a compile-fail fixture exercise it. The ruling is untouched: the api still ships no executor.

### Two: sentences that still give the engine threads to own

`mock/agent/rules/cookbook.md.tmpl` says the engine provides the `ThreadPoolApi` implementation, which is what op ruled against. The same class: `mock/DESIGN.md.tmpl` has `Scheduler::Drop` joining handles, where the code waits on an exit counter and holds no handle; `mock/PRINCIPLES.md.tmpl`, Pre-allocated thread pool, pins each pool thread to a core, which the backlog gives to the consumer executor; the module tables in `mock/DESIGN.md.tmpl` and the engine design list core pinning as the thread module's; `mock/agent/rules/implementation.md.tmpl` lists core pinning as a plan parameter. The engine chooses a core assignment and the executor pins, so each says core assignment. `mock/agent/MAIN.md.tmpl` says threads are spawned once at pipeline construction without saying through whose executor. The trunk-to-core ownership sentences in the engine design (`core-pinned unit`, `core-pinning of a following round`) are about which core owns a trunk, not about OS threads, and stay.

### Three: a std type in a no_std design

`mock/crates/hilavitkutin-build/DESIGN.md.tmpl`, Entry point, hands hardware topology to `LazyLock` in the scheduler. The engine is `no_std`; topology is read by the thread module's `classify_cores` through the platform's own interfaces.

### Four: persistence's cold store has no tests left

The previous round deleted five tests that restated the skeleton bodies. What remains unguarded is real behaviour that survives the real impls: a freshly opened store has an empty manifest and string table, has nothing to load, and hands back the context it was given. The stubbed `flush` and `snapshot` carry no `FIXME:`, and nothing states what they are meant to do. The design's Flush coordination section says what: a flushed store's data is what a later load finds, and a snapshot copies the files. Those go in as catalogued-red contracts in the shape `tests/adapt_perf_contracts.rs` set.

### Five: `ProgressCounter` has no test

It is the Release-store and Acquire-load pair domain 17 builds on. A two-thread message-passing test holds it to that.

### Six: an em-dash

`mock/crates/hilavitkutin/src/dispatch/engine_ctx/mod.rs` header. The branch's added lines are grepped for others.

### Seven: an executor reporting more than `MAX_CORES` workers panics

`run_parallel` indexes `worker_ctxs[c]` for every `c < worker_count()`, and `worker_ctxs` holds `MAX_CORES` (256). At 257 it panics. At 0 it spawns nothing, publishes a frame nobody runs, and returns as though the frame ran. The design is silent on both. The code already expects a worker count past `MAX_CORES` (`thread/barrier.rs` bounds its idle slot for exactly that, and `classify_cores` clamps), so the engine clamps the count it runs on into `1..=MAX_CORES`: past the ceiling the extra workers are never handed a closure, and at zero the engine still hands the executor one, since `spawn` submits work whatever the executor reports. The engine design gains the sentence.

### Eight: persistence's dependency list and the lint comment above it

The persistence design lists `rkyv`, which the crate does not yet depend on, and omits `hilavitkutin-api`, which op ruled it builds on. `mock/mockspace.toml` says "no cross-deps" over the persistence line that now allows two.

### Nine: a test that asserts nothing

`hilavitkutin-extensions-macros/tests/lto_smoke.rs` has a `#[cfg(not(unix))]` test that prints a line. It becomes a catalogue ignore naming the gap.

### Ten: `Option` beside `Maybe`

`hilavitkutin-build`'s `BuildConfig::target` is an `Option` with a `no-bare-option` allow, next to `Maybe` parameters. The type-surface rule names `notko::Maybe`, notko's `Maybe` has the `Default`, `Clone` and `Debug` the struct derives, and nothing in the build design asks for `Option`, so the field is `Maybe` and the allow goes.
