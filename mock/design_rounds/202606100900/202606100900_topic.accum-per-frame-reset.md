# Per-frame accumulator reset in run()

## What this round does

`Scheduler::run` reuses one built scheduler across many frames (the canonical schedule-once-reuse model). An `Accum<T>` binding holds a `Cell<USize>` live-length that the append accessor advances during a frame; the drain zeroes it once, at `build()` time. There is no per-frame reset. So the second frame starts at the live offset the first frame left behind: every append lands past the prior data, and once the live-length reaches the reserved capacity the appends saturate (drop). One built scheduler therefore produces correct accumulator output on frame one and broken output on every frame after.

This round makes `run` reset every accumulator's live-length to zero at frame start, so each frame appends into a fresh buffer. The reset is a type-level `ResetAccumulators` walk over the bindings cons-list: a no-op at every non-accumulator node, a single `Cell` write at each `AccumBinding`. For an accumulator-free carrier (the common case, the morsel-outer path) the walk visits no `AccumBinding` and compiles to nothing.

## Why this is design, not a stopgap

The schedule-once-reuse model is canonical (`DESIGN.md.tmpl:470` "Schedule reuse across frames (construct once, reuse)"; CLAUDE.md "Schedule once, reuse across frames"). Per-frame mutable state that the engine owns must therefore be reset at frame boundaries by the engine, not by the consumer and not by accident. The accumulator live-length is exactly such state. A frame lifecycle that leaves it carrying the prior frame's offset is a correctness gap in the reuse model, and #665 names it as a Gate-1 gap ("single-core runtime to COMPLETION, no placeholders"). This is not greening a red perf arm: the accumulator perf arm (#664, ~6.3x) stays red and is owned by a later gate. This round fixes a correctness bug in the frame lifecycle that the perf bench currently masks with a hand reset in its timed closure.

## What it removes downstream

`mock/benches/engine_vs_std/src/accumulator.rs` zeroes the live-length cell before each timed `run` as a documented accommodation for this exact missing reset. Once `run` performs the reset, that accommodation is removed (the bench measures real per-frame append work without hand-resetting). The bench change is a sibling follow-up in the same GATE-1 branch, recorded in the src changelist's lock criteria, not gated on this round's doc/src edits to the engine crate.

## Test shape (fail-first)

A new integration test builds a scheduler with one `Accum<T>` and an appending WorkUnit, runs two frames, and asserts the second frame's post-run live-length equals the per-frame append count (not twice it, and not saturated at capacity). Before the reset lands the test is red (the second frame's live-length is the sum of both frames' appends, or the saturated capacity); after, green. The existing single-frame `accum_dispatch` round-trip stays green unchanged.

## Drive-shape note

The accumulator-bearing carrier dispatches unit-outer (one full-range walk); the reset happens once, at `run` entry, before either drive shape. `run_fused` is the linear-fusion path for accumulator-free chains and grows no accumulator, so it needs no reset; this round touches `run` only.
