# D6: a standing ASM-checklist gate on the emitted dispatch monos

GATE-1 single-core dispatch is functionally complete: the type-level `RunFiber`
walk devirtualises, the linear-chain fusion (`run_fused`) keeps intermediates in
registers, and incremental skip (E7) gates clean WUs by a predicated branch.
Every one of those properties was confirmed the same way: build a release mono,
disassemble it, and read the instruction stream for the absence of an indirect
call and the presence of indexed, stack-free, immediate-morsel inner loops. That
disassembly check is currently an ad-hoc step run by hand per sketch and a
bench-side module (`mock/benches/src/disasm_5check.rs`, the Topic-4 axis-A
five-check method). D6 makes it a standing regression oracle: a gate that fails
the build when a future change reintroduces an indirect dispatch slot, a
stack-spilled inner loop, or a non-baked morsel constant into the real engine's
emitted dispatch functions.

The reason this gate must exist before any threshold tuning (r1 §189) is that the
whole single-core perf story rests on devirtualisation. The `#664` perf gate
measures throughput against optimal std; it catches a regression only as a
slowdown, after the fact, and only at the sizes it benches. The ASM gate catches
the *cause* directly: the moment a `blr` (aarch64) or `callq *` (x86_64) appears
in a dispatch mono's inner body, dispatch is no longer devirtualised, and the
gate says so by symbol, regardless of whether the slowdown happened to show up in
a particular bench size. It is the mechanical complement to the perf oracle: perf
measures the outcome, the ASM gate measures the mechanism.

## What the gate asserts

The five checks already exist and are platform-aware
(`disasm_5check.rs:124-247`); D6 reuses them rather than reinventing. Stated as
the contract the emitted dispatch monos must hold:

1. Zero indirect call in the inner body. `blr xN` (aarch64) / `callq *rN`
   (x86_64). This is the load-bearing check: an indirect call means a stored
   function pointer survived, dispatch is type-erased, devirt is lost. A FAIL
   here is a hard gate failure.
2. Indexed addressing on column loads (`ldr xN, [xBase, xIdx, lsl #s]` /
   `mov ..., [rBase + rIdx*s]`). Confirms morsel record access is a base-plus-
   scaled-index load, not a recomputed address.
3. No stack-relative accesses in the inner loop (`[sp, ...]` / `[rsp ...]`).
   A spill in the hot loop means a value that should have stayed in a register
   round-trips memory.
4. Immediate-constant morsel size baked where the plan fixes it as a constant
   (`#256` / decimal immediate). Where the morsel is a runtime plan param (R6
   adaptive), this check is scoped to the symbols where the constant genuinely
   bakes, not the adaptive ones.
5. No direct `bl` to morsel/fiber/`wu_fn` helper symbols: the walk inlines the
   per-WU `invoke_wu_in_fiber` and the morsel loop, so a surviving direct call to
   a named helper means inlining did not happen.

Check 1 is the gate. Checks 2 to 5 are quality assertions: a FAIL there is a
regression worth surfacing but its severity (hard-fail vs reported) is a per-check
decision the doc CL settles, because some are legitimately shape-dependent (an
adaptive-morsel symbol will not bake an immediate).

## The genuinely open design questions

These are what the doc CL must settle; the topic only frames them.

### Which symbols does the gate cover, and how are they named under LTO?

The real dispatch monos are `Scheduler::run`'s and `run_fused`'s monomorphised
bodies plus the `RunFiber::run` / `run_gated` walk they inline. Under
`lto = "fat"` + `codegen-units = 1` (the shipping profile) these inline into the
caller and carry mangled, instantiation-specific symbol names; there is no stable
`run_fused` symbol to objdump. The sketches solved this with an
`#[inline(never)]` named entry wrapping the dispatch call (e.g. the
`gated_run` / `bench_entry` pattern), which forces one stable symbol that still
inlines everything *below* it. D6 needs a small set of such named fixture entries
exercising the representative dispatch shapes (a column chain, a fused chain, an
accumulator carrier, a dirty-gated frame), each `#[inline(never)]` so the gate has
a stable symbol to read, while the dispatch body inside still fully inlines. The
question the doc CL answers: where do these fixtures live (a dedicated
`asm_gate` fixture crate / bench, or a `#[cfg(...)]` test entry in the engine),
and which shapes are the minimum representative set.

### Where does the gate run, and what reuses the check module?

`disasm_5check.rs` lives in the bench crate and runs post-bench, reading the
bench's own release dylib. Options for the standing gate: (a) a dedicated bench
binary whose only job is to build the fixtures, objdump them, run the five
checks, and exit non-zero on a check-1 FAIL, runnable via `cargo mock` / CI; (b)
an integration test that shells out to build a release fixture and objdumps it
(heavier, a test that invokes cargo); (c) lift the check module into a shared
location both the bench and the gate import. The doc CL picks; the leaning is (a)
plus (c) (a dedicated gate bin reusing a lifted check module), because the check
logic is already proven and a bench-shaped binary is the established shape for
"build a release artifact and read its asm".

### Platform coverage

The checks already carry both aarch64 and x86_64 patterns. The dev machine is
aarch64 (objdump via Xcode CLT, otool fallback); CI is likely x86_64 Linux. The
gate must pass on both: the check functions already branch on the instruction
forms, so the open question is only operational (is `objdump` present in the CI
image, or is the gate gated on a `cfg`/env that disables it where the tool is
absent), not a pattern-coverage question.

### What is in scope for GATE-1 vs deferred

D6 gates the single-core dispatch monos that exist today. The N-core per-core
program (GATE-2) and the meta-WU self-hosting loop (E4) are not yet emitted, so
their symbols are out of scope until those land; the gate grows to cover them
when they do. D6 ships the gate for the shapes GATE-1 actually emits: the
column-chain `run`, the fused `run_fused`, the accumulator unit-outer `run`, and
the E7 dirty-gated `run_gated`.

## Why this closes GATE-1

Per r1 §7 the GATE-1 dispatch items are the devirtualising single-core walk
(D1), the within-fiber fusion (D2/D4), incremental skip (E7), and the ASM gate
(D6) that keeps all of them honest. The first three are shipped (rounds through
202606111200). D6 is the last: with it, GATE-1 single-core dispatch is complete
and guarded, and the GATE-1 PR can land the whole arc with a standing regression
oracle attached. D6 is mechanical (the checklist is proven, the patterns exist,
the fixture pattern is the same `#[inline(never)]` entry the sketches used); the
work is wiring it into a standing gate, not discovering whether it can be done.
