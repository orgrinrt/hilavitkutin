# Lift the engine plan and thread const dimensions to Cap

The engine's plan and thread layers size their const-generic dimensions with
bare `usize` const params: `DependencyGraph<const MAX_UNITS: usize, const
MAX_EDGES: usize>`, `PlanInputs<const MAX_UNITS: usize, const MAX_STORES:
usize>`, the eight-param `compute_execution_plan`, the thread pool, and roughly
forty more structs, impls, and free functions. Every one carries a
`lint:allow(no-bare-numeric) lint:allow(arvo-types-only)` keyed to task #121.

This round lifts that whole vocabulary to `arvo::Cap`, removing the bare
primitive from the engine's const-generic surface and bringing it in line with
`no-bare-primitives` (which applies on the hilavitkutin side, not only arvo) and
`harness-the-type-system` (climb the discipline ladder rather than weld one
primitive in place).

## Why the deferral no longer holds

The bare `usize` was a deliberate, tracked deferral (#121: "revisit when rustc
const-eval stabilises"). The reason was real: Rust's `[T; N]` array-length
position requires a `usize`-typed const, the engine sizes its plan arrays
directly by the param (`[USize; MAX_UNITS]`), and using `Cap` instead requires
two unstable features (`adt_const_params` so `Cap` is a valid const-param type,
`generic_const_exprs` so arrays size via `[USize; cap_size(MAX_UNITS)]` and
every generic item carries `[(); cap_size(MAX_UNITS)]:`). The engine had neither
feature enabled, so the plan layer chose raw `usize` rather than pull two
unstable features in purely for the const-param's type.

That premise is overtaken by the arvo-analysis-wiring work. The CSR adapter
(round 202605290312, now archived and re-planned as the follow-on round) returns
`arvo_sparse::CsrBidirectional<{...}, EdgeKind>` parameterised on the engine's
plan dimensions, which requires `generic_const_exprs` in the engine regardless.
Once the engine is a GCE crate for that reason, keeping the plan dims as raw
`usize` stops buying anything: the cost #121 was waiting to avoid is paid for the
adapter anyway, and `adt_const_params` is already enabled in the sibling
`hilavitkutin-api` crate and is ALLOWED/sound per the unstable-feature soundness
sweep. arvo's own `Csr<const ROWS: Cap, const NNZ: Cap, W>` and `BitMatrix<W,
const N: Cap>` are the proof that `Cap`-as-const-param works today.

Lifting before the adapter lands also makes the adapter cleaner: with the plan
dims already `Cap`, `to_csr_bidirectional` returns `CsrBidirectional<MAX_UNITS,
MAX_EDGES, EdgeKind>` with the params passing straight through to arvo's
`Cap`-typed positions, instead of bridging `usize` through `cap(MAX_UNITS)` in
the signature.

## Scope

The lift covers the full plan + thread const-dimension vocabulary, roughly
thirteen params across roughly forty structs, impls, and functions in
`plan/{graph,inputs,unit,phase,trunk,fiber,access,dirty,column,core_program,steps,mod}.rs`
and `thread/{mod,assignment}.rs`: `MAX_UNITS`, `MAX_EDGES`, `MAX_STORES`,
`MAX_FIBERS`, `MAX_PHASES`, `MAX_TRUNKS`, `MAX_LANES`, `MAX_COLUMNS`,
`MAX_COLUMNS_PER_FIBER`, `MAX_CORES` (the generic param, not the
`thread/class.rs` module constant `MAX_CORES: usize = 256`), and the per-core
trio `MAX_PHASES_PER_CORE` / `MAX_TRUNKS_PER_CORE` / `MAX_FIBERS_PER_CORE`.

## Out of scope

Internal indexing `usize` (the `end_for(i: usize) -> usize` helper, loop
counters, intermediate index arithmetic) is tracked separately under #72 and
stays as-is. That is a weaker case (pragmatic indexing inside method bodies, not
a public const-generic surface) and is not part of this round. The module
constant `thread/class.rs:47 MAX_CORES: usize = 256` is a fixed array size, not
a generic param, and stays `usize`.
