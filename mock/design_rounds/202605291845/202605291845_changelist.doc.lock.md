# Design changelist

This is a source-focused round. No `*.md.tmpl` template prose changes are
required: the lift changes const-param TYPES (`usize` to `Cap`), not type NAMES,
so `DependencyGraph`, `PlanInputs`, `ExecutionPlan`, and the rest stay the same
pub items the `design-doc-source-mismatch` lint tracks. The design rationale
lives in the topic; this changelist records the mechanical design of the lift so
the src changelist can claim it precisely.

## The transform

Every plan and thread const-generic DIMENSION parameter moves from
`const MAX_X: usize` to `const MAX_X: arvo::Cap`. A parameter is a dimension
parameter when it sizes a fixed-capacity array. The four mechanical rules:

1. Parameter declaration. `const MAX_X: usize` becomes `const MAX_X: Cap`, on
   every struct, impl block, and free function that declares it. The
   `lint:allow(no-bare-numeric) lint:allow(arvo-types-only) ... tracked: #121`
   comment on the lifted site is removed; the bare primitive it excused is gone.

2. Array sizing. `[T; MAX_X]` becomes `[T; cap_size(MAX_X)]`. Rust's array-length
   grammar requires a `usize`-typed const, and `cap_size(c: Cap) -> usize`
   (`arvo_tensor::cap_size`) is the projection. This is the same shape arvo's own
   `Csr` uses: `row_ptr: [USize; cap_size(ROWS)]`.

3. Where-bounds. Any generic item (struct, impl, fn) that names a
   `[T; cap_size(MAX_X)]` array, directly or through a type it constructs,
   carries `[(); cap_size(MAX_X)]:` for each such `MAX_X`. The bound is viral:
   `compute_execution_plan` declares eight dimension params and so carries the
   bounds for the subset its arrays and called functions need. The compiler is
   the authority on exactly which bounds each item requires; the rule is to add
   the bound the compiler demands, never to silence the demand.

4. Call sites. Anywhere a plan or thread type is instantiated with a concrete
   `usize` dimension (the scheduler entry, tests, examples), the literal `N`
   becomes `cap(N)` (`arvo_tensor::cap`, `cap(n: usize) -> Cap`). `cap` and
   `cap_size` are exact inverses (`cap_size(cap(n)) == n`), so every array keeps
   the length it had before the lift; this is a type-surface change, not a
   capacity change.

## Crate-level prerequisites

The engine crate root `mock/crates/hilavitkutin/src/lib.rs` gains two feature
gates:

- `#![feature(generic_const_exprs)]`. Required for rule 2 (const-fn call in
  array-length position) and rule 3 (the `[(); cap_size(MAX_X)]:` bounds). WATCH
  tier per the unstable-feature soundness sweep (task #626); the engine already
  carries `#![allow(incomplete_features)]`. A justifying comment above the gate
  records the WATCH disposition, matching the discipline applied at arvo's
  `cap.rs` use site.
- `#![feature(adt_const_params)]`. Required so `Cap` is a valid const-generic
  parameter type. ALLOWED tier per the sweep; already enabled in the sibling
  `hilavitkutin-api` crate.

The engine gains an `arvo-tensor` dependency for `cap` and `cap_size`. The
workspace `[workspace.dependencies]` table gains the git entry and the engine
`Cargo.toml` references it with `.workspace = true`. `cap_size` is also reachable
through `arvo_bitmask::cap_size` (a re-export the engine already has), but since
`cap` lives only in `arvo-tensor` and is needed at call sites, the engine takes
the `arvo-tensor` dependency and imports both from there.

## Boundary held

Internal indexing `usize` is out of scope (tracked #72): the `end_for(i: usize)
-> usize` helper, loop counters, and intermediate index arithmetic inside method
bodies stay `usize`. The `thread/class.rs` module constant `MAX_CORES: usize =
256` is a fixed array size, not a generic parameter, and stays `usize`. The lift
covers the const-generic DIMENSION-PARAMETER surface only.
