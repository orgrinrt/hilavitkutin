# Doc changelist: GATE-2 accumulator unit-outer threaded path (deviation §9)

**Date:** 2026-06-07
**Phase:** DOC
**Round:** 202606071933 (GATE-2 accumulator unit-outer threaded path)
**Sketch:** `mock/research/sketches/202606071945_gate2-accumulator-percore-region-merge/` (outcome WORKS)

## Current state

The engine DESIGN already states the canonical convergence-accumulator intent
(`mock/crates/hilavitkutin/DESIGN.md.tmpl:401-403`): "each head+tail thread gets
its own stack-local accumulator. Merged after convergence (addition for additive,
sequential fallback for non-commutative)." It does NOT yet describe how
`run_parallel` realizes that intent on the shipped no-alloc `Accum` /
`AccumColPtr` / append surface, nor that `run_parallel` currently dispatches only
the morsel-local pure-RAW path (accumulator-bearing unit-outer fibers do not run
threaded). The §8 head+tail convergence text (`:474-476`) covers the morsel-local
single-trunk record-range split but not the accumulator variant.

## Changes proposed

One doc edit to `mock/crates/hilavitkutin/DESIGN.md.tmpl`, expanding the
convergence-accumulator paragraph (`:401-403`) into the concrete `run_parallel`
realization the sketch proved:

- Each core appends into a disjoint sub-region of the single reserved capacity
  buffer: region c is placed at element offset `lo_c` (the §8 record-slice start,
  `per = ceil(total/ncores)`, `lo = (c*per).min(total)`, `hi = (lo+per).min(total)`)
  with cap = `hi_c - lo_c` and its own live-length cell. Offset `lo_c` (not a
  separate `c*per_cap` buffer) tiles the same reserved buffer exactly, since the
  accumulator reserves cap = build-time record count = the global `<=1`-append-
  per-record bound and the slice sizes sum to total.
- Disjoint byte ranges plus per-core cells mean no shared mutable state: the
  append path (`resolve_append`) is unchanged; only the per-core handle projection
  is new. The binding's live-length cell stays single-writer (need not become
  atomic for this path); only the per-core live counts cross to the merge, a
  write-before-barrier / read-after-barrier handoff on the existing §4 waist
  barrier.
- After the phase, a forward compaction concatenates the per-core live prefixes in
  ascending core order into `[0, sum live)`. The write cursor never exceeds `lo_c`,
  so the copy is forward-safe; order is preserved because each core walks an
  ascending contiguous record slice and appends in record order. The result is
  byte-identical to the single-core unit-outer `run()` append.
- First slice scopes the threaded accumulator path to the `<=1`-append-per-record
  convergence pattern (the head+tail-convergence eligibility at `:474-476`).
  Multi-append-per-record needs region cap = per-region worst case, not slice size;
  that capacity policy is a follow-up. Non-commutative resource accumulation skips
  convergence and stays single-core (the existing `:403` sequential fallback);
  routing needs a commutativity hint (domain 08), defaulting to single-core for any
  accumulator until the hint is reachable at dispatch.

No new backticked type names are introduced by this doc edit (the realization uses
the already-documented `Accum`, `AccumColPtr`, `AccumBinding`, `run_parallel`), so
the design-doc-source-mismatch lint surface is unchanged.

## Lock criterion

The expanded paragraph reads as the concrete realization of the existing
convergence-accumulator design, consistent with spec `:1750-1766` and `:770-771`,
and names no type that does not exist in source.
