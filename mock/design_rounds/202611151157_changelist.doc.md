## The points to look at

A build script that writes into the source tree is what cargo's own guidance advises against, and this design does it once per workspace, outside every package directory, for two files that are then committed. The alternative is a step by hand or a tool, and the first remark of 15 November rules the step by hand out.

The crate is `no_std` by the ratified tenet `every_crate_is_no_std_with_no_allocation_and_the_consumer_provides_the_memory_provider` and writes text only, by the provisional tenet `the_build_crate_is_no_std_takes_the_profile_and_target_strings_as_parameters_and_writes_its_text_into_a_formatting_writer`. `script!` keeps to both: what to write and when is decided by functions of the crate over a `core::fmt::Write`, and the file reads and writes and the question to cargo are code the macro expands in the consumer's script, which is std by nature. No `extern crate std` and no std feature enters the crate.

The dependency lines are not automated. A build script cannot add the dependency that lets it run, and no tool is proposed for two lines.

The sketch `mock/research/sketches/202611191725_script-macro-offered-from-a-no-std-crate/FINDINGS.md` shows the cases this changelist first left owed, and this changelist was reopened once for what it found. A `no_std` crate offers the macro with no feature gate. A `config.toml` that exists without the line is left alone. A git dependency's script writes nothing into its checkout. `cargo package` failed its verify build, since the unpacked crate is not under `CARGO_HOME` and the script wrote into it; a root that holds `Cargo.toml.orig` is now declined too, and the verify build passes. The same reopening has the script ask for the root on every run, since a wired workspace would otherwise keep a wrapper whose text an update of the crate changed.
