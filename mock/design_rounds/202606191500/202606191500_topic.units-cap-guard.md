# Topic: compile-time Units-cap guard for run_parallel

**Date:** 2026-06-19
**Crate:** hilavitkutin (engine, scheduler/mod.rs)
**Tracked:** #690 (part), completion-arc P0.1c capstone-review finding 1

## Problem

P0.1c lifted the grouping producer (`masks_of`/`final_phases_of` and the
`phase_of`/`trunk_of`/`group_n` consumers) to size its scratch by `D::Units`.
But `run_parallel`'s `gate2_phase` / `gate2_trunk` scheduler fields and its
first-call precompute locals stayed fixed `[USize; GATE2_MAX_UNITS]` (256).
`grouping_arrays` writes `phase_out[u]` for `u in 0..group_n()`, and
`group_n <= Units::CAP`. So a consumer setting `Units` above 256 (with that
many units) would index past the 256-wide arrays in `run_parallel` (a runtime
OOB panic). Pre-P0.1c the producer and these consumers shared one 256 ceiling;
the lift left an unenforced precondition `Units::CAP <= GATE2_MAX_UNITS`.
Nothing in-tree sets `Units > 256`, so it is latent.

## Decision

Add a compile-time `const { assert!(...) }` at the top of `run_parallel` that
fails the build (per-D monomorphisation) when
`cap_size(<D::Units as Capacity>::CAP) > GATE2_MAX_UNITS`, turning the latent
runtime panic into a clear compile error naming the ceiling and the #690 lift.
Zero runtime cost. Single-core `run` is unaffected (it indexes via
`ConstCapacity::get`, no 256-wide buffer).

This is the guard half of #690; the full lift (sizing `gate2_phase` /
`gate2_trunk` onto `D::Units`, removing `GATE2_MAX_UNITS`) lands with the
`gate2_accum_live` nesting + `merge_accums` redesign in #690.
