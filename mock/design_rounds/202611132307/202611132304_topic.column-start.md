# column-start

What every record of a column holds before any unit has written it, for the plain column as for the buffered one.

## Where it comes from

Three mails of the coordinator's from 20:20 and 20:21 UTC on 13 November reached this seat only after that round had closed. ## The sequence, and why the constructor is ahead of the default

Op's first answer puts the null bit ahead of the default. His second adds `HasTrivialCtor` and gives it no place. Between the constructor and the default the sequence matters for a type that has both and gives two values, and this round keeps what the last one chose: the constructor first.

`HasTrivialCtor` is the stack's own way for a type to say what it is made as from nothing, and a type that implements it beside `Default` has said so on purpose. It is a const trait, so `start()` through it is callable in a constant, which the default is not under the features this workspace has vetted (ticket b4df1365a3f7). With the constructor first, a column of a type that has both can be registered from a constant, and with the default first it could not. The default of such a type stays within reach: through the trait's own path, or as `start_from(T::default())`.

The null bit would be first and is still not buildable. `notko` has no trait that gives a type a null value (ticket df2e4da2d376, and the last round's topic has what was looked at). The types that carry a null of their own say it through `Default`, so no type is left without a start for the tier's absence.

## The shape

One abstraction serves both columns. A column, plain or buffered, is a store that holds a value at every record, and the api says so with one trait over the two markers. The carrier of a start is one type over that trait, and the last round's `StagedBuffered<T, M>` becomes its buffered case and stops being a type of its own. `StartsFromDefault` becomes one impl over the same trait. Each marker has its two inherent functions, `start()` under the constructor's bound and `start_from(value)` for every type, since an inherent function is what lookup finds ahead of a trait's and an inherent function is written on a type.

`Column::<T>::new()` stays the marker a unit names the store by, as `Buffered::<T, M>::new()` did, and the builder stops taking it.

The engine has one drain for the carrier. The marker says which kind of column it is, a plain one of one reservation or a buffered one of two, and the drain reserves by the kind and writes the start to every record of each reservation. The plain column is written once and not twice.

## What a start does not reach

A resource carries its value in already. An accumulator is empty at the top of a frame and a read of it sees what was appended, so it has no record nothing wrote. A virtual has no data.

A column a kit owns has no node in the bindings today: the kit names the marker and the engine reserves nothing for it yet. What it starts from belongs to the round that builds that drain, ticket ac91dfb44d6e, and the marker alone will not be enough there either.

Data that differs from record to record still enters as the founding design has it, by a unit that writes it in a pass. The start is one value and no loader.

## What it costs

One write a record a column at build, and nothing in a pass. On a provider whose memory comes zeroed the write repeats what the provider did, and the null tier, when `notko` has the trait, is what would spare it.

Every scheduler builder that registers a plain column changes: `.with(Column::<T>::new())` becomes `start()` or `start_from(value)`. A unit's lists and body name the marker as before, so no unit changes.
