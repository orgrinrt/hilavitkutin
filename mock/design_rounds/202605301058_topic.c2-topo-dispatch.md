# C2 slice 3: plan-derived topological dispatch

Slice 2 connected the builder to `run()`: registered WorkUnit instances
are retained on the scheduler's `WuVals` list, and `run()` walks them via
the slice-1 `RunFiber` recursion. That walk visits the units in
type-positional order, which is registration-list order (the builder
prepends each `.with(unit)`, so the last-registered unit runs first). A
correct pipeline does not run units in registration order. It runs them
in dependency order: a unit that writes a store another unit reads must
dispatch before that reader. The plan already computes this order. Slice
3 makes `run()` honour it.

The plan side has shipped this since C1: `compute_execution_plan`
produces an `ExecutionPlan` whose `unit_meta[u].id` is `topo[u]`, the
unit-id placed at topological position `u`. That is a runtime permutation
over unit indices. The slice-2 walk cannot consume it, because a
heterogeneous typed cons-list cannot be indexed by a runtime `usize`: you
cannot ask "give me the third element" of `WuCons<A, WuCons<B, ...>>`
where the third is chosen at runtime. The list is walked in the order its
types nest, full stop. Any order other than that nesting needs the units
in a uniform, runtime-orderable form. Producing that form is the
codegen tier this slice opens.

## The mechanism

The form is an array of `(erased instance pointer, monomorphised shim)`
pairs, one per unit, indexed by list position. The shim is a per-unit
free function, monomorphised over that unit's concrete type, that casts
the erased pointer back to the concrete unit, projects that unit's own
resource-only `EngineCtx` from the arena (the slice-1 projection
unchanged), and calls `execute`. A recursive walk over the typed `WuCons`
list emits one slot per unit; the emitted array is then walked in any
runtime permutation. This is exactly what the shipped `WuFn` /
`FiberDispatch` / `run_fiber<S: FiberShape>` skeletons were designed to
hold: a uniform per-unit dispatch shape the order can index.

Why an erased instance pointer and not a bare `fn(&Ctx)` pointer:
monomorphisation specialises over types, not runtime values. A unit can
carry `.with()`-time configuration in its fields (slice 2 retains the
instances precisely for this). A bare function pointer with the receiver
"closed over at monomorphisation" cannot carry a per-instance runtime
field. Pairing the monomorphised shim with a pointer to the retained
instance does. Feasibility was proven by the sketch at
`mock/research/sketches/202605301032_topo-erased-shim-array` (WORKS):
heterogeneous list to uniform slot array via a recursive trait, runtime
config round-trips through the erased pointer, an arbitrary permutation
drives dispatch order, all pure generics plus one back-cast per shim, no
`dyn`, no `TypeId`.

## Where the order is computed and stored

The scheduler retains `WuVals` and `Vals` as type parameters, not the
`Wus` work-unit bundle or the `Stores` access set. So `run()` cannot
recompute the plan: it does not have the types the projection needs.
`build()` does have them (they are builder type parameters), so `build()`
is where the plan is computed. It projects the registered bundle into
`PlanInputs` (`plan_inputs_from_bundle`), runs `compute_execution_plan`,
and extracts the topological permutation: the sequence of list positions
to dispatch, read off `unit_meta[u].id.index()`. That permutation is a
plain array of indices, movable and free of borrows, so it is stored on
the scheduler. `run()` reads it.

The instance pointers are not stored on the scheduler. A pointer into
`self.wu_values` stored inside `self` is a self-referential struct: the
scheduler moves at least once after `build()` returns it, invalidating
the pointer. So the slot array (which holds the pointers) is rebuilt
inside each `run()` call from `&self.wu_values`, where the borrow is live
only for that call. The scheduler stores the order; the walk materialises
the slots.

## Scope boundary

Resource-only, carried forward from slices 1 and 2: a unit that reads or
writes a `Column` does not satisfy the walk's projection bound and cannot
enter the sequence. Real per-frame column buffers are a later slice
(B2b). The dependency edges that drive the topological order come from
resource access: a unit writing `Resource<R>` before a unit reading
`Resource<R>` is a write-before-read edge, and the plan orders the writer
first. Resources project only on the read side of the `EngineCtx` (they
are singletons, not per-frame windowed writes), so a resource "write" is
a plan-dependency signal, not a per-frame `Ctx` mutation. That is enough
to exercise a real topological reorder.

The plan dimensions (`MAX_UNITS`, `MAX_STORES`, and the rest) are fixed
engine-budget constants in this slice, the same shape as the existing
`[AtomicBool; 256]` plan-dirty width and its tracked note. The per-`Cfg`
lift waits on rustc gaining field access on generic constants
(`generic_const_exprs`), tracked under #345 / #641. The LLVM inlining and
devirtualisation tier (the per-fiber program as one optimisation unit)
stays deferred throughout; this slice is the pure-generics ordering core.

## What lands

A type-erasure walk in the engine dispatch layer (the `Collect` trait +
per-unit shim + slot array), a topological-order computation and storage
in `build()`, and a `run()` that walks the slot array in that order. A
strict test registers a resource-writer before a resource-reader so the
registration-list order disagrees with the topological order, and asserts
the dispatch follows the topological order, not the list order.
