## Why this corrects the prior topic

The 080100 topic proposed building a new `dispatch/` module with `RunTrunkSel<A, WL, const POS, const TRUNK>` + `run_one_trunk::<TRUNK>`. That walk ALREADY ships: `dispatch/trunk_gate.rs::RunGatedTrunk` (round 2a), the const-gated per-(phase,trunk) member-only walk over a Peano `Pos` witness (`Here`/`There<..>`). Its module doc states plainly that "the const-generic phase / trunk dispatcher that runs every (phase, trunk) in phase order, and the `Scheduler::run` re-point, are round 2b" — round 2b IS G-e. Building a parallel `RunTrunkSel` would reinvent shipped infrastructure (use-the-stack-not-reinvent). G-e must DRIVE `RunGatedTrunk`.

## The proven shape (sketch 202606080200, WORKS)

The integration seam the 080100 framing missed: enumerating (phase, trunk) and calling a per-trunk mono forces materialising a trunk or phase id into a const-generic argument, and `trunk_gate.rs` itself records a generic-const-expression overflowing the trait solver through this recursion. The sketch resolves it.

1. **Trunk-only keying.** A trunk lies wholly within one phase, so `RunGatedTrunk`'s `const PHASE` is redundant for membership. Drop it; the gate becomes `trunk_of(Pos::INDEX) == TRUNK` only. This removes the always-GCE `PHASE = phase_of(POS)` const-argument. Phase ORDER is the runtime outer loop, not a const on the walk.

2. **Inner walk (shipped, Peano).** `RunGatedTrunk<const TRUNK, Pos>` over `WuCons` / `WuNil`; the recursion threads `There<Pos>` (a type, no const arithmetic, the idiom that dodges the `{POS+1}` solver overflow at the inner level). Per cell, gate the member const and run it through `RunFiber::run_head`.

3. **Outer dispatcher (new).** `Discover<Full, const POS>` walk over the carrier threading `{POS+1}`, bound `Full: RunGatedTrunk<POS, Here>`. Per cell, const-gate `const { trunk_of(POS) == POS }` (is this a trunk-root) and, inside, the runtime `phase_of(POS) == p` match (fire this trunk only in its phase's pass); dispatch `RunGatedTrunk::<TRUNK = POS, Here>` on the FULL carrier. `POS` reaches the inner `TRUNK` by identity, so there are zero GCE const-arguments.

4. **Top.** Runtime phase loop `for p in 0..phase_count { carrier.run(carrier, p, ..); waist }`. Single-core waist is a no-op; G2-N inserts the real barrier.

Key compile proof: the `{POS+1}` outer recursion survives with the inner Peano `RunGatedTrunk` instantiated under a representative-weight const gate at each step. Verified dispatch order `[0,2,1,3]` (phase-ordered, per-trunk contiguous, each trunk once) against a grouping computed by the real same-phase union-find, not hardcoded.

## Change proposed

1. Refactor `dispatch/trunk_gate.rs::RunGatedTrunk` to trunk-only keying: drop the `const PHASE` parameter and the `phase_of` half of the membership gate. Add a trunk-only membership const (`trunk_of::<..>(Pos::INDEX) == TRUNK`) in `plan/grouping.rs`. Pre-1.0 churn: delete the PHASE-keyed form, do not alias it.
2. New `dispatch/trunk_dispatch.rs`: the `Discover<Full, const POS>` outer walk + runtime phase loop, `<Wus, Stores, Witnesses, CU, CS, Adj>`-parameterised, reading the shipped const `trunk_of` / `phase_of` / `phase_count`.
3. Re-point `Scheduler::run` to the outer dispatcher (single-core, sequential, output-equivalent). Keep `run_parallel` on its runtime-mask path; G2-Na re-points it onto these monos.
