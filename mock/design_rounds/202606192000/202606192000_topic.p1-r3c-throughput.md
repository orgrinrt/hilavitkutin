# Topic: P1 R3c — throughput axis sampling via last_record_count

**Date:** 2026-06-19
**Crate:** hilavitkutin (engine) + hilavitkutin-api (SchedulerMetrics)
**Tracked:** #341 (P1 adapt), completion-arc R3c

## Hypothesis

The throughput adapt axis (records/ns trend, spec domain-22 :2019-2026) needs no
new instrumentation: both inputs already exist at the between-frame fold point
where `fold_ema` runs (`scheduler/mod.rs:1374`/`1794`/`2024`). `record_count` is
a Scheduler field; the pass-duration EMA is `SchedulerMetrics::ema_pass_duration_ns`.
A consumer derives throughput = `record_count / ema_pass_duration_ns`. The only
missing piece is exposing `record_count` through the engine-owned `MetaBlock` so
an `OnMeta<ScheduleEnd>` hook can read it (the bridge proven by the R2a keystone
+ gate2_meta_metrics).

## Change

Add `last_record_count: Cell<USize>` to `SchedulerMetrics` (hilavitkutin-api),
set it beside the existing pass-duration EMA fold in all three run paths
(`run` / `run_parallel` / `run_fused`). An `OnMeta<ScheduleEnd>` consumer reads
`ctx.meta::<SchedulerMetrics>().last_record_count` and divides by
`ema_pass_duration_ns` for the throughput trend. Mirrors the shipped pass_count /
ema_pass_duration_ns bridge exactly; no new arena, no new Ctx surface.
