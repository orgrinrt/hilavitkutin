# doc changelist

Round topic `202611200531-k026_topic.the-bench-reads-its-build-from-the-crate.md`, the only flat topic. It holds op's answers with their options, what the canon says, what the bench holds by hand today and the four routes chosen.

The design of `hilavitkutin-build` gains what the bench of the build needs to read its configuration from the crate: the linker of a set, the toolchain's own linker for a target, a set's cargo configuration for a caller that writes no file, and checksum freshness as a pragma. Everything below is in `mock/crates/hilavitkutin-build/`. The bench's own source is under `mock/benches/support/` and belongs to the source changelist.

## Changes proposed

### `DESIGN.md.tmpl`, section "Pragma system"

The table of the crate's pragmas gains one row, `ChecksumFreshness`: cargo decides whether a file changed by its content and not by its time, by `unstable.checksum-freshness = true` in the generated cargo file. Its group is `Free` and its reach the workspace. The key belongs to no profile and is written once, by the first set that holds the pragma, as `Shared` already tells a writer. The paragraph under the default sets says it is in none of them.

The paragraph on `Set` names one more walk, `write_set_config`, which writes the cargo configuration of every member of one set at one site.

### `DESIGN.md.tmpl`, section "Reach"

`write_generated` is said to write its keys through `write_set_config`, once for the `dev` set and once for the `release` set. One sentence is added: a caller that builds without the generated file, a bench of the build itself, hands the same lines to cargo one by one as `--config`, since a dotted key with its value is the form that option takes.

### `DESIGN.md.tmpl`, new section "The linker of a set", after "Tools"

A set is linked by one linker, and the crate answers which. `linker_of::<S>()` answers a `Linker`: `Linker::Toolchain` where the set holds no pragma of `LinkerGroup`, else `Linker::Named` with the pragma's name and the mark its tool leaves in `.comment`, which is the `mark` of the first row of its `NEEDS` and nothing for `Bfd`. `linker_named` answers the same from a name, `toolchain` or a pragma's name, and nothing for any other; it is for a reader that has a recorded name and no type. `Linker::name` is the name `linker_named` takes back.

`Linker::leaves` says whether a mark read from an executable is that linker's: a named linker with a mark where the text read starts with it, a named linker with none where nothing was read, and the toolchain's own where the text is exactly the mark the caller worked out for it, which it hands in.

The toolchain's own linker differs by target, and rustc says which in its description of the target, the text `--print target-spec-json` prints. `ToolchainLinker::of` reads that text: `ToolchainLinker::RustLld` where the linker flavor is an lld one and `link-self-contained` names the linker, else `ToolchainLinker::Other` with the flavor as the text has it. The crate reads the two fields it needs by searching the text and parses no JSON. `rust_lld_mark` takes the first line `rust-lld` printed for `--version` and answers a `RustLldMark`, which displays as `Linker: ` and the version with the LLVM commit it was built from, or nothing where the line is not lld's. For any other toolchain linker the crate has no mark, and a caller that needs one refuses.

The running of rustc and of `rust-lld` stays the caller's, as every looking does.

### `DESIGN.md.tmpl`, section "Flag ownership by pragma"

The table of what a pragma writes today gains `ChecksumFreshness`: its one key, in the generated cargo file or as a `--config` line, waiting on nothing.

### `README.md.tmpl`

No change. The summary names pragmas as the mechanism and stays true.

### `BACKLOG.md.tmpl`

No change. It holds no entry on a linker's mark, on the toolchain's own linker or on checksum freshness, so nothing is promoted.
