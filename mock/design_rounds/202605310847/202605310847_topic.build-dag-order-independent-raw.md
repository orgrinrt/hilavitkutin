# Order-independent RAW hazard detection in build_dag

The plan stage analyses a registered WorkUnit bundle into a dependency
graph, topologically sorts it, and records the dispatch order on
`ExecutionPlan::unit_meta`. The dispatch tier (task #647) is meant to
walk that order so a WorkUnit runs after every unit it depends on,
regardless of the order the consumer registered them in. Wiring the
plan into dispatch was scoped as the next runtime slice.

Reading the plan stage to wire that slice surfaced a blocker one layer
deeper. `build_dag` (`plan/steps.rs`) only inspects unit pairs `(i, j)`
with `i < j` in input order, and adds a RAW edge `i to j` when the
higher-indexed unit `j` reads what the lower-indexed unit `i` wrote.
Every edge therefore runs forward in input order (`i to j`, `i < j`).
Three consequences follow, all load-bearing for the dispatch slice:

The graph is acyclic by construction, so `topo_sort` always places
every unit and the cycle signal (`placed < unit_count`) is unreachable.
The plan spec (`design_rounds/202605101036`) names cycle rejection as a
required outcome (`PlanError::Cycle` on a cyclic registration); the
current `build_dag` can never trigger it.

The topological order `topo_sort` produces is always ascending input
index, because forward-only edges make ascending order the unique
topological order. The retained-unit dispatch walk
(`dispatch::fiber_walk::RunFiber`, driven by `Scheduler::run`) already
walks the value list head-first, which is the same ascending input
order. So plan-derived topological dispatch, wired today, would produce
the identical order to the registration walk for every input. The slice
would change no observable behaviour and could not be tested red-first.

A reader registered before its writer gets no edge at all: `build_dag`
checks `reads[j]` against `writes[i]` only for `i < j`, never
`reads[i]` against `writes[j]`. The genuine data dependency (the reader
must run after the writer) is dropped when the writer happens to be
registered later.

## Current state

`build_dag` walks the upper triangle (`for i in 0..n`, `for j in
i+1..n`) and adds:

- a RAW `Read` edge `i to j` when `reads[j]` overlaps `writes[i]`, and
- a WAW `Write` edge `i to j` when `writes[j]` overlaps `writes[i]`.

`add_edge_kind` carries a CSR append-order invariant: an edge's source
must not be smaller than the current frontier (`unit_count - 1`), so
edges must be appended with their source non-decreasing. The forward
loop satisfies this because every edge has source `i` and `i` ascends.

`topo_sort` (Kahn's algorithm, ascending-index tiebreak) already handles
arbitrary graphs including cycles: it returns the placed count, and
`compute_execution_plan` maps `placed < unit_count` to
`PlanError::Cycle`. The cycle path is exercised today only by
`plan_runner.rs`'s `topo_sort_detects_two_node_cycle`, which hand-builds
a two-node cycle directly because `build_dag` cannot produce one.

## Changes proposed

Make RAW hazard detection order-independent. For every ordered pair
`(s, t)` with `s != t`, add a RAW edge `s to t` when the reader `t`
reads what the writer `s` wrote (`reads[t]` overlaps `writes[s]`),
regardless of whether `s` precedes or follows `t` in input order. The
writer always sorts before the reader, which is the unambiguous true
data dependency. WAW serialisation stays deterministic: a `Write` edge
`s to t` only when `s < t`, the lower input index first.

The restructure keeps the CSR append-order invariant: the outer loop
walks the source `s` in ascending order, so every appended edge has a
source no smaller than the previous one. The inner loop walks the
target `t`; the trailing-sink finalize that pads zero-out-degree rows is
unchanged.

This delivers two observable, testable behaviours that the forward-only
graph cannot:

- A reader registered before its writer reorders after the writer in
  `unit_meta` (a genuine dependency that input order would otherwise
  drop).
- A pair of units that each read what the other writes forms a cyclic
  data dependency, which `topo_sort` leaves partially placed and
  `compute_execution_plan` rejects as `PlanError::Cycle`.

## Out of scope

WAR (write-after-read anti-dependency) detection is deliberately left
out. RAW gives the writer-before-reader direction unambiguously; WAR
gives the opposite direction for the same store access pair (the reader
must see the value before the writer overwrites it), and reconciling the
two needs the program-order-versus-value-flow decision that belongs to
the full plan algorithm chain (#339). This round lands the unambiguous
RAW core and the WAW serialisation that already shipped; WAR is a
tracked #339 follow-up.

The dispatch tier that consumes the corrected order (task #647: the
scheduler computes the plan at build and walks `unit_meta` rather than
the retained value list head-first) is the follow-on slice, landing once
the plan computes a genuine dependency-respecting order.
