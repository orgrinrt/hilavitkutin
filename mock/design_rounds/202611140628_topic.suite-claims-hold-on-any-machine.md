# Suite claims hold on any machine

The closing review of the suite work found four places where what the code or a test says is weaker than it claims. Each is in a crate outside the engine lane's `scheduler/`, `plan/` and `dispatch/`.

The core-idle accumulator test works out how many cores walk a slice with the same `div_ceil` slicing the engine uses. A wrong slice formula therefore moves the expected count along with it, and the test stays green. Its comments already give the counts by hand: four slices at four workers over 64 records, and 32 at forty workers. Those numbers belong in the assertion as literals.

The imbalanced parallel test branches on the machine's worker count. On a one-core runner its multi-core claim, that a waist crossing parks a follower and records idle, is never checked; on a many-core runner the single-core arm is never checked. `FixedWorkers` exists to pin the count, so both arms can run on every machine, at four workers and at one.

Two comments outside the engine lane still name the process that produced the code. `thread/frame.rs` opens with the gate and round id it was written under, and `resource/bindings/per_core.rs` names a numbered deviation of the same gate. They should say what the protocol and the rebase are. The comment lint does not see either form, a gate name or a round id that is not the word `round`, and the engine lane's files carry many more of them; that wider sweep is the engine lane's.

`adapt_ema.rs` writes the stub notice in bold in published rustdoc, which the writing rules forbid, and its task does not point at the committed NEON sketch the finished body is to follow.

The `undeclared_read_fail` fixture reports a second error, from the engine's `ColSelector` resolution, on the same token as the first. Clearing it needs a change in `dispatch/engine_ctx`, so it goes to the engine lane as a ticket rather than into this round.
