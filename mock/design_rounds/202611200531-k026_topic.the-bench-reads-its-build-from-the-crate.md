## The shape

The crate learns three things it did not know, all of them text in and text out.

The first is the linker of a set. A set that holds a pragma of `LinkerGroup` is linked by that pragma's linker, and any other set by the toolchain's own. `linker_of::<S>()` answers a `Linker`: `Linker::Toolchain`, or `Linker::Named` with the pragma's name and the mark its tool's row gives, which is none for `Bfd` since GNU ld leaves none. `linker_named` answers the same from a name, for a reader that has a record's line and no type. A linker says whether a mark read from an executable is its own through `Linker::leaves`.

The second is the toolchain's own linker for a target. `ToolchainLinker::of` reads rustc's description of the target, the text of `--print target-spec-json`, and answers whether the toolchain links with its own `rust-lld` or with something the crate has no mark for, naming the flavor. `rust_lld_mark` turns the version line that `rust-lld` printed into the mark it leaves. The reading of the JSON moves here from the bench with it.

The third is a set's cargo configuration as lines for any caller. `write_set_config::<S, _>` writes the keys of one set at one site, which `write_generated` did for the two sets of a prototype and now does through it. Each line is a dotted key, which is the form cargo's `--config` takes, so the bench hands a set's keys to cargo with no file.

Checksum freshness becomes a pragma, `ChecksumFreshness`, of workspace reach and no group, writing `unstable.checksum-freshness = true` once. It is a choice a consumer has too: a workspace whose files get new times without new content, a fresh clone or a restored cache, rebuilds nothing under it. It joins no default set.

In the bench an arm is a type. `build-call` gains `Quantity`, implemented by the unit types `Build`, `Relink` and `Replay`, and every arm calls `bench_call::<S, Q>` with its set and its quantity. From the set the call takes its cargo configuration lines, its rustc flags, whether it builds incrementally and its linker; nothing is read from a name. The arms of `build-static` name `(ChecksumFreshness, Incremental)` and `(ChecksumFreshness, NoIncremental)`, and the arms of `link-static` name `(ChecksumFreshness, NoIncremental)`, which is what `CARGO_INCREMENTAL=0` gave them. A record's line gains two columns, the linker's name and the quantity, written from the types, and the check after a cell reads those and asks the crate what that linker leaves.

What stays the bench's own is the looking: resolving the pinned toolchain through rustup, running `rust-lld --version`, clearing the environment, the cell's own directories, `--offline` and `--locked`. The stamped row puts the looking with the caller, and none of it is a choice a consumer makes. The marker in `toolchain.rs` that said the resolving would move is taken out with that reason.

The fixture keeps `opt-level` and debug information in its manifest. The design leaves those keys to a consumer's manifest, the fixture is the consumer, and file 59 names those values as the fixture's own. What the crate owns of a profile, its pragmas' keys, now reaches the fixture's build through the arm's set. The marker in `manifest.rs` goes with that said in its place.

## What waits

An arm whose set needs a tool (`Mold`, `Wild`, a driver, cranelift) has to find it as a consumer's script does. The finding is inside the expansion of `script!` today and a caller that is no build script cannot use it. The arms of file 59 are the next work of this job and bring it; until then `build-call` refuses a set that needs a tool, with a marker naming a ticket. No arm in the tree names such a set.
