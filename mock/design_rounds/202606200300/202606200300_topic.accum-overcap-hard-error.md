# Topic: accumulator over-capacity is a hard error, not silent drop

**Date:** 2026-06-20
**Crate:** hilavitkutin
**Tracked:** #659 (accumulator append surface), R3b review follow-up

## Problem

`resolve_append` (dispatch/engine_ctx.rs) saturates at the reserved capacity: once
the live length reaches `cap`, the append `return`s without writing. That keeps
the write inside the reserved buffer (the soundness floor) but silently DROPS the
record. A consumer that under-sizes an accumulator for its per-frame appends loses
data with no signal. The R3b parallel test surfaced this: with fewer records than
cores, per-core consumer marks plus the epilogue exceeded the record-count-sized
capacity and the surplus appends vanished.

## Decision

Over-appending a fixed-capacity accumulator is a capacity-contract violation (a
bug, like an out-of-bounds index), not a recoverable runtime condition. The run
entries return the consumer-defined `Cfg::Out`, so there is no uniform `Outcome`
channel to carry a recoverable error. The fix is fail-loud: `resolve_append`
asserts `live < cap` and panics before the write when the contract is violated.
The assert fires before any write, so the soundness floor (no out-of-bounds write)
is preserved; the difference is a loud abort instead of a silent drop. A consumer
sizes the accumulator for its maximum per-frame appends; that is the contract.

## Test

Keep the RECORDS=64 happy cases (single-core and parallel) that exercise the
change_seen_count logic with headroom. Add a deterministic single-core over-append
test (`#[should_panic]`): a WorkUnit appends `cap + 1` times in one `execute`, the
assert fires, the panic is caught. Single-core because a worker-thread panic under
`run_parallel` is not reliably caught by the test harness; the same assert guards
every dispatch path.
