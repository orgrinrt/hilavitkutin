## Where it stands

No crate's build script calls `hilavitkutin-build`, hilavitkutin's own included. The crate resolves a
`BuildConfig` from cargo's values and writes one cfg directive and a placeholder config file. Nothing
turns a pragma into a rustc flag: the design's wrapper, which a build would generate into `target/`
and cargo would run, cannot exist before the first build that would make it, and the design reads the
tier back out of rustc's arguments although the build script already knows its profile.

Four things in the design no longer hold on the pinned toolchain (rustc 1.98.0-nightly, 2026-05-27),
each checked by compiling a one-function library with the flag:

- `-C llvm-args=-enable-unsafe-fp-math`, FastMath's flag, is refused: `Unknown command line argument`.
  LLVM dropped the global unsafe-fp-math option. Fast float math is per operation now, which is what
  arvo's `arvo_fast_math` cfg already selects.
- `-C llvm-args=-vectorize-with-block-frequency`, one of Pgo's flags, is refused; the option is
  `-loop-vectorize-with-block-frequency`.
- The five flags LoopOptimization owns without its plugin (`-enable-loop-distribute`,
  `-enable-loop-versioning-licm`, `-enable-interleaved-mem-accesses`, `-loop-prefetch-writes`,
  `-enable-histogram-loop-vectorization`) are accepted, as are `-Zthreads=0` and `-Zshare-generics=y`.
- `from_cargo_profile` matches `dev`, `dev-opt`, `profiling` and `ci`, and cargo never passes any of
  them: `PROFILE` is `debug` or `release`, by which of the two the profile inherits from. The dev
  profile reaches `Dev` only through the fallback.

The manifest names `arvo`, which no line of the crate uses, while the design says the crate has no
dependency on arvo. `notko` is used, for `Maybe`.

## The question

How a pragma a crate chose reaches the rustc that compiles that crate, with nothing generated before
the build and nothing a consumer writes twice; which pragmas the first config turns on where; and how
the gain and the cost are measured.

## Shape proposed

1. **The build script chooses, the wrapper applies.** A crate's build script calls
   `hilavitkutin_build::configure`, which reads `PROFILE` and `CARGO_CFG_TARGET_FEATURE` through a
   closure the script passes (the crate stays `no_std` and touches no environment), resolves the
   pragma set, and writes the directives: the cfg it owned before, and
   `cargo::rustc-env=HILAVITKUTIN_BUILD_RUSTFLAGS=<flags>`, the flags of that crate's pragmas. Cargo
   sets that variable on the rustc process of that crate alone. The workspace wrapper, a fixed
   three-line POSIX shell script committed at `.cargo/hilavitkutin-rustc-wrapper` and named by
   `.cargo/config.toml` as `build.rustc-workspace-wrapper`, appends it to rustc's arguments. Where the
   variable is unset (a build script's own compilation, `rustc -vV`, a crate with no build script) the
   wrapper is rustc unchanged. The wrapper's text is `hilavitkutin-build`'s, written by
   `write_wrapper`, and a consumer's committed copy is checked against it, so it is defined once.
   Plain POSIX `sh`, because cargo runs it for every rustc call on any host, before anything else is
   built.
2. **A crate's pragmas are its own.** `configure_with` takes a function over the profile's defaults,
   so a crate turns a pragma off where it does not hold for it. FastMath is the one this round needs:
   kaski's deterministic simulation and engine crates turn it off.
3. **Flags only where their mechanism exists.** LoopOptimization writes its five built-in flags; the
   plugin flag waits for the plugin. FastMath writes its cfg and no flag. ParallelCodegen and
   SharedGenerics write theirs. Pgo, Bolt, Profiling, MathPeephole and Polly write nothing until their
   tools and profiles are found by the build script; each is a ticket.
4. **ExpandedLto stays in the consumer's manifest.** Fat LTO and one codegen unit are profile keys a
   build script cannot set. hilavitkutin's workspace manifest gets the release profile kaski already
   has.
5. **No `-C target-cpu=native`.** The design's always-on wrapper flag makes a release binary that runs
   only on the machine that built it. It moves to the backlog as a pragma a local build opts into.
6. **Measured in kaski's bench harness**, against op's second ask of the same day ("a bench that
   ensures the binary size or build time don't suffer too much on dev time, and that a mock/test
   binary compiled with the same config shows measurable wins using it, and keep track of it across
   time"): the dev build's wall time and binary size with the wrapper and without, and a release test
   binary of a hilavitkutin and notko shaped loop with the config and without.
