# Src changelist: remove the N-way branch and its carve-out

**Date:** 2026-07-19
**Phase:** SRC
**Topic:** `202607192400_topic.delete-the-n-way-record-split.md`
**Doc CL:** `202607192410_changelist.doc.lock.md`

## CHANGE: `Scheduler::run_core_phase` DROPS the single-trunk N-way branch

File: `mock/crates/hilavitkutin/src/scheduler/mod.rs` (the `tphase.0 == 1` arm)

The arm computed `per = ceil(total / ncores)`, gave each core `[lo, hi)`, and walked that slice
under the whole-phase mask via `run_gated`. It goes entirely. The `if / else if / else` chain
collapses to the record-less case and the ordinary trunk-rank case.

Single-trunk phases then take the trunk-rank branch like any other, which for one trunk means one
core runs it and the rest do nothing that phase. Serial, and correct until W1.

Verification: `! grep -q "Head+tail convergence (spec :770)" mock/crates/hilavitkutin/src/scheduler/mod.rs`,
and `grep -c "(total + ncores" mock/crates/hilavitkutin/src/scheduler/mod.rs` drops from one to zero
in that function while the two accumulator-path sites are untouched.

## CHANGE: `run_core_phase` SHEDS three parameters

File: same, the signature at `:2070` and its one call site

The cascade went further than this changelist first anticipated, and the extra step is worth naming
rather than folding in silently.

Removing the arm left `tphase` unused, so the `phase_trunk_count` call went. That left the `phase`,
`trunk` and `n` parameters unused, because nothing else in the function read them: they existed to
feed `phase_trunk_count` and `phase_mask`, both of which served only the deleted arm. The signature
loses all three, and the call site stops passing `&s.gate2_phase`, `&s.gate2_trunk` and `s.gate2_n`.
The `core_mask` import narrows to `grouping_arrays` alone.

So the branch was not only extra behaviour, it was the sole reason three arguments were threaded
into a per-core hot path. That is a better argument for the deletion than the changelist opened with,
and it only became visible by making the change.

No underscore-prefixing: pre-1.0 discipline is to delete rather than silence, and an underscored
parameter would leave the next reader wondering what it was for.

Verification: `cargo check -p hilavitkutin` clean with no warnings, and
`grep -c "phase_trunk_count\|phase_mask" mock/crates/hilavitkutin/src/scheduler/mod.rs` is zero.

## Test movement

**None, as expected. 132 binaries green, 0 failed, 0 errors, 18 ignored: identical to the
pre-deletion baseline.**

Two tests specifically exercise the path this touches and must stay green.
`gate2_convergence.rs::run_parallel_single_trunk_phase_converges` asserts per-record coverage with
no gap or overlap on a single-trunk phase, which serial execution satisfies as readily as the N-way
split did. `gate2_run_parallel.rs::every_producer_runs_when_cores_outnumber_records` is the case an
earlier pass predicted would flip to failing here; it will not, and its passing is the evidence that
prediction was wrong.

If either goes red, the deletion is unsound and the round stops rather than adapting the test.

**Result: both green, along with the other six in those three files.**
`run_parallel_single_trunk_phase_converges` passes with the phase now running serially, confirming
what it always actually asserted: every record processed exactly once, which one core satisfies as
readily as N did. And `every_producer_runs_when_cores_outnumber_records` passes, which is the
evidence that the earlier prediction of stranded trunks was wrong.

## Not in scope

Head+tail convergence (W1). Anything on the accumulator path.
