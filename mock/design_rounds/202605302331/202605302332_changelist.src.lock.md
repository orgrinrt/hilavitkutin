## Intent

Flatten the nested const-array `ExecutionPlan` into CSR flat pools. The nested `Phases x TrunksPerPhase x ComponentsPerTrunk` fiber tree reserved 32768 fiber slots and measured 11 MB at `DefaultPlanDims`, overflowing the stack in `compute_execution_plan::<DefaultPlanDims>` and blocking the topological-dispatch slice (#647). The dense nesting collapses to the plan-wide `D::Fibers` pool (64 slots at the default budget), dissolving the overflow.

`ExecutionPlan` stays a value type. `Phase` and `Trunk` reshape in place into CSR index records: `Phase` drops its nested `trunks` array for a `(trunk_offset, trunk_count)` range into a flat plan-level `trunks` pool, and `Trunk` drops its `components` array for a `(fiber_offset, fiber_count)` range into a flat plan-level `fibers` pool. `Fiber` is reused unchanged. The fiber-formation algorithm in `project_fiber_components` keeps its per-block greedy / spectral logic; only its output target changes from the nested arrays to the flat pools. `TrunkComponent`, `Branch`, and `Bridge` stay defined as forward fan-out / fan-in vocabulary.

The runner derives each phase's CSR trunk range from the layout the projection actually emitted (the layout is the single source of truth for the flat trunk count per phase), so the per-phase `(trunk_offset, trunk_count)` ranges always bracket the trunks written into the flat pool. This is the one deviation from the deprecated full-store-backed design: the per-phase trunk count comes from the projection's emission, not a separate `phase_trunk_counts` pass, which keeps the CSR offsets exact under the plan-wide trunk cap.
