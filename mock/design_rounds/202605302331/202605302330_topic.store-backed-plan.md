# Topic: store-backed execution plan

The plan-stage output `ExecutionPlan<DefaultPlanDims>` measures 11,031,312 bytes. `compute_execution_plan::<DefaultPlanDims>` builds it as a stack value, so the call overflows the stack at the real default budget and is unusable outside tiny test dimensions. The dominant term is the `phases` field: `[Phase<D>; 32]`, where each `Phase` embeds `[Trunk<D>; 32]`, each `Trunk` embeds `[TrunkComponent<D>; 32]`, and each `TrunkComponent` is dominated by a ~256-byte `Fiber<D>`. The nesting reserves `32 x 32 x 32` worst-case fiber slots (~8.4 MB of the 11 MB) regardless of how many fibers a real plan forms. Everything else (`unit_meta`, `column_class`, `dirty`, `morsel_sizes`, `rcm_order`) is a few kilobytes combined.

Two facts shape the fix. First, every leaf of the plan tree is already a `ColumnValue`-eligible arvo scalar: `FiberId`, `UnitId`, `TrunkId`, `PhaseId`, `USize`, `StoreId`, `Bool`, and small `repr` enums (`PhaseStrategy`, `DispatchApproach`, `AccumType`, `MergeOp`, `ColumnClassification`). The `Maybe<HeadTailConvergence>` inside `Fiber` decomposes to the same scalars. The bulk is array nesting, not non-scalar leaves, so the plan needs no `Decompose` derive (which is the deferred ergonomic shape); it needs a structural flattening of scalar leaves. Second, there are no live consumers yet: the `Scheduler` does not hold an `ExecutionPlan` (the `PlanCache` is a stub), and the dispatch tier (`select_approach` / `codegen_fiber` / `codegen_core`) returns zero-init records. The plan is built-but-not-yet-read. That is the low-risk window to redesign the representation: no consumer read path has to be migrated in lockstep.

## The design: one flatten, directly into the store

There are two orthogonal levers. Flattening changes the shape (the nested `[[[Fiber]]]` tree becomes flat columns plus CSR offset/count indices). Store-backing changes the backing (a const-array field becomes a `ColumnStorage` column allocated by live count). The flatten is required either way, because a nested tree cannot be one flat column. A flatten that lands in const-arrays would dissolve the 11 MB but produce another non-columnar plan store, which is exactly the deviation the arc exists to remove ("the actual columnar storage for everything, plan included"). So the flatten lands directly in store-backed columns: one coherent migration, no const-array intermediate to churn through later. The no-consumers window makes the single cut feasible.

This realizes the original design. Consolidation epic domain 09 names `meta::ExecutionPlan` (alongside `meta::Dag`, `meta::LaneAssignment`) as a data-plane meta-Resource the self-hosting meta pipeline accesses, not a bespoke const-array field. The archaeology note restates it: "The plan is a meta-`Resource<ExecutionPlan>`... making it genuinely store-backed (live-count-sized) is what dissolves the 11 MB."

## Representation (the design direction, to be locked in DOC after the sketch)

CSR-style flattening of the phase tree, every column reserved in the scheduler-owned `ColumnStorage`:

- Flat `fibers` columns sized by the live fiber count: the `Fiber` fields SoA-split into scalar columns (fiber id, unit-slice offset/count, column-slice offset/count, head-tail, dispatch approach), plus flat `fiber_units` and `fiber_columns` columns the fiber slices index into (CSR within the fiber too).
- A flat `trunks` column, each trunk holding `(fiber_offset, fiber_count)` into the fibers column plus its id.
- A flat `phases` column (still capped at the real phase count, small), each phase holding `(trunk_offset, trunk_count)` plus its id / strategy / config.
- The already-flat fields (`unit_meta`, `morsel_sizes`, `rcm_order`, `dirty`, `column_class`) move to store columns too, for one uniform plan backing.

`ExecutionPlan` stops being a giant value. It becomes a small handle: the set of meta-`StoreId`s naming its columns plus the live counts. The scheduler owns the `ColumnStorage`; `compute_execution_plan` reserves the columns by live count and writes the scalars; future dispatch reads via `column_ptr` by `StoreId`. The meta-Resource framing (domain 09) is the consumer-facing shape: the plan is `Resource`-like state in the data plane.

## Scheduler wiring

The `Scheduler` gains a `ColumnStorage` (generic `CS: ColumnStorage`, defaulting to the `ArenaColumnStorage<M>` that landed in PR #112), constructed at build time and owning the plan's columns for the pipeline lifetime. The `PlanCache` stub becomes the real plan handle plus the dirty-bit array. This is the DI shape the stack favors: the engine takes `CS: ColumnStorage`; consumers wire the default.

## Open questions (sketch + architect-review before DOC locks)

- Exact handle shape: `ExecutionPlan` as a struct of meta-`StoreId`s plus counts, versus a thinner index type. How the meta-`StoreId`s are assigned (a fixed plan-column enumeration vs dynamic).
- Reserve timing: the step chain computes live counts as it runs (phase/trunk/fiber counts emerge mid-chain). Either a two-pass shape (compute counts into small scratch, reserve columns, write) or reserve-as-you-go with grow-on-demand. The two-pass shape is the likely answer; confirm against how the chain currently materializes counts.
- How the step chain writes columns: today it writes `plan.phases[p].trunks[t].components[c]` into nested arrays. Store-backed, it writes flat columns by computed offset. Whether a thin typed write-cursor over the store keeps the chain readable.
- Whether to flatten ALL fields this round or land the dominant `phases` tree first and move the already-small flat fields in a follow-on. Leaning all-at-once for one uniform backing, but the dominant tree is the value.
- Scheduler `Send`/`Sync`: `ArenaColumnStorage` is `!Send`/`!Sync` (raw pointer; recorded in the providers BACKLOG). The plan crosses thread boundaries when dispatch hands per-core slices; the store-backed plan's cross-core access needs the `unsafe impl Send`/`Sync` on the store with a provenance justification. This round is where that argument gets stated.

A sketch under `mock/research/sketches/` de-risks the representation (does the CSR-over-`ColumnStorage` plan compile, can the step chain write it ergonomically, does the handle thread through the scheduler) before the DOC CL locks. A `feature-dev:code-architect` review of the handle-shape + reserve-timing fork corroborates the call.
