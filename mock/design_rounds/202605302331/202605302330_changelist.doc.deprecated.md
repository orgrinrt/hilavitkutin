## Intent

Reframe the engine DESIGN to describe the store-backed execution plan: `ExecutionPlan` becomes a small handle (meta-`StoreId`s naming its flat columns plus live counts) whose data lives in the scheduler-owned `ColumnStorage`, replacing the nested const-array tree that measures 11 MB at `DefaultPlanDims`. The TOPIC (`202605302330_topic`) carries the problem and the design; a `feature-dev:code-architect` review corroborated the four representation forks. This DOC pins the contract shape; the api DESIGN is unchanged (`ColumnStorage` shipped in PR #112).

## The design (corroborated)

`ExecutionPlan` stops being a value type and becomes a `Copy` handle: the `StoreId`s of its flat columns plus the live phase / fiber / unit counts. The phase / trunk / fiber tree flattens CSR-style (flat fiber columns, trunks holding `(fiber_offset, fiber_count)`, phases holding `(trunk_offset, trunk_count)`), every column reserved in the scheduler's `ColumnStorage` and sized by the live count. The `PlanDims` dimensions become the per-column reserve CAP, not a worst-case const-array allocation. `compute_execution_plan` runs the step chain into flat CSR scratch (a few kilobytes of stack, not the nested tree), then reserves the store columns by the now-known live counts and copies the scratch in; the step functions are structurally unchanged, only the final assembly writes the store. The `Scheduler` gains `CS: ColumnStorage = ArenaColumnStorage<M, Dim<256>>`, owns the plan columns for the pipeline lifetime, and carries the `unsafe impl Send`/`Sync` whose invariant is that the plan columns are frozen between commit and the next `&mut self` replan. `ArenaColumnStorage` itself stays `!Send`/`!Sync`.
