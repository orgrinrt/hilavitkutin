## Current state

PR #104 wired step 5 to block detection and dropped the alignment-check `Err` path. Two review findings, both source-comment only:

1. The `PlanError::PhaseAlignmentMismatch` and `FeasibilityCheckFailed` doc comments still say `block_diagonalise` returns `Bool::FALSE`. After C1c, `block_diagonalise` returns `BlockPartition` and never constructs either variant. The prose describes a code path that no longer exists.
2. The runner's trunk-skeleton projection assigns `PhaseId` (`Uint<5>`, max 31) and `TrunkId` (`Uint<6>`, max 63) via `from_index` with no note of the width cap; a plan with more total trunks than 63 would truncate silently.

## Change

Rewrite the two `PlanError` variant docs to mark them reserved for the later column-classification check (the deviation reasoning itself stands and is documented in the runner). Add a comment at the projection loop noting the `PhaseId` / `TrunkId` width caps are the deliberate engine limit on phase and trunk counts. A hard bound-check that returns an error is filed as a follow-up (it is a broader engine id-width-policy concern, not specific to this projection).

## Out of scope

The bound-check-with-error itself (filed as a follow-up task). No behaviour change; comments only.
