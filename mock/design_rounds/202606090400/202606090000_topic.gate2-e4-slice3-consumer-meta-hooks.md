Slice 2 made the meta WUs (`OnMeta<V>`) run in lifecycle band order, with the
plan band skipped on a clean frame. It did NOT fire real `Virtual<meta::V>`
flags: the band ordering alone sequenced the meta WUs, and the `OnMeta<V>` gate
is const-open. Slice 3 makes the meta lifecycle observable by CONSUMER work
units: a consumer declares `On<meta::ScheduleEnd>` (the ordinary consumer
schedule `On<V>`, slice-1 gate machinery) and reads `SchedulerMetrics` to
implement its own cadence policy. For that, the kernel must fire REAL
`Virtual<meta::V>` flags at the lifecycle points, so the consumer's `On<V>` gate
(stamp == epoch) opens. This is the firing slice 2 deferred.

## What the canonical spec states

Self-hosting (`:2121-2137`): meta virtuals fired by the kernel at lifecycle
points (`PlanStage` on DAG change, `ScheduleReady` after plan-stage units,
`PassStart` per pass, `ScheduleEnd` after all consumer work); four meta
resources restricted via the `MetaAccess` marker trait
(`Dag` / `ExecutionPlan` / `LaneAssignment` / `SchedulerMetrics`).

Adaptation cadence (`:1985-1991`, T5 §Q5): `SchedulerMetrics` carries
`pass_count`, `ema_pass_duration_ns`, `active_units`, `stolen_count`, `idle_ns`
(EMA 1/8 decay). The consumer reads it via an `On<meta::ScheduleEnd>` WU and
implements its own cadence logic. hilavitkutin provides the measurement data;
the consumer decides policy. So the "adaptation work unit body" is
CONSUMER-side; hilavitkutin's slice-3 job is to fire `meta::ScheduleEnd` as a
real virtual and to populate `SchedulerMetrics`.

## What exists today (truth-of-impl, post slice-2)

- `meta::PlanStage` / `ScheduleReady` / `PassStart` / `ScheduleEnd` exist as
  markers (run_cfg.rs); `MetaVirtual` classifies them with lifecycle ranks;
  `MetaAccess` + the four meta resource markers exist (`meta.rs`). The four
  resource markers are bare ZSTs (no fields yet).
- `OnMeta<V>` meta WUs dispatch in lifecycle bands; the kernel skips the plan
  band on a clean frame. NO real `Virtual<meta::V>` firing.
- The slice-1 firing/gating machinery is real: `VirtualStampSelector<V, GI>`
  resolves a `Virtual<V>` stamp cell from the full bindings; `On<V>`'s
  `GateWith` opens when `stamp == epoch`; a producer WU fires via the projected
  write-virtual bundle. A consumer `On<meta::ScheduleEnd>` would gate exactly
  like any `On<V>` IF something stamps `Virtual<meta::ScheduleEnd>` this pass.
- `MetaAccess` is a bare marker; no `Context` bound enforces meta-resource
  access restriction yet.

## Open design questions (resolve in DOC, re-grounding T5 §Q9 L716-802)

1. **Real meta firing with optional registration (the de-risk target).** The
   kernel fires `Virtual<meta::ScheduleEnd>` only if a consumer registered it
   (an `On<meta::ScheduleEnd>` consumer registers `Virtual<meta::ScheduleEnd>`,
   as slice-1's test registered `Virtual<Tick>`). A pipeline with no meta-hook
   consumer registers no meta virtual, and the kernel must not require it. So
   the kernel needs to stamp a meta virtual IF PRESENT in the bindings and
   no-op if absent. A type-level "stamp if present else no-op" is the crux: a
   blanket "absent -> no-op" plus a specific "present -> stamp" overlaps
   (specialization wall, the slice-2 finding). Candidate escapes to sketch:
   (a) the consumer's `Virtual<meta::V>` registration makes the bindings carry a
   `VirtualBinding<meta::V>`, and a `TryFireMeta<V>` trait is impl'd on the
   bindings cons-list structurally (a `VirtualBinding<meta::V>` head stamps; any
   other head recurses; the nil tail no-ops) so "present" is found by the same
   structural walk `VirtualStampSelector` uses, and "absent" bottoms out at nil
   as a no-op WITHOUT a negative bound; (b) the meta virtuals are always
   auto-registered by the builder (4 extra `VirtualBinding`s on every pipeline),
   so the kernel always stamps unconditionally. Sketch decides; (a) is
   lower-footprint (no always-on cost), (b) is simpler but taxes every pipeline.

2. **Lifecycle firing points in the single-core `run` kernel.** Slice 2's
   band-skip stays (it sequences the `OnMeta<V>` meta WUs). On top, the kernel
   stamps each meta virtual at its band boundary so consumer `On<meta::V>`
   hooks in later bands observe it. `ScheduleEnd` stamps after the consumer
   bands, before the schedule-end band, so a consumer `On<meta::ScheduleEnd>`
   WU (which lands in the schedule-end band by its rank... or by a data edge?)
   runs. Resolve: does a consumer `On<meta::ScheduleEnd>` WU get placed in the
   epilogue band? Its schedule is `On<V>` (consumer rank 3), not `OnMeta`
   (rank 4). So by rank it is a consumer, NOT epilogue. For it to run AFTER
   consumers observing `ScheduleEnd`, either its rank must shift, or the fire +
   gate ordering must place it correctly. This is the load-bearing ordering
   question: how a consumer-schedule `On<meta::ScheduleEnd>` is ordered relative
   to the `ScheduleEnd` fire. Likely: the fire happens at the consumer->epilogue
   band boundary, and the consumer hook must be in the epilogue band, which
   means a consumer `On<meta::ScheduleEnd>` needs epilogue rank. Reconcile the
   rank model: `On<meta::V>` (consumer observing a meta virtual) vs `OnMeta<V>`
   (engine meta WU) both want the meta virtual's lifecycle rank for placement.

3. **`MetaAccess` compile-time `Context` enforcement.** A bound so a consumer
   WU's `Ctx` cannot reach a `meta::*` resource while a meta WU's can. Mirror
   the existing access-set gating; decide the bound's shape (supertrait on a
   meta-resource provider, or a marker checked at the resource accessor).

4. **`SchedulerMetrics` population.** Slice 3 ships the resource with its real
   fields (`pass_count`, `ema_pass_duration_ns`, `active_units`,
   `stolen_count`, `idle_ns`) and the kernel populating `pass_count` +
   `ema_pass_duration_ns` (EMA 1/8) at `ScheduleEnd`. The richer metrics
   (`stolen_count`, `idle_ns`) are parallel-path data (work-stealing, parking),
   so they populate meaningfully only with `run_parallel`; single-core ships the
   fields + the single-core-meaningful ones, parallel fills the rest in the
   parallel pass.

5. **Slice 3 scope vs E8.** Slice 3 ships: real meta firing (the kernel stamps
   meta virtuals at lifecycle points), `MetaAccess` enforcement, the
   `SchedulerMetrics` resource + single-core population, and a behavioral test
   (a consumer `On<meta::ScheduleEnd>` WU runs after consumers and reads
   `SchedulerMetrics`). The consumer's actual cadence POLICY (deciding to
   recompute the plan from the metrics) is consumer-layer, demonstrated by the
   test reading the metric; the real domain-22 reorganisation triggers
   (recompute morsel sizes / re-select configs / full recompute) wire the
   `plan_dirty` seed and are the adapt-subsystem follow-on (#341), single-core
   first then parallel.

## Slice-3 scope boundary

core); the optional-registration mechanism; `MetaAccess` compile-time `Context`
enforcement; the `SchedulerMetrics` resource with fields + single-core

findings); the real domain-22 reorganisation triggers + plan recompute (#341);
`stolen_count` / `idle_ns` parallel metrics.
