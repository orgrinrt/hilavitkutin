Slice 3 lands the engine-to-meta bridge: engine-owned mutable meta state read by
a consumer `OnMeta<ScheduleEnd>` work unit, so a consumer can adapt from
`SchedulerMetrics`. The deprecated thin-3a CLs (`202606090200`) tried to ride a
consumer `Resource<T>` and hit the `Copy` wall; the bridge is the real shape.

## What this round locks

The bridge mechanism (candidate 1, sketch-proven):

- An engine-owned `MetaBlock` holds the meta resources as interior-mutable
  fields (`SchedulerMetrics` carries a `pass_count: Cell<USize>`). It is a
  `Scheduler` field, NOT registered in `Stores`, NOT `Copy`-constrained. The
  engine writes it directly (a plain field write, no registration, no `Selector`
  witness, no specialization). `SchedulerMetrics` starts with `pass_count`; the
  remaining canonical fields land with their data sources.
- `EngineCtx` gains a meta-pointer type parameter defaulted to a nil marker
  (`MetaNil`), so existing consumer Ctx aliases are unchanged (mirrors slice-1's
  `write_virtuals = VirtNil` default). The engine wires a real meta reference
  (`MetaRef<'frame>`) into the Ctx only for `OnMeta` work units; consumer work
  units keep `MetaNil`. A `BuildMetaPtr` trait produces the right pointer value
  per work unit at Ctx construction (`MetaNil` ignores the block; `MetaRef`
  captures it).
- A `meta::<T>()` accessor (`T: MetaAccess`) is implemented ONLY on the Ctx
  carrying a `MetaRef`. A consumer work unit's `MetaNil` Ctx has no such method,
  so a consumer cannot reach meta state at compile time. The `MetaAccess`
  enforcement falls out of the gating for free, no negative bound, no
  specialization.
- The single-core `run` increments `SchedulerMetrics::pass_count` once per pass
  (a direct write to the block field). An `OnMeta<ScheduleEnd>` consumer hook
  reads it through `ctx.meta::<SchedulerMetrics>()`, in the epilogue band after
  consumer work (slice-2 band order).

## Doc claim

Replace the engine `DESIGN.md.tmpl` self-hosting section's `MetaAccess`
follow-up paragraph with the real bridge design: meta state is engine-owned (a
`MetaBlock` on the scheduler, not a `Store`, because consumer stores are `Copy`
read-only); an `OnMeta` work unit reads it via a `MetaAccess`-gated Ctx accessor
that a consumer work unit's Ctx does not have; `SchedulerMetrics::pass_count`
maintained per pass by the engine, read by a consumer `OnMeta<ScheduleEnd>`
hook. The section backticks `MetaBlock`, `MetaRef`, `pass_count`; those land in
source in this round's SRC CL.

## Out of scope (follow-on)

`ema_pass_duration_ns` (a `Clock` + frame timing, #341); `active_units` and

(parallel path); `run_parallel` meta parity (one pass, per 202606082300, which
also threads the `MetaRef` to worker-side OnMeta dispatch).

## Comparison to deprecated changelist

Replaces `202606090200_changelist.doc.deprecated.md` (thin slice-3a). That CL
described `SchedulerMetrics` as a mutable consumer `Resource<T>` populated by a
provided `SchedulerMetricsWu`. It was deprecated because that hit a hard compile
wall (resolution `202606090100` Correction 2): a consumer `Resource<T>` is `Copy`
and read-only after init, so it cannot carry mutable per-pass state. This CL
replaces the resource-backed design with the engine-owned `MetaBlock` written by
the scheduler and read through a `MetaAccess`-gated Ctx accessor (the bridge,
candidate 1, sketch `202606090300`).
