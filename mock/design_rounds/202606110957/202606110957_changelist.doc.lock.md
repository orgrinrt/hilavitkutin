# DOC changelist: E8 adapt slice 1 — pass-duration EMA + clock

**Date:** 2026-06-11
**Phase:** DOC
**Round:** 202606110948 (GATE-2 E8, task #341, branch `feat/hilavitkutin-parallel-engine-gate2`)
**Topic:** `202606110948_topic.gate2-e8-adapt-pass-duration-ema.md`

First adapt slice: the engine reads a clock, maintains the canonical EMA of
pass duration (1/8 decay) in the meta block, and a consumer reads it through
the slice-3 bridge. Also reconciles the duplicate pre-bridge `SchedulerMetrics`
(the `scheduler/metrics.rs` resource-shaped struct) out of existence.

## Current state

The engine `DESIGN.md.tmpl` `## Runtime adaptation (domain 22)` section states
the design (frame time prediction via EMA 1/8 decay, between-frames triggers)
but documents no mechanism, because none exists: the scheduler stores no clock
and takes no time samples. The earlier dispatch-strategy section says "Cadence
via SchedulerMetrics resource (consumer reads, consumer decides policy)", which
is pre-bridge wording: the slice-3 round hard-proved meta state is engine-owned
(`MetaBlock`), not a consumer resource, and the self-hosting section already
documents the bridge.

## Changes proposed

### `mock/crates/hilavitkutin/DESIGN.md.tmpl`

1. **Extend `## Runtime adaptation (domain 22)`** with the slice-1 mechanism
   paragraph: the scheduler owns a `ClockApi` provider (a builder slot,
   defaulted to the os-tier clock; `no_os` consumers supply their own), reads
   `now_ns` at frame start and end on every run entry (single-core, parallel,
   fused), and folds the duration into `SchedulerMetrics` in the meta block
   with the canonical 1/8 decay (seed frame takes the raw sample). The fold
   happens at frame end while every worker is parked, the same cross-thread
   discipline as `pass_count`. Consumers read it through the `MetaAccess`-gated
   bridge from an `OnMeta<ScheduleEnd>` hook (frame budgeting, cadence,
   progress estimation).
2. **Correct the cadence sentence** in the dispatch-strategy section: cadence
   reads go through the meta bridge (`OnMeta<ScheduleEnd>` +
   `SchedulerMetrics`), not a consumer resource.

No api template changes: the api `DESIGN.md.tmpl` does not enumerate
`SchedulerMetrics` fields, and the platform-contract listing (`ClockApi`,
`HasClock`) already covers the clock surface. The deletion of the stale
`scheduler/metrics.rs` struct is a source-only change (no template documents
its fields); it lands in the src CL.
