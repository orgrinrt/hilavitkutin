# Src changelist: remove thread/pool.rs and its re-export

**Date:** 2026-07-19
**Phase:** SRC
**Topic:** `202607192500_topic.delete-the-orphaned-thread-pool.md`
**Doc CL:** `202607192510_changelist.doc.lock.md`

## CHANGE: `mock/crates/hilavitkutin/src/thread/pool.rs` IS DELETED

The file defines `ThreadPool` (with `new`, `builder`, `shutdown_requested`, `Default`, `Drop`) and
`ThreadPoolBuilder` (with `new`, `with_wake_strategy`, `with_spin_budget`, `with_thread_count`,
`build`, `Default`). Nothing constructs either type. The `Drop` sets a flag no reader observes.

The running thread pool is `PoolFrame` plus the platform tiers' `ThreadPoolApi` implementations,
which share no code with this file.

Verification: `! test -f mock/crates/hilavitkutin/src/thread/pool.rs`.

## CHANGE: `thread/mod.rs` DROPS the module and its re-export

Both `pub mod pool;` and `pub use pool::{ThreadPool, ThreadPoolBuilder};` at `:43` go. The re-export
was the file's only reference in the workspace, and it is what kept the dead-code lint quiet: `pub`
items in a library crate are not flagged, so nothing ever reported this.

Verification: `! grep -q "pool::" mock/crates/hilavitkutin/src/thread/mod.rs` and
`cargo check -p hilavitkutin` clean.

## CHANGE: whatever the deletion orphans FOLLOWS it

`WakeStrategy` and any other type the builder alone consumed may lose their last reader. Each is
traced the same way before removal rather than deleted alongside: check every reference across all
crates including `tests/`, and check whether a design template names it. Anything still referenced
stays, and anything a template names stays regardless.

This is the R1 lesson applied in advance. There, deleting one branch cascaded through `tphase`,
`phase_trunk_count`, three function parameters and an import, and each step only became visible
after the previous one landed.

**No cascade materialised here.** `cargo check` came back clean on the first pass, with only the two
pre-existing `AdaptArena` warnings that band W4 owns. The one candidate the changelist named,
`WakeStrategy`, was traced anyway rather than inferred from the absence of a warning: it lives in
`hilavitkutin-api/src/platform.rs:273`, not in the deleted file, is referenced across that crate, and
is documented in two templates. The deleted builder merely consumed it. Correctly untouched.

Worth stating plainly that the anticipated work did not exist. The check was cheap and the answer was
"nothing follows", which is a real result rather than a step skipped.

Verification: `cargo check -p hilavitkutin` clean, no new warnings.

## Test movement

**None, as expected. 132 binaries green, 0 failed, 0 errors, 18 ignored: the same baseline as before
the deletion.** No test referenced either type, which is part of why the deletion was safe.
