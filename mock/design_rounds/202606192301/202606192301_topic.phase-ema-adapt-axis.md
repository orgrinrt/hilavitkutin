# Topic: per-phase duration EMA adapt axis (domain 22)

**Date:** 2026-06-19
**Phase:** TOPIC
**Scope:** `hilavitkutin` engine (single-core `dispatch_trunks` timing tap + a per-phase EMA store)
**Source topics:** spec domain 22 (adapt, per-phase EMA timing), the shipped scalar-axis pattern (pass_duration / change_class / throughput / core_idle)

## Current state

The adapt subsystem folds four signals at frame end: `ema_pass_duration_ns`,
`change_seen_count`, `last_record_count`, and `idle_ns` (the per-core barrier
idle just shipped). All four are scalar fields on `SchedulerMetrics`, consumer-
readable through the `OnMeta<ScheduleEnd>` bridge. The next adapt signal the
spec names is the per-PHASE EMA: how long each phase takes, so the tuning logic
(`select_adapt_config`, R5) can spot the bottleneck phase and re-balance.

Per-phase timing is not a scalar; it is one EMA per phase. The breadcrumb's R4a
analysis settled that per-unit / per-N EMA detail is ENGINE-INTERNAL (consumed by
`select_adapt_config`, never consumer-named), because `SchedulerMetrics` must
stay non-generic for the `ctx.meta::<SchedulerMetrics>()` accessor. So per-phase
EMA does not go on `SchedulerMetrics`; it lives engine-internal.

The timing tap is clean on the single-core path: `Scheduler::dispatch_trunks`
(`&self`, the clock in scope) loops phases (`while p < nphases`, the per-phase
dispatch). Sampling the clock around each phase's `dispatch` call gives the phase
duration directly. The parallel path (`worker_main`'s phase loop) measures
per-phase per-worker timing and is a follow-up, the same single-core-first
scoping core_idle used.

## Changes proposed

1. A per-phase EMA store on the `Scheduler`: `phase_ema: [Cell<Nanos>;
   GATE2_MAX_UNITS]` (phases are bounded by units, so the unit cap bounds the
   phase cap; this mirrors the shipped fixed-cap `[_; MAX_CORES]` per-core arrays
   rather than reaching for a `Capacity::Array` of interior-mutable cells). This
   is option A (owned `Scheduler` field, the shipped precedent) for the first
   functional slice; the `AdaptArena` aligned-scratch realisation (option B) is
   the bench-gated perf follow-up, not this round.

2. `dispatch_trunks` samples `self.clock.now_ns()` before and after each phase's
   `dispatch` and folds the raw-nanos delta into `phase_ema[p]` with
   `fold_ema(prev, dur, seed)`, the same 1/8 EMA the pass-duration fold uses;
   `seed = self.first_frame` (frame 1 stores the raw duration, later frames
   fold), matching the scalar-EMA seed discipline. Bounds-guarded by the array
   length.

3. A white-box `__phase_ema(USize) -> Nanos` accessor: per-phase EMA is engine-
   internal (feeds `select_adapt_config`), so there is no `OnMeta` consumer read;
   the accessor lets a white-box test assert the per-phase durations recorded.

## Edge cases (catalogued as tests)

- multi-phase single-core run: each phase's EMA is positive after a frame (under
  a strictly increasing clock, every phase's before/after pair brackets a
  positive delta). The measurement.
- single-phase carrier: only `phase_ema[0]` is touched; higher slots stay zero.
- second frame folds toward the new sample (1/8 weight), seed only on frame 1.
- `run_parallel`: `dispatch_trunks` is not on its path, so `phase_ema` stays zero
  there (parallel per-phase timing is the follow-up; the single-core invariant
  is that the parallel path does not spuriously write it).

## Not in scope

Parallel-path per-phase timing (worker-side, the `worker_main` loop); the
`AdaptArena` option-B aligned-scratch storage; `select_adapt_config` (R5)
consumption; `fiber_ema` (per-fiber, same plumbing, follow-up).
