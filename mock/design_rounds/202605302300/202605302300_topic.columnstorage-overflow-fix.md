# Topic: ArenaColumnStorage reserve overflow guard

Local review of PR #112 found a soundness gap in `ArenaColumnStorage::reserve`. The byte length is computed as `*count * size_of::<T>()`, an unchecked `usize` multiply. A large `count` times a wide `T` overflows: it wraps to a small `bytes`, `allocate` returns an undersized block, and the subsequent `column_ptr_mut` writes of `count` records overrun the allocation. The overflow is reachable from a safe `reserve` call; the later `column_ptr` deref honors its documented "index < count(id)" contract yet the buffer is too small. The `ColumnStorage` trait rustdoc already names "length overflow" as a failure `Error` covers, but the impl never produces it.

Fix: compute the byte length with `checked_mul` and return a new `StorageError::LengthOverflow` when it overflows, before any allocation. A test reserves a count whose byte product overflows `usize` and asserts the overflow error.

Second finding, recorded not fixed: `ArenaColumnStorage` holds a `*mut u8` in `ColumnSlot`, so it is `!Send` / `!Sync`, while `MemoryProviderApi: Send + Sync` and the engine schedules across cores. No consumer threads it yet (the PR is additive), so this is not a bug today, but the store cannot be wired into the multi-core scheduler without an `unsafe impl Send`/`Sync` carrying a provenance justification. A BACKLOG note records it so the migration round does not rediscover it.

## Out of scope

The Send/Sync `unsafe impl` itself (lands with the migration that wires the store into the scheduler), the `Decompose`-driven multi-column reserve, and the engine migrations.
