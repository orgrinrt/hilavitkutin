## Design resolution: `PlanDims` lives in the engine, not hilavitkutin-api

The numeric-position convention memo (T13) first-guessed `PlanDims` into `hilavitkutin-api`. Grounding the placement against the actual code reverses that:

1. `PlanDims` is consumed only by engine plan/thread/dispatch/adapt structures. The exploration of `hilavitkutin-api` found zero plan-dimension parameters in any api contract (`WorkUnit`, `AccessSet`, `Column`, `Resource`, `Context`, the platform traits). Nothing in the contract layer needs the bundle.
2. `hilavitkutin-api` already declares its own `trait Capacity { fn capacity(&self) -> USize; }` (a collection-introspection atom in the `Push` / `Len` / `Capacity` / `BoundedPush` capability layer). `PlanDims`'s associated types are bounded by arvo's `Capacity` (the array-backing GAT trait). Placing `PlanDims` in the api would put two distinct `Capacity` traits in one module, forcing a qualified `arvo_tensor::Capacity` path at every bound. The engine uses neither `Capacity` today, so it imports `arvo_tensor::{Capacity, Dim}` unambiguously.
3. `PlanDims` is engine capacity configuration (the engine's plan-sizing budget), not a consumer-contract atom. The `Scheduler` that carries `D: PlanDims` is itself an engine type; a consumer reaching for a custom budget imports `PlanDims` from the engine alongside the `Scheduler` it parameterises.

`PlanDims` and `DefaultPlanDims` therefore live in the engine crate (`hilavitkutin`), in a `plan` submodule, re-exported from the engine root. `hilavitkutin-api` is untouched by this round. (The api does depend on arvo and arvo-bitmask already, so the workspace "no arvo re-export through the api" rule, which targets `pub use` of arvo types, does not by itself force the placement; reasons 1 through 3 do.)

## The contract shape

```rust
// hilavitkutin engine, plan module. `Capacity` and `Dim` are arvo-tensor's.
pub trait PlanDims {
    type Units: Capacity;
    type Stores: Capacity;
    type Edges: Capacity;
    type Phases: Capacity;
    type Trunks: Capacity;
    type TrunksPerPhase: Capacity;
    type Fibers: Capacity;
    type Lanes: Capacity;
    type Columns: Capacity;
    type ComponentsPerTrunk: Capacity;
    type UnitsPerFiber: Capacity;
    type ColumnsPerFiber: Capacity;
    type Cores: Capacity;
}

pub struct DefaultPlanDims;
impl PlanDims for DefaultPlanDims { /* each dim = Dim<N> at the engine's current default budget */ }
```

The engine plan/thread/dispatch structures take one `D: PlanDims` parameter and project `<D::Units as Capacity>::Array<UnitMeta>` etc. `ExecutionPlan<D: PlanDims>` replaces the ten-const-generic form; `compute_execution_plan<D: PlanDims>` replaces the twelve-const-generic form. Nested structures (`Phase`, `Trunk`, `Fiber`, `DirtyMasks`, `ColumnClassMap`, `CoreAssignment`, `FiberDispatch`, `CoreDispatch`, `AdaptArena`) take `D`, or a single `C: Capacity` where they genuinely size by one dimension. `Scheduler` gains `D: PlanDims = DefaultPlanDims` to thread into plan computation.
