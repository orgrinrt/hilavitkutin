**Phase:** TOPIC
**Scope:** the hilavitkutin engine adopts arvo's `Capacity` foundation via a bundled `PlanDims` type parameter, replacing the ~209 `const _: Cap` capacity dimensions across plan/thread/dispatch/adapt. Task #652. Branch `feat/hilavitkutin-capacity-plandims`.

# Topic

The engine sizes every plan structure with `Cap` const generics: `ExecutionPlan<const MAX_UNITS: Cap, const MAX_PHASES: Cap, ...>` and ~209 such parameters across 20 files. Each feeds `[T; cap_size(N)]` array lengths, which lean on `generic_const_exprs`. That is exactly the surface that ICE'd when C2 slice 3 (#647) tried to thread plan dims through generic scheduler code: a `Cap` const generic threaded from generic code forms the `cap_size(cap(K))` round-trip that overflows rustc WF evaluation. The root cause and the decision are recorded in `mock/research/202605301130_numeric-position-convention.md` (T13: capacity-as-a-type).

arvo now ships the fix. Round 202605301321 (#650) added `trait Capacity { type Array<T>: AsRef<[T]> + AsMut<[T]>; const CAP: Cap; fn filled / from_fn }` and `struct Dim<const N: usize>`; round 202605301415 (#651) migrated arvo's own `Array`/`Matrix`/`BitMatrix`/`Csr`/graph/sparse/spectral off `Cap` const generics onto `C: Capacity`. The dimension is a TYPE; the array length is a literal inside `Dim<N>`'s impl; no `cap_size` sits in type position; GCE never runs and cannot ICE.

This round adopts that foundation in the engine. The bare-usize-dim fallback (memo T12) is not needed: the capacity-as-type path is proven.

## The dimension inventory (what becomes PlanDims)

The engine carries 13 distinct capacity dimensions. They bundle into one trait whose associated types are each a `Capacity`:

| PlanDims assoc type | Current param | Sizes |
|---|---|---|
| `Units` | `MAX_UNITS` | WorkUnits in the pipeline |
| `Stores` | `MAX_STORES` | distinct stores (access-mask width) |
| `Edges` | `MAX_EDGES` | dependency-graph edges (CSR) |
| `Phases` | `MAX_PHASES` | waist-delimited sync phases |
| `Trunks` | `MAX_TRUNKS` | trunks plan-wide |
| `TrunksPerPhase` | `MAX_TRUNKS_PER_PHASE` | trunks within one phase |
| `Fibers` | `MAX_FIBERS` | fibers plan-wide |
| `Lanes` | `MAX_LANES` | parallel dispatch lanes (core assignment) |
| `Columns` | `MAX_COLUMNS` | distinct columns tracked plan-wide |
| `ComponentsPerTrunk` | `MAX_COMPONENTS_PER_TRUNK` | fiber/branch/bridge components per trunk |
| `UnitsPerFiber` | `MAX_UNITS_PER_FIBER` | WUs within one fiber |
| `ColumnsPerFiber` | `MAX_COLUMNS_PER_FIBER` | columns one fiber touches |
| `Cores` | `MAX_CORES` | hardware cores driving dispatch |

Relationships observed (not all enforced today, none block the bundle): `Columns >= Stores` (a compatibility cast in `compute_execution_plan` assumes it), `UnitsPerFiber <= Units`, `ColumnsPerFiber <= Columns`, `TrunksPerPhase <= Trunks`, block-count `<= Units`. `Stores` and `Columns` are nearly the same axis used in different contexts; the bundle keeps them distinct (matching today's separation) and a default impl can set them equal.

Excluded (NOT plan dimensions, stay as-is): `hilavitkutin-api` `Seq<T, const N: Cap>` / `Map<K, V, const N: Cap>` (store-internal caps), `RunCfg::MAX_PLAN_AFFECTING_RESOURCES` (a `USize` assoc const, not a dimension).

## The shape

`PlanDims` lives in `hilavitkutin-api` (a contract; the api carries zero plan dimensions today, so this is a clean additive surface, and `PlanDims` references only arvo's `Capacity`, never the engine):

```rust
pub trait PlanDims {
    type Units: Capacity;
    type Stores: Capacity;
    type Edges: Capacity;
    type Phases: Capacity;
    type Trunks: Capacity;
    type TrunksPerPhase: Capacity;
    type Fibers: Capacity;
    type Lanes: Capacity;
    type Columns: Capacity;
    type ComponentsPerTrunk: Capacity;
    type UnitsPerFiber: Capacity;
    type ColumnsPerFiber: Capacity;
    type Cores: Capacity;
}

pub struct DefaultPlanDims;
impl PlanDims for DefaultPlanDims {
    type Units = Dim<64>; // the engine budget, one impl; concrete sizes per the current defaults
    // ... each dim a Dim<N>
}
```

Engine plan/thread/dispatch structures take one `D: PlanDims` parameter instead of N const generics, and project `<D::Units as Capacity>::Array<UnitMeta>` etc. `ExecutionPlan<D: PlanDims>` replaces the 10-generic form; `compute_execution_plan<D: PlanDims>` replaces the 12-generic form (Stores and Edges are now `D::Stores` / `D::Edges`, available without being separate params). Nested structures (`Phase`, `Trunk`, `Fiber`, `DirtyMasks`, `ColumnClassMap`, `CoreAssignment`, `FiberDispatch`, `CoreDispatch`, `AdaptArena`) likewise take `D` (or a single `C: Capacity` where they genuinely size by one dimension only).

The de-risk sketch `mock/research/sketches/202605301700_plandims-bundle/` (FINDINGS green) proved the bundle resolves through fully-generic code, including the nested `D::Edges::Array<D::Units::Array<T>>` two-dimension projection, with no feature gate. The only generic-consumer bound that surfaces is `<D::Dim as Capacity>::Array<T>: Copy` wherever a 2-D array is built via `filled` (the same Copy-propagation seen in the arvo #651 migration).

## Why one atomic round

The plan structures nest (`ExecutionPlan` contains `Phase` contains `Trunk` contains `Fiber`), and the step functions thread the same dim set through each other. `no-legacy-shims-pre-1.0` forbids a transitional parallel definition, so the engine cannot half-adopt: the structs and the functions co-migrate. One round, one PR, workspace-green at lock. The 6 current compile errors (`plan/laplacian.rs` `SymmetricLaplacian` + its `LinearOperator` impl + `apply`; `plan/steps.rs` calls to arvo `rcm_reorder_via` / `block_diagonal_via` / `k_way_partition`) resolve as a consequence of threading `Capacity` through, not as a separate fix.

## Scope and method

13 dims, ~209 `const _: Cap` params, ~376 `cap_size` sites, 20 files (`plan/*`, `dispatch/*`, `thread/*`, `adapt/arena.rs`) plus the new `PlanDims` declaration in `hilavitkutin-api`. The arvo dep is already on `branch = "dev"`; a `cargo update -p arvo` pulls the #651 migration (the engine builds against the migrated arvo). Behaviour-preserving: array sizes are identical (`Dim<N>::Array<T>` is `[T; N]`), algorithms unchanged, bench-neutral by construction. Method follows the arvo migration: TDD a generic-threading test, mechanical per-file adoption (likely split across subagents with independent verification, given the volume), atomic commit at workspace-green.
