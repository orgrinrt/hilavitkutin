# Topic: plan-projection correctness hardening

**Date:** 2026-06-04
**Scope:** hilavitkutin engine (`scheduler/mod.rs`). Correctness hardening of the just-completed single-core dispatch projection, clearing two flagged pr-reviewer-senior notes. No new capability.
**Source topics:** PR #122 reviewer note (the `topo_count` partition-completeness divergence); #657 (PlanHandle column-id coupling + slot-table bound, from the PR #117 reviewer notes).

The engine's single-core dispatch is complete. Two silent-failure surfaces in the plan projection were flagged during review and deferred as non-blocking; this round converts them to loud or compile-enforced, in the strict-by-design spirit (a silent corruption or drop is worse than a loud failure).

## The two surfaces

**`topo_count` partition-completeness (PR #122 review).** `derive_phase_dispatch_order` flattens `plan.phases -> trunks -> fibers -> units`, collecting each unit's slot index, and returns the flattened total as `topo_count`. The `topo_count` field doc still says "registered unit count". These coincide only for a complete fiber partition (every unit assigned to exactly one fiber), which the plan produces today. If a future plan change left a unit assigned to no fiber, or a capacity guard tripped, the flatten would silently emit fewer units than registered, dropping them from dispatch with no error. The reviewer suggested a `debug_assert_eq!(next, plan.unit_count.0)` to surface it, plus rewording the field doc.

**PlanColumn offset coupling + the magic count (#657).** `column_id` maps `base + (c as usize)`, so a `PlanColumn` variant's offset is its declaration position; reordering the enum silently shifts every offset. Store and read both route through `column_id`, so they stay consistent within one build, but the offset-is-declaration-position coupling is a latent footgun and the count `6` (the number of plan columns the slot table must accommodate past the resource columns) is a magic literal in the `store_plan` doc.

## Round changes

1. **`topo_count` guard** (`scheduler/mod.rs`): add `debug_assert_eq!(next, plan.unit_count.0, ...)` at the end of `derive_phase_dispatch_order` so an incomplete fiber partition surfaces in debug and test builds rather than silently dropping units. Reword the `topo_count` field doc from "registered unit count" to "the flattened dispatch total (equals the registered unit count when the fiber partition is complete)".

2. **PlanColumn offset single-source + count const** (`scheduler/mod.rs`): replace `column_id`'s `c as usize` with an exhaustive `match c` mapping each variant to an explicit offset, so reordering the enum no longer shifts offsets and adding a variant is a compile-forced change (the match goes non-exhaustive). Add a `PlanColumn::COUNT` const naming the number of plan columns, and use it in the `store_plan` doc (and any slot-table-bound prose) in place of the literal `6`.

## Test plan (red-first where it discriminates)

A focused unit test in `scheduler/mod.rs` (or `tests/`) pins the `column_id` offset contract: for a known `base`, assert each `_id()` accessor returns the expected `base + offset` (Phases through RcmOrder, offsets 0 through 5). This discriminates a wrong match arm and pins the offsets against accidental shift. The `topo_count` guard has no discriminating red-first test (the partition is complete, so the assert passes); it is exercised passing by the existing dispatch tests in debug builds and stands as a regression guard. The existing column / accumulator / morsel / phase-sequential tests stay green (the `column_id` change preserves the current offsets; the guard does not change behaviour).

## Out of scope

- The major engine tiers (parallel #342, plan chain #339, codegen #340, persistence #344) and the arvo-graph widening they depend on. This round is correctness hardening of the existing projection only.
- Converting the slot-table overflow to an earlier explicit error: it already returns `BuildError::AllocationFailed` (loud, not silent), so only the doc note is in scope.
