# Doc changelist: sym peer collision and a generic kind width

**Phase:** DOC
**Topic:** `202608082215_topic.sym-peer-collision-and-generic-kind.md`
**Scope:** `mock/crates/hilavitkutin-sym/DESIGN.md.tmpl`, `README.md.tmpl`.

## The shape this round settles

Both defects are the same defect twice: a **layout policy hardcoded in the
substrate** that only one consumer's needs justify. Three bits of kind and
twenty-eight of id is one split; a single global counter is one minter policy.
Neither is the substrate's to choose.

So one mechanism answers both. A **shape trait** carries the layout, the
current split is its default impl, and `Generator` takes its origin from the
same place.

```
SymShape
  KIND_BITS      how many domains this shape admits
  ORIGIN_BITS    how many independent minters, zero for one
  COUNTER_BITS   derived: 32 - 1 - KIND_BITS - ORIGIN_BITS
  Kind / Origin / Counter    the Bits types at those widths
```

The arithmetic sits in each impl, where expressions are legal, and every bound
names the trait. Writing `Bits<{32 - 1 - K}>` in type position would need a
forbidden feature; the workspace rule for exactly this shape is to carry the
derived quantity as a trait contract instead.

`Standard` is the default impl and is byte-identical to today: kind 3, origin 0,
counter 28. **The string domain's `0b000` tag and baked-handle compatibility hold
under it unchanged**, which is the compatibility constraint the topic names.

## CHANGE: `DESIGN.md.tmpl`, the `Sym` section

State the layout as a **property of a shape** rather than as fixed field widths.
Keep the current widths as the default and say they are the default rather than
the definition. Keep the existing statement that comparison is integer equality
over the whole layout, which is unaffected.

Add the consequence a consumer needs and cannot currently read: **two `Sym`s
from different shapes are not comparable and must not be mixed in one store.**
A shape is a wire format, so choosing a non-default one is choosing not to
interoperate with baked handles.

## CHANGE: `DESIGN.md.tmpl`, new section for `SymShape`

New section, placed before `SymKind` because `SymKind` now depends on it. States
the four widths, the derivation, and that the arithmetic lives in the impl for a
reason worth naming. States `Standard` as the default and what it costs to
depart from it.

## CHANGE: `DESIGN.md.tmpl`, the `SymKind` section

`SymKind` becomes generic over the shape rather than wrapping `Bits<3, Hot>`.
The kind-assignment table stays and stays a documented convention; what changes
is that the table is per-shape, and `Standard`'s table is the current one.

## CHANGE: `DESIGN.md.tmpl`, the `Generator` section

This is the substantive one.

**State the freshness contract exactly, because the current sentence is true and
has already been misread.** It says each mint is distinct from every prior mint
*of the same generator*, which is accurate and never says what follows: two
generators for one domain mint the same handles. Say it outright. A consumer
building on this crate measured 132 of 144 scenarios false-identifying,
including 24 in which the two peers shared no value at all, because it read
per-generator freshness as global.

Then say why silence here is worse than elsewhere. `Sym` compares by integer
equality, so colliding handles do not fail: they compare **equal**. Incomparable
would be a wrong answer a consumer can detect; falsely equal is silent.

**Make disjointness constructible rather than conventional.** A generator is
built for an origin, and origins partition the counter space by construction.
Under `Standard` there are zero origin bits and exactly one origin, so the
current single-minter behaviour is what the default gives and nothing changes for
the engine. A consumer with peers picks a shape with origin bits and can then
only construct a generator by naming which origin it is.

Keep the existing exhaustion contract, which already refuses rather than
corrupts, and note that it is the same principle: the crate does not reissue a
live id, and two peers reissuing each other's ids is that fault arriving from a
direction the counter cannot see.

## CHANGE: `DESIGN.md.tmpl`, the monomorphic-handle rationale

The existing section argues the handle stays monomorphic rather than
`Sym<D>` parameterised by domain. That argument is about the **domain** and
survives untouched. Add one sentence distinguishing the shape parameter from it:
a shape is a storage format, not a domain, and a store holds one shape, so
parameterising by shape does not create the erasure boundary parameterising by
domain would.

## CHANGE: `README.md.tmpl`

The feeder summary gains the shape in one clause and the per-generator freshness
contract in one clause. No structural change.

## What this changelist does not do

It does not name the constructors, the trait's method spellings, or whether
`Origin` is a newtype or a `Bits` alias. Those are the source changelist's, and
naming them here would be the doc tier reaching into the code tier's business.

## Lock criteria

- Every claim above is stated in the design document in the design's own voice.
- The default shape is stated as byte-identical to the current layout, and the
  string domain's fixed tag is stated as surviving it.
- The freshness contract reads unambiguously without the reader having to
  notice the phrase "of the same generator".
- No backticked type name appears that the source changelist does not undertake
  to create.
