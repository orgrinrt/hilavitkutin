## Current state

GATE-2 dispatches column-disjoint trunks on separate cores, joined by waist
barriers between phases. op resolved the dispatch mechanism (2026-06-07,
"bench-first: runtime mask"): each worker walks the flat carrier gated by a
runtime mask of the trunks it owns, reusing the shipped `run_gated<M:
BitAccess>`. Single-core is the one-core degenerate of that model, not a
separate path.

R4a landed the mask foundation (`dispatch/core_mask`, round closed, commit
`306a6ba`): `grouping_arrays` lifts the R2 const grouping (`phase_of` /
`trunk_of`, the canonical waist-bounded phase axis plus within-phase trunk
component-mins) into per-unit `phase[]` / `trunk[]` arrays, and
`core_phase_mask` selects, for one core and one phase, the carrier positions
that core runs (bit `u` set iff `phase[u] == p` and the within-phase rank of
`trunk[u]` modulo `ncores` equals the core). Its tests prove every unit is
dispatched exactly once across the per-core programs and that `ncores == 1`
collapses to "core 0 owns everything per phase".

What does not exist yet: a scheduler entry that runs those masks as real
dispatch. `Scheduler` has `run` (flat single-core walk), `run_one_trunk` (one
const-fixed `(phase, trunk)`, the superseded enumeration precedent), and
`run_fused`. None integrates the R4a per-(core, phase) masks into an
end-to-end multi-trunk dispatch.

## Changes proposed

Add `Scheduler::run_parallel<Witnesses, GW>(ncores)`: the GATE-2 N-core
dispatch in its inline (single-threaded) form. It fills `phase[]` / `trunk[]`
via `grouping_arrays`, computes the phase count, then walks
`for phase p { for core c { run_gated(core_phase_mask(p, c)) over morsels } }`.
The phase loop is outermost so the waist barrier between phases collapses to
the loop boundary; within a phase the column-disjoint trunks run in any order;
within a trunk the gated carrier walk preserves topological (carrier) order.

This is output-equivalent to `run` for a pure read-after-write carrier:
phases run in waist order, so a phase-`p+1` reader sees every record a
phase-`p` writer produced; trunks within a phase touch disjoint columns;
each trunk's units run in carrier order. The accumulator (unit-outer / cross
-record) path that `run` routes specially stays out of scope here and lands
with the threaded executor step (a red arm until then, per the strict-by
-design discipline).

Why inline first: it integrates the R4a masks into real dispatch and proves
the per-(core, phase) partition produces correct output, with threading
isolated to the next step. Real worker threads (the spawned-once pool,
column-disjoint borrow split, waist-barrier sync) replace the sequential
core sweep without changing the partition this step proves. The phase /
trunk arrays are recomputed per call in this inline form; the threaded form
lifts them to a build-time precompute (schedule-once-reuse).

The test (`tests/gate2_run_parallel.rs`) builds a fan-in workload (two
disjoint phase-0 producers feeding one phase-1 combiner) and asserts
`run_parallel(USize(2))` computes the combiner output correctly, which holds
only if both phase-0 trunks are dispatched and the phase-1 unit runs after
both. Red first: `run_parallel` does not exist, so the file does not compile.
