# Recommended registration order in the build error

## Current state

D1d-b (round 202606061730) added `BuildError::NonTopologicalRegistration { producer, consumer }`:
the build path rejects an acyclic-but-anti-topological registration and names the
first offending carrier-slot pair (a producer registered after its consumer). The
error tells the consumer which pair is out of order, so the local fix is "register
producer before consumer", but it does not name a full registration order that
would satisfy the gate. `mock/crates/hilavitkutin/DESIGN.md.tmpl` (line 634) already
states the design target: "a BuildError that names the recommended order".

The plan is computed in `compute_plan` at the exact point the gate fires. A
successful plan carries `rcm_order` (the RCM renumber permutation, populated
unconditionally by the plan chain): `rcm_order[new_pos]` is the original `UnitId`
placed at `new_pos`. Per the canonical consolidation Step 5 ("RCM reordering ->
fiber grouping order + arena layout") the RCM row reordering IS the WU execution
order: a topological order that is cache-optimal among the valid topological orders
a naive topo sort would pick arbitrarily. So `rcm_order` is both topologically
valid and the cache-optimal recommended order, matching op call (a) (loimu is
order-sensitive; the recovery mechanism is the RCM-row order).

## Changes proposed

Carry the recommended registration order in the error so a consumer sees not only
which pair is out of order but the full order that would satisfy the gate.

- A `RecommendedOrder` newtype: a fixed-capacity carrier-slot sequence plus a live
  count, sized by the engine's default unit capacity. It exposes the recommended
  order as a slice of carrier-slot indices (`as_slice`) and carries a `Debug` that
  prints the sequence. `Copy + Clone + Debug + PartialEq + Eq` so it composes with
  `BuildError`'s derives.
- `BuildError::NonTopologicalRegistration` gains a `recommended: RecommendedOrder`
  field alongside `producer` / `consumer`. The recommended order is built from
  `plan.rcm_order` (the cache-optimal topological order) over the live unit count.
- No allocation: `RecommendedOrder` is a fixed-size stack value, consistent with
  the no-alloc engine. The error remains a cold, build-time-only value.

The recommended order is the RCM-reordered topological order (canonical Step 5),
not a plain topological sort, because the RCM order is the cache-optimal one and is
what the consumer should register to match the eventual auto-ordering (op call b's
relaxation, the §7-6 guarded walk, will apply the same RCM-row order automatically).

### Test consequence (handled in this round's src CL)

The D1d-b rejection test (`build_rejects_anti_topological_registration`) asserts the
variant shape; it widens to also assert the `recommended` order names the producer
before the consumer (the writer slot before the reader slot in the recommended
sequence). No other test registers anti-topologically.
