# Topic: post-review fixes for the plannable split

**Date:** 2026-07-17
**Phase:** TOPIC
**Scope:** Three fixes from the PR #168 senior review, on the same branch as the plannable split.
None changes the shipped surface; all three close gaps between what shipped and what the round
claimed or the sketch mandated.

## The three findings

1. **The blanket impl is untested (also a claim-vs-shipped mismatch).** The prior src CL claimed a
   test that a `WorkUnit` is accepted at a `Plannable` bound with its associated types recovered. No
   such test shipped. The engine suite compiling proves the blanket impls exist, but nothing in the
   workspace names a `T: Plannable` bound over a real `WorkUnit`, so the forwarding is never
   monomorphised by a test. Fix: add the assertion to `tests/work_unit.rs`, which already defines a
   full `Integrate: WorkUnit<Always>` with a stub `Ctx`, reusing it rather than rebuilding the
   accessor machinery.

2. **The E0119 both-is-a-conflict obligation is missing from the `Plannable` doc.** The sketch
   FINDINGS states that "a downstream type must not be both a `WorkUnit` and hand-implement
   `Plannable`" belongs in the doc comment rather than being discovered at a red build. The shipped
   doc omits it. Fix: add the note to the blanket impl's doc comment.

3. **"The engine reads the first three axes and ignores the fourth" is stated as present fact.** The
   engine is untouched, `SchedulingHint` is a bare marker with no extraction API, and no `HintExt`
   markers ship, so that sentence describes behaviour that is not yet reachable. It appears in both
   `src/hint.rs` and the api `DESIGN.md.tmpl`. Fix: soften both to state the intent (a 4-tuple
   schedules as its `(U, D, S)` prefix would) without asserting an engine mechanism that is a later
   gate.

## What the round does not do

No change to `Plannable`, `HintExt`, the blanket impl, the 4-tuple arm, or the exports. The traits
that shipped are correct; the gaps are a missing test and two over-stated doc sentences.
