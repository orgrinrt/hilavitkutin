## What this round adds

The data foundation for the N-core runtime-mask dispatch op chose: pure functions
that produce, per core and per phase, the unit mask a worker walks. No threading
yet (that is R4b, the executor mainloop keystone); this round ships the mask
machinery and tests it in isolation.

op's chosen mechanism: each worker walks the flat carrier gated by a runtime mask
of its owned trunks (reuse the shipped `run_gated<M: BitAccess>`). Single-core =
one worker owns all trunks = the existing flat walk (already the canonical 1-core
degenerate). The mask a worker needs for (its core, a given phase) is: the units
whose trunk is owned by that core AND whose phase is that phase.

## The mask source (resolved)

Per-unit (phase, trunk) comes from the shipped const grouping (`plan::grouping`,
R2): `phase_of(pos)` / `trunk_of(pos)` give each carrier unit's waist-bounded
phase and within-phase column-conflict trunk, callable at run time with concrete
types. The const-gated mono ENUMERATION (`run_one_trunk` / `RunGatedTrunk`) is
superseded by op's runtime-mask choice, but the grouping DATA stays on-path: it
is the direct per-unit (phase, trunk) source the runtime mask needs, trunk-level,
no CSR traversal. The runtime plan's richer fiber / RCM / spectral structure is an
orthogonal within-trunk ordering refinement (later), not needed for the
trunk-level core mask.

Trunk-to-core ownership is per-phase round-robin (trunks are within-phase, so a
core's owned trunk set is decided per phase, redistributed at each waist barrier;
a global one-trunk-per-core mapping would idle cores across phases they hold no
trunk in). Core `c` owns trunk `t` in phase `p` iff `rank_of(t within phase p) %
ncores == c`, where `rank_of(t within p)` is the count of distinct trunks in
phase `p` with id less than `t` (trunk ids are component-min positions, a stable
order). Round-robin is the simplest correct distribution; a smarter policy
(load-balanced by trunk cost) is a later perf fork (bench, not ask). Single-core
(ncores = 1): every rank `% 1 == 0 == core 0`, so core 0 owns all trunks = the
full walk (the degenerate, no special path). The shipped `CoreAssignment` is the
richer assignment structure R4c's scheduler will populate; R4a needs only the
round-robin policy.

## What lands

1. `grouping_arrays<Wus, Stores, Witnesses, CU, CS, Adj>(phase_out, trunk_out)`:
   fill per-unit phase / trunk arrays by looping the shipped `phase_of` /
   `trunk_of` over the carrier positions. Reuses R2; concrete types at the call
   site (mirrors `gate2_const_grouping` test setup).
2. `core_phase_mask<Adj>(phase, trunk, n, core, target_phase, ncores) -> Adj`
   (`Adj: BitAccess + Identity`, the plan's `D::AdjRow` run_gated mask type): pure
   builder. Bit `u` set iff `phase[u] == target_phase` and the within-phase rank
   of `trunk[u]` modulo `ncores` equals `core`. Lives in a new dispatch helper
   module (`core_mask.rs`).
3. Fail-first tests over a hand-built phase/trunk fixture: assert each (core,
   phase) mask selects exactly the right units; assert the union of all (core,
   phase) masks over all cores and phases equals the full unit set (every unit
   dispatched exactly once across the per-core programs); assert single-core
   (ncores = 1) core-0 masks reproduce the full per-phase walk.
