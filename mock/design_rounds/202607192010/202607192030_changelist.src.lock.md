# Src changelist: make spawn spawn, make deallocate free correctly

**Date:** 2026-07-19
**Phase:** SRC
**Topic:** `202607192000_topic.reachable-bodies-contradicting-contracts.md`
**Doc CL:** `202607192010_changelist.doc.lock.md`

Each defect gets its failing test before its fix, so the fix has something that fails first
rather than something that merely passes afterward.

## CHANGE: `tests/platform_std.rs` GAINS a spawn observation test

File: `mock/crates/hilavitkutin/tests/platform_std.rs`

No test exercises `ThreadPoolApi::spawn` under `platform-std`, which is why a pool that
spawns nothing has stayed green. The test spawns a closure that stores into an
`Arc<AtomicBool>` and joins on a channel with a timeout, asserting the closure ran.

Against the current body it fails by timing out rather than by running and observing false,
which is the honest shape: the defect is that nothing runs, so nothing sets the flag.

Verification: `cargo test -p hilavitkutin --features platform-std --test platform_std`
fails before the next change and passes after.

## CHANGE: `StdThreadPool::spawn` FROM `let _ = _f;` TO a real `std::thread::spawn`

File: `mock/crates/hilavitkutin/src/platform/std_tier.rs:119`

The body becomes `std::thread::spawn(f);`, and the parameter loses its underscore. The bound
on the signature is already `F: FnOnce() + Send + 'static`, which is exactly what
`std::thread::spawn` requires, so no boxing and no allocator is involved.

The stale comment pointing at `os.rs` goes. It described a `no_os` constraint that does not
hold in this tier, and leaving it would preserve the reason the gap looked intentional.

Verification: `! grep -q "let _ = _f;" mock/crates/hilavitkutin/src/platform/std_tier.rs`,
and the spawn test above passes.

## CHANGE: `MemoryProviderApi::deallocate` GAINS an `align` parameter

File: `mock/crates/hilavitkutin-api/src/platform.rs:44`

Signature becomes `unsafe fn deallocate(&self, ptr: *mut u8, len: USize, align: USize)`. The
safety comment states that all three must match the prior `allocate`, per the locked doc CL.

Verification: `grep -q "fn deallocate(&self, ptr: \*mut u8, len: USize, align: USize)"`
on that file.

## CHANGE: every `deallocate` impl and call site ADOPTS the alignment

Files: `platform/std_tier.rs:68`, `platform/os.rs`, `hilavitkutin-providers/src/storage.rs:78`
and `:159`, plus the test providers in `tests/resource_bindings.rs`,
`tests/platform_std.rs`, `tests/platform_os.rs`, and
`hilavitkutin-providers/tests/column_storage.rs`.

`StdMemoryProvider::deallocate` builds its `Layout` from the passed alignment instead of
`align_of::<usize>()`. `ArenaColumnStorage` passes `CACHE_LINE_ALIGN` at both free sites,
matching what it passes at `:99`.

Verification: `! grep -q "align_of::<usize>()" mock/crates/hilavitkutin/src/platform/std_tier.rs`
in the deallocate body, and `cargo test --workspace` green.

## CHANGE: `providers/tests/column_storage.rs` DROPS its avoidance rationale

File: `mock/crates/hilavitkutin-providers/tests/column_storage.rs:5-13`

The module doc currently explains that `StdMemoryProvider` is avoided because its
`deallocate` mismatches a 64-byte block. Once the mismatch is gone the rationale is false,
so it goes, and the note becomes a plain statement of what the bump provider is.

A test that documents a defect as a reason to avoid exercising it is worth calling out
rather than quietly deleting: the comment was accurate, and the suite stayed green because
the failing path was routed around rather than fixed.

Verification: `! grep -q "mismatches a 64-byte-aligned block"` on that file.

## CHANGE: `classify_cores` module doc STATES its actual state

File: `mock/crates/hilavitkutin/src/thread/class.rs:1-6`

The doc asserted "The engine queries `classify_cores()` once at pool construction" as fact.
It becomes a statement of intent, followed by an explicit note that nothing calls the function,
that every `detect_into` arm discards its argument, that all cores are therefore treated as P,
and that wiring is band W3. No behaviour changes; the function is unreached either way.

Verification: `! grep -q "engine queries \`classify_cores" mock/crates/hilavitkutin/src/thread/class.rs`.

## CHANGE: `AdaptArena` module doc STATES its state before describing its target

File: `mock/crates/hilavitkutin/src/adapt/arena.rs:1-8`

The module doc opens by describing "per-fiber 64-byte-aligned hot lines", "per-core 64-byte-aligned
park slots" and a "cold SoA region" in present tense. The struct is two `PhantomData` fields. The
module does disclose this, at lines 14 to 18, but twelve lines after the claim, which is far enough
that a reader who stops at the first paragraph comes away with the wrong picture.

The fix front-loads the state: the module now says it is not built, that the struct is two
`PhantomData`s, and that the description that follows is the target rather than a report. The design
prose stays as written, because it is correct about the intent.

Worth recording how this one nearly went wrong. A first pass through this round read only the struct
doc at `:23`, saw it honestly say "the fields land in Pass 6", concluded the audit had overcalled
the entry, and started writing that correction into both the CL and the audit. The module doc above
it, unread, was the thing the audit was actually describing. The audit was right; the correction was
the error, produced the same way as the two mistakes the audit itself documents, by judging from a
partial read. It was caught before it landed, which is the only difference.

## CHANGE: `tests/platform_std.rs` clock assertion IS REHABBED

File: `mock/crates/hilavitkutin/tests/platform_std.rs:53-56`

Discovered while adding the spawn test: this file did not compile under `platform-std` at all.
`now_ns()` returns a `UFixed` that implements neither `PartialOrd` nor `Display`, and the
assertion compared and formatted it directly. The os-tier copy was updated to `.to_raw()` when
that API changed; the std-tier copy was not, and nothing noticed because nothing built it.

The assertion adopts the same `.to_raw()` shape as `platform_os.rs:60-62`.

This is worth stating as a finding rather than a tidy-up. `platform-std` is described as a
supported configuration with its own smoke tests and its own validation gate, and its smoke
tests could not build. A gate that never compiled the thing it gates is not a gate.

Verification: `cargo test -p hilavitkutin --no-default-features --features platform-std` builds
and passes.
