# Topic: reachable bodies that contradict their own contracts

**Date:** 2026-07-19
**Phase:** TOPIC
**Scope:** `platform/std_tier.rs` spawn and deallocate, plus doc comments that describe
behaviour their bodies do not perform.
**Grounded on:** `mock/research/202607191400_engine-three-way-audit.md` (live defects),
sequenced by `mock/research/202607191500_engine-roadmap-r7.md` band 0.

The engine audit read function bodies rather than names, and found reachable code whose
behaviour contradicts the contract stated directly above it. These are worse than absent
implementations. An absent implementation fails loudly at its call site. A body that returns
normally while doing nothing lets every caller above it proceed on a false premise, and the
doc comment actively confirms that premise to anyone who reads it.

This round takes the two that are executable defects, plus the doc comments that misdescribe
their own bodies. The fourth defect, `replace_resource` discarding its argument, is not here:
op directed that its install arm be sketched before the contract is decided, so it gets its
own round once that sketch reports.

## The pool that spawns nothing

`StdThreadPool::spawn` (`platform/std_tier.rs:119`) takes `F: FnOnce() + Send + 'static` and
its body is `let _ = _f;`. The closure is dropped, never run. The module doc calls the type a
"`std::thread`-backed thread pool", and the inline comment reads "See os.rs: generic-closure
support arrives in 5a4."

That comment is the interesting part, because it is a constraint borrowed from a different
tier. In the `no_os` tier a generic closure genuinely cannot be spawned without boxing it, and
boxing needs an allocator the crate does not have. Under `platform-std` the constraint does
not apply: `std::thread::spawn` accepts exactly `F: FnOnce() + Send + 'static`, which is
already the bound on the signature. The same module calls it fifteen lines above, in
`spawn_fn`, which nothing uses.

So the tier that could implement this in one line inherited a blocker from the tier that
cannot, and the borrowed comment made the gap look deliberate.

The consequence is that `run_parallel` publishes a frame and blocks on `frame_await_done`
waiting for workers that were never created. `platform-std` is a real feature with its own
smoke tests and its own validation gate, so this is a supported configuration that hangs.
Stated precisely: the hang is a read of the code, not an observed failure, because no test
exercises `spawn` under that feature. Establishing the observation is the first act of this
round, so the fix has something that fails before it.

## The deallocation that forgets its alignment

`StdMemoryProvider::deallocate` (`:68`) reconstructs the `Layout` for the freeing call using
`align_of::<usize>()` rather than the alignment the allocation was made with. For any
allocation whose alignment exceeds a word this is undefined behaviour, and the engine asks for
exactly that: 64-byte column alignment is canon (consolidation spec `:562`), so the case the
engine depends on is the case that breaks.

The reason the bug is easy to miss is structural. `MemoryProviderApi::deallocate` carries
`len` but not `align`, so the alignment has to come from somewhere, and reconstructing it from
a guess is the shape of the defect. Any real fix makes the original alignment available at the
free site rather than inferring it, which is a question about the contract and not only about
this body. The round decides that shape before writing it.

## Doc comments that describe absent behaviour

Two bodies state behaviour they do not perform. `classify_cores` (`thread/class.rs:55`) carries
a module doc describing sysfs, sysctl and `GetSystemCpuSetInformation` probing, and asserting
"The engine queries `classify_cores()` once at pool construction"; its four `detect_into` arms
each discard their argument, and nothing calls it. `AdaptArena` (`adapt/arena.rs:30`) is two
`PhantomData` fields behind a doc describing an arena.

Neither is reached, so neither is an executable defect today. They are corrected here as
documentation only. The wiring decision belongs to the bands that own those subsystems, and
pulling it forward would be scope creep into work that has its own dependencies. What is fixed
now is the false promise, because a doc comment claiming a mechanism the body lacks is exactly
how this audit's own earlier drafts went wrong, twice, by reading such a comment as evidence
that the mechanism shipped.

## Out of scope

The `replace_resource` install (sketch first, then its own round). Core-classification and
adapt-arena wiring (bands W3 and W4). Any change to `MemoryProviderApi` beyond what the
alignment fix strictly requires.
