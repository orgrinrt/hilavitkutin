**Date:** 2026-06-08
**Phase:** TOPIC
**Round:** 202606081900 (GATE-2, task #685, branch `feat/hilavitkutin-parallel-engine-gate2`)
**Source:** canonical consolidation spec `:2119-2137` (Self-hosting scheduler, T5 §Q9 L716-802) + `:1989` (adaptation via `On<meta::ScheduleEnd>`); roadmap r2 (`mock/research/202606081500_engine-roadmap-r2.md`); E4 slice-1 (round 202606081200, closed: virtual firing + `On<V>` gating shipped).

The engine is meant to be self-hosting: the scheduler schedules itself through meta WorkUnits fired at lifecycle points, the same `Virtual` / `On<V>` machinery slice 1 just made real for consumer work. Slice 2 stands up that meta layer: the four meta lifecycle virtuals as real fired virtuals, the `MetaAccess` gate that restricts the four meta resources to meta WUs, and the irreducible kernel that fires the virtuals in canonical order around the dispatch the engine already drives. The consumer-facing payoff (an `On<meta::ScheduleEnd>` adaptation WU, phase-overlap pipelining, domain-22 reshaping) is slice 3 / E8, one connected arc; slice 2 builds the substrate those hooks attach to.

## What the canonical spec states

The self-hosting scheduler (`:2119-2137`) is a pipeline over four meta virtuals and four meta resources, driven by a ~50-line kernel:

Meta virtuals (fired by the kernel):
- `meta::PlanStage` — fired when the DAG changes (recompute the plan).
- `meta::ScheduleReady` — fired when plan-stage units complete (per-core programs assembled).
- `meta::PassStart` — fired at the start of each pass.
- `meta::ScheduleEnd` — fired after all consumer work (the adaptation observation point, `:1989`).

Meta resources (restricted via the `MetaAccess` marker trait):
- `meta::Dag` — the dependency graph.
- `meta::ExecutionPlan` — fiber / trunk / phase assignments.
- `meta::LaneAssignment` — core assignments.
- `meta::SchedulerMetrics` — EMA timing data (domain 22).

The irreducible kernel (`:2136-2137`): fire `PlanStage`, wait for the plan WUs, fire `ScheduleReady`, dispatch the consumer WUs, fire `ScheduleEnd`. `PassStart` fires at each pass top inside that loop. "Schedule once, reuse across frames" (`:2110-2117`): `PlanStage` fires only when the DAG changes (rare), so the plan-stage recompute is amortised; the steady-state frame fires `PassStart` -> dispatch -> `ScheduleEnd`.

## What exists today (truth-of-impl)

- The four lifecycle markers ALREADY exist as plain marker structs in `hilavitkutin-api/src/run_cfg.rs` (`PlanStage:172`, `ScheduleReady:178`, `PassStart:184`, `ScheduleEnd:192`), with doc comments already framing them as `On<PlanStage>` / `On<ScheduleReady>` / etc. observation points. They are NOT yet fired anywhere, and they are markers, not registered `Virtual<_>` stores.
- Slice 1 shipped the firing + gating machinery the kernel needs: `VirtualFirerApi::fire<V, I>` (real, stamps the cell), `On<V>` dispatch-gating via `GateWith` (stamp == epoch), the shared `VirtualStampSelector`, the per-pass `virtual_epoch`. A producer fires `Virtual<V>`; an `On<V>` consumer ordered after it runs.
- `MetaAccess` does NOT exist. The `host.rs` / `extension.rs` hits are the unrelated plugin-extension descriptor surface.
- The scheduler `run` / `run_parallel` loop does the real per-trunk dispatch but fires no meta virtuals and has no meta-resource concept.
- The kernel sketch `mock/research/sketches/202606062100_e4-meta-wu-pipelining` proves the FIRING ORDER + frame-loop shape (PlanStage-only-on-dirty -> ScheduleReady -> PassStart -> dispatch -> ScheduleEnd) but is GATE-1-era: it predates the const-gated dispatch and the slice-1 virtual mechanism, and uses the stale `dispatch::fiber_walk::{WuCons,WuNil}` path. Its value is the order + loop shape, not the current types.

## Open design questions (resolve in the DOC phase, re-grounding T5 §Q9 L716-802)

1. **Carrier shape for meta WUs.** Are meta WUs registered in the SAME builder carrier as consumer WUs (so the existing per-trunk dispatch runs them, gated `On<meta::X>`), or a SEPARATE meta-carrier the kernel dispatches explicitly? The spec's "fire PlanStage, WAIT for plan WUs, fire ScheduleReady" reads as explicit kernel sequencing, which argues for the kernel dispatching meta WUs at explicit points rather than relying on the consumer-grouping to order them (and sidesteps slice-1's known gap: the grouping does not yet treat a `Virtual<V>` write -> `On<V>` as a scheduling edge).

2. **What slice 2 actually fires vs defers.** Minimum coherent slice-2: the four markers usable as `Virtual<meta::X>`, `MetaAccess` gating the four meta resources, and the kernel firing the four at the canonical lifecycle points around the existing dispatch (observable: a meta WU bound `On<meta::ScheduleEnd>` runs once per pass after consumer work). The real adaptation WU body + phase-overlap pipelining + domain-22 reshaping is slice 3 / E8 (`:1989`, `:2042-2048`).

3. **`MetaAccess` mechanism.** A sealed marker trait on the four meta resource types plus a bound on the meta WU's Ctx (or on the resource accessor) so consumer WUs cannot reach `meta::*`. Mirror the existing access-set gating; decide whether `MetaAccess` is a supertrait bound on a meta-resource provider trait or a marker checked at registration.

4. **`meta::PlanStage` "wait for plan WUs".** How the kernel's "wait for plan-stage units to complete" maps onto the current dispatch (the plan-stage units are a phase the kernel runs before firing `ScheduleReady`). Likely: plan-stage meta WUs run, the kernel observes completion (version stamp / explicit return), then fires `ScheduleReady`.

5. **`PassStart` vs `PlanStage` cadence.** `PlanStage` fires only on DAG change (the `plan_dirty` seed already on the scheduler); `PassStart` fires every pass. The kernel reads `plan_dirty` to decide whether to fire `PlanStage`.

## Slice-2 scope boundary

In: the four meta virtuals (markers -> fired virtuals), `MetaAccess` + the four meta resource types gated by it, the kernel firing the four at lifecycle points in `run` (single-core first; `run_parallel` parity after), a behavioral test (a meta WU `On<meta::ScheduleEnd>` observes it ran once per pass after consumer work; `On<meta::PlanStage>` runs only on a plan-dirty frame). Out (slice 3 / E8): the real domain-22 adaptation WU body, phase-overlap pipelining via progress counters, EMA-driven plan recompute, consumer-authored meta hooks beyond the test.
