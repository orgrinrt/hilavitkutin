Op ruled, verbatim, "Configurable by the consumer", asked among [a refusal as a value everywhere | the assert stays the default, refusal is a provider's opt-in | configurable by the consumer: a const, generic or trait parameter on the run configuration picks refuse or assert, default refuse]. The intent: the consumer picks at compile time, on the run configuration, between the refusal as a value (the default) and a run that panics on it. This changelist states it in both designs and the README.

## Changes

### CHANGE 1: `hilavitkutin-api/DESIGN.md.tmpl`, `AccumRefused` and the run's output

The section's second half is rewritten. Every run entry has the frame's verdict, `notko::Outcome<(), AccumRefused>`, at the close. A sealed `AccumOverflow` (`type Out; fn conclude(verdict) -> Out`) names the choice, a fixed engine vocabulary of two: `Refuse` (the verdict is the output) and `Assert` (the output is `()`, a refusal panics naming the `AccumRefused`). `RunCfg` carries it as `type Overflow: AccumOverflow<Out = Self::Out>`, and every run entry returns `Cfg::Overflow::conclude(verdict)`. `DefaultRunCfg<O: AccumOverflow = Refuse>` is the one impl: `build` keeps the refusal, `build_with::<DefaultRunCfg<Assert>, _, _>` takes the assert. Under `Assert` the output is `()`, so a consumer cannot name `AccumRefused` in it. The append path is the same under both; the assert fires at the close on the calling thread after every worker re-parks, so it never stalls a `run_parallel` join. The `From` bound on `RunCfg::Out` goes, since `()` cannot be built from the verdict. The `impl RunCfg for MyApp` example gains `type Overflow`.

### CHANGE 2: `hilavitkutin-api/DESIGN.md.tmpl`, the accumulator writer

The refusal paragraph after the bridge block says the run concludes on the first refusing accumulator, returned under `Refuse` or asserted under `Assert`.

### CHANGE 3: `hilavitkutin/DESIGN.md.tmpl`, appending past the capacity

The paragraph opens on the refusal being never written and never a silent drop, a value by default and a panic when the consumer picks it. The close walks into the verdict and hands it to the configuration's `AccumOverflow`; it states where the `Assert` panic fires and why that place: `dev` asserted inside the append, so under `run_parallel` the panic hit a worker and the join stalled. The drain paragraph says the run entry concludes on the first refusing accumulator, returned or asserted by the choice.

### CHANGE 4: `README.md`, the two choices

A paragraph in the builder section says an over-capacity append is never written, that the run returns the refusal as a value by default, and that `build_with::<DefaultRunCfg<Assert>, _, _>` returns `()` and panics at the end of the frame on the calling thread. A root document needs no round; it is listed so the round names what it touched.
