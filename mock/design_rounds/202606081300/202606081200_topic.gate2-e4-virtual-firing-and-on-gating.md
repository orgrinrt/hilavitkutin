## Why this is next (truth-of-impl, 2026-06-08)

The GATE-2 parallel core is functionally complete: per-trunk core-pinned dispatch (`dispatch_core`, round 202606080600), waist barriers (sense-reversing, multi-episode, shipped), general DAGs incl. fan-in/fan-out across waists (the `gate2_run_parallel` two-waist test), and a fair perf oracle (engine at parity with optimal multi-threaded std, round of 202606081100). Walking the remaining r4 stages against the source:

- G2-Nc bridge fan-in (full range): already shipped. A bridge that runs after the waist is a normal phase-(p+1) WU reading multiple prior-phase columns, which the two-waist test exercises green. Sketch C (`202606070600`) confirms the partial-range progress-gated bridge is an E4 refinement riding on progress counters, not a standalone stage.
- E3 multi-episode waist barrier: shipped (`thread/barrier.rs` sense-reversing barrier handles a fast worker looping into the next episode).
- E4 self-hosting meta pipeline: NOT built. `VirtualFirerApi` in the engine is a B3 no-op (`engine_ctx.rs:1047`), and no dispatch path gates a WU on a fired virtual (`On<V>` is an API marker with no engine wiring). The four meta lifecycle virtuals and `MetaAccess` do not exist.

So E4 is the next genuinely-unbuilt canonical stage, and its foundation (real firing + `On<V>`-gated dispatch) is what both the meta lifecycle pipeline and consumer event-driven WUs (domain 10) need.

## This round's mechanism (to design in the doc/src CLs)

The firing surface already exists in the API: `VirtualFirerApi<W: AccessSet>` (context.rs:179) with `HasVirtualFirer`, `Virtual<T>` (store.rs:155), `On<V>` (work_unit.rs:25), `VirtualBinding<T, Tail>` (engine bindings.rs:163). The gap is engine behaviour:

- Firing: a WU calls `ctx.virtuals().fire::<V>()` (or equivalent); the engine records `V` in a frame-scoped fired-set carried on the bindings (a small fixed-cap mask keyed by the registered `Virtual` position, mirroring how columns/resources are positioned). Cleared at frame start (like the accumulator reset).
- Gating: a WU registered with an `On<V>` trigger dispatches in a frame iff `V`'s fired-bit is set when the walk reaches it. The const grouping already orders units by dependency; an `On<V>` consumer is ordered after the firer (the virtual is a DAG edge), so by the time the walk reaches the `On<V>` unit the firer has run this frame and the bit is current. The gate is a runtime bit-test in the per-unit walk (cheap, like the dirty-skip mask), not a new dispatch path.

Open question for the doc round: whether `On<V>` gating composes with the const-gated per-trunk walk (`RunGatedTrunk` / `dispatch_core`) by folding into the existing `dirty`-style per-member mask, or needs a separate fired-mask threaded alongside. The dirty mask is already a per-member `BitAccess` gate; the fired-set is the same shape, so the likely answer is a second mask ANDed at the member gate. A sketch will confirm before the src CL.

## Tests / gates (strict, fail-first)

- A consumer firer WU fires `Virtual<V>`; an `On<V>` consumer WU runs that frame and observes the effect; with the firer absent (or not firing), the `On<V>` consumer does NOT run. Red first (the no-op firing makes the consumer never/always run until the mechanism lands).
- Output bit-identical for the non-virtual workloads (the full engine suite stays green; firing is additive).
- D6 ASM gate: the `On<V>` gate is a bit-test, not an indirect call; devirt preserved.

## Out of scope (later E4 slices)

The four meta lifecycle virtuals, `MetaAccess`, the self-hosting kernel wiring, consumer metrics hooks, phase-overlap pipelining, and domain-22 adaptation. This round is only the firing + `On<V>` gating mechanism they all build on.
