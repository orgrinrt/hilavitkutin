# engine-design-registers-with-a-start

The round before this one (`202611132307`, topic `202611132304_topic.column-start.md`) settled how a column starts: a column of either kind is registered with its start, through `Column::<T>::start()`, `Column::<T>::start_from(value)` or the same two on `Buffered<T, M>`, and the bare marker registers nothing. Its design change was made in `hilavitkutin-api/DESIGN.md.tmpl` and in the engine design's section on bindings. Its source changelist left one thing for a round of its own, since a design is not edited in the source phase: the engine design still shows a plain column registered by the bare marker in the section on the builder.

## What is stale, by place

All three are in `mock/crates/hilavitkutin/DESIGN.md.tmpl`, in the section that begins "The builder takes one verb".

The example call site registers `.with(Column::<Player>::new())` with the comment "store: zero-data". Since the column start that line does not build: `Column<T>` has no impl of the builder's input trait, and the compile-fail arm `tests/trybuild/column_marker_registered.rs` of the api crate holds it so.

The paragraph on how `.with` routes lists `Column<T>` among the store providers. What is registered for a column is the carrier `Started<S>`.

The quoted diagnostic for a store nobody registered names `.with(Column::<Interner>::new())` as one of the ways to register it. The source's note, on `Holds` in `hilavitkutin-api/src/access.rs`, says `.with(Column::<T>::start())` since the column start, and the quote is of that note.

## What this round does

It brings those three places to what the api design and the source say. Nothing else of the section moves, and no source changes with it.

The same section calls the builder's input trait `Provider` where the source has `BuilderInput`. That is older than this branch and is the same staleness the kit and providers designs carry, on ticket 63f55f605465; it is left to that work so this round stays the size of what the column start left behind.
