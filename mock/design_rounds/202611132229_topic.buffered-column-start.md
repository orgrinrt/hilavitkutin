# buffered-column-start

What every record of a buffered column holds before any unit has written it.

## Where it comes from

Review 1 of `work/api-revision` at `eeb7f555`, finding 2. The drain reserves both sides of a `Buffered<T, M>` and initialises neither, and in the first pass every read through `map` goes to the frozen side, which nothing has written. No supported call fills it between `build` and the first `run`. The engine's tests fill it through the hidden `__frozen()`. The api design says what the second pass reads and not what the first one does. The review left the answer to op.

## Op's words

Asked what pass 1 reads from the frozen side of a buffered column, 13 November, between 20:15 and 20:30 UTC, relayed by the coordinator on the channel at 20:41 with these three as his words verbatim. The options he was shown are not in what reached this seat.

1. "Pretty sure notko has some traits for this. If the type implements the null bit or whatever equivalent then that should be used for init. If it implements default, then that. If neither, only method available is explicit initial value"
2. "HasTrivialCtor is another one to support too"
3. "This should follow the same pattern as ctx does. As in wrong APIs that aren't applicable aren't even available and result in compiler error."

The intent, in this seat's words. The element type of the column decides what the column starts from. There is a sequence: the type's null bit, its trivial constructor, its default. Where the type gives none of them, the only way to name the column is with an explicit start. A way that does not apply to a type is not there for it, and reaching for it does not compile, the way a context has a method only where its providers give it. Nothing leaves a side unwritten behind a safe call.

Kept for provenance and not an intent: "Pretty sure notko has some traits for this" is a pointer to look, and "or whatever equivalent" leaves the name of the null trait open.

The coordinator's reading of the sequence is null bit, then `HasTrivialCtor`, then `Default`, with the tiers that exist landing where `notko` lacks one and a ticket upstream for the one it lacks.

## What `notko` holds

Asked of the clone at `8a74dbc`, which is the `dev` the manifests take.

`HasTrivialCtor` is there, a const trait with `fn new() -> Self`. `Default` is core's.

No trait gives a type a null value. `NicheFilled` is the nearest name, and it says the reverse: it marks a type whose all-zeros pattern is not one of its values (references, `NonNull`, the `NonZero` integers, function pointers), which is what lets `MaybeNull<T>` use that pattern for its own null. A column of such a type has no value to start from by that trait. The types that do carry a null of their own, `MaybeNull<T>`, `Slot<T>` and `Maybe<T>`, say it through `Default` and nothing else. So the null tier is not buildable from `notko` today, and every type it would cover is covered by the default tier. Ticket df2e4da2d376 asks `notko` for the trait.

## The shape

The store that is registered says its start, and the marker alone is no longer something the builder takes. `Resource<T>` is already this way: `Resource::new(value)` hands the builder a carrier of the value.

`Buffered::<T, M>::new()` stays the marker a unit names the store by, and is not accepted by `with`. `Buffered::<T, M>::start_from(value)` is there for every element type. `Buffered::<T, M>::start()` is there where the type has a trivial constructor or a default, and means the constructor where it has both. Each hands the builder the same carrier, which holds the one value, and the engine writes it to every record of both sides at build. The engine has one path and does not know which tier the value came from.

The sequence between the two tiers cannot be two blanket impls of one trait, since they overlap and ranking them is specialisation. It is had from lookup: `start` is an inherent function under the constructor's bound and a trait's function under the default's, and an inherent function is found first and passed over where its bound does not hold. The sketch `202611132225_buffered-start-by-type` shows it on `notko`'s own trait, with the case that fails and the refusal in the compiler's words.

Both sides are written, and not the frozen one alone. Under `Snapshot` a unit may write part of the store and the boundary copies the whole live side over the frozen one, so a record no unit wrote would carry whatever the live side held. Under `Exchange` the live side becomes the frozen one.

## What it leaves open

The choice between the tiers is made where `start()` is written, from what is known of the type there. A generic caller that knows only that the type has a default gets the default, also for a type that has a constructor too.

When `notko` gains the null trait, a third tier ahead of the two needs one more level of lookup, since two inherent functions of one name overlap. Not designed here.

A plain `Column<T>` has the same hole and is not in this round, whose order named the buffered column: ticket 9b64b95e42d1.
