# Topic: GATE-2 const grouping from the registered bundle

**Date:** 2026-06-07
**Phase:** TOPIC
**Scope:** hilavitkutin engine, `plan` module. The first build round of the GATE-2 carrier mechanism (op mandate 2026-06-07).
**Source:** roadmap r4 (`mock/research/202606070700_engine-roadmap-r4-gate2-mechanism.md`), mechanism sketches `202606071230` / `202606071330` / `202606070800`, canonical spec domain 17 (`mock/design_rounds/202604200055/202603181200_topic.hilavitkutin-design-consolidation.md:1540-1617`).

## What this round does

Compute the GATE-2 grouping (per-unit phase + trunk assignment) at compile time from the registered work-unit bundle, as a const-evaluable structure the later const-gated dispatch walk indexes. This round is the grouping computation only; it does not touch `Scheduler::run` (that is the next round).

The grouping is a pure function of the registered types: each WU's `Read`/`Write` `AccessSet` folds to a store-bit mask over the global `Stores` numbering, read-after-write edges between masks give phase depth, and within-phase column-disjoint components give trunks. Sketch `202606071330` proved the const fns; sketch `202606070800` proved the fold compiles as a `const trait` over a fixed-capacity array with the grouping exposed as an associated `const`, and that a `const { trunk_of(POS) == TRUNK }` gate DCEs the dispatch walk to member-only per-trunk programs.

## The mechanism (proven), and how it maps to the engine

The carrier materialisation is pure Rust: const-eval grouping plus a const-gated flat-carrier walk that DCE collapses into N isolated, devirt-clean, member-only per-trunk programs (one per core, run with zero cross-trunk sync, joined only by the waist barrier). No proc-macro, no build.rs, no LLVM pass. Features: `const_trait_impl` + `generic_const_exprs`, both already enabled in the engine crates.

The engine already ships the bit-index machinery this needs: `plan::project` has `Locate<Target, Index>` (type-level position witness), `WitnessIndex { const INDEX }` (already const), and `MaskProject` (a `pub const trait` folding an access set to an `AccessMask` via `Locate` + `INDEX`). `AccessMask` is fully const (`empty`/`set`/`overlaps`/`raw`). So the per-unit masks reuse `MaskProject`; this round adds the const grouping over them.

## Reconciliation: flat-carrier const-gate supersedes the value-nest

G2-0a/0b (rounds on this branch) built `RunTrunk` / `RunPhase` / `RunPipeline` over value-carrying nested carriers (`FiberCons` / `TrunkCons` / `PhaseCons`), executing r3's plan to build a nested carrier *type* from the plan. That plan walled at G2-0c (deriving a heterogeneous nested type from flat registration is a forbidden type-level N-way partition; see the fork doc `202606071200`). The canonical mechanism (spec domain 17) instead emits, per core, a flat ordered sequence of that core's WUs with barriers between phases. The proven realization is a flat `WuCons` walk gated by `const { phase_of(POS) == PHASE && trunk_of(POS) == TRUNK }`, member positions delegating to the unchanged `RunFiber`, DCE producing one member-only mono per (phase, trunk).

Consequence for the build: `RunFiber` is reused verbatim (member execution). The value-carrier walks `RunTrunk` / `RunPhase` / `RunPipeline` and the `FiberCons` / `TrunkCons` / `PhaseCons` carriers are superseded by the flat-carrier const-gate for trunk isolation; they are not extended by this arc. Whether to remove them is a later cleanup CHANGE (they are unused, not harmful); this round does not touch them. `RunPipeline`'s phase-loop-plus-`waist_barrier` logic is conceptually reused later (the per-core program loops phases with a barrier between), but driven by const phase gates over the flat carrier, not a `PhaseCons` value walk.

This reconciliation is derivable from the canonical design (the flattener is the oracle; the value-nest was intermediate-round drift), per `canonical-design-outranks-intermediate-rounds`. It refines roadmap r4, which already records that the mechanism replaces G2-0c; this names the further consequence that the G2-0a/0b value walks are superseded rather than built upon.

## The one new compile-risk this round resolves (gap a)

The mechanism sketches used a hardcoded per-unit mask. This round wires the real `MaskProject` const trait into a const fold over the registered bundle. `MaskProject` threads its store-position witness list (`Indices`) as a call-site-inferred type parameter to dodge E0207 and the duplicate-store coherence wall. A const grouping computed as an associated const has no value-level call site to infer that witness list from, so the witness list is threaded as a type parameter of the grouping carrier (the same shape `BundleProject` uses at runtime). Confirming that `MaskProject`'s const `project_mask` composes inside a const fold with the witness list so threaded is the round's first fail-first step; if it walls, that is the finding to handle (most likely a witness-list parameter on the grouping carrier, precedented by `BundleProject`).

## Build sequence after this round

Next round: the const-gated flat-carrier dispatch walk (`run_gated::<Bundle, PHASE, TRUNK>`) delegating members to `RunFiber`, re-pointing `Scheduler::run` to dispatch the per-(phase, trunk) monos single-core in phase order with the degenerate waist barrier between phases, output-equivalent to the current flat walk, `#664` no-regress. Then G2-N core-pinning: assign each phase's trunks to pool threads, run concurrently zero-sync with the shipped `phase_barrier_arrive` waist (sketch B keystone). Bench is the GATE-2 oracle; the `#664` branching/accumulator red arms turn green via real trunk parallelism + waisting, never single-core stopgaps.
