# Topic: a generic interned-identity core, with strings as one domain

**Date:** 2026-07-24
**Phase:** TOPIC
**Scope:** factor a domain-agnostic interned-identity crate out of `hilavitkutin-str`; make `hilavitkutin-str` a consumer that supplies the string domains. No change to the string interner's behaviour or the baked linker-section layout.
**Source topics:** a vehje consumer need (a fresh-binder identity for the ANF and macro-expansion passes) plus op's direction that a minted identity is not a string concern and interning should be generalised beyond strings into a reusable form. The consumer-side design that surfaced this is `vehje/mock/research/202607241815_generic-interning-and-anf-gensym.md`; that consumption lands in a separate vehje round, not here.

Today `hilavitkutin-str` owns one interned-identity handle, `Str`, hardwired to one family of concerns: compile-time strings registered through a linker section, and runtime strings handed out by an arena. The handle is a 4-byte integer-equality identity whose top bit distinguishes const from runtime origin. That shape is more general than the string concern it currently serves. The handle, the integer-equality identity, and the two ways a value acquires a handle (deduplicated from an existing value, or minted fresh) are all domain-agnostic. Only the const linker section, the FNV hashing, and the arena resolution are actually about strings.

A vehje pass needs a fresh compile-time identity for a bound variable it introduces during normalisation. That identity has no text, is never resolved to a string, and exists only to be compared for equality against other identities. Riding it on the string handle by claiming one of the reserved flag bits would conflate two concepts that merely share a bit layout. The property the pass depends on, that a minted identity provably never equals an interned-string identity, should fall out of a genuine distinction between two domains of one identity core, not from a flag squatting on the string type.

So this round lifts the generic parts of `hilavitkutin-str` into a new standalone crate and leaves the string-specific parts where they are, now expressed as one domain of the generic core. The new crate knows nothing about strings. `hilavitkutin-str` depends on it and supplies the string domains. A future domain (interned paths, interned type keys, a consumer's minted-identity need) brings its own table or its own counter and reuses the same handle, the same equality, and the same domain-tagging, which is the reuse the direction asks for. This round is the identity core and the `hilavitkutin-str` refactor only; every consumer of the new generative half lands in its own round.

## Current state

`hilavitkutin-str` ships `Str`, a `#[repr(transparent)]` 4-byte handle over `StrLayout` (an `arvo::bitfield!` over `Bits<32, Hot>`). The layout is `origin: 1 at 31`, `reserved: 3 at 28` (documented "unused today"), `id: 28 at 0`. `Str::__make` builds a const-origin handle (origin 0); `Str::__runtime` builds a runtime-origin handle (origin 1). `is_const` reads the origin bit. `str_const!` bakes a `StaticStrEntry { hash: Str, value: &'static str }` (a `#[repr(C)]` record, `hash` first) into a platform linker section and returns the same const `Str`; the const handle's id is the FNV-1a content hash truncated to 28 bits. `StringInterner<A: ArenaInterner>` consults the const section first, then falls back to the host arena for runtime strings, tagging the result with `__runtime`. Nothing outside this workspace depends on any of it.

## Changes proposed

Factor a new crate `hilavitkutin-sym` holding the domain-agnostic identity core, and rework `hilavitkutin-str` into a consumer of it. The decisions this round settles, each stated as the chosen shape:

The identity handle. `hilavitkutin-sym` defines `Sym`, a 4-byte `#[repr(transparent)]` handle over a `SymLayout` bitfield with `kind: 4 at 28` and `id: 28 at 0`. This reinterprets the current `Str` layout's four high bits (one origin plus three reserved) as one 4-bit `kind` field over the same 28-bit id. It is a zero-byte-change reinterpretation: every bit pattern a `Str` can hold today is a valid `Sym`, and the fields simply gain a unified meaning. `Sym` carries integer-equality identity on its whole 32-bit layout, so two `Sym`s with different `kind` values are never equal whatever their ids. That disjointness by kind is the core property the whole design rests on.

The domain distinction. `hilavitkutin-sym` defines `SymKind`, a newtype over `Bits<4, Hot>` naming the runtime domain tag, and three traits: `Domain` (carries `const KIND: SymKind`), `InterningDomain: Domain` (adds `type Value`; deduplicates a value into a stable handle and resolves back), and `GenerativeDomain: Domain` (mints a fresh handle with no backing value and no resolution). A domain is a marker type that picks one of the two refinements, so the mode is a type-level fact.

The two producers, typed by domain. `hilavitkutin-sym` defines the `Interner<D: InterningDomain>` trait (interns a `D::Value`, resolves a `Sym`) and the concrete `Generator<D: GenerativeDomain>` (a monotonic counter over the 28-bit id width; `mint` returns a fresh `Sym` tagged with `D::KIND`, or reports exhaustion at the 28-bit boundary as `Maybe::Isnt` rather than wrapping the counter). Because the producers are typed by the refined domain, constructing a `Generator` for an interning domain, or an `Interner` for a generative domain, is a type error. The handle stays monomorphic for storage; the producers carry the domain type for safety.

The kind-assignment discipline. `hilavitkutin-sym` owns the kind-assignment convention and documents it, so two domains cannot claim one kind. The four-bit field gives sixteen kinds. Two are reserved for the string domains at exactly the values the current `Str` layout already produces, which is mandatory for byte-compatibility: const strings at `0b0000` and runtime strings at `0b1000` (today's origin-plus-reserved patterns). The remaining values are assignable to other domains; the first consumer generative domain (vehje's minted binder, landing in its own round) is recorded in the table as `0b0001`. The string-domain kind constants themselves live in `hilavitkutin-str`, since they are string-domain facts; `hilavitkutin-sym` documents the reservation.

`hilavitkutin-str` becomes a consumer. It depends on `hilavitkutin-sym`. `Str` becomes a `#[repr(transparent)]` view over a `Sym` restricted to the string kinds. `Str::__make` constructs a `Sym` of kind `STR_CONST`; `Str::__runtime` constructs a `Sym` of kind `STR_RUNTIME`; both produce byte-identical handles to today. `is_const` tightens from "origin bit is zero" to "kind is exactly `STR_CONST`", which is identical for genuine string handles and correctly answers "not a string handle at all" for a non-string `Sym`. `StaticStrEntry`, the linker section and its walkers, the FNV hashing, `str_const!`, the `AsStr`/`IntoStr` ergonomics, and `StringInterner<A: ArenaInterner>` all stay in `hilavitkutin-str` because they are string-specific. `StringInterner` implements the generic `Interner` for the string domain; the const linker-section table plus the arena is that domain's deduplicate-and-resolve implementation.

Byte-compatibility is the load-bearing constraint and it holds by construction. Because `STR_CONST` is `0b0000` and `STR_RUNTIME` is `0b1000`, every const `Str` already baked into a linker section by `str_const!` keeps its exact 32-bit value under the `kind`/`id` view, and `StaticStrEntry`'s `#[repr(C)]` layout is unchanged (a transparent-over-`Sym` `Str` is the same four bytes as a transparent-over-`StrLayout` `Str`). No data migration, no re-baking. Per the pre-1.0 no-legacy-shims rule, `Str`'s internal move to a `Sym` view is a clean rewrite with no deprecation alias; the workspace call sites (none outside this repo) update in the same change.

Crate dependencies and constraints. `hilavitkutin-sym` depends only on `arvo` (for the `bitfield!` macro and `Bool`), `arvo-bits` (for `Bits`), and `notko` (for `Maybe`). It is `#![no_std]`, no alloc, no `dyn`. It takes a `forbidden-imports` scope keeping it standalone (arvo, arvo-bits, notko only; no other hilavitkutin crate), matching how `hilavitkutin-str` is kept independently usable. `hilavitkutin-str`'s existing `forbidden-imports` scope already permits depending on a sibling that is not the engine/api/ctx/persistence set, so adding the `hilavitkutin-sym` dependency needs no severity change; adding the new crate's own scope is a new lint scope, not a severity downgrade.

## What this round does not cover

The vehje consumption. Flipping the Core-form binder fields to `Sym`, declaring vehje's `BinderDomain` generative domain (kind `0b0001`), and implementing the ANF node-creating fold that threads a `Generator<BinderDomain>` all land in a vehje round that depends on this crate. That round decides the vehje-side placement calls (which crate declares `BinderDomain`, which Core fields flip). This round ships only the reusable identity core and the `hilavitkutin-str` refactor.

The phantom-typed handle. A `Sym<D>` phantom-parameterised by domain was considered and rejected for this round: it would type-check the intern and mint edges but must erase to a common type wherever a field holds either domain, buying type-checking only at a few edges the runtime kind and the typed producers already cover, at the cost of an erasure boundary. The monomorphic handle plus typed producers is the chosen balance.
