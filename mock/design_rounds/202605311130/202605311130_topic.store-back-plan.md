# Store-back the execution plan on ColumnStorage

The scheduler computes a full `ExecutionPlan` at `build()` (to read the
topological permutation off `unit_meta`), then drops everything but the
`topo_order` field. The plan's flat CSR pools (phases, trunks, fibers,
per-unit metadata, per-fiber morsel sizes, the RCM renumber) are lost. The
unified-storage arc holds that all engine runtime state, including the plan,
lives in the one `ColumnStorage` over `MemoryProvider`, not on the stack and
not in a bespoke arena. This round store-backs the plan's flat pools: `build`
reserves plan columns in the scheduler's storage and copies the computed flat
arrays in, keeping a small `Copy` handle so the plan persists for the dispatch
consumer that reads it at run time.

## Reconciliation with prior work

The original #655 scope described dissolving an 11 MB nested const-array plan
tree (`[Phase;32]` nesting `[Trunk;32]` nesting fibers). That dominant term is
gone: PR #113 already flattened `ExecutionPlan` into flat CSR trunk/fiber
pools (the structural flatten the #655 de-risk sketch called "PART 1:
dissolve"). `ExecutionPlan<DefaultPlanDims>` now fits on the stack (the
`plan_flat_size` regression test pins it). So this round is only the thin
store-backing layer the sketch called "cheap once the shape is flat": reserve
plus copy plus a handle. The sketch's own fallback path (flatten alone first,
store-back in a follow-on) is what happened; this is the follow-on.

PR #114 also already gave the scheduler a `storage: CS` field and handled its
`Send`/`Sync`. So the meta-store does not need a separate allocator: the plan
columns reserve in the existing `storage: CS`, after the resource drain, at a
continued `StoreId` namespace (the drain reserves resources at `0..N`; the
plan columns reserve at `N..N+K`). No `StoreId`-value collision (disjoint
ranges) and no access-path collision (the resource accessor is type-keyed and
never reads a `StoreId`).

## Current state

`compute_topo_order` (in `scheduler/mod.rs`) computes the plan, reads the
permutation into `topo_order`, and returns only `(topo_order, topo_count)`.
The plan value is dropped. `build` / `build_with` call it before draining the
store arena (a dependency cycle returns `BuildError::PlanFailed` without
allocating), then drain resources and construct the `Scheduler`.

## Changes proposed

1. A `PlanHandle`: a small `Copy` record of the base plan-column `StoreId`
   plus the live counts (phase / trunk / fiber / unit). Plan-column ids are a
   fixed offset enumeration off the base, since the plan columns are a closed
   set.

2. `compute_topo_order` becomes `compute_plan`, returning the full
   `ExecutionPlan<DefaultPlanDims>` (or `BuildError::PlanFailed` on a cycle),
   so `build` has the plan to store-back. `build` extracts `topo_order` from
   `unit_meta` as before, then drains resources, then reserves and copies the
   six flat plan pools (phases, trunks, fibers, unit_meta, morsel_sizes,
   rcm_order) into store columns at the continued id namespace, builds the
   `PlanHandle`, and stores it on the `Scheduler`.

3. The `Scheduler` gains a `plan_handle: PlanHandle` field. The plan persists
   in `storage` for the dispatch consumer; the `topo_order` field stays (it is
   the dispatch order `run` already walks).

## Out of scope

`column_class` and `dirty` are nested per-fiber structures whose true columnar
form needs the `Decompose` derive (not yet shipped) and whose consumers
(column-dispatch column roles, plan-caching dirty propagation) are later
rounds. They stay off the store this round (dropped with the transient plan,
the same as today); store-backing them lands with their consumer. Reading the
store-backed plan at dispatch time (the morsel loop) is the next round; this
round only writes the columns and keeps the handle.
