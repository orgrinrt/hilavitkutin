## Current state

The api's design names three store types (`Resource`, `Column`, `Virtual`), while the source has `Accum` beside them, which the api's design never mentions and the engine's design describes. The scheduler is built with one record count (`build(storage, record_count)`) and every column has that many records, though `ColumnStorage` already keeps a count per column.

A unit is a `WorkUnit`. It iterates through `each`, `batch` or `reduce` with a closure over a position, and reads and writes columns through `unsafe fn read` and `unsafe fn write` at that position. `RecordOp` exists beside it as an opt-in map of one value to one value, used only by the fused fold. The founding record has `each` take a function from values to values (the api surface topic, `:1840-1843`), which the shipped `each` does not.

A unit reads the record it is at and no other. The engine design has units ranked by lifecycle (plan-stage, consumer, epilogue) through `OnMeta<V>`, and plan step 1 builds a read-after-write edge from any writer to any reader of a store whatever their ranks, so a store written on the epilogue band and read by a consumer unit gets an edge against its rank.

Two writers of one store are ordered by registration position alone in the engine design (`:43-44`) and in the code, where the spec has hint priority first.

The type-level list is declared in the api (`Cons`, `Empty`, `Contains`, `ContainsAll`, `Concat`), a second copy of what `notko-hlist` now holds.

Formats are generic: any `Copy + 'static` type is a `ColumnValue`. Registration is typed, through `.with`. Neither changes.

## Changes proposed

The first eight follow the eight things the coordinator asked to have restated on the record, in its numbering. The remaining ones carry over from the first writing.

### 1. Reading a store as it stood when the pass began, and what the counters are for

What the record designs. Hilavitkutin has two access modes and no buffered store. The core design topic, `:643-661`:

> Resolved by Q2: two modes only. Read and Write. Write implies Read.
>
> loimu's seven access modes (Pinned, Immediate, MutImmediate, Sample, Post, Approx, Defer) control ordering, freshness, and determinism within the double-buffered view system. [...] loimu maps its seven modes to Read/Write at the hilavitkutin boundary and implements the richer semantics in its own layer.
>
> If hilavitkutin later needs a third mode (e.g. ReadExclusive for consumers that need guaranteed exclusive read access), it can be added without changing the WorkUnit trait — it would be a new store wrapper type like `Exclusive<Resource<T>>` in the AccessSet.

The counters are for one thing, knowing whether something changed so that unchanged work is skipped. The spec, `:2406-2408` (R2): "hilavitkutin owns per-morsel generation counters and skip-unchanged DAG propagation logic (runtime scheduling concern)". No passage has a counter select or hold an earlier value of a store.

The record has one value that is a pass behind, and it says how. The core design topic, `:595-598`: "The scheduler writes `Resource<SchedulerMetrics>` at the START of each pass, containing the PREVIOUS pass's metrics. This is always one-pass-behind data, which is consistent and non-paradoxical". And `:639-641`: "The write happens at pass start → it's the first thing in the DAG. All readers naturally come after. The version stamp increments every pass (pass_count always changes), so readers always dispatch." This is the passage his answer below points at, the counters and increments "designed exactly for something like this". What it designs: the value is written once, on the band before the ordinary units, by the plumbing; every reader of the pass sees that one value; and the stamp's increment is how the readers know to run. The stamp marks the change. It does not pick between two held values, and nothing in the passage holds two.

The record also has the bands. The engine design's meta pipeline section (`:840-843`) ranks every unit by its schedule: "plan-stage work units land in the early phase(s), consumers in the middle, and epilogue (`ScheduleEnd`) work units in the final phase(s)". A store whose every writer is on the leading bands holds one value for every consumer unit of a pass, as the scheduler metrics do, and a store whose every writer is on the epilogue band holds for them what it held when the pass began.

The record has a consumer's unit write columns at the close. The core design topic, `:730-731`: "`meta::ScheduleEnd` — fired after all consumer work completes. Gates epilogue work: error inspection, rollback, cleanup." And `:763-779`, its example of one: `impl WorkUnit<On<meta::ScheduleEnd>> for RollbackOnError` with `type Write = (/* columns to restore */);`, under "No rollback hardcoded in the scheduler. Consumers who need rollback (loimu with WASM plugins) build it from work units". So a unit a consumer writes, scheduled on the close, writing columns after every consumer unit has run, is the record's own. The second review of this writing found these passages, which this seat had not cited.

And the record has the counters carry such a write to the next pass. The spec, `:862`: "Per-morsel generation counter — bump on write, skip if unchanged". And `:1420-1424`: "At runtime (not plan-time), before each pass: check generation counters on root WU inputs. If unchanged since last pass, set dirty bit to 0."

Two further passages bear on who holds a buffer, each said of signals and not of columns. The core design topic, `:386-389`, of virtuals fired from outside: "No signal bus, no arena, no double buffering. Just bits." And `:550-553`: "loimu builds its signal bus on top: virtuals for scheduling edges + loimu-owned arena columns for signal data + buffer modes (Replace/Queue/ReplaceBy) as loimu-layer logic. hilavitkutin provides the bit; loimu provides the arena." For signals, then, the engine keeps the bit and the consumer's layer keeps the buffered data in columns it owns. The record does not say the same sentence of a column's values across a pass, and the two forms below have that division.

What later work and research hold on buffering itself. He asked for it to be read, and four things were found. None of them is the record in the sense above.

A later round sketches a double buffer and has a meta unit rotate it. `mock/design_rounds/202605101036/202605101036_topic.plan-algorithm-chain.md:1181-1208`, "Double-buffer pattern for AdaptWu snapshot publish": a resource value holds `buffer_a`, `buffer_b` and `current`; the adapt unit, at `ScheduleEnd`, fills the buffer that is not current and then stores the index ("single atomic publish"); a consumer unit loads the index and reads the buffer it names. The same round's adapt topic has that unit refresh the consumer-readable metrics resources "at `ScheduleEnd`" (`202605101036_topic.adapt-subsystem.md:26`). The pattern cannot be written against the designs as they stand: it calls `ctx.writer::<MetricsResource>()` and keeps an atomic field in the value, where the api has no write of a resource (`ResourceProviderApi` gives `&T`) and the engine design says "A consumer `Resource<T>` is `Copy` and read-only after init [...] so it cannot carry mutable per-pass state" (`:877-878`). It shows which unit that round expected to do a rotation, and it is no form a consumer can use.

The founding research has a swap buffer in two modes and calls it portable. `mock/design_rounds/202604200055/202603141800_research.loimu-storage.md:244-259`: `Exchange` is "pointer swap + reset (ephemeral data)" at O(1), `Snapshot` is "memcpy live -> frozen copy (persistent data)" at "O(dirty), zero when idle". The synthesis rates it "Directly portable | Double-buffering primitive for any column data" (`202603141800_research.loimu-synthesis.md:294`) and the storage note says "hilavitkutin should own the buffer primitives (SlabColumn, SwapBuffer, BitSet, ErasedColumn, Shape)" (`:1153`). The spec took up neither sentence, and no round designs a swap buffer in the engine or the api.

The "swap" that was specified, built and benched is the replacement of a whole resource value between passes, and part of it never landed. The spec is on the trunk, `mock/research/202607200200_replaceable-swap-semantics-spec.md` (S1 to S7, by its own header "DRAFT pending op ratification"): `replace_value` installs the new value as one write and marks the store dirty, legal only between frames. The evidence memo is on the trunk too (`mock/research/202607201100_swap-semantics-ratification-evidence.md:30-58`): the install at 2 ns for 64 bytes, 85 ns for 1 KiB and 1.81 us for 64 KiB on one M1 run, and the frame after it at the cost of the store's dirty cone. The bench results it reads (`mock/benches/results/swap_cost`, `swap_band`) were on `origin/recover/unlanded-rounds-and-benches` alone and reached the trunk at `6524900` while this was being written. The source that does the install is still only on that branch (`mock/crates/hilavitkutin/src/scheduler/mod.rs:1303-1321` there, a `ptr::write` through the witness); on the trunk `replace_value` marks the store dirty and discards the value (`mock/crates/hilavitkutin/src/scheduler/dirty.rs:62-73`, under a FIXME). The spec's S3 says of columns: "columns are sized at plan time and never resized". Neither the trunk nor that branch holds a design, sketch or bench of a column held in two or three buffers.

One expert memo on the trunk says "Hilavitkutin's columns are double-buffered (frozen/live) for the pass boundary" (`mock/research/202606210600_expert-loimu-heritage-storage-model.md:289`). It cites nothing for it, and neither the spec nor either design has such a passage. I have not found what it rests on and do not build on it.

ikiuni, read as a reference and not as this repository's record, states the model a consumer wants: "All computation this tick reads the PREVIOUS committed frame, immutable for the whole tick. Output is Mutations applied to the NEXT frame." (ikiuni `mock/research/202606221200_imported-design-history/design-research/2026-06-19-replicated-state-stateless-compute-model.md:19-21`), and "State changes apply at the frame barrier through a double-buffer swap, one journal entry per change" (ikiuni `mock/PRINCIPLES.md.tmpl:7-8`). It says what holds and not how an engine's stores carry it.

What changes. No store kind and no read marker is added. The api design gains the section "Maintenance units and the close" with the subsection "Reading a store as it stood when the pass began". It says what the record's passage says, of a consumer's stores where the record says it of the scheduler's own: a store whose every writer is a maintenance unit holds one value for every ordinary unit of a pass, the one left on the leading bands or, where the writers are at the close, the one it held when the pass began; a maintenance unit's write marks the store changed for its readers; and the counters and stamps are for that mark. It then names the two ways a consumer writes the bringing-in with what the api has. Changes appended by ordinary units and applied by a close unit, which is ikiuni's model as it stands and costs what changed. A second column carried into the first by a close unit, which is the snapshot mode of the research with a whole copy. Both are the consumer's stores and units. Between passes `replace_value` stands as it is designed, and its install is owed to the trunk by the landing of the unlanded branch.

What is derived here and what is the record's, said plainly. The record's are: a value written at the start of a pass and read unchanged through it; a consumer's unit on `ScheduleEnd` writing columns after all consumer work; the bands; and counters bumped on write and checked before each pass. What this seat puts together from them is the sentence that a store whose every writer is a maintenance unit holds one value for every ordinary unit of a pass, and the two forms as the ways to write it. No passage of the record says that sentence. The two forms add no mechanism: each is written with stores, units and accessors the api has apart from them.

Two reviewers read this point and did not agree. The first, without the `ScheduleEnd` passages in front of it, found the record ambiguous here and his answer choosing no option. The second read the record first and found the placement of a writer at the close settled by `:763-779` with the spec's `:2128`, and the proposal matching the shape of his answer while short in its grounding, which the passages above now supply. Where two readers differ the call is not this seat's. It is question ticket `does_a_store_only_a_close_unit_writes_hold_its_pass_start_va` (2143d534c715), held by the coordinator, with its options, and the design text carries a marker naming it until it is answered.

Not in this revision: two buffers in one resource value flipped by a close unit, which needs a write of a consumer resource inside a pass that the designs rule out; and an exchange of two columns' storage, which would step a whole field with no copy. Nothing in the record designs either, and the exchange's worth against the copy is a number nobody has. Ticket `bench_a_close_unit_s_copy_of_a_column_against_an_exchange_of`.

Two engine rules make it hold. The engine design, `:41-43`:

> RAW edges are order-independent: for any unit pair where one writes a store the other reads, the writer sorts before the reader, regardless of which was registered first.

becomes: order-independent between units of one lifecycle rank, and two units of different rank that share a store take the order of their ranks, an edge that agrees with the ranks built as any other and one that would run against them not built. Without this, step 1 orders a close-band writer before a consumer reader of the same store, against the bands. A writer on the leading bands needs no rule: its edge to a consumer reader agrees with the ranks, which is the record's "first thing in the DAG".

The engine design, `:106-110`, lists the seeds of the dirty set (a replaced resource, a replaced value, "an input the consumer marked changed", the cold first frame). It gains one: a store a maintenance unit changed. For a writer on the leading bands the store counts as changed in every pass the unit runs and its readers dispatch in that pass, which is the record's "readers always dispatch". For a writer at the close, a consumer unit that read the store before the close unit wrote it has not seen that write, so the write makes the store's readers dirty for the next pass. The second half is the spec's `:862` and `:1420-1424` (quoted above) said of a close unit's write, and it is new to the engine design, which has no seed from any unit's write today. The engine design takes it for maintenance units only and says so as a gap: an ordinary unit that reads a store it writes is still seeded by the consumer marking its input, where the spec bumps a counter on every write. Ticket `hilavitkutin_reads_a_write_s_changed_mark_for_maintenance_un` (8e2e2326d588), with a marker in both designs.

### 2. Columns of different record counts

What the record designs. A column is `Column<T>` and the schema is the consumer's. The spec, `:2397-2404` (R1): "hilavitkutin doesn't know or care about domain schemas — it schedules based on Read/Write column sets only", with the typed schema pattern "consumer-side" as a "consumer wrapper around hilavitkutin's `Column<T>`". Record counts are run-time parameters of the plan stage (the spec, `:2110-2117`: "The plan stage adjusts only what compile time cannot: morsel sizes from runtime hardware detection, record counts, EMA-based recomputation"), they come from the consumer's data (`:2435-2446`, R6), and a count belongs to a fiber's run of work (the memory layout topic, `:854-863`: "the row count cascades: if the upstream chain processed N rows, the downstream chain also processes N rows", in that topic's older vocabulary). The storage contract already answers per column: `ColumnStorage::count(id)`, and a second `reserve` of an id resizes it (`mock/crates/hilavitkutin-api/src/storage.rs:38-80`).

His answers. Asked how columns of differing record counts are held [a: on the column in storage, a unit over unequal columns refused | b: on the column's type as a group parameter | c: consumer wrappers name groups], he answered: "Okay so i am fairway confident this is also answered. Isn’t the intent a contiguous per prototype and indices to process needed windows to it? Pretty sure the design has answers to these things and more". The intent, in my words: the design already holds this, as contiguous storage per kind of thing and windows of indices over it. Asked whether a domain's extent is fixed or replaceable [a: replaceable between passes up to a capacity fixed at build | b: fixed at build | c: both, declared per domain in its type], he answered: "Both, declared per domain". Then, at 10:35 UTC, asked how record sets of different counts are held in the first place [a: several sets in one schedule, each contiguous with its own count as a plan parameter | b: one schedule per set, crossings through resources or accumulators | c: bench both first], he answered: "Bench both first". The intent, in my words: neither form is chosen before both are measured. That answer is the later one and it is on the question the other two rest on, so it governs, and "Both, declared per domain" waits with it.

The api design gains a short section "Record counts" that says so, names the two forms, and says the api takes neither before both are measured on data of that shape; until then a consumer with several record sets builds a scheduler for each, which is his option b as it works today and is not a choice of it. The engine design's `:269` and `:1191` stand as they are; the accumulator sentence at `:1195` loses the words "this round" and nothing else.

Withdrawn from the second writing as it stood before this revision: `Column::<T>::with_count`, `Column::<T>::with_capacity`, the registration wrapper and the staged count value they returned, `replace_count` on the scheduler, the `Replaceable` bound on a column value type, and the refusal of a unit over columns of unequal counts. None of it reached source.

What the bench owes. Both forms as arms under the harness, on data of the shape that asks for it (a few record sets whose counts differ by orders of magnitude, with units that cross from one to another), and a sketch first of what each form asks of the plan. Ticket `sketch_and_bench_several_record_sets_in_one_schedule_against`.

Not in this revision either: a unit reading a column of another count at a record it computes (a lookup by key). Idea ticket `a_readable_member_that_gives_a_record_its_own_key` stands for it.

### 3. The order of two writers of one store

What the record designs. The spec, `:589-595`:

> - DAG edges from Write→Read column overlap
> - Write-write ambiguity resolved by scheduling hint priority (Urgency, Divisibility, Significance). Tie-break: most deps first, then deterministic fallback. Supersedes T6 L2637 `order` field.

One rule for every store, and no store has a refusal in place of an order.

His answers. Asked about two units writing one frame-buffered column [a: refused at build now, later disjoint record sets | b: always refused at build | c: resolved by scheduling priority like every other kind], he answered: "Schedule should exist for this specifically. Are we sure that you and the agents working on this actually know what hilavitkutin is and is intended to be?" The intent, in my words: ordering writers is what the schedule is for, and nothing is refused. Asked for the write-write order [a: hint priority, most dependents, fixed fallback as founded; registration order a deviation to fix | b: hint priority, then most dependents, with registration position named as the fixed deterministic fallback | c: registration position, founding rule retired], he answered: "Hints, registration as fallback". That was read as option b, whose text spells the middle step, though his own words named the first and the last step only. The coordinator put the middle step to him at 10:35 UTC [a: hints, dependents, registration | b: hints, registration] and he answered: "Hints, dependents, registration". So all three steps are his.

What changes. The api design, `:366-368`:

> Write-write ambiguity resolved by scheduling hint priority across three dimensions. Tie-break: most deps first, then deterministic fallback.

becomes: two units that write one store are ordered by the schedule, for every store; hint priority across the three dimensions decides first, then the unit with more dependents downstream, then the position the units were registered in, which is the deterministic fallback; no second writer is refused.

The engine design, `:43-44`:

> WAW conflicts serialise deterministically by input index (the lower index first).

becomes the same rule, with the input index as its last step. The code orders by input index alone (`mock/crates/hilavitkutin/src/plan/steps/step1_dag.rs:49`), a deviation from the spec that predates this round, ticket `hilavitkutin_orders_two_writers_of_one_store_by_registration`. The source window either carries hint priority into step 1 or leaves a FIXME there naming that ticket.

### 4. Who declares what changed means

What the record designs. The engine owns the counters, the stamps and the skip (R2, quoted under 1), and "Version stamps increment only on completion" (the core design topic, `:375-377`). Whether a write that stored the same value counts is not the engine's to fix. The loimu research of the founding round, `mock/design_rounds/202604200055/202603141800_research.loimu-dag.md:1021-1025`:

> **Version stamps:** the concept is universal (track whether a resource actually changed). hilavitkutin should own the version stamp type and the early cutoff algorithm. Phantom-write detection (bitwise comparison for small values, explicit marking for large values) is a storage concern that each consumer can implement differently.

His answers. Asked what "changed" means for a computed column [a: differs from the frame before, compared with the committed value at a granularity fixed in the contract | b: written this frame, whatever the value | c: declared per column: the column or the unit writing it declares which of the two holds, as a trait or const, default differs], he answered: "Declared per column". Asked which stores declare it [a: every per-record kind, default differs for frame-buffered and written for in-place | b: frame-buffered kind only | c: every per-record kind, default differs everywhere | d: the writing unit declares it, not the store], he answered: "Last option. Pretty sure this is somewhere in the research and proposed canon…". The intent, in my words: the unit that writes a column declares, for that column, what a change is.

What changes. The api design gains "What counts as changed" under "Members of an access set". The declaration is on the member the unit writes, and the default is his: the option he chose reads "default differs". The second review found that. ### 6. The accumulator

What the trunk has. The founding record has no accumulator. The engine design on the trunk describes one (`:1195-1198`), from a later round whose topic reports a choice of his in an agent's words. That topic, `mock/design_rounds/202606041800/202606041800_topic.accumulator-columns.md:8`:

> An accumulator is written by APPEND during the frame, growing from zero toward a capacity; a later PassEnd drain reads the populated prefix into persistence. op chose this two-kind surface deliberately rather than a single global record count.

What changes. The api design, `:138-152`:

> Three store types, one scheduling mechanism.

becomes "Four store markers and one scheduling mechanism", followed by: by what it holds, state is still one of three things (a collection of records, a single value, a signal with no data), and the accumulator is a collection with a marker of its own beside the column. `Accum<T>` is listed in the code block with a paragraph on it and a paragraph on why it is a marker. The first writing changed the count to five and the heading to "Store kinds"; both are taken back.

His answer. Asked whether the accumulator is a fourth store kind [a: a column with an append write, marked by a wrapper in the access set | b: a fourth store kind], he answered: "Whichever makes most sense typestate and plumbing wise". The intent, in my words: the choice is the round's, by which form is tighter in the types and simpler to carry through the engine, with the reason written.

The decision is the marker, option b in its form, with the count of things state can be left at three. Four reasons.

Storage follows from the registered marker alone. An accumulator's storage is not a column's: a region per core, each with its own length, reset each frame, written at its end. The drain walk picks it by the marker (`StoreDispatch<Accum<T>>`) with no look at any unit. Under a wrapper, the same registered `Column<T>` would be reserved one way or the other by whether some unit somewhere lists it wrapped, so a store's shape would be a fact of the whole schedule and the walk would need every unit's lists first.

A wrong access fails where it is written. `append` is bounded on `Holds<Accum<T>>` and the positional `read` and `write` on `Holds<Column<T>>`, so a unit that appends to a column or reads an accumulator at a position does not compile, at the call. Under a wrapper, one unit listing `Column<T>` bare and another listing it wrapped is a conflict between two units, which no bound on either sees; it would be a const assertion at `build` or a refusal at run time.

A column of `T` and an accumulator of `T` stay two stores. Under a wrapper they are one name, and a consumer that wants both needs a second value type.

It is what the source has, and the accumulator round put it there on his choice: "op chose this two-kind surface deliberately rather than a single global record count" (quoted above). The marker costs no change to a unit, a kit, the drain walk or a suite.

What the wrapper would have bought is one fewer marker in the list of stores. The wrappers of 4 and 5 are of another kind: `Written` and `Reach` change how one unit reads or writes a store whose storage is the same either way, which is why they sit in a unit's list and not in the registration.

`append` stays safe as the first writing made it, with `len` beside it; see 9.

Added under his word on maintenance units (the next section): a reader of the pass's appends for a close unit. The accumulator topic quoted above names such a reader ("a later PassEnd drain reads the populated prefix") and left the drain out of its scope (`:42`), and the engine design repeats it (`:1198`). A later round has the same unit ("Cold-side writes: PassEnd WU drains accumulator columns into persistence via `PersistenceProvider::commit`", `mock/design_rounds/202605101036/202605101036_topic.resource-resolution.md:51`). No accessor is designed for it anywhere, and "PassEnd" is none of the spec's four meta virtuals (`:2124-2128`); the reader added here is on the context of a maintenance unit, whichever of the four it is scheduled on.

### The close and maintenance units

This is not one of the eight. It is asked for by a word of his from the kaski canon walk, relayed by the coordinator: "mutations are NOT writes, in this sense. Write here refers to in-place writes that are discouraged or forbidden at the contract level and forces in-engine / sim changes to go through mutations. Special contracts exist f or work units that are maintenance (can write in place, primarily do frame close and setup and such)". The intent, in my words: an ordinary unit does not write in place, its changes go through mutations, and the units that write in place are maintenance units, which do the setup and the close of a frame.

What the record gives maintenance units. The spec, `:2119-2137`, has the scheduler schedule itself through meta units on the meta virtuals `PlanStage`, `ScheduleReady`, `PassStart` and `ScheduleEnd`. The engine design's meta pipeline section has them in the same carrier as consumer units, ranked by schedule type at const evaluation, scheduled with `OnMeta<V>` where a consumer writes `On<V>`, with a `meta` accessor that exists only on the context of a meta unit ("enforced at compile time by the gating, not by a separate bound"), and with the meta bands run once per frame on one core over the whole range.

The record gives them one piece of work of its own: the scheduler's metrics, written at the start of each pass with the figures of the pass before (the core design topic, `:595-598`, quoted under 1). The engine design has that written by the engine directly into a block it owns and read by `OnMeta` units through a bridge (`:876-882`).

A later round gives them more, which is what his answer on rotation (under 1) expected to exist, and it is not the record. Its adapt unit is a meta unit on `ScheduleEnd` that reads the pass's metrics and refreshes the consumer-readable metrics resources (`202605101036_topic.adapt-subsystem.md:26`); it is in source as `impl WorkUnit<On<ScheduleEnd>> for AdaptWu` with nine resources in both its lists (`mock/crates/hilavitkutin-providers/src/adapt_wu.rs:64-100`), its body empty, and with no accessor that could write them. Its resource-resolution topic has a plan-stage unit load a pass's data into a column (`202605101036_topic.resource-resolution.md:50`) and a unit at the end of the pass drain the accumulators (`:51`). So earlier work expected maintenance units to set a pass up by writing columns and to close it by reading what the pass appended.

What neither gives them is a contract of their own for either: every unit has the same `unsafe fn write`, and no accessor reads an accumulator.

What changes. The api design gains "Maintenance units and the close". A unit scheduled `OnMeta<V>` is a maintenance unit; one on a plan-stage virtual or `PassStart` sets a pass up, one on `ScheduleEnd` is the close. Its context is bound to the whole record range and no ordinary unit runs beside it, which makes it the place for a write at a record named from data, and an ordinary unit that means a change for another record appends it for a close unit to apply. It reads the appends through `AccumReaderApi`, an accessor a runner implements on the context of a maintenance unit alone, the way the `meta` accessor is gated, so no bound of `WorkUnit::Ctx` changes. The design says in so many words that the contract does not hold an ordinary unit to this, and that the sequence a close unit meets appended values in depends on the worker count after a parallel run.

How far his word reaches. It was said in the walk of kaski's canon, about kaski's mutations, and the coordinator relayed it as bearing on the api. The api gets from it the mechanism (the rank, the reader of appends, the write by position on a context that holds the whole range). The rule itself, that a simulation's changes go through mutations and only maintenance units write in place, is the consumer's to hold, and the core design topic has the same division for loimu's richer modes (`:653-655`). The first review asked for exactly this split.

`OnMeta<V>` is added to the api design's list of schedule conditions (just above `:366`), which named `Always` and `On<V>` only.

What is not done. `write` is not taken away from an ordinary unit. Every positional unit in the suites calls it, and the brief's item 9 asks that the existing parts keep working. It stays `unsafe` for everyone, and the design says a consumer that forbids in-place writes outside its maintenance units keeps its ordinary units in crates that forbid `unsafe`. The stricter contract, `write` existing only on a maintenance context by the same gating, would match his word more closely and would break every positional unit.

The second review found the contract short of his word at this point: he says "Special contracts exist f or work units that are maintenance (can write in place", and the revision gives a maintenance context the reader of appends and no write an ordinary unit lacks. That is so. A third form would close it with no break: a safe write, checked against the record count, on a maintenance context alone, beside the `unsafe` one every context keeps. It is not built in this writing, since it is new surface that rests on the one-core dispatch of a meta band stated below. The three forms are question ticket `which_write_in_place_a_maintenance_unit_has_that_an_ordinary` (7f93b9f3e621), held by the coordinator, with a marker in the api design.

What a write at a record named from data rests on. The api design says a maintenance unit is dispatched once in a pass by one core over the whole record range with no ordinary unit beside it. The engine design on the trunk says that for `run` (`:265-267`) and for the unit-outer path of `run_parallel` (`:947-954`), and for the phase-loop path it says only that the bands are phases the waist barrier puts in sequence across cores (`:940-943`). The second review found the guarantee stated without its mechanism on that path. The engine design's new subsection now states it for both paths, and for the phase-loop path that is this round's addition, which the source window checks against what the source does and makes so.

Read-after-write edges and the DAG: unchanged between units of one rank. Across ranks the rank decides, which changes the plan only for a registration that has a meta unit sharing a store with a consumer unit.

The planner's steps, phases, waists, trunks and fibers: step 1 as above, and one new boundary, behind a read with a reach. A registration with no wrapper plans as before, bar the write-write order where two writers' hints differ.

Within-fiber fusion: the fold is unchanged in what it does. The trait it bounds on is the widened `RecordOp`, so the units that offer a map to it write one-member lists where they wrote `In` and `Out`.

Morsel sizing: unchanged.

Per-core dispatch programs, the executor and the thread pool: nothing.

`MemoryProviderApi` and `ColumnStorage`: nothing.

The resource model: `ResourceRead` is added beside `ResourceFootprint` and written by the same derive. A hand implementation of `ResourceFootprint` is untouched and its resource cannot be named in the read list of a unit that calls `map` until it has a `ResourceRead`.

Virtuals, `On<V>`, `OnMeta<V>` and the meta pipeline: the cross-rank order and the accumulator reader on the meta context. Nothing else.

`Accum`: `append` is safe. Capacity stays the run configuration's record count.

Scheduling hints and `COMMUTATIVE`: nothing. Hints now decide the order of two writers, as the spec has it.

`Plannable` and `HintExt`: nothing.

Kits, `BuilderInput`, `.with`, `Replaceable`, `PlanAffecting`, plan caching: nothing.

Adapt, persistence, `hilavitkutin-ctx`, extensions and linking, `-str`, `-sym`, `-build`: nothing. Persistence was not examined beyond its design naming none of the changed items.

## Breaks of the public api, counted

He allows a break where the design is better for it and asks that each be stated and counted. The ledger of the next round starts from this list.

For a unit author, two. `append` loses `unsafe`, so the `unsafe` block around the call is no longer needed. A unit that implemented the one-value `RecordOp` for fusion writes its map over one-member lists.

For whoever builds a scheduler, none. `build` and `build_with` are as they were.

For the author of a runner or of a context, three. `EachApi` gains `map`, which a runner implements. Folds over a unit's lists read `Member::Store` where they read the cell. The accumulator bridge `ResolveAccumAppend` becomes an `unsafe trait` with safe methods, so its one implementation is written `unsafe impl` and its methods lose `unsafe`.

For the author of a kit, one where it applies. The `.build()` proof and the kit's own where-clauses are written on `HoldsAll` where they were on `ContainsAll`, so a kit that wrote a `ContainsAll` bound of its own to reach `.build()` writes `HoldsAll`. `ContainsAll` keeps its name and path. The second review found this one missing from the count.

For the author of a data structure, none.

Two changes of behaviour that are no change of signature. Two writers of one store whose hints differ may be ordered otherwise than by registration, once the source carries the spec's rule. And a meta unit that shares a store with a consumer unit is placed by its rank, with no read-after-write edge built against it. What the source does with such a pair today was not read for this changelist; the source window finds it, and which registrations of the suites have such a pair (`AdaptWu` lists resources a consumer unit may read, `mock/crates/hilavitkutin-providers/src/adapt_wu.rs:64-100`).

New surface that asks something an author might not expect, and is no break since nothing has it today: a plain `Column<T>` in the write list of a value function asks `T: PartialEq`, and `Written<Column<T>>` does not.

Not breaks: `Column<T>`, `Accum`, `Resource`, `Virtual`, `WorkUnit`, `Plannable`, `read`, `write`, the kit traits and `.with` are as they were; `Cons`, `Empty`, `Contains`, `ContainsAll` and `Concat` keep their names and paths through the api's re-export.

## How each form holds the pillars

His words of 13 November bound every change to hilavitkutin: it may be "added and extended and changed" while it does not compromise "full, exhaustive typestate, contracts first, all machinery and logic runs on contracts alone, people impl its parts and the engine runs it via the contracts", with "optimisations first and foremost, always", started simpler and deepened later, and nothing "a drop looser in typestate or strictness with no std, no alloc, unless behind a feature that is entirely opt in".

The value function. In the types: each read bounded on the read list, the return total over the write list. Contract: `EachApi::map`, `Readable`, `Writable`, and `RecordOp` under `WorkUnit`. Optimisation: the function is pure over values, so the engine is free in the sequence of records, the thread and in composing units; in this revision it runs one gather, call and scatter per record and fuses only one-column maps.

Members and wrappers. In the types: a wrapper is a type in the list, `Reach` only readable and `Written` only writable, the reach a const parameter, an offset past it a compile error. Contract: `Member`, with `AccessSet` over members. Optimisation: the plan knows a cross-record read and a change rule at build, which is what a boundary, a halo and a skip need.

Record counts. Nothing changes, so nothing is loosened: one count, one contiguous range per fiber.

The accumulator. In the types: the marker picks the storage at registration and each accessor is bounded on its own marker, so a wrong access fails at the call. Contract: `StoreDispatch<Accum<T>>` and the accessor bounds, as in source. Optimisation: none gained or lost.

Maintenance units and the close. In the types: the schedule `OnMeta<V>` is the unit's rank, and the accumulator reader exists only on a maintenance context. Not in the types: an ordinary unit can still call the `unsafe` positional `write`, and that a store's writers are all maintenance units is a fact of a registration that no bound states. Contract: `WorkUnit<OnMeta<V>>`, `AccumReaderApi`, and the two accumulator bridges as `unsafe trait`. Optimisation: a store only a close unit changes seeds the skip, so its readers rest once it settles; the close band is one core for now.

The shared list. As in the first writing: the same sealed list and marker membership, `Holds` and `HoldsAll` over it.

Nothing above needs `std` or alloc, none of it is behind a feature, and no unstable feature is added to either crate.
