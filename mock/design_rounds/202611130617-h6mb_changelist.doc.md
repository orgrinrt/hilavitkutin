**Round:** 202611130617-h6mb
**Scope:** `mock/crates/hilavitkutin-api/DESIGN.md.tmpl`, `mock/crates/hilavitkutin/DESIGN.md.tmpl`

This changelist takes into the api's design what kaski's engine needs of hilavitkutin, as revisions and extensions of concepts the design already has. The lead designer asked for it in those terms ("Revise the api in place now") after the branch `work/loop-core` had built the same needs as a second vocabulary beside the scheduler, and the map of that branch against his design says, item by item, which of them extend a concept, which correct one and which are new. The two topics of this round record his words and the shapes chosen.

The designs here are his and stand in for a canon the repository does not declare. So every line this changelist changes is quoted as it stood, with what it becomes and why, and nothing is changed that the map did not class as an extension, a correction or new. He reads the result afterwards and may overturn any of it, which is the other reason each change is stated as a change.

No human sat in this round. Where the designs and his words do not decide, the changelist names a question ticket and decides nothing.

## Current state

The api's design names three store types (`Resource`, `Column`, `Virtual`), while the source has a fourth, `Accum`, that the api's design never mentions and the engine's design describes. A column has no domain: the scheduler is built with one record count (`build(storage, record_count)`) and every column has that many records.

A unit is a `WorkUnit`. It names the engine's context in its `Ctx` type, iterates through `each`, `batch` or `reduce`, and reads and writes columns through `unsafe fn read` and `unsafe fn write` at a `USize` index, the safety being a sentence in the design. `RecordOp` exists beside it as an opt-in map of one value to one value, used only by the fused fold.

A unit reads the record it is at and no other. No store kind separates what readers see from what a writer is producing within a pass, so a unit that needs last pass's value of a column it also writes cannot say so.

The type-level list is declared in the api (`Cons`, `Empty`, `Contains`, `ContainsAll`, `Concat`), a second copy of what `notko-hlist` now holds.

Formats are generic: any `Copy + 'static` type is a `ColumnValue`. Registration is typed, through `.with`. Neither changes.

## Changes proposed

Each change gives the file and the passage as it stood, what it becomes, the reason, the map's row and the evidence. "The api design" is `mock/crates/hilavitkutin-api/DESIGN.md.tmpl` and "the engine design" is `mock/crates/hilavitkutin/DESIGN.md.tmpl`. Line numbers are those of the files before this changelist.

### C1. Store kinds: five, with `Accum` and `Buffered` named (brief item 4, map row 30)

The api design, `:138-152`, said:

> Three store types, one scheduling mechanism.

and listed `Resource<T>`, `Column<T>` and `Virtual<T>`.

It becomes "Five store kinds, one scheduling mechanism", listing `Resource<T>`, `Column<T, D = Records>`, `Buffered<T, D = Records>`, `Accum<T>` and `Virtual<T>`, with a sentence on each of the two the section did not have. The section's heading changes from "Store types" to "Store kinds".

`Accum` is a correction of the count: it has been in source and in the engine's design since the accumulator rounds, and the sentence was never updated. `Buffered` is new (row 30), a sibling of `Column` as `Accum` was. The edge sentence that follows (`Write<Resource<X>> → Read<Resource<X>>` builds the same edge as for a column) stands, and gains one sentence: a `Buffered` store builds no edge between its writer and its readers.

The registration paragraph under "Store wrappers as Providers" gains the two kinds, registered as `Column` is.

### C2. The list is the shared crate's (brief item 6, map row 38)

The api design, `:159-163`, said:

> `AccessSet` is a sealed marker on the cons-list typestate. `Empty` and `Cons<H, T>` are the substrate primitives consumer code encounters either directly or through the `read!` / `write!` macros (which expand to nested `Cons` chains).

It becomes: `AccessSet` is the api's bound over the type-level list of `notko-hlist`; `Empty`, `Cons`, `Contains`, `ContainsAll` and `Concat` are that crate's, the first two re-exported from the api's root.

The same change reaches four later passages. At `:498-512` the two `Contains` impl blocks shown as the api's are replaced by a description of the shared trait. At `:519-523` `AccessSet::LEN` keeps its definition and gains the statement that the recursion stays the api's own. At `:652-671` the `ContainsAll` code block is replaced by a sentence, and "Sealed by being declared in api alongside `Contains`" becomes "Sealed in the shared crate by its `List` supertrait". At `:576` and `:598` "cons-list" becomes "list" in the two sentences that are rewritten for other reasons.

The reason is the map's row 38, which classes the api's copy as a fault, and the parked topic `202607281547_topic.adopt-the-shared-hlist.md`, which this change consumes. Three things differ from what that topic sketched, each for a reason found while doing it.

The count. The topic has `AccessSet::LEN` supplied "by implementing the shared `Cardinal` property" for `USize`. Neither the trait nor the type is hilavitkutin's, so the orphan rule leaves that impl to arvo. The api keeps its own two-impl recursion over the shared types. Ticket `arvo_implements_notko_hlist_s_cardinal_for_usize`. The first topic of this round says the count is "read from the shared crate's cardinal", which is wrong for the same reason and is corrected here.

The diagnostics. The topic says dropping the api's messages on a missing store "would be a regression however clean the types were". An attribute cannot be put on a foreign trait, so the api declares `Holds<S>`, implemented by one blanket for every list that `Contains<S>`, carrying the api's message, with `#[diagnostic::do_not_recommend]` on the blanket so the compiler reports the unmet `Holds` bound and does not descend. The accessor where-clauses (`:436-451`) and the `.build()` where-clause (`:820-821`) are written on `Holds` and on `HoldsAll<L>`, the api's walk that asks `Holds` of each member. The "`Contains` diagnostic" section (`:738-755`) is rewritten to say this. Evidence for `Holds`: fixture 11 of the sketch, whose recorded diagnostic carries the api's message and no line of the shared crate's. `HoldsAll` is not shown in the sketch and is to be shown by the builder's own missing-store fixtures in the source window.

The aliases. The topic carries a sketch of `Access<H, T>` and `Deny` and says the leaf's name is not settled. This changelist introduces no alias and re-exports the shared names. Question ticket for him: `which_names_the_access_list_s_cell_and_end_take_in_hilavitku`.

### C3. Record domains (brief item 1, map row 4)

New section "Record domains" in the api design, after the store wrappers. `Domain` (axes and a reach), `Records` (the default domain of one axis), `Extent<D>` (a singleton store holding the run-time shape of `D`), the rule that a unit iterates one domain computed from its lists, and that the plan carries a count per domain.

Three existing passages change with it.

The engine design, `:1097`: "`build(storage, record_count)` walks `Stores` and `StoreValues` in lockstep" becomes "`build(storage)` walks ...".

The engine design, `:1134-1141`:

> `build` / `build_with` take the frame record count as the column-reservation dimension: they feed it to the plan computation in place of the zero placeholder, and the `Column<T>` drain arm reserves a real column sized by the record count

becomes: they take no record count, the dimension of a column is the count of its domain read from the registered `Extent<D>`, the counts are fed to the plan one per domain, and the `Extent<D>` drain arm stores the shape as a resource does. In the same passage "(capacity sized to the record count this round)" for `Accum<T>` becomes the count of the largest registered domain.

The engine design, `:269`: "a `morsel_local` fiber windows `[0, record_count)`" becomes `[0, n)` with `n` the count of the domain the fiber's units iterate.

The api design, `:826` gains: `build` takes the storage and no record count, and the store list holds an `Extent<D>` for the domain of every `Column` and `Buffered` store in it.

Reason: row 4, new. A domain is placed on the column marker as a defaulted parameter because a column's domain is a fact about the store, and the default keeps every existing `Column<T>` meaning what it meant. The extent is a store and not a `build` argument so that a unit can read it through its declared reads like any other value, and so that `build` does not grow one argument per domain. Evidence: the sketch runs a world of two domains with different counts, and its fixtures 02 and 03 are the two-domain refusals with the message quoted in the design.

Stated as provisional in the engine design: where the plan wants one figure (`select_approach`, the `last_record_count` cell) it takes the sum of the extents, marked with a FIXME naming ticket `approach_selection_takes_the_sum_of_the_domain_extents_where`.

### C4. The value form as the primary form (brief item 2, map row 1)

The api design, `:239-243`, the section "Opt-in per-record transform (within-fiber fusion contract)", said:

> A work unit that is a pure per-record map (reads one column, writes one column, value to value, no cross-record state) may additionally declare that map as an opt-in fusion contract: an associated input type, an associated output type, and an apply function from one to the other. This is orthogonal to the execute contract (it does not change execute) and opt-in (a simple work unit never implements it).

The section is replaced by "The value form". `RecordOp` is widened from `type In`, `type Out` and `apply(In) -> Out` to a read list, a write list and `apply(&Vals<Read>) -> Vals<Write>`, and is the form a unit is written in first. The fusion paragraph of the old section is kept as the subsection "Fusion", narrowed to say which units the fold takes in this revision.

How the two forms relate is the subsection "The two forms and their routers": `WorkUnit` stays as the block form, the form is read off the router named on `BuilderInput` (`UnitDispatch` or the new `RecordDispatch`), and one api trait, `Declares`, implemented once per router type, gives the plan what it needs of either. The frozen authors of the next round use the value form, since a block-form unit is bound to the one runner whose context it names.

With it:

The api design, `:403-404`: "The plan stage reads `Plannable`, never `WorkUnit::execute`, so planning is generic over `Plannable<S>`." becomes: the plan stage reads `Declares`, which for a `UnitDispatch` unit is its `Plannable` and for a `RecordDispatch` unit is derived from its lists. `Plannable` itself is unchanged.

The api design, `:564-573`: the `WorkUnitBundle` impl bound `W: WorkUnit` becomes `W: BuilderInput` with `W::Dispatch: Declares<W>`, and the sentence at `:576` says a bundle is a list of units of either form.

The api design, after `:368`: a paragraph saying `WorkUnit` is the block form and that the section's statements on schedules, hints and priority hold for either form.

The engine design, `:361-363`: the fused fold's unit is described as a `RecordOp` with one-column lists of `Records`, and a `RecordOp` over longer lists is said to run per unit for now.

Reason: row 1 classes the kernel of `work/loop-core` as this trait widened, and his words of 12 November ask that the contract let the plumbing change without the implementors changing, which a unit that names no engine type and sees no index gives. The router was chosen over a blanket `WorkUnit` for every `RecordOp` (it would need the engine's context type in the api, and overlaps for a unit in both forms) and over a second builder method (it splits `.with`). Evidence: the sketch runs two value-form units and one block-form unit from one list under an engine runner, and the same value-form units under a second runner that walks the records the other way, with the same stores after five passes; its fixtures 04 and 05 show a value unit cannot name the engine or declare a context, and the `check` fixture shows a runner without a block-form impl refusing a block-form unit.

Not shown by the sketch: the schedule and hint as defaulted parameters of `RecordDispatch`. They are there because the api does not enable defaults for associated types and a second blanket of `HasSchedule` would overlap. The next round's frozen authors include an emitter of each trigger kind and a triggered consumer, which is where this is exercised.

### C5. Neighbour reads (brief item 3, map rows 5, 9, 12)

New section "Neighbour reads" in the api design: `Shift<A, const N: isize>`, `Near<C, O, E>` as a read-list member, `Edge<V>` giving the value past the extent, the offset checked against the domain's reach where the type is named, and more than one axis as a list of shifts.

Reason: row 9 classes the neighbour read as an extension of the read access set, and row 12 notes that the outside value sits better on the read or the domain than on the column. It is on the read because two readers of one store may want different values. The reach is on the domain because the plumbing needs it once for all readers. Evidence: the sketch's author reads east, west, north, south and a diagonal on a plane; fixture 01 is the read past the reach.

### C6. The frame-buffered kind (brief item 4, map rows 27, 30)

New section "The frame-buffered kind" in the api design, and a paragraph in the engine design's new section on how it is stored and swapped.

The api design's `ResourceSnapshot` section (`:1072-1080`) gains a paragraph on the relation: the committed side of a `Buffered` store is the snapshot's guarantee given to columns across a pass, the snapshot stays the form for a resource at a phase boundary, and neither is built on the other. Row 27 calls this an extension of the snapshot's idea. The root design's `ResourceSnapshot` line (`mock/DESIGN.md.tmpl:90`) is left as it is, since it says nothing this changes.

Evidence: the sketch's in-place mutant (a write to a `Buffered` store landing on the committed side at once) turns all three comparison tests red, and its third test reads the committed frame after the writer has run in the same pass.

### C7. Two writers of a frame-buffered store (brief item 5, map row 21)

The api design, `:366-368`, said:

> Write-write ambiguity resolved by scheduling hint priority across three dimensions. Tie-break: most deps first, then deterministic fallback.

It stands, and gains: "This holds for every store kind but `Buffered`, where a second writer is refused at `build`".

Reason: row 21, a correction scoped to the staged kind. Under priority the later writer would replace the earlier writer's staged values whole with no reader between them, so the rule would have nothing to resolve and the earlier unit would be dead work. The map says of this row that "the supersession is his", so it is stated here as a correction he has not yet read. The existing rule for other kinds is not touched: nothing in the map's evidence for row 21 speaks against it for a column written in place. Evidence: the position-mask refusal of `202611122242_frame-view-typestate`, fixtures 05 and 06. The sketch of this round does not show it, and the refusal on the real builder gets its own compile-fail pair in the source window.

### C8. Safe reads, writes and appends in the block form (brief item 5, map row 25)

The api design, `:436-443`, had `unsafe fn read<T: ColumnValue, I>(&self, i: USize) -> T` and `unsafe fn write<T: ColumnValue, I>(&self, i: USize, v: T)`, and at `:527-528` said:

> Raw-pointer access `unsafe read / write` pinky-swears ownership discipline that the engine proves at plan time.

`read`, `write` and `append` become safe and take an `Index<'b>`, an opaque position minted by `each`, `batch` and `reduce` inside a higher-ranked closure. `batch` hands a `Block<'b>` that iterates indices. The sentence at `:527-528` becomes: the engine proves the discipline at plan time and the `Index` a write takes carries that proof to the call. The `Resolve*` bridges (`:477-482`) stay `unsafe` and take a bare position; the accessors become provided methods of the api over those bridges, and the engine mints through `Index::mint`, an `unsafe fn`. That is how the type lives in the api and is minted in the engine with no public way to read the position back.

Two things change with it that the brief does not name. `read` and `write` are keyed by the store marker (`C: PerRecord`, implemented for `Column` and `Buffered`) where they were keyed by the value type, because a value type no longer names one store once a column has a domain and a second kind holds one value per record. And `append`, which the brief's line range does not include, is made safe the same way, since row 25's complaint is that an author's body is `unsafe` and an accumulator unit's body would stay so.

A body can no longer use the index as a number. Idea ticket for a readable key member: `a_readable_member_that_gives_a_record_its_own_key`.

Evidence: `202611130417_branded-morsel-index`, which is on `origin/work/sketch-branded-index` and not on this branch. In that sketch the brand and the runner are one crate. The split across the api and the engine described above is not shown there and is for the source window to show, with the compile-fail twins of the index leaving its closure and being built by hand.

## What the revision changes for each existing part

The list is the map's section 2. "Nothing" means the design text for it is untouched and its suite is expected green without a change to what it asserts.

Read-after-write edges and the DAG: unchanged for every existing kind. A `Buffered` store is the one kind that adds no edge.

The planner's steps, phases, waists, trunks and fibers: the steps are unchanged. Grouping gains one rule, that a fiber holds units of one domain. A registration that names no domain is in `Records` throughout and plans as before.

Within-fiber fusion: the fold is unchanged in what it does. The trait it bounds on is the widened `RecordOp`, so the units that offer a map to it write one-member lists where they wrote `In` and `Out`.

Morsel sizing: unchanged per fiber. The window is taken over the fiber's own domain's count.

Per-core dispatch programs, the executor and the thread pool: nothing. `run_parallel` gains a bound that its units iterate `Records`.

`MemoryProviderApi` and `ColumnStorage`: nothing. A `Buffered` store is two reservations through the same trait.

The resource model (`Field`, `Seq`, `Map`, the footprint derive, the snapshot, the erased addressing): nothing. `Extent<D>` is drained as a resource is.

Virtuals, `On<V>`, `OnMeta<V>` and the meta pipeline: nothing for block-form units. A value-form unit fires by returning a set flag and names `On<V>` on its router.

`Accum`: the store is unchanged. `append` takes an index and is safe. Capacity is sized by the largest domain.

Scheduling hints and `COMMUTATIVE`: nothing for the block form. A value-form unit's hint rides on its router, and it has no `COMMUTATIVE` since it holds no cross-record state.

`Plannable` and `HintExt`: unchanged. `Declares` reads `Plannable` for `UnitDispatch` units.

Kits, `BuilderInput`, `.with`, `Replaceable`, `PlanAffecting`, plan caching: nothing. `RecordDispatch` is one more router under the same `Dispatch` trait, and a kit's unit bundle may hold units of either form.

Adapt: nothing beyond the single figure named in C3.

Persistence, `hilavitkutin-ctx`, extensions and linking, `-str`, `-sym`, `-build`: nothing.
