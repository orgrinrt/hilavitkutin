# A sequential walk over a fiber's WorkUnit sequence

The engine analyses a pipeline into phases, trunks, and fibers, then needs to actually run each fiber's work units. A fiber is a sequential dispatch unit: an ordered sequence of WorkUnits that run over one morsel window. To run a fiber the engine constructs each unit's `Context` and calls `execute`. The single-unit case is already proven in shipping source: `tests/engine_ctx.rs::context_drives_wu_execute` builds a real scheduler arena, projects a concrete WorkUnit's `EngineCtx` through `EngineCtx::project`, and drives `execute`. What that test does not cover is the heterogeneous sequence: a fiber holds units of different types, each with its own `Read` set, its own projection index, its own resource bundle, and therefore its own `Ctx<'frame>` GAT instantiation.

This round adds that walk. It is the dispatch core C2 needs before any codegen: a recursive monomorphic walk over a fiber's typed unit sequence that, per unit, projects the unit's `EngineCtx` from a shared arena and runs `execute`. The architect framing for C2 holds that the basic per-fiber dispatch loop is pure Rust generics, not LLVM; the LLVM follow-up is only the inlining and devirtualisation optimisation. This slice is that pure-generics core.

The feasibility was de-risked first. The sketch at `mock/research/sketches/202605300823_run-fiber-wutuple-walk` models the engine's `Project` / `Selector` / `EngineCtx` shapes and proves the recursive heterogeneous walk type-checks and runs under the pinned toolchain. The load-bearing bound it confirmed the solver accepts and uses is an HRTB associated-type-equality on the GAT: for all frame lifetimes, a unit's `Ctx<'frame>` equals the projection of its `Read` set over the arena. The per-unit projection index is carried as a parallel witness list, mirroring how the bundle projection (`plan::project::BundleProject`, landed last round) constrains each per-unit index. No specialization, no generic-const-exprs, no codegen.

## The shape

A value-carrying cons-list holds the fiber's unit instances: `WuNil` terminates, `WuCons<W, Tail>` carries a `WorkUnit` instance plus the tail. The naming follows the engine's existing value-cell convention in `dispatch::engine_ctx` (`PtrCons` / `PtrNil` for the projected resource bundle). The walk is a sealed-shaped trait `RunFiber<A, Witnesses>` with two impls: the `WuNil` base case is a no-op; the `WuCons<W, Tail>` recursive case projects `W`'s `EngineCtx` from the arena `A`, runs `execute` through the existing `invoke_wu_in_fiber` shim, and recurses on the tail. A free `run_fiber_walk(fiber, arena, morsel)` entry function drives the walk with the witness list inferred at the call site, no turbofish for the caller.

The projection reuses the shipped machinery directly. `RunFiber` does not duplicate the index witness, the resource projection, or the context constructor: it calls `EngineCtx::project` (the public projecting constructor) and threads the per-unit resource index through the witness list. Only the walk trait, the two value-cell types, and the entry function are new; the projection itself already exists.

## What stays out of scope

The walk is resource-only this slice. Column projection adds more recursion of the same shape, but the per-frame column buffers depend on real column-buffer allocation from the `MemoryProvider`, which the B2a arena leaves as a dangling placeholder. Resource-only units sidestep that: resource pointers in the arena are real and stable. The resource-only boundary is expressed in the type system, not by runtime check: a unit that reads or writes a column has a non-empty column projection in its `Ctx`, so it does not satisfy the walk's bound and cannot be placed in the sequence. Columns become a type-level extension point for the following slice.

Two further boundaries. The walk does not touch the sealed `run_fiber<S: FiberShape>` stub in `fiber_dispatch`: wiring a `FiberShape`'s `WuTuple` into this walk is the codegen step that follows. And the walk does not source unit values from the scheduler: `build()` retains the store values but erases the work-unit type list, so capturing the unit sequence at build time and sourcing per-unit values is the separate next slice. This slice ships the walk machinery and the proof that it executes a heterogeneous unit sequence, with the unit values hand-built in the test.
