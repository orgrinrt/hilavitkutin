# Topic: morsel-loop windowing (single-core, unit-outer)

**Date:** 2026-06-04
**Scope:** hilavitkutin engine (`mock/crates/hilavitkutin`) + one `RunCfg` const in `hilavitkutin-api`. Slice 3 of the engine runtime frontier (HILA-RUNTIME-C5, #343), single-core-correct first.
**Source topics:** the dispatch-build-plan memo (`mock/research/202605282100_engine-dispatch-build-plan.md`, Phase E line 52 + the keystone sequencing step 5); a neutral `feature-dev:code-architect` read (agent a7ce8368ba5e5a0bd); the column + accumulator data-plane rounds (`202606041631`, `202606041800`).

`Scheduler::run` today dispatches a single morsel covering `[0, record_count)`: for each step of the flat global topological order it calls the unit's shim over the whole range, so each unit processes every record before the next unit runs. This round windows that range into multiple morsels. It stays single-core and keeps the flat topological order; the phase-sequential, per-fiber, codegen'd morsel loop the memo's Phase E describes in full is gated on Phase C (the plan algorithm chain, #339) and Phase D (dispatch codegen, #340) and is a later arc.

## The loop nesting: unit-outer, morsel-inner

For each topological step, window the record range into morsels and dispatch the unit once per morsel: `for step in topo_order { for m in morsels_of(record_count) { shim(unit[step], bindings, m) } }`. Each unit still completes its full record range before the next unit runs.

This nesting is correct for every plan. The flat topological order guarantees only that for an edge (u, v), u precedes v in the sequence; that is enough to satisfy a cross-unit column dependency only if u finishes all its records before v reads any. Unit-outer preserves exactly that: the windowing chunks one unit's pass without interleaving the next unit, so a downstream unit always sees the full output of an upstream unit regardless of whether the dependency is element-wise or crosses record indices.

The morsel-outer alternative (a morsel processed by all units before the next morsel) is the eventual cache-friendly model, but it is correct only when every cross-unit dependency is morsel-local (record i of v depends only on record i of u). Establishing that safely needs the phase/fiber structure and phase barriers, which is the Phase C/D arc. Shipping morsel-outer over the flat topological order now would commit a contract correct only for element-wise plans. Unit-outer is the correct single-core increment; when the phase/fiber tier lands, only the outer loop is restructured (phase-then-fiber), and the per-morsel body, the morsel-size handling, and the windowing carry forward.

A neutral domain-expert read converged on this nesting for the same correctness reason.

## Morsel size source (and the zero guard)

The morsel window size for this round comes from a new `RunCfg::MORSEL_SIZE` associated const (consumer-tunable default, per `arvo-toolbox-not-policer.md`, exactly like the existing `MICRO_MORSEL_INTERVAL` / `MAX_DRIFT_RECORDS`). The morsel window is coarser than the micro-morsel sync interval; default 256 records (a multiple of the 64-record `MICRO_MORSEL_INTERVAL`).

The plan's per-fiber `morsel_sizes` column is NOT the source this round: it is populated by the Phase C formula (`L1_usable / sum(write_sizes)`) which has not landed, so it may be zero-filled. A zero morsel size produces zero-length morsels and silently skips all work. The run-loop guards against this: the effective morsel size is `max(Cfg::MORSEL_SIZE, 1)`, never zero. When the Phase C formula lands, the run-loop reads the per-fiber size and the `RunCfg` const becomes its seed/fallback.

Single-core, unit-outer, the morsel size has no correctness or throughput effect (the same total work, the same column re-streamed per unit either way); it only sets the windowing granularity. The cache-relevant sizing is the eventual morsel-outer per-fiber model. So the size is not a perf fork to bench this round; a documented default is enough.

## The morsel-relative body contract (why the test is position-agnostic)

A WU body reads the morsel-relative index from `each` / `reduce` / `batch` (`[0, morsel.len)`); `read(i)` / `write(i)` add `morsel.start` for the absolute column index. So a WU is position-agnostic by design: it transforms record i of a morsel reading input[i] and writing output[i], and the absolute placement is handled by `read`/`write`. A WU that computes a value from the absolute record position cannot, because `each` does not expose the absolute index; the rust-pipe body the memo describes (read inputs at morsel start, pure-locals pipeline, group output stores) is element-local by construction.

Consequence for testing: the column-dispatch round's producer writes `Cv(i * 10)` from the morsel-relative `i`, so it is only correct at `start = 0`. That is a single-morsel test artifact, not a general WU pattern. Existing tests keep the default `MORSEL_SIZE` (256), which exceeds their record counts, so they stay single-morsel and unaffected. The windowing test uses a position-agnostic WU and a small `MORSEL_SIZE` to force multiple morsels.

## iter_morsel stays untouched (vestigial)

`dispatch/morsel.rs::iter_morsel` walks a range record-by-record inserting a `sync_probe` every `MICRO_MORSEL_INTERVAL`. It predates the `each` / `reduce` / `batch` Context API, which moved the per-record loop into the WU body. The morsel loop this round dispatches per morsel (the shim runs `execute`, which loops the morsel's records via `each`); it does not own a per-record loop, so it does not call `iter_morsel`. The micro-morsel inter-fiber sync probe is a multi-core concern (the thread-pool slice, #342); single-core needs no sync. `iter_morsel` is left as-is; a later round either repurposes it into the `each` loop for the multi-core sync or removes it.

## Round changes

1. **`RunCfg::MORSEL_SIZE`** in `hilavitkutin-api/src/run_cfg.rs`: a new associated const, default `USize(256)`, documented as the single-core morsel window with the Phase C per-fiber formula noted as its eventual superseder.

2. **`Scheduler::run`** in `scheduler/mod.rs`: replace the single full-range morsel with a unit-outer / morsel-inner windowing loop over `[0, record_count)` in steps of `max(Cfg::MORSEL_SIZE, 1)`, dispatching the step's shim once per morsel with the windowed `MorselRange`. The topological-order walk and the slot materialisation are unchanged.

## Test plan (red-first)

New `tests/morsel_loop.rs`: a position-agnostic self-transform WU (`Read` and `Write` both contain the column; `each(|i| write(i, read(i) + 1))`) over a record count spanning multiple morsels under a custom `RunCfg` with a small `MORSEL_SIZE`. The test pre-fills the column with `col[k] = k * 10` through the binding pointer, runs, and asserts `col[k] == k * 10 + 1` for every record across all morsels. Red first: with the single full-range morsel, a `MORSEL_SIZE` smaller than the record count is ignored, so the windowing (and the `start > 0` morsels) does not happen; the test discriminates that every record across every morsel is visited exactly once and `read`/`write` compute the right absolute index at `start > 0`.
