## Current state

The `DESIGN.md.tmpl` dispatch section (the `Scheduler::run` paragraph) states the
parallel path as interim: "The parallel `run_parallel` path dispatches per-(core,
phase) through a runtime mask until G2-N re-points it onto the same per-trunk
monos." That sentence names the re-point as future work. G2-N lands it, so the
doc must describe the shipped shape: the worker drives the same const-gated
per-trunk monos the single-core path drives, filtered to the trunks the core owns
in the phase.

## Changes proposed

### CHANGE: DESIGN.md.tmpl `Scheduler::run` paragraph (run_parallel sentence)

Rewrite the interim sentence to the shipped shape. The worker's per-(core, phase)
dispatch walks the carrier through the same `RunTrunkDispatch` const-gated
per-trunk walk the single-core path uses, with one added runtime branch per
trunk-root: the within-phase trunk rank modulo core count selects the owning
core (`rank % ncores == core`, the R4a ownership rule). A core fires only the
`RunGatedTrunk` monos for the trunks it owns; non-owned trunk-roots fold past.
The per-unit runtime mask test (`core_phase_mask` + `run_gated`) is gone from the
ordinary trunk-ownership branch; the per-trunk monos stay devirtualised and a
non-owned trunk's body is dead-code-eliminated from the core's program. The
head+tail convergence branch (a single-trunk waist-bounded phase split by record
range across cores) is unchanged: ownership there is by record slice, not by
trunk. Single-core (`ncores == 1`) is the degenerate case where every rank
`% 1 == 0 == core 0`, so one core drives every trunk, identical to `run`.

### CHANGE: DESIGN.md.tmpl accumulator paragraph (run_parallel realizes this)

No content change required: the per-core accumulator region description (offset
`lo_c`, cap `hi_c - lo_c`) is orthogonal to the dispatch re-point and stays
accurate. Listed here only to record that it was reviewed and left as-is.
