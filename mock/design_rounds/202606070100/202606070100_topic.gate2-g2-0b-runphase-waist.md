## Current state

G2-0a landed the trunk level: `FiberCons` / `FiberNil` (a trunk = a list of fibers) in `hilavitkutin-api::work_unit_values`, and `RunTrunk<A, WL>` in `hilavitkutin::dispatch::trunk_run`, delegating each fiber to the shipped `RunFiber`. A trunk walk is output-equivalent to a flat fiber walk over the concatenated units and devirtualises (objdump: zero indirect call).

Above the trunk, the canonical hierarchy names two more levels: a phase is a set of trunks running together (`:768`), and the pipeline is the sequence of phases separated by waists (`:74`, `:87`). The waist is the phase boundary: a synchronisation point all of a phase's trunks reach before the next phase begins (`:1306`). Today neither level has a carrier type or a walk; `Scheduler::run` walks one flat list with no phase or waist structure, even though the plan computes `PhaseBoundaries` (`compute_waists`).

## Changes proposed

Add the phase and pipeline nesting levels above `RunTrunk`, plus the waist barrier, all proven in sketch A:

1. **Phase carrier + walk.** `TrunkCons<T, Rest>` / `TrunkNil` in the api crate (a phase = a value-carrying list of trunks), mirroring `FiberCons` / `FiberNil`. `RunPhase<A, WL>` in the engine `dispatch/` walks `TrunkCons` / `TrunkNil`, delegating each trunk to `RunTrunk` and recursing. Single-core the trunks run sequentially; at N cores (a later round) a phase's trunks run concurrently on pinned cores with zero cross-trunk sync.

2. **Pipeline carrier + walk + waist barrier.** `PhaseCons<P, Rest>` / `PhaseNil` in the api crate (the pipeline = a list of phases). `RunPipeline<A, WL>` in the engine walks `PhaseCons` / `PhaseNil`, running each phase via `RunPhase`, then arriving at a waist barrier before the next phase. The barrier is a degenerate one-arriver shape at single core (an `AtomicUsize` counter that never spins when `expected == 1`); the load-bearing N-core waist is the shipped `phase_barrier_arrive` (wired in a later round, Sketch B). The single-core barrier is present so the waist composes into the nest without breaking devirt, proven by sketch A (the full four-level nest plus barrier objdumped to zero indirect call).

The witness lists nest the same way as G2-0a: `RunPhase`'s `WL` is a cons-list of per-trunk witness lists; `RunPipeline`'s `WL` is a cons-list of per-phase witness lists. The whole `RunPipeline -> RunPhase -> RunTrunk -> RunFiber` nest is a 3-deep witness cons-list inferred with no turbofish (sketch A settled 3-deep inference).

The output-equivalence contract holds at each level: a pipeline walk over phases of trunks of fibers produces the same column state as the flat `RunFiber` walk over the units concatenated in the same order, because each level only sequences the level below and the waist barrier is a no-op at one arriver. This round's test (TDD, fail-first) drives a two-phase pipeline (phase 0 with two column-disjoint trunks, phase 1 with one trunk reading phase 0's output across the waist) through `RunPipeline` and asserts the columns match the flat `Scheduler::run` over the same units.

`Scheduler::run` is still not re-pointed in this round. Building the nested carrier from the plan's `PhaseBoundaries` + `BlockPartition` + fiber grouping and routing the run through it is G2-0c, the round that makes the engine actually consume the trunk/waist sectioning.

## Why this slice

G2-0a proved the inner trunk level in isolation; this round proves the phase and pipeline levels plus the waist on top of it, still single-core and still output-equivalent, so G2-0c can build the plan-driven carrier against three landed, tested walk levels rather than constructing and validating the whole nest at once. Sequential rounds on one branch per `branch-pr-flow.md`; G2-0c follows on this same branch, and the G2-0 stage (all three rounds) lands together in one PR.
