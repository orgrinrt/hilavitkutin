# Topic: default implementations behind opt-in features

**Date:** 2026-11-20
**Round:** 202611200518-zrf9
**Source:** op's call, recorded in `mock/research/202611200520_default-impls-opt-in/OP-CALL.md`

Round 202611200201-yszg made `ArenaColumnStorage::release` give its block back, added `StaticFreeListMemory` beside `StaticBumpMemory` in `hilavitkutin-providers`, and added `allocate_zeroed` to the memory provider contract. It did so without superseding the provisional row that says release is a no-op, and two independent reads disagreed on whether a no-os provider in the providers crate breaks the ratified row that the no_os tier is contracts only. Op answered: "Option a/b but make the default impls an opt in feature on their respective crates. Default to contracts only." This round carries that answer through the canon, the designs and the code.

## What the answer settles

Release frees, so the release row is superseded. `StaticFreeListMemory`, `StaticBumpMemory` and `allocate_zeroed` stay where they are. Every default implementation of a contract sits in its own crate behind a cargo feature a consumer turns on, and a build on default features carries the contracts alone. That reaches the implementations that existed before the branch as well: the engine's `OsClock` and `OsMemoryProvider`, which its default-on `platform-os` feature carried, and everything `hilavitkutin-providers` ships. Each principle an implementation rests on has one feature name, the same in every crate, and the readmes name the features.

Two standing rows say the os tier is the default and so become wrong: the held row on the three platform tiers ("os as the default") and the provisional row on the clock ("defaults to the os-tier monotonic clock under the default feature"). Both are superseded by held rows that say what holds now. The ratified row that the no_os tier is trait contracts only stays as it is: a build on default features is that tier, and an implementation behind a feature a consumer turns on is the consumer's choice, not the tier's.

## The principles and their names

An implementation here rests on one of three things, and the feature is named for that thing:

| Feature | Rests on | Implementations |
|---|---|---|
| `os` | the operating system's services | `OsMemoryProvider`, `OsClock`, the operating-system arms of thread parking and thread classes (`hilavitkutin`) |
| `static` | memory the consumer hands in, with no operating system | `StaticBumpMemory`, `StaticFreeListMemory` (`hilavitkutin-providers`) |
| `portable` | the contracts alone, on any target | `ArenaColumnStorage`, `MemoryArena` with the interner surface and `InternerKit`, `AdaptWu` with its kits and EMA helpers, the metrics resources with `MetricsKit` (`hilavitkutin-providers`) |

The names are a proposal of this round, made to op's words "each needs a unified name" and posted to the coordinator before the doc changelist locks.

`platform-os` becomes `os`. `platform-no-os` goes, since it gated nothing and its only work was to satisfy a check that one of the two was on; that check goes with it, because a build with neither is now the default and means no operating-system reach. With `os` off, the builder's starting clock is the null clock and parking spins, as it did under `platform-no-os`.

`intrinsics-std` and `mutant-truncating-append` are not implementations of a contract and stay as they are. `hilavitkutin-linking`'s operating-system loader is that crate's own subject rather than a default implementation of a contract, and the port lane `work/port-seam-and-loader` overhauls the crate, so it is left alone.

## What it costs

Inside the workspace `hilavitkutin-providers` is only ever a dev-dependency, so each dependent names the feature it uses. A consumer outside it that builds on default features loses `OsClock`, `OsMemoryProvider` and every providers implementation until it names `os`, `static` or `portable`.
