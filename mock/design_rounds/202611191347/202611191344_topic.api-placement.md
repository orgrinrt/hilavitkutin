# api-placement

Op, 16 November, on where the items of `hilavitkutin-api` belong, choosing all four of the placements two blind seats agreed on (`mock/research/202611191345_api-placement/OP-CALL.md`). The unit vocabulary stays in the api. Capability, sink and codec leave hilavitkutin, since `Push` and `BulkPush` there duplicate notko's sink. The items only the engine reads move into the engine: `dispatch_codegen`, `PoolFrame`, `WakeStrategy`, `Executor`, `ExecutorError`, `HybridExecutor` and `ceiling_div`, with adaptation named a candidate opt-in crate. `MemoryProviderApi` stays in the api, and the held agent-written persistence row is superseded.

What the tree holds today. The api crate declares `capability.rs`, `sink.rs` and `codec.rs`; nothing in the workspace reads them but `tests/sink_smoke.rs` and `tests/codec_smoke.rs` in the api itself. `dispatch_codegen.rs` declares the four engine ids (`PhaseId`, `TrunkId`, `FiberId`, `UnitId`), `CoreProgram`, `PhaseEntry`, `SyncRole`, `RecordRange`, the sealed `DispatchCodegen` and `FiberShape`, `StandardCodegen` and an unused `StoreMarker`; the engine reads all but the last, the api reads none of them in code, and the api's own `tests/engine_id_index.rs` tests the ids. `platform.rs` declares the runtime data plane, `PoolFrame`, `WakeStrategy`, `Executor`, `ExecutorError` and `HybridExecutor`, below the three platform contracts; the engine re-exports them from `thread`, and three bench support crates read `PoolFrame` and `RecordRange` by their api paths. `ceiling_div.rs` declares `CeilingDiv` and `Ceil`, which nothing reads: the engine's plan module took capacity types in its place.

The canon. The provisional row `the_api_crate_carries_the_consumer_facing_types_and_traits_and_the_platform_contracts` says, in its second sentence, that the api carries the consumer contract surface for positions outside unit execution, capability, sink and codec; op's answer overturns that sentence, and the rest of the row stands. The held row `the_persistence_crate_is_the_generic_hot_cold_storage_bridge_as_a_standalone_ecosystem_crate` calls persistence standalone, against the ratified `op_ruled_that_the_persistence_crate_builds_on_the_str_and_api_crates_and_its_design_holds_over_the_lint`. Nothing cites the first outside the registry; the second is named only by a research note and a `related` line in the registry.
