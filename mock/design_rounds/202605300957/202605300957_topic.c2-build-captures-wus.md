# C2 slice 2: build captures WorkUnit instances, run walks them

Slice 1 shipped the `RunFiber` walk: given a value-carrying WorkUnit
sequence (`WuCons` / `WuNil`) and a built arena, `run_fiber_walk`
constructs each unit's `EngineCtx` and calls `execute`, resource-only.
It proved the heterogeneous walk works as pure Rust generics. What slice
1 did not do is connect the walk to the scheduler: the slice-1 test
hand-built the `WuCons` list and called the walk directly. A real
consumer registers WorkUnits on the builder with `.with(unit)` and then
calls `scheduler.run()`.

That connection is the gap this slice closes. Today the builder tracks a
registered WorkUnit's TYPE in the `Wus` typestate cons-list but drops
its VALUE at the `.with` call site (the `UnitKind` placement is
identity). `build()` then erases the `Wus` typestate entirely; the built
`Scheduler<Cfg, Vals, M>` retains only the store-value list. So the
scheduler has no way to obtain the registered WorkUnit instances at run
time, and `run()` is a no-op that returns `Cfg::Out::default()`.

The resolution is to retain the WorkUnit instances in a parallel
value-list that survives into the `Scheduler`, exactly as the
store-value list already survives for the arena drain. The TYPE list
(`Wus`) stays the plan and AccessSet identity (it drives the
`ContainsAll` proof at `build()`); the new VALUE list carries the
runtime WorkUnit instances (including any `.with`-time configuration a
unit holds in its fields). Both accumulate the same units in parallel,
one prepend per `.with`. `run()` then walks the retained value-list via
the slice-1 `run_fiber_walk`.

## Why retain instances rather than reconstruct from the type

The alternative considered (and rejected, after architect review) was to
keep dropping the value and materialize each WorkUnit from its type at
run time. That needs a construction contract on `WorkUnit` (a `Default`
bound, a sealed const-constructor, or ZST-only materialization). It is
inverted coupling: a WorkUnit can legitimately carry per-instance
configuration set at `.with` time, and reconstructing from the type
discards it. Retaining the instance is purely additive over the
shipped, proven slice-1 pieces and preserves whatever the unit was
registered with. The eventual LLVM-optimized dispatch tier (per-unit
monomorphised Ctx-erasing shims) is a separate, later concern; it does
not gate the generics walk this slice wires up.

## What lands

The builder gains a second value accumulator alongside the store-value
list. A new placement kind, `WorkUnitKind`, prepends a registered
WorkUnit instance onto a `WuCons` value-list; the `UnitDispatch<W>`
router (which today routes its value to the drop kind) routes to the new
kind instead. The run-config and platform routers keep dropping their
value, so the WorkUnit retention does not accidentally retain a
`RunCfg` or a platform provider. The placement trait that today routes
one value onto the store list is reshaped to route one value onto both
lists at once (it must, because the single registered value is consumed
once and lands on exactly one of the two lists). The `WuCons` / `WuNil`
value-list types move from the engine to `hilavitkutin-api` so the
builder can construct them (the api crate cannot depend on the engine);
the engine re-exports them next to the walk that consumes them.

`build()` and `build_with()` carry the retained WorkUnit value-list into
the `Scheduler`, which gains a value-list type parameter and a field for
it. `run()` walks the retained list via `run_fiber_walk` over a single
full-range morsel, resource-only.

## Scope boundary

The walk order this slice is registration-list order. Because each
`.with` prepends, the built list runs last-registered-first; the test
asserts and documents that honestly. Dependency-topological order (from
the merged `plan_inputs_from_bundle` then `compute_execution_plan`) is
the next slice, not this one. There is no morsel loop and no plan
computation here: `run()` walks the retained units once over the full
range. Columns stay out of scope (resource-only, the slice-1 boundary
carries forward); per-frame column buffers wait on real column-buffer
allocation from the `MemoryProvider`. WorkUnits contributed by a Kit are
not retained this slice (a Kit hands the builder unit TYPES through a
bundle, not instances; materializing them is the same construction
problem deferred above). The sealed `FiberShape` codegen stub and the
LLVM dispatch tier are untouched.

## The public-contract change

`Scheduler` gains a WorkUnit-value-list type parameter (it becomes
`Scheduler<Cfg, WuVals, Vals, M>`, `WuVals` defaulting to the empty
list). The parameter is inferred through the builder, defaults to the
empty list for the bare type, and the `scheduler.run()` call shape is
unchanged (the added `run` witness parameter is inferred at the call
site, no turbofish). No code outside the engine names `Scheduler<...>`
with explicit value parameters; the change is additive, pre-1.0, and
in-crate, so it lands clean with no compatibility shim per the
no-legacy-shims rule.
