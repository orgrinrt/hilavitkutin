# Doc changelist: an over-capacity accumulator append is a value

**Date:** 2026-11-13
**Phase:** DOC
**Round:** 202611130358 (branch `work/overflow-is-a-value`), roadmap step HV1b
**Source topics:** `202611130400_topic.overflow-is-a-value.md`

The engine design and the api design stop saying that an append past an accumulator's reserved capacity asserts and panics. Both now state the sticky refusal once, the count beside the live length that carries it, how the per-core regions of `run_parallel` publish and merge it, where it is read, and how it reaches the caller through the run config's output. The api design gains the accumulator writer and its bridge, which it did not list, and a section for `AccumRefused`.

## Changes

### CHANGE 1: `hilavitkutin/DESIGN.md.tmpl`, appending past the reserved capacity

The paragraph under dispatch codegen that called an over-capacity append a contract violation which asserts and panics is replaced. An append always bumps `wanted`; it writes and bumps the live length only when `wanted` equals the live length and the live length is below the capacity, so `wanted` never falls below the live length and the accumulator has refused exactly when `wanted` is above it. Nothing is written on a refusal. At the close the bindings are walked in registration order and the first refusing accumulator is returned as an `AccumRefused` through `RunCfg::Out`. The sentence before it ("hit the assert") now reads "be refused".

Verification: `grep -n "asserts\|panics" mock/crates/hilavitkutin/DESIGN.md.tmpl` names no accumulator append.

### CHANGE 2: `hilavitkutin/DESIGN.md.tmpl`, the drain arm and the reset

The drain-arm paragraph says an append past capacity is refused and counted in `wanted`, that the entry returns `AccumRefused`, and points back at CHANGE 1's paragraph as the one statement of the rule. The per-frame reset zeroes the live length and `wanted`, two `Cell` writes per `AccumBinding`.

### CHANGE 3: `hilavitkutin/DESIGN.md.tmpl`, the per-core regions of `run_parallel`

Each core's projected binding carries its own live and `wanted` cells. A region refuses under the same sticky rule, so it never writes into the next region. Each worker publishes both counts into its own rows of `gate2_accum_live` and `gate2_accum_wanted` before it arrives; the main thread reads them after `frame_await_done`, with every worker parked. The merge sets the shared live length to the summed live counts and the shared `wanted` to that sum plus every refused append (the leading bands' and `wanted_c - live_c` per core). The trailing bands append on the merged binding under the same rule, and the refusal is read after them, still with every worker parked. The region skew that the at-most-one-append-per-record bound leaves (refused at more than one worker and accepted at one, with `wanted` at or below the capacity) is stated. A panic inside a unit's own body on a worker is stated as not caught and not reported.

### CHANGE 4: `hilavitkutin-api/DESIGN.md.tmpl`, the accumulator writer

`AccumWriterApi` joins the provider API block, `ResolveAccumAppend` the bridge block and the `HasAccumWriter` accessor the `provider_generic!` block, matching `src/context.rs`. A paragraph after the bridge block states the refusal from the caller's side: refused, never asserted, never written; sticky for the frame; `len` is the live length; the run hands back the first refusing accumulator; no caller obligation covers the capacity.

### CHANGE 5: `hilavitkutin-api/DESIGN.md.tmpl`, `AccumRefused` and the run's output

A new section before the lifetime contract. `AccumRefused` carries the registration position (`accum()`) and a `notko::Exhausted` (`exhausted()`), private fields, `const fn` accessors. `RunCfg::Out` is bound on `From<notko::Outcome<(), AccumRefused>>` and every run entry returns `Cfg::Out::from(verdict)`. `DefaultRunCfg` takes `Out = notko::Outcome<(), AccumRefused>` and `Err = AccumRefused`. The value is the same at every worker count because `wanted` does not depend on the split.

## Keeping the assert

The refusal is decided in one branch of `resolve_append`. Should the lead designer want the assert kept, that branch reads a strategy parameter (an associated type on the run config) or a property of the memory provider the binding was reserved from; the counts, the merge, the close and the return do not move. Only the refusing arm is built, under call 13's default.
