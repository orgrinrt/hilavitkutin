# overflow-is-a-value

**Date:** 2026-11-13
**Phase:** TOPIC
**Scope:** the accumulator append in `hilavitkutin` (`src/dispatch/engine_ctx/ctx_writers.rs`), the bindings walks it needs (`src/resource/bindings/`), the three run entries and the worker (`src/scheduler/run.rs`, `run_fused.rs`, `run_parallel.rs`, `worker.rs`), and the append and run-config contracts in `hilavitkutin-api` (`src/context.rs`, `src/run_cfg.rs`).
**Grounded on:** roadmap step HV1b, the consolidation's fault rows H1, H2 and D4, and the lead designer's call 13, which takes its default meanwhile: a refusal as a value everywhere.

An append past an accumulator's reserved capacity panics today. On the calling thread that is a loud failure. On a worker of `run_parallel` it is worse: the engine is `no_std` and spawns nothing (`src/lib.rs:10`, the design's "Neither tier spawns threads"), so it cannot catch the panic, the worker never arrives at the frame's done barrier, and `run_parallel` waits on `frame_await_done` for an arrival that never comes. The comment at `src/scheduler/run_parallel.rs:387-394` calls that stalled join "the accepted failure mode". A hung worker is a dead tab on the web, and nothing told the caller why. This round makes the overflow a value the caller is handed, at every worker count, and takes the comment out.

## What the tree does at the start

Dev is `c2b392d`, the landing of `work/suite-can-fail`. `resolve_append` (`ctx_writers.rs:143-146`) asserts `live < cap` and panics before the write. The single-core `run` and `run_fused` reach it on the calling thread. `run_parallel` reaches it on a worker for the unit-outer accumulator carrier: each worker appends into its own region of the reserved buffer through a per-core copy of the bindings (`resource/bindings/per_core.rs:76-92`) whose capacity is the core's record slice (`hi - lo`), then publishes its live counts into `gate2_accum_live` and arrives; the main thread merges the regions after `frame_await_done`. The only over-capacity test, `accum_append_panics_past_reserved_capacity` in `tests/accum_dispatch.rs`, is a `#[should_panic]` on `run`.

## The shape

The sticky refusal is a second count on each accumulator binding beside the live length: how many appends the frame asked of it. Every append bumps it. An append writes and bumps the live length only when nothing has been refused yet (`wanted == len`) and the live length is below the capacity; otherwise it writes nothing and only `wanted` moves. So `wanted >= len` always, and the accumulator has refused this frame exactly when `wanted > len`. That is the sticky state: once one append is refused, every later append on the same binding is refused and the live length does not move, which is the law `notko`'s `Fill` keeps for a lend and the panel stated for the window (L75, N3). No flag is stored apart from the two counts, so there is nothing to keep consistent with them.

The refusal is read at the close. After the last band of the frame, `run` walks the bindings in registration order and returns the first accumulator whose `wanted > len`, as a value naming its registration position among the accumulators and `notko::Exhausted { wanted, had }`, with `had` the reserved capacity. The value goes out through the run-config's output: `RunCfg::Out` is bound on `From<Outcome<(), AccumRefused>>`, the default config's `Out` is `Outcome<(), AccumRefused>` (the reflexive `From` covers it), and every run entry returns `Cfg::Out::from(verdict)`. `RunCfg` is sealed, so the default config is the only impl and no consumer impl breaks.

`wanted` is the count of appends the frame asked for, so it does not depend on how the records were split. On one core it is every append the bodies made; on `n` workers the merge sums the per-core counts. `had` is the reserved capacity of the shared binding in both. The refusal of an emitter that asks more than the reserved capacity is therefore the same value at 1, 2, 4 and the maximum worker count, which is the proof the roadmap asks for.

## Who writes the sticky refusal, when it is read, and why every worker has re-parked

On the calling thread (`run`, `run_fused`, the meta bands of `run_parallel`) the bindings belong to that thread for the frame; the two `Cell`s are written only there. On a worker, the unit-outer path appends through the per-core copy that `rebase_accums` builds with fresh cells, so each core's `len` and `wanted` are written by that core alone and never shared. The worker publishes both counts with Relaxed stores into its own row of `gate2_accum_live` and a new `gate2_accum_wanted`, before its `frame_done_arrive`, whose Release pairs with the main thread's Acquire in `frame_await_done`. The main thread reads the rows only after that wait returns, which is the point at which every worker has arrived and gone back to `frame_await`, so no worker touches the bindings again until the next publish. The merge then sets the shared binding's live length to the sum of the per-core live counts and its `wanted` to that sum plus every refused append (the shared binding's own refused appends from the leading bands, and each core's `wanted - live`), which keeps `wanted > len` exactly when some append was refused anywhere. The trailing bands append on the merged binding under the same sticky rule. `run_parallel` reads the refusal after the trailing bands, still with every worker parked, and returns it.

Nothing waits on a worker that panicked over capacity any more, because no worker panics over capacity. A panic in a unit's own body on a worker is not reported: the engine cannot catch it without std and without owning the thread, and that half of D4 has no implementation here.

## If the lead designer wants the assert kept

The refusal is decided at one place, the refused branch of `resolve_append`. Keeping the assert is a strategy parameter read there (an associated type of the run-config, refuse by default and assert as the other impl), or a property of the memory provider the binding was reserved from; the counts, the merge, the close and the return stay as they are, since an asserting strategy never leaves `wanted > len` behind. Call 13 takes its default here, so only the refusing arm is built.

## What this round leaves for others

The per-core region of `run_parallel` is the core's record slice, the design's at-most-one-append-per-record bound (`DESIGN.md.tmpl`, the convergence accumulator paragraph, which names multi-append as a follow-up). A frame that fits the reserved capacity whole but asks more than one append per record on one slice is refused on more than one worker and accepted on one. With the assert it panicked on the worker; with this round it is refused with `wanted <= had`, which says the layout and not the reservation refused. The test stating the intended behaviour is catalogued with a ticket. The leading meta bands of `run_parallel` append on the shared binding before the workers write their regions from offset zero, and the merge then sets the live length from the per-core counts, so a leading-band append is lost; that is ticketed too, and the merge keeps the band's refused appends so a refusal is never lost with it.

## Tests

A skewed emitter, one append per record and three more on record 0, over a reserved capacity equal to the record count, run through `run` and through `run_parallel` on executors reporting 1, 2, 4 and `MAX_CORES` workers. Each run returns the same `AccumRefused`, the accepted records are a prefix of the emitter's sequence per region in record order, and a second accumulator laid out directly after the refusing one in the arena holds exactly its own records, so no refused append wrote past its region. The truncating mutant, an append that drops at the capacity without recording, is a committed feature of the engine crate, `mutant-truncating-append`; the suite run with it fails the refusal assertion, shown once in the changelist. The `#[should_panic]` test becomes a value test.
