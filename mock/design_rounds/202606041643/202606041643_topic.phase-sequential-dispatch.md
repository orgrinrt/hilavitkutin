# Topic: phase-sequential dispatch (consume the plan structure)

**Date:** 2026-06-04
**Scope:** hilavitkutin engine (`mock/crates/hilavitkutin`, `Scheduler::run`). The next single-core slice after the column / accumulator / morsel-windowing arc. HILA-RUNTIME, the memo's Phase E first single-core step.
**Source topics:** the dispatch-build-plan memo (`mock/research/202605282100_engine-dispatch-build-plan.md`, Phase E line ~52); a neutral `feature-dev:code-architect` read (agent a7ff9218df0ecdf19) resolving the next-slice fork and verifying feasibility.

`Scheduler::run` today walks the flat global topological order (`topo_order[0..topo_count]`, a Scheduler field) and dispatches each unit once per morsel. The plan computes a full `phases -> trunks -> fibers -> units` structure and `build` stores it on `ColumnStorage`, but dispatch consumes none of it. This round makes `run` walk `plan.phases` in order, and within each phase its trunks, fibers, and the fibers' units, dispatching each unit through the same `FiberSlot` shim. Single-core, no barriers, no parking; this is the correctness oracle the parallel path validates against later.

## Why this slice (the fork resolution)

The cron's enumerated scope (column data plane, column dispatch, morsel loop) is complete; the single-core dispatch is behaviourally done. The fork was: persistence drain (#344), a plan-chain sub-slice (#339), virtual firing, an accumulator reader, or phase-sequential dispatch. A neutral architect read plus memo-mining resolved it:

- The PassEnd persistence drain (#344, the memo's Phase B step 6) is gated upstream: `hilavitkutin-persistence`'s disk layer (`ColdStore::flush` / `load` / `snapshot`) is an explicit stub deferred pending an rkyv/mmap no_std vetting. Not a quick fix; ruled out.
- The `UnitId` `transmute_copy` hazard (memo Phase C step a / risk R1) is already gone from `plan/`; moot.
- Improving the plan internals (real `waist_detect`, RCM into fiber grouping) improves a structure nothing in dispatch reads yet, so it has no observable effect until dispatch consumes the structure. Lower leverage until this slice lands.
- Virtual firing needs a multi-pass run loop (a larger structural change); the accumulator reader's canonical consumer is the gated drain.
- Phase-sequential dispatch is the memo's explicit Phase E first single-core step, un-gated, and the first time dispatch consumes the plan's phase structure: the foundation for phase barriers, phase-boundary meta-WU firing, the per-fiber morsel loop, and per-phase configs. It also validates `project_fiber_components` and the phase / trunk / fiber pools, a correctness check the flat walk bypasses entirely.

## The traversal (feasibility confirmed by the architect read)

The plan is fully populated and traversable today: `plan.phases[0..phase_count]`, each `Phase` carrying `trunk_offset + trunk_count` into the flat `plan.trunks` pool; each `Trunk` carrying `fiber_offset + fiber_count` into `plan.fibers`; each `Fiber<D>` carrying `units: Array<UnitId>` with a live `unit_count`. So dispatch routes `phases -> trunks -> fibers -> units`, dispatching each unit through the existing `FiberSlot` shim. `store_plan` already copies `phases` / `trunks` / `fibers` / `unit_meta` into storage; `run` has `&self.storage` + `__plan_handle()`, so it reads them back via `column_ptr::<Phase>(...)` etc. (the same `unsafe` read pattern `store_column` writes with; `Phase` / `Trunk` / `Fiber<DefaultPlanDims>` are `Copy` / `ColumnValue`, so the bound holds).

## The correctness contract and its risk

Phase-sequential dispatch is correct iff the plan's phase structure is a valid topological layering: phases are topologically ordered, and units within one phase have no cross-dependencies (so their dispatch order within the phase is free). A phase boundary exists exactly where a dependency crosses it, so a `phases -> trunks -> fibers -> units` walk is a valid topological order, equivalent to the flat `topo_order` for single-core (same units, same dependency-respecting order).

The risk: this trusts the plan's phase assignment. If the plan wrongly places a dependent pair (a column producer and its consumer) in the same phase, phase-sequential dispatch can run them in the wrong order where the flat topological walk did not. The slice therefore VALIDATES the plan's layering: the red-first test is a column producer/consumer pair (a RAW edge) dispatched phase-sequentially, asserting the consumer reads back the producer's output. If it fails, the plan mis-layers and the fix is in scope (verify the waist/phase assignment separates dependent units into ordered phases). The current `waist_detect` over-segments (treats any out-degree-zero unit as a waist) which yields MORE phase boundaries than ideal but preserves correctness (extra boundaries never merge dependent units); the real `waist_detect` is a later Phase C slice and is not required here.
