# Src changelist: phase-sequential dispatch (build-time flatten)

**Date:** 2026-06-04
**Phase:** SRC
**Round:** 202606041643 (phase-sequential-dispatch, branch `feat/hilavitkutin-phase-sequential-dispatch`)

Makes dispatch follow the plan's phase structure: the dispatch order becomes the plan flattened `phases -> trunks -> fibers -> units` instead of the flat `unit_meta` topological permutation. This is the first time dispatch consumes the plan's phase/trunk/fiber structure, and it validates `project_fiber_components` (a complete, ordered partition of the units).

## Refinement from the topic: build-time flatten, not run-time walk

The topic and the design review framed this as `Scheduler::run` walking the plan structure at runtime. Apply surfaced a concrete friction: the plan is computed and stored as `ExecutionPlan<DefaultPlanDims>` (monomorphic), but `Scheduler` / `run` carry a generic `D: PlanDims`, so a run-time `column_ptr::<Fiber<D>>` read-back from storage confronts a `D`-vs-stored-`DefaultPlanDims` mismatch and needs a `Fiber<D>: ColumnValue` bound on `run`. The order derivation already happens at build (`extract_topo_order`, which is `&ExecutionPlan<DefaultPlanDims>`-concrete), so flattening the phase structure there is clean: no `D`-generic storage read, no new `run` bound. The dispatch order and the `project_fiber_components` validation are identical to the run-time walk; only the traversal site differs (build, where the plan is in hand, versus run). The run-time phase boundaries the parallel path needs for barriers are that path's concern (it restructures `run` regardless); this slice delivers the single-core phase-sequential order.

## CHANGE: `extract_topo_order` becomes a phase-structure flatten
File: `mock/crates/hilavitkutin/src/scheduler/mod.rs`
Rename `extract_topo_order` to `derive_phase_dispatch_order` and rewrite its body: instead of reading `plan.unit_meta[u].id` (the flat topological permutation), walk `plan.phases[0..phase_count]`, for each phase its trunks `plan.trunks[trunk_offset .. +trunk_count]`, for each trunk its fibers `plan.fibers[fiber_offset .. +fiber_count]`, and for each fiber its units `fiber.units[0..unit_count]`, collecting each unit's slot index (`unit_id.index()`) into the order array. Returns the order array plus the count of units emitted (the flattened total). The `topo_order` / `topo_count` Scheduler fields are retained (the result is a valid topological order, now grouped by the plan's phase/fiber structure); the field doc notes the phase-sequential derivation. `build` / `build_with` call the renamed function unchanged. `Scheduler::run` is unchanged: it walks `topo_order[0..topo_count]` (now the phase-sequential order) dispatching each unit per morsel.
Verification: `grep "fn derive_phase_dispatch_order" mock/crates/hilavitkutin/src/scheduler/mod.rs` returns one match; `! grep "fn extract_topo_order"` (the old name is gone).

## Tests

New `tests/phase_sequential_dispatch.rs`: a column producer + consumer with a RAW edge (producer writes `Column<T>`, consumer reads it, registered so a plain registration walk would run the consumer first), dispatched through `run`. Asserts the consumer reads back exactly what the producer wrote across the records. This exercises the phase-sequential order: the plan must place the producer in an earlier phase than the consumer (the RAW edge crosses a phase boundary), and the flatten must visit both in dependency order. Red against a flatten that drops a unit (an incomplete partition leaves the consumer reading uninitialised records) or mis-orders phases. The existing `column_dispatch` / `accum_dispatch` / `morsel_loop` tests must stay green (the phase-sequential order is dependency-equivalent to the flat topo order for single-core; they already exercise producer/consumer ordering and now run through the phase-flattened order).
