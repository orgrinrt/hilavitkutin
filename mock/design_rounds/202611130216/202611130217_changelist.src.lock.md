## CHANGE: what a consumer can do with replace_value is a committed pair, and the intended test is catalogued
Files: `tests/ui/replace_value_unreachable_{fail,pass}.rs` with the `.stderr`, `tests/ui/replace_value_orphan_{fail,pass}.rs` with the `.stderr`, `tests/ui.rs`, `mock/catalogue.md`.
The intended test is that the next run reads the replaced value. It cannot be written: `replace_value` takes the store marker `Resource<InA>` as its argument, so it names no value to install, and its `Replaceable` bound cannot be met, because `impl Replaceable for Resource<InA>` is refused by the orphan rule in a consumer crate (E0117, probed and now committed). The first pair shows the refusal at the call (twin: `mark_dirty`), the second shows the refused impl (twin: a local trait). `replace_resource` is not exercised: its bound `PlanAffecting` is sealed and implemented only for `DefaultRunCfg`, which review pass 3 reported and this round did not probe. The `mock/catalogue.md` row (ticket `147e3897011f`, with `e9bb6a0f7600`) says the two fixtures are replaced by the value test when the methods take a value type and a consumer can opt in. Both fixtures record what a consumer can do today, not what the design says.
Verification: each new `.stderr` holds one error (`grep -c "^error"` returns 1 for `replace_value_unreachable_fail.stderr` and `replace_value_orphan_fail.stderr`). `cargo test -p hilavitkutin --test ui` passes.
