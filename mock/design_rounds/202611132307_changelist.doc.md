## Current state

The api's design registers a plain column by its bare marker, `.with(Column::<T>::new())`, with `Init = ()`. A plain column is then reserved memory nothing has written. A unit of the first pass that reads it ahead of its writer reads that memory through a safe call, and so does the compare the scatter makes for a `Differs` write. The last round closed the same hole for the buffered column alone, with a carrier `StagedBuffered<T, M>` and a trait `StartsFromDefault` that carries an associated type and is open to any implementor.

Op's words of 13 November settle a column's start by its element type, and say the constructor that does not apply to a type is not to exist for it. They reached this seat after the last round closed. The topic has them, with the options he was shown.

Two markers in the designs name a commit where the ticket's id belongs, and one sentence of the engine's design says a failing test is kept "with its ticket".

## Changes proposed

### 1. A column, plain or buffered, is registered with its start, in `hilavitkutin-api/DESIGN.md.tmpl`

"Store types" says it of both columns. The sealed trait `Starts` is what the two markers share, with the element type as `Value`. The carrier is `Started<S: Starts>`, one for both, in place of `StagedBuffered<T, M>`. Each marker has `new()`, which stays the marker a unit names the store by, `start_from(value)` for every element type, and `start()` under `HasTrivialCtor`. `StartsFromDefault` loses its associated type and is bounded on `Starts`, with one blanket impl where the element type has a `Default`, so nobody outside the crate can add a tier. `start_from` and the constructor tier are `const fn`.

Why one carrier and one trait, and not the buffered column's pair written a second time for the plain one. The two columns differ in how the engine keeps them and in nothing the api says of their start. Two carriers would be two arms of every list in the engine that takes one, and the second copy is the one that goes stale.

Why the constructor is ahead of the default is in the topic, and the design has the paragraph. Op's second remark gives `HasTrivialCtor` no place in his sequence, so the place is a reading of this round: question ticket 2d660de45432 asks him. Whether `start_from` should exist for a type that has a start of its own is question ticket 6fe661a77c64. Both are built the way the design says and both can turn on his answer without a unit author changing anything.

The null bit is still no tier, for the reason the last round gave, on ticket df2e4da2d376.

"Store wrappers as Providers" is rewritten around which stores register by a carrier of a value and which by the marker. `Column<T>` and `Buffered<T, M>` are not providers. The paragraph on `Init` follows.

What a start does not reach. It is one value for the whole store, so data that differs from record to record is a unit's write in a pass. A column a kit owns is named by marker in the kit's list and gets no start from this round: the design carries a marker on ticket ac91dfb44d6e.

### 2. One drain for both columns, in `hilavitkutin/DESIGN.md.tmpl`

The paragraph on the two reservations becomes a paragraph on a column of either kind. The drain takes one carrier, reads the kind off the marker through the engine's trait `Kept`, reserves by the kind and writes the start to every record of every reservation. The list of carriers the builder retains is corrected to what it retains.

### 3. Small corrections

The two markers that named `8e2e2326d588` name ticket 8c7cc9768579, which is the ticket they were filed with (ticket 6d613ddd8607). The engine's sentence on a frame where an entry and the reference differ no longer says how the test is tracked.

### 4. What is not changed

The engine design's sentence that the reach cuts fold at compile time stands. The source calls the three functions at run time, which is review 2's finding 3, and the source is what changes.

The conformance crate's reference runner is lent its stores by the caller and starts from what it is lent, so its design stands. The frozen author units name `Column` and `Buffered` as markers in their lists and bodies, which does not change, so no frozen file is edited and `BREAKS.toml` gains no line.

The api design still says of `generic_const_exprs` that it has a stabilisation profile of its own, and the engine still enables it for one type. That is older than this branch and is a migration of the plan's capacity types: a ticket of its own, named in the source changelist.

## Breaks counted

Scheduler builders, two. `.with(Column::<T>::new())` no longer compiles and becomes `start()` or `start_from(value)`. The type `StagedBuffered<T, M>` is now `Started<Buffered<T, M>>`, for whoever wrote it out. Unit authors, none: a unit's lists and body name the marker as before.

## Proving checks owed by the source

A compile-fail arm for each wrong pairing on the plain column: `start()` on an element type with neither a constructor nor a default, and the bare marker handed to `with`. A test that a plain column of a type with both starts from its constructor, and one that a type with a default alone starts from it. A test in the engine that a unit of the first pass reads the start from a plain column nothing wrote, with a provider whose memory is not zero, committed red ahead of the write that makes it green. A test that a compared write of the start's own value to a plain column, by a unit at the close of the first pass, which is where the engine makes that compare for a plain column, marks nothing changed. The engine's tests register every column with a start, and none seeds a whole column through a hidden accessor in place of one.
