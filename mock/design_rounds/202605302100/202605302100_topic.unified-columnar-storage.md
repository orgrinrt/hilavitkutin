# Topic: unified columnar storage for all engine state

The engine has accreted several disjoint, hand-rolled storage mechanisms. The resource data plane is a bespoke arena (`resource/arena.rs`, the `ArenaFor` / `DrainStores` machinery). The adapt subsystem has its own `AdaptArena`. The execution plan is a monolithic nested const-array struct owned directly by the `Scheduler`. The dispatch tier grows its own fixed slot buffers. None of these route through a single storage contract. They each reinvent "hold N things of T in fixed memory," which is precisely the pattern the engine's design exists to prevent.

The sharpest symptom surfaced while wiring plan-derived dispatch: `ExecutionPlan<DefaultPlanDims>` measures at 11,031,312 bytes. It is a dense `Phases(32) x TrunksPerPhase(32) x ComponentsPerTrunk(32)` nested array tree, so it cannot be a stack value at the real default budget, which makes `compute_execution_plan` unusable outside the small test dimensions. Relocating that 11 MB onto the `Scheduler` as a field does not help: it just moves the un-stackable value. The structure itself is the problem, and the structure is bespoke storage that never went through the engine's own data plane.

The design always intended one storage abstraction for everything. Domain 07 of the consolidation epic names `ColumnStorage` as the single contract for all typed multi-record data, sitting above `MemoryProvider` (the raw allocator the consumer supplies; "Library never calls allocator directly"). Bespoke per-subsystem arenas are explicitly forbidden ("all storage via SlabColumn or stack arrays"; the `hilavitkutin-workunit-mental-model.md` rule). The plan was meant to be exposed as meta-Resources (`meta::ExecutionPlan`, `meta::Dag`, `meta::LaneAssignment`) in the scheduler's own data plane. The current state is the deviation: `ColumnStorage` was designed but never shipped in `hilavitkutin-api`, so with no contract to depend on, each subsystem grew its own arena to fill the void.

This round establishes the contract and its api shape so that all storage, including the plan, depends on it. Per the design's own staging, we do not need to finish the entire columnar storage engine here. The api is trait-based, so we depend on the contract and ship a naive arena-backed placeholder behind it. The implementation can mature later; the trait bounds and the in-body apis are what every consumer interfaces with regardless.

## The model: everything decomposes to columns of column-sized scalars

The floor of all storage is a column of column-sized scalars. A `ColumnValue` is the scalar unit (`Copy + 'static`, `BIT_WIDTH`-certified). `ColumnStorage` holds columns of those scalars, allocated through `MemoryProvider`. Every piece of engine state reaches this floor.

`Resource`, `Column`, `Seq`, `Map`, and `Field` are access-and-intent sugar over that floor, not separate storage mechanisms. Each decomposes, struct-of-arrays style, to scalar columns:

1. A `Resource<T>` is not one column and not necessarily a singleton. Its fields break down: a multi-field struct becomes one column per field, recursing until every leaf is a column-sized scalar. `Field<T>` / `ColumnValue` is the base case the recursion stops at, so scalar promotion is preserved as the fundamental, not dropped.
2. `Seq<T, N>` and `Map<K, V, N>` map to a column more directly, because a sequence or map is already column-shaped. If the element type is not itself a column-sized scalar, it expands the same way: several scalar columns, one per leaf field.
3. The distinction between `Resource` and `Column` is intent and access pattern, not mechanism. Both live in the same columnar store. `Resource` holds persistent, infrequently computed or written state (config, providers, and the plan), with cardinality one or more. `Column` holds hot-path records crunched per morsel. Same backing, different role.

So the unification is at the floor (columns of scalars), not at the marker level. The markers stay distinct for how code declares and accesses state; underneath, they all SoA-decompose onto `ColumnStorage`. This is the resolution of the earlier "does `Resource` collapse into a cardinality-1 `Column`?" question: neither marker is the storage unit. The scalar column is.

The plan follows directly. The execution plan is a meta-`Resource`: cold, computed once and reused across frames. It SoA-decomposes into scalar columns sized by the live count (the phases, trunks, and fibers that actually exist), allocated through `MemoryProvider`. The 11 MB dissolves structurally: there is no dense nested const-array tree, only flat scalar columns whose lengths track reality.

## The contract surface

Two pieces are load-bearing. The first exists in the api as markers and access views but lacks its backing trait; the second does not exist yet and is the real design work.

`ColumnStorage` is the missing backing trait: the contract for owning and accessing columns of `ColumnValue` scalars over `MemoryProvider`. The api already ships the declaration markers (`Resource` / `Column` / `Virtual` / `Field` / `Seq` / `Map`), the per-morsel access views (`ColumnReaderApi` / `ColumnWriterApi` / `ResourceProviderApi` / `VirtualFirerApi` plus the `Resolve*` witnesses), and `MemoryProviderApi`. It does not ship `ColumnStorage` itself. Establishing it (trait-only) is what gives engine-internal storage something to depend on.

The decomposition mechanism maps an aggregate type `T` to its constituent scalar columns. `ColumnValue` is the base-case certification; the open work is the trait (and likely a derive) that walks a struct's fields and produces the SoA column set, recursing through nested structs to scalar leaves, and handling the `Seq` / `Map` element-expansion case. This is the heart of "everything goes through columnar storage" and the part with the most design surface (field iteration, naming, alignment, the cardinality-1 fast path that preserves scalar promotion).

A naive arena-backed `ColumnStorage` impl ships as the placeholder so function and method bodies have a real backing to call against while the columnar engine matures. It can be a single arena over `MemoryProvider`; correctness and the trait shape matter, not its performance.

A lint forbids any storage that does not go through these contracts: no hand-rolled arenas, no `MaybeUninit` pools, no raw fixed buffers holding runtime data outside `ColumnStorage` / the markers. The design already forbids bespoke arenas; the lint makes it enforceable. The sanctioned exceptions the design names (the thread-pool `PoolFrame` synchronisation structure) are carved out explicitly.

## Decisions and open questions

- Scalar-promotion fast path: the cardinality-1 decomposition (a single-field or scalar `Resource`) should retain the `Field<T>` LLVM-promotable path rather than always paying a column indirection. Confirm `ColumnStorage` special-cases cardinality one.
- Decomposition surface: trait-only with hand-written impls first, or a derive from the start. A derive is the natural ergonomic end state, but the trait shape must settle before the derive is worth writing.
- Where `ColumnStorage` lives: `hilavitkutin-api` (it is a consumer-facing contract, alongside `MemoryProviderApi` and the markers).
- Migration ordering of the existing bespoke stores (resource arena, adapt arena, plan, dispatch buffers) onto the contract; each is its own follow-on round.

## Impact map: backward fixes and forward framing

Two directions: code that already exists in the wrong shape (fix it), and the surfaces whose framing must change to describe the unified store going forward. The consolidation epic (domain 07) already specifies `ColumnStorage` as the one store, so this is not a new direction; it is correcting the shipped deviations and aligning the shipped docs to the always-intended design.

Current code to correct (the deviations the engine accreted):

- `hilavitkutin-api`: `ColumnStorage` and the decomposition trait do not exist; add them. `Resource` / `Column` / `Virtual` / `Field` / `Seq` / `Map` are PhantomData markers plus the per-morsel access apis; they gain their defined relationship to `ColumnStorage` as decomposition views. `ColumnValue` stays the scalar base cert.
- `hilavitkutin/src/resource/arena.rs` (`ArenaFor` / `DrainStores`, the B2a resource arena from round `202605290018`): the bespoke resource data plane. A resource is a decomposed set of scalar columns, so this arena collapses into the store. This is the central deviation.
- `hilavitkutin/src/adapt/arena.rs` (`AdaptArena`): adapt metrics route through the store.
- `hilavitkutin/src/plan/*` (the `ExecutionPlan` / `Phase` / `Trunk` / `Fiber` / `DependencyGraph` const-array tree): the plan becomes a meta-`Resource`, SoA-decomposed to scalar columns sized by live count. This dissolves the 11 MB and makes `compute_execution_plan` usable at the real budget.
- `hilavitkutin/src/dispatch` slot buffers (the parked #647 `FiberSlot` array): route through the store, not a bespoke stack buffer.
- `Scheduler` fields: the owned arena and the plan storage become store handles / meta-Resources.

Forward framing to amend (align shipped docs to the design):

- `mock/crates/hilavitkutin-api/DESIGN.md.tmpl` and `mock/crates/hilavitkutin/DESIGN.md.tmpl`: the resource / storage / plan / domain-19 sections describe the bespoke shapes (resource arena, plan const-arrays). Reframe to `ColumnStorage` + decomposition + plan-as-meta-Resource.
- `mock/DESIGN.md.tmpl`: the plan-caching prose names an engine-level const-array plan (`[USize; MAX_UNITS+1]`); reframe to store-backed.
- `BACKLOG.md.tmpl` entries referencing the resource arena or the const-array plan; any rule / agent-doc text describing the resource arena as the resource data plane.

The arc, future steps, and ideal state are in "Arc and phasing" below and "The contract surface" above. The capacity-as-type chain (#650/#651/#652) is complete and stays valid: `Capacity` is how columns size.

## Arc and phasing

1. Establish `ColumnStorage` in `hilavitkutin-api` (trait-only) plus the decomposition trait, with `Resource` / `Column` / `Seq` / `Map` / `Field` defined as views over it.
2. Ship a naive arena-backed `ColumnStorage` impl as the placeholder.
3. Add the lint forbidding storage outside the contract.
4. Migrate the disjoint stores onto the contract incrementally, one round each: resource arena, then the plan (store-backed, live-count-sized, which is what makes `compute_execution_plan` usable at the real budget), then adapt, then dispatch buffers.

## Relationship to in-flight work

The #647 topological-dispatch slice is parked on this arc. Its DOC is committed on `feat/hilavitkutin-c2-topo-dispatch`; its source is stashed. It reworks on top of the contract once it is set: the scheduler's `topo_order` becomes a meta-`Resource` (a small scalar column), not a const-array field, and the dispatch slot array routes through the store rather than a bespoke stack buffer. The dispatch-erasure mechanism itself (`CollectFiber` / `FiberSlot` / `fiber_shim`) is unaffected; it is about dispatch, not storage.
