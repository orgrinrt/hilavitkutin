The intent: a build script belongs to its project, and where it sits is the project's choice. `hilavitkutin-build` serves whatever script calls it and says nothing about where scripts live. The rest is kept for provenance.

His two remarks of 15 November in the topic stand. The first keeps its intent whole: taking the crate is one step, and the wrapper and its config follow with nothing done by hand. The second is read beside the new answer: nothing a prototype does is written out in a consumer, so there is nothing in a consumer to drift, and whether several crates share one script file is the consumer's own arrangement, which cargo already allows.

## Changes proposed

- `mock/crates/hilavitkutin-build/DESIGN.md.tmpl`: the entry point is one line, `hilavitkutin_build::script!(<prototype>)`, in a script the consumer keeps at a path of its choosing. The section "Prototypes and the wiring a workspace takes" states `Prototype` (`Default`, `Deterministic`), that taking the crate is the workspace dependency and each crate's `[build-dependencies]` line, and that the first build's `script!` puts the wrapper and the `build.rustc-workspace-wrapper` line into the workspace's `.cargo/` by itself: each time the script runs it asks cargo for the workspace root, writes the wrapper again whenever its text differs from `write_wrapper`, leaves a `config.toml` without the line alone and names the line to add, and writes nothing into a root under `CARGO_HOME` or a root that holds `Cargo.toml.orig`. The build that writes the wiring runs without the flags and says so; the next one takes them. `RUSTC_WORKSPACE_WRAPPER` decides only what is said. The wrapper section and the config files table say the same. The rerun directive is `rerun-if-env-changed=RUSTC_WORKSPACE_WRAPPER`.
- `mock/crates/hilavitkutin-build/README.md.tmpl`: a crate takes the build-dependency and writes the one line; the first build wires the workspace.
- `mock/crates/hilavitkutin-build/BACKLOG.md.tmpl`: the "Windows wrapper" entry says the build script's call picks the wrapper text by host.

## The points to look at

A build script that writes into the source tree is what cargo's own guidance advises against, and this design does it once per workspace, outside every package directory, for two files that are then committed. The alternative is a step by hand or a tool, and the first remark of 15 November rules the step by hand out.

The crate is `no_std` by the ratified tenet `every_crate_is_no_std_with_no_allocation_and_the_consumer_provides_the_memory_provider` and writes text only, by the provisional tenet `the_build_crate_is_no_std_takes_the_profile_and_target_strings_as_parameters_and_writes_its_text_into_a_formatting_writer`. `script!` keeps to both: what to write and when is decided by functions of the crate over a `core::fmt::Write`, and the file reads and writes and the question to cargo are code the macro expands in the consumer's script, which is std by nature. No `extern crate std` and no std feature enters the crate.

The dependency lines are not automated. A build script cannot add the dependency that lets it run, and no tool is proposed for two lines.

The sketch `mock/research/sketches/202611191725_script-macro-offered-from-a-no-std-crate/FINDINGS.md` shows the cases this changelist first left owed, and this changelist was reopened once for what it found. A `no_std` crate offers the macro with no feature gate. A `config.toml` that exists without the line is left alone. A git dependency's script writes nothing into its checkout. `cargo package` failed its verify build, since the unpacked crate is not under `CARGO_HOME` and the script wrote into it; a root that holds `Cargo.toml.orig` is now declined too, and the verify build passes. The same reopening has the script ask for the root on every run, since a wired workspace would otherwise keep a wrapper whose text an update of the crate changed.

## Reopened after the first review pass

The source was written and reviewed once (`mock/research/202611191930_review-of-the-consumer-setup-round.md`), and the review found two things the design had wrong and one it had left unsaid. This changelist was reopened for them, and `DESIGN.md.tmpl` now says:

- The script asks to be rerun when either file of the wiring changes, by `cargo::rerun-if-changed` on both paths. The directive on `RUSTC_WORKSPACE_WRAPPER` alone never fired in a wired workspace, since cargo watches its own environment and the wrapper is named by its configuration, so a stale wrapper stayed. The account of why the second build runs the scripts again is corrected: the wrapper changes how cargo names the members' artifacts.
- A third root is left alone: one whose `.cargo/` does not hold the `hilavitkutin-rustc-wrapper` that `RUSTC_WORKSPACE_WRAPPER` names, which is a workspace wired from a `config.toml` above it.
- A path dependency that is a member of another workspace has that workspace written into, and the design says so. The first text of this reopening had the script tell that case from the wrapper variable once the outer workspace is wired. A test of exactly that failed: cargo names no workspace wrapper to the script of a crate outside the workspace it was run in, so the script sees what the dependency's own first build would show it. The changelist was reopened a second time for this one paragraph. The script's output in that test, with the `Wired` notice in the build that should have left the tree alone, is the evidence, and the test now holds the case as the design states it.
- A wrapper deleted, or left without its executable bit, in a wired workspace stops cargo before any script runs, and the script cannot help there.
- The entry point section says what `script!` expands to as the source has it: the prototype's directives straight to standard output, and no warning before the wiring has been looked at. Three places that said every crate calls `configure` say the crate builds through `script!`.

## Reopened after the second review pass

The second pass (same record) found three things the design did not say, and it says them now:

- In a workspace of several members the first build has one script write the config file and the others find it with no wrapper named. Their warning said to run cargo from inside the workspace, which was where cargo ran. The warning for dropped flags is worded to hold for both that build and a cargo started elsewhere, and the design says how two scripts that write at the same moment keep out of each other's way.
- A host that is not unix is written nothing, since the wrapper is a POSIX `sh` script and a config file naming it there stops every later build. The script says the flags are dropped on that host.
- A wrapper is named by its file name, in `RUSTC_WORKSPACE_WRAPPER` and in a `config.toml`, where the source matched any path ending with the same letters.

Whether a `no_std` crate may ship a macro whose expansion is std code in the consumer's script is read by both review passes as within the ratified row on `no_std` and as not decided by the provisional row on the build crate, which was written before the crate did anything about the wiring. Neither reviewer nor the author settles that, and it is with op as a question ticket.

## Reopened after the third review pass

The third and last pass found the design saying two things about `clippy-driver`, and ten public items of the wiring named nowhere in it. `DESIGN.md.tmpl` now says in the wrapper section what the section above it says, that nothing is said under `cargo clippy` and that a wrapper is known by its file name. It names the items the macro's expansion reaches the crate through and says why they are public. It also says that a script which does more than configure names its own files for cargo to watch, since `script!` writes rerun lines.

The root `README.md` section "Build tooling and hooks" described a builder call and a generated include that the crate never had. It is rewritten to what ships. A root document is outside the round's gate and is listed here because the review read it against this round.
