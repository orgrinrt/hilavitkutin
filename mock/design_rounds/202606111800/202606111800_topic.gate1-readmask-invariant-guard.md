# GATE-1 read-mask copy: guard the carrier-equals-topo invariant

The GATE-1 PR senior review flagged a silent coupling in
`plan/mod.rs::compute_execution_plan`. The runtime incremental-skip masks
(`plan.read_masks`) are keyed by carrier position, the space the dispatch walk
and the `dirty_units` propagation thread. They are filled by copying
`inputs.reads` slot-for-slot. But `inputs.reads` is keyed by registration slot
(unit-id index), and the sibling `unit_meta` population two blocks up reindexes
through `topo_s[u]` precisely because those are different spaces in general.

The copy is correct today only because GATE-1 enforces the provisional invariant
that carrier order equals registration order equals topological order
(`build` rejects anti-topological registration via `first_back_edge`, so
`topo_s[u].index() == u`). That coupling is load-bearing and currently silent.
Op call (b) in the roadmap marks the producer-before-consumer registration
constraint as provisional: when post-GATE-1 RCM auto-ordering relaxes it,
carrier position and registration slot diverge, and this copy would misalign
`read_masks` against the predecessor-mask space the propagation assumes, a
correctness bug that no current test would catch (every GATE-1 fixture registers
in topological order).

The fix is to name the invariant at the copy site and add a `debug_assert_eq!`
that the carrier position equals the registration index for every live unit, so
the RCM relaxation work trips a loud failure at this exact seam rather than
shipping a silent misalignment. The assert is debug-only (no release cost) and
covers only the live-unit range. This is the post-review fix the reviewer asked
for; it changes no behaviour, only documents and guards the existing invariant.
