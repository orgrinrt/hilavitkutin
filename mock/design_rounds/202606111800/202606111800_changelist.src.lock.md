# Source changelist: read-mask invariant guard

## CHANGE: document why the read-mask copy is registration-slot keyed
File: `mock/crates/hilavitkutin/src/plan/mod.rs`
Verification: `grep "Reindexing this copy through" mock/crates/hilavitkutin/src/plan/mod.rs` returns one match; `cargo test -p hilavitkutin` passes unchanged.

The PR reviewer flagged the `plan.read_masks` copy from `inputs.reads` as a
possible mis-keying because the sibling `unit_meta` population reindexes through
`topo_s` while this copy does not. Investigation (this round) showed the copy is
correct and the asymmetry is intentional: `unit_meta` is topo-position keyed for
the codegen / schedule tier, while `read_masks` and `predecessor_masks` (built
from the same DAG node indices in `compute_predecessor_masks`) are
registration-slot keyed, which is the carrier-position space the runtime
`dirty_units` propagation and the `RunFiber` dispatch walk thread.
`Scheduler::build` rejects anti-topological registration
(`BuildError::NonTopologicalRegistration` via `first_back_edge`), so at dispatch
registration slot == carrier position == topological order and all three runtime
arrays agree. Reindexing the copy through `topo_s` would misalign it against
`predecessor_masks` and break propagation. The fix is a clarifying comment at the
copy site recording this; no behaviour change, no `pub` surface change. (An
earlier attempt added a `debug_assert_eq!(topo_s[u].index() == u)` here; it was
removed because `compute_execution_plan` is also exercised by `build_dag`
analysis tests with anti-topological input where `topo_s` legitimately reorders,
so that equality is not an invariant of this function, only of the dispatch
path.)
