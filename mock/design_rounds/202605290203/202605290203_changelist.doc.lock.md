# Doc changelist

## No design-document edits

This round hardens an existing projection; it adds no new design concept. The
engine ids (`UnitId`, `FiberId`, `PhaseId`, `TrunkId`) already exist and are
documented as `repr(transparent)` newtypes over `Uint<N>`. The new `index` and
`from_index` accessors are method surface, not new types. The
`hilavitkutin-api` `DESIGN.md.tmpl` does not enumerate per-id method surfaces,
and the `design-doc-source-mismatch` lint checks backticked type names only, so
no template edit is required for the lint to pass or for the design to stay
honest.

The accessor pair replaces the `transmute_copy` projection. The design intent
(typed id to raw index travels through arvo's strategy-aware `to_raw` /
`from_raw`, not through a layout-coupled transmute) is recorded in the topic
file and carried into the src changelist as structured CHANGE claims.

## API confirmation

Confirmed against arvo source before locking, so the src phase builds against a
known surface:

- `UFixed::to_raw(self) -> <S as BitsContainerFor<..>>::T` is `pub const fn`
  (`arvo/src/ufixed.rs`). It is the defined container projection that replaces
  `transmute_copy` in the read direction.
- `UFixed::from_raw(bits) -> Self` is `pub const fn` (same file). It is the
  write-direction projection.
- `arvo::USize` is `USize(pub usize)`; arvo's own `UFixed::logical_width`
  constructs `USize(<value> as usize)`, the idiom `index` reuses.

The one detail the src build verifies is whether `from_raw(i.0 as _)` infers the
strategy-projected container type at the call site; if inference does not reach
through the associated-type projection, the src phase names the container type
explicitly. Either shape keeps the accessor `const fn`.
