# Doc changelist: D1d builder-append + topo-registration validation

Round `202606061446` (topic: gate1-dispatch-builder-append). Updates the design docs that describe the builder as prepending the WorkUnit carrier, to reflect the append flip (registration order == carrier type order) and the new build-time topological-registration precondition. The provisional nature of the producer-before-consumer requirement (op decision (b)) is noted with a pointer to the proven auto-RCM relaxation path.

## File: `mock/crates/hilavitkutin-api/DESIGN.md.tmpl`

- Line ~342: change "`UnitDispatch<Self>`, prepending the WU type onto the `Wus`" to describe APPEND: the WU type is appended onto the `Wus` accumulator so the carrier type order equals registration order. Add a sentence: the producer-before-consumer registration order this implies is a provisional constraint (the engine validates it at build time and can auto-apply the cache-optimal order in a later step).

## File: `mock/crates/hilavitkutin/DESIGN.md.tmpl`

- Line ~627-629: the passage stating WorkUnit values are retained on a carrier the run walk consumes and "the WorkUnit placement kind prepends each registered" WU. Change to APPEND: the placement kind appends each registered WorkUnit, so the carrier type order is the registration order, and `build()` requires that order be a valid topological order of the dependency DAG (returning a `BuildError` naming the recommended order otherwise). Store and platform carriers are unaffected (they keep prepending; their layout is plan-driven, not dispatch-order-bearing).
- Line ~730: "`Dispatch = UnitDispatch<Self>`, which prepends `Self` onto the" -> appends `Self` onto the `Wus` accumulator. Keep the store/kit/platform prepend wording (lines ~733, ~736) unchanged: only the WorkUnit kind changes to append.
