# GATE-1 dispatch, step D1d: builder appends, build validates registration is topologically valid

This is the first source increment of the GATE-1 dispatch keystone (#669 / #340 / #661). It does not yet rewrite the run walk (that is D1e); it makes the WorkUnit carrier's TYPE order equal the registration order and adds the build-time precondition that the registration sequence is a valid topological order of the derived dependency DAG. The why traces to the dispatch pivot: devirtualised dispatch (the proven type-level cons-list walk, sketch 202606081200) follows the carrier's type order, so for dispatch to run in a valid order the carrier type order must itself be valid. The engine cannot reorder a heterogeneous cons-list type at runtime, and type-level grouping derivation hits an E0119 coherence wall (proven thrice). The resolution the canonical design and the pivot converge on: the consumer lists WorkUnits producer-before-consumer, the builder preserves that order in the carrier type, and `build()` rejects an invalid order with a `BuildError` that names the engine-computed recommended (RCM-row) order.

## Current state

The scheduler builder PREPENDS each registered WorkUnit onto the carrier. The type accumulator router `UnitDispatch<W>::NextWus = Cons<W, Wus>` (`hilavitkutin-api/src/builder_input.rs:116`) and the value carrier `impl Place<P> for WorkUnitKind { type NextWus<W> = WuCons<P, W>; fn place(..) }` (`hilavitkutin-api/src/store_values.rs:182-196`) both cons the newly-registered WU onto the front. So the `WuVals` carrier ends up in REVERSE registration order. `Scheduler::run` compensates with the runtime `topo_order` field (computed by `derive_phase_dispatch_order` in `build()`) consumed through the `CollectFiber`/`FiberSlot` indexing path. `build()` runs Kahn cycle-detection on the dependency graph but does NOT check that the registration SEQUENCE is itself a valid topological order; it then discards the `DependencyGraph`.

The design docs describe the prepend: `hilavitkutin/DESIGN.md.tmpl:629` ("the WorkUnit placement kind prepends each registered"), `:730` ("`UnitDispatch<Self>`, which prepends `Self` onto the"), and `hilavitkutin-api/DESIGN.md.tmpl:342` ("`UnitDispatch<Self>`, prepending the WU type onto the `Wus`").

## Changes proposed

Three coupled changes (D1d-a/b/c), one design topic:

1. **D1d-a: builder appends.** Flip both router sites from prepend to append so registration order equals the carrier TYPE order. Add a recursive `WuAppend<P>` trait on the `WuCons`/`WuNil` value carrier (`WuNil.append(p) = WuCons{p, WuNil}`; `WuCons{h, t}.append(p) = WuCons{h, t.append(p)}`, type and value in lockstep). `UnitDispatch<W>::NextWus` becomes the append output; `WorkUnitKind::place` appends rather than prepends. The store and platform routers keep prepending (store binding order is not the dispatch carrier; its layout is driven by the plan, not registration order). The crate stays compiling: `CollectFiber` still indexes by position and the plan's `topo_order` field still remaps, so the run path stays correct through this step; `CollectFiber` is deleted in the later D1e step, not here.

2. **D1d-b: build-time topological-registration validation.** Thread the `DependencyGraph` (currently discarded after planning) to a precondition check in `build()`: the registration sequence must be a valid topological order of the dependency DAG (every WorkUnit registered after all WorkUnits whose writes it reads). Return a `BuildError` variant when it is not. This is a typestate precondition, not a delegation of grouping: the engine still computes phases, trunks, fibers, and morsel sizes; the consumer is only required to list WorkUnits in a valid order, a natural constraint.

3. **D1d-c: recommended-order in the error.** The `BuildError` from D1d-b names the engine-computed recommended order (the RCM-row order from `plan.rcm_order` where available, else a plain topological order), so a consumer hitting the error is told the exact permutation to register in.

The producer-before-consumer registration requirement is a PROVISIONAL compromise (roadmap r2 §8 op decision (b)): it is to be relaxed once the engine auto-applies the cache-optimal order itself. Sketch 202606090300 (§7-6) proved a devirt-free auto-RCM mechanism (a const-position-guarded type-level walk: each WU carries a const RCM position, the walk executes per output slot, zero blr, reorders a scrambled registration to RCM order), so the relaxation has a proven path and is not gated on toolchain maturity. The docs and the `BuildError` note the constraint as provisional and point at the auto-RCM follow-on; they do not present it as permanent.
