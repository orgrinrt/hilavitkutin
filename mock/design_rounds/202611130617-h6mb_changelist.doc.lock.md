## Current state

The api's design names three store types (`Resource`, `Column`, `Virtual`), while the source has `Accum` beside them, which the api's design never mentions and the engine's design describes. The scheduler is built with one record count (`build(storage, record_count)`) and every column has that many records, though `ColumnStorage` already keeps a count per column.

A unit is a `WorkUnit`. It iterates through `each`, `batch` or `reduce` with a closure over a position, and reads and writes columns through `unsafe fn read` and `unsafe fn write` at that position. `RecordOp` exists beside it as an opt-in map of one value to one value, used only by the fused fold. The founding record has `each` take a function from values to values (the api surface topic, `:1840-1843`), which the shipped `each` does not.

A unit reads the record it is at and no other. The engine design has units ranked by lifecycle (plan-stage, consumer, epilogue) through `OnMeta<V>`, and plan step 1 builds a read-after-write edge from any writer to any reader of a store whatever their ranks, so a store written on the epilogue band and read by a consumer unit gets an edge against its rank.

Two writers of one store are ordered by registration position alone in the engine design (`:43-44`) and in the code, where the spec has hint priority first.

The type-level list is declared in the api (`Cons`, `Empty`, `Contains`, `ContainsAll`, `Concat`), a second copy of what `notko-hlist` now holds.

Formats are generic: any `Copy + 'static` type is a `ColumnValue`. Registration is typed, through `.with`. Neither changes.

## Changes proposed

The first eight follow the eight things the coordinator asked to have restated on the record, in its numbering. The remaining ones carry over from the first writing.

### 1. Reading a store as it stood when the pass began, and what the counters are for

What the record designs. The designs on the trunk have two access modes and no column held in two sides. The core design topic, `:643-661`:

> Resolved by Q2: two modes only. Read and Write. Write implies Read.
>
> loimu's seven access modes (Pinned, Immediate, MutImmediate, Sample, Post, Approx, Defer) control ordering, freshness, and determinism within the double-buffered view system. [...] loimu maps its seven modes to Read/Write at the hilavitkutin boundary and implements the richer semantics in its own layer.
>
> If hilavitkutin later needs a third mode (e.g. ReadExclusive for consumers that need guaranteed exclusive read access), it can be added without changing the WorkUnit trait — it would be a new store wrapper type like `Exclusive<Resource<T>>` in the AccessSet.

The counters are for one thing, knowing whether something changed so that unchanged work is skipped. The spec, `:2406-2408` (R2): "hilavitkutin owns per-morsel generation counters and skip-unchanged DAG propagation logic (runtime scheduling concern)". No passage has a counter select or hold an earlier value of a store.

The record has one value that is a pass behind, and it says how. The core design topic, `:595-598`: "The scheduler writes `Resource<SchedulerMetrics>` at the START of each pass, containing the PREVIOUS pass's metrics. This is always one-pass-behind data, which is consistent and non-paradoxical". And `:639-641`: "The write happens at pass start → it's the first thing in the DAG. All readers naturally come after. The version stamp increments every pass (pass_count always changes), so readers always dispatch." This is the passage his answer below points at, the counters and increments "designed exactly for something like this". What it designs: the value is written once, on the band before the ordinary units, by the plumbing; every reader of the pass sees that one value; and the stamp's increment is how the readers know to run. The stamp marks the change. It does not pick between two held values, and nothing in the passage holds two.

The record also has the bands. The engine design's meta pipeline section (`:840-843`) ranks every unit by its schedule: "plan-stage work units land in the early phase(s), consumers in the middle, and epilogue (`ScheduleEnd`) work units in the final phase(s)". A store whose every writer is on the leading bands holds one value for every consumer unit of a pass, as the scheduler metrics do, and a store whose every writer is on the epilogue band holds for them what it held when the pass began.

The record has a consumer's unit write columns at the close. The core design topic, `:730-731`: "`meta::ScheduleEnd` — fired after all consumer work completes. Gates epilogue work: error inspection, rollback, cleanup." And `:763-779`, its example of one: `impl WorkUnit<On<meta::ScheduleEnd>> for RollbackOnError` with `type Write = (/* columns to restore */);`, under "No rollback hardcoded in the scheduler. Consumers who need rollback (loimu with WASM plugins) build it from work units". So a unit a consumer writes, scheduled on the close, writing columns after every consumer unit has run, is the record's own. The second review of this writing found these passages, which this seat had not cited.

And the record has the counters carry such a write to the next pass. The spec, `:862`: "Per-morsel generation counter — bump on write, skip if unchanged". And `:1420-1424`: "At runtime (not plan-time), before each pass: check generation counters on root WU inputs. If unchanged since last pass, set dirty bit to 0."

Two further passages bear on who holds a buffer, each said of signals and not of columns. The core design topic, `:386-389`, of virtuals fired from outside: "No signal bus, no arena, no double buffering. Just bits." And `:550-553`: "loimu builds its signal bus on top: virtuals for scheduling edges + loimu-owned arena columns for signal data + buffer modes (Replace/Queue/ReplaceBy) as loimu-layer logic. hilavitkutin provides the bit; loimu provides the arena." For signals, then, the engine keeps the bit and the consumer's layer keeps the buffered data in columns it owns. The record does not say the same sentence of a column's values across a pass.

The record has a frozen and a live split of its own, for resources. The spec, `:1714-1723`, "Stack-local resource caching": "Before the morsel loop, the fiber dispatcher: 1. Snapshots all accessed resources to a stack-local array 2. Redirects res_ptr to the stack-local copy [...] After the loop, mutable resources are written back to canonical storage via `stp`." A unit's loop reads a copy taken before it, and the canonical value is elsewhere. The storage addendum on the trunk keeps that for a scalar and stops it for a collection (`mock/research/202606210600_resource-storage-model-canonical-addendum.md:16-45`: a `Seq` or a `Map` is "live-streamed, not copied", since a live read beats a snapshot copy by about 2.5 times once the collection is past the cache).

Every branch of the repository was searched by concept (frozen, live, committed, snapshot, generation, swap, flip, double buffer): `origin/dev`, `origin/recover/unlanded-rounds-and-benches`, `origin/work/recover-landing-swap`, `origin/work/loop-core`, `origin/work/bench-wide` and `origin/work/bench-convergence`. A later round sketches a double buffer and has a meta unit rotate it. `mock/design_rounds/202605101036/202605101036_topic.plan-algorithm-chain.md:1181-1208`, "Double-buffer pattern for AdaptWu snapshot publish": a resource value holds `buffer_a`, `buffer_b` and `current`; the adapt unit, at `ScheduleEnd`, fills the buffer that is not current and then stores the index ("single atomic publish"); a consumer unit loads the index and reads the buffer it names. The frozen and live split of columns is in the founding research, as loimu's storage, with its mechanism. `mock/design_rounds/202604200055/202603141800_research.loimu-storage.md:191-197`: "Non-temporal fields get 2 SlabColumns (frozen + live). [...] Record data is double-buffered per-column within views. Each column's SnapshotBuffer performs a dirty-region copy from live to frozen at pass boundary. Idle passes with no writes pay zero memcpy." The buffer is one type in two modes, `:244-251`: `struct Exchange;  // pointer swap + reset (ephemeral data)`, `struct Snapshot;  // memcpy live -> frozen copy (persistent data)`, `struct SwapBuffer<T, Mode = Exchange> { a: T, b: T }`. Who reads which side, `:826-828`: "Record data in views is double-buffered (frozen + live) by default. Behaviors reading `nodes M` get the frozen snapshot (parallel); behaviors writing `nodes M` get the live buffer (exclusive)." And why the swap needs no lock, `:337-338`: "The pass boundary is a synchronization point (DAG guarantees no concurrent writes), so no atomics are needed on the dirty index." The same note has the other path, writes deferred into a queue and fused before they are applied (`:502-634`), which rests on the same split (`:508-510`): "Because frozen data is immutable during a pass, there are no dependencies between readers of the same column."

The evidence memo is on the trunk too (`mock/research/202607201100_swap-semantics-ratification-evidence.md:30-58`): the install at 2 ns for 64 bytes, 85 ns for 1 KiB and 1.81 us for 64 KiB on one M1 run, and the frame after it at the cost of the store's dirty cone. The spec's S3 says of columns: "columns are sized at plan time and never resized". Neither the trunk nor that branch holds a design, sketch or bench of a column held in two or three buffers.

What mechanism the swap benches exercise, read from their arms on `origin/work/recover-landing-swap` (`mock/benches/variants/swap_common/src/lib.rs`, with `sb_none`, `sb_plan` and `sb_value`, and `bench.toml:846-887`). The units' context carries a snapshot list of the resources they read (`SnapCons<SwapVal, SnapNil>`), the swap installs the new value into the canonical blob between two frames, outside the timed region, and the timed frame after it pays for the cone the dirty mark seeds. So the frozen side there is the snapshot a context reads and the live side the canonical blob, the swap is one install between frames, and the readers learn of it through the dirty mark. Three properties of that are taken over for columns below: the swap is between frames with the workers parked (S1, "legal only between frames"), it "never changes the base pointer" (S3), and it marks the store dirty so that the next frame's readers run (S1). The benches measure a resource value's swap. They do not measure a column's.

One expert memo on the trunk says "Hilavitkutin's columns are double-buffered (frozen/live) for the pass boundary" (`mock/research/202606210600_expert-loimu-heritage-storage-model.md:289`). It cites nothing for it, and neither the spec nor either design has such a passage. What it describes is loimu's view storage as the founding research has it, said of hilavitkutin.

Two readings of who holds the buffer, both quoted. The core design topic (`:643-661`, quoted at the top of this section) leaves loimu's richer modes, which live "within the double-buffered view system", to loimu: "loimu maps its seven modes to Read/Write at the hilavitkutin boundary and implements the richer semantics in its own layer." Hilavitkutin is primarily the replacement for it" takes away the layer the first reading left the buffer to. And his answer of 13:35 says to build on the double buffering where the record has it. What changes. The api design gains a fifth store marker, `Buffered<T, M = Snapshot>`, a column held in two sides. Every read of it, by a unit of any rank, sees the frozen side, which is the store as the last boundary left it. Every write of it lands on the live side. So a reader and a writer of a buffered column have no sequence between them and may run at once, one unit may be both, and what a unit writes in one pass every unit reads in the next. Two writers are ordered as the writers of any store are (3), and the later one's values are what the boundary brings in. There is no read of the live side.

The mode is a type parameter of the marker, sealed to two, with the research's names. Under `Snapshot` the boundary copies the live side into the frozen one. Under `Exchange` the two sides trade places and nothing is copied. `Snapshot` is right under any writer. `Exchange` is right only where every writer writes every record, since the side a pass writes into holds the values of two passes before; a value function is applied at every record of the unit's range, which makes it so, and a buffered column is reached through the value function alone. The default is `Snapshot` for that reason, where loimu's buffer defaulted to `Exchange` for its ephemeral data. Which mode costs less at which size is a bench nobody has run: ticket `bench_a_close_unit_s_copy_of_a_column_against_an_exchange_of` (ecb940c91d26), bumped and now about the two modes.

The boundary is the engine's. It runs after the last unit of the close, with the workers parked, as plumbing, the way the accumulator reset at frame start is plumbing. A buffered column the pass did not change is not touched, which is the research's "Idle passes with no writes pay zero memcpy" at the grain of a store. A column it did change is swapped and marked dirty for its readers in the next pass. Neither reservation's base ever moves: `Exchange` flips an index that the dispatch reads when it binds the next frame's contexts.

A marker and not a wrapper, for the reasons 6 gives for the accumulator. The storage follows from what is registered (two reservations for a `Buffered<T, M>`, one for a `Column<T>`), where under a wrapper a store's shape would depend on whether some unit somewhere lists it wrapped. And a `Column<T>`, a `Buffered<T, M>` and an `Accum<T>` of one value type stay three stores.

The section "Reading a store as it stood when the pass began" of the api design is rewritten around it, with the field step as its example: a unit that reads `Reach<Buffered<Heat, Exchange>, 1>` and writes `Buffered<Heat, Exchange>`, which is kaski's `a_field_over_space_steps_whole` in hilavitkutin's terms. The other way to keep a change out of sight until the pass is over stays in the section as it was: ordinary units append to an accumulator and a close unit applies the appends in place to a plain column. That is the queue of his 13:20 answer and the research's deferred writes, without the fusion. Between passes `replace_value` stands as it is designed, and its install is owed to the trunk by the landing of the unlanded branch. A single value is not held in two sides inside a pass.

The split between hilavitkutin and kaski that this proposes, with its reasons. His 13:20 answer leaves it open ("All depends what part of that is in hila and what is a kaski impl of hila or work on top of its work unkts"). Hilavitkutin holds the pair of sides, the frozen read and the live write, the rule that such a store takes no read-after-write edge, the swap at the boundary with its dirty mark, the queue store with its reader for a close unit, and `replace_value`. Four reasons. Only the scheduler holds a column's memory and its base pointers, so only it can keep two reservations under one store and flip between them without a pointer moving under a context. The swap has to seed the next pass's dirty set, which is the engine's. That nothing reads or writes while the swap runs is the engine's parked-workers point and cannot be promised by a unit. And the plan has to know that a reader and a writer of such a store are not ordered, which no consumer wrapper over two plain columns can tell it; with two plain columns and a carrying unit the consumer pays a whole copy every pass and an edge it does not need. kaski holds what a mutation is, the units that drain its queues, the journal and the conservation check, which of its stores are buffered and in which mode, and the rule that its ordinary units never write committed state in place. Those are meanings and policy, and the record keeps a consumer's schema out of the engine (R1, quoted under 2).

What is the record's and what is put together here, said plainly. The record's: two modes and a new need entering as a store type in the access set; a resource read through a snapshot beside its canonical value; a swap between frames that moves no base pointer and marks the store dirty; counters bumped on write. The founding research's, as a reading of loimu with a recommendation to adopt it: the frozen and live column pair, its two modes, the copy only where dirty, the readers on the frozen side with no dependencies between them. What this seat puts together: that pair as a store marker of the api, the mode as a sealed type parameter, the no-edge rule in plan step 1, the boundary as engine plumbing after the close, and `Snapshot` as the default. The sketch `mock/research/sketches/202611131330_buffered-sides-and-write-members/` shows the pair generic over the mode, with both modes giving one result under a total write, the regions never moving, and a partial write going stale under `Exchange` alone. No bench stands under any of it.

The earlier writings of this section said a store whose every writer is a maintenance unit holds one value for every ordinary unit of a pass, and offered that as the frame-start read. It was question ticket `does_a_store_only_a_close_unit_writes_hold_its_pass_start_va` (2143d534c715) after two reviewers disagreed on it, and his answer to it is the one at the top of this changelist: not accepted. The sentence is still true of such a registration and the api design keeps it as a remark, since the scheduler metrics work that way. It is no longer what the frame-start read rests on.

Not in this revision: a positional read or write of a buffered column, which under `Exchange` would let a unit leave records stale (ticket `positional_read_and_write_of_a_buffered_store_in_hilavitkuti`, 24fa3df63a9d); a copy of only the morsels that changed under `Snapshot`, which waits on marks per morsel (8e2e2326d588); and two buffers in one resource value flipped by a close unit, which needs a write of a consumer resource inside a pass that the designs rule out.

Three engine rules make it hold. The first is the one above: plan step 1 builds no read-after-write edge on a buffered column, and the engine design says so in step 1. The second, the engine design, `:41-43`:

> RAW edges are order-independent: for any unit pair where one writes a store the other reads, the writer sorts before the reader, regardless of which was registered first.

becomes: order-independent between units of one lifecycle rank, and two units of different rank that share a store take the order of their ranks, an edge that agrees with the ranks built as any other and one that would run against them not built. Without this, step 1 orders a close-band writer before a consumer reader of the same store, against the bands. A writer on the leading bands needs no rule: its edge to a consumer reader agrees with the ranks, which is the record's "first thing in the DAG".

The third. The engine design, `:106-110`, lists the seeds of the dirty set (a replaced resource, a replaced value, "an input the consumer marked changed", the cold first frame). ### The close and maintenance units

This is not one of the eight. It is asked for by a word of his from the kaski canon walk, relayed by the coordinator: "mutations are NOT writes, in this sense. Write here refers to in-place writes that are discouraged or forbidden at the contract level and forces in-engine / sim changes to go through mutations. The intent, in my words: an ordinary unit does not write in place, its changes go through mutations, and the units that write in place are maintenance units, which do the setup and the close of a frame.

What the record gives maintenance units. The spec, `:2119-2137`, has the scheduler schedule itself through meta units on the meta virtuals `PlanStage`, `ScheduleReady`, `PassStart` and `ScheduleEnd`. The engine design's meta pipeline section has them in the same carrier as consumer units, ranked by schedule type at const evaluation, scheduled with `OnMeta<V>` where a consumer writes `On<V>`, with a `meta` accessor that exists only on the context of a meta unit ("enforced at compile time by the gating, not by a separate bound"), and with the meta bands run once per frame on one core over the whole range.

The record gives them one piece of work of its own: the scheduler's metrics, written at the start of each pass with the figures of the pass before (the core design topic, `:595-598`, quoted under 1). The engine design has that written by the engine directly into a block it owns and read by `OnMeta` units through a bridge (`:876-882`).

A later round gives them more, which is what his answer on rotation (under 1) expected to exist, and it is not the record. Its adapt unit is a meta unit on `ScheduleEnd` that reads the pass's metrics and refreshes the consumer-readable metrics resources (`202605101036_topic.adapt-subsystem.md:26`); it is in source as `impl WorkUnit<On<ScheduleEnd>> for AdaptWu` with nine resources in both its lists (`mock/crates/hilavitkutin-providers/src/adapt_wu.rs:64-100`), its body empty, and with no accessor that could write them. Its resource-resolution topic has a plan-stage unit load a pass's data into a column (`202605101036_topic.resource-resolution.md:50`) and a unit at the end of the pass drain the accumulators (`:51`). So earlier work expected maintenance units to set a pass up by writing columns and to close it by reading what the pass appended.

What neither gives them is a contract of their own for either: every unit has the same `unsafe fn write`, and no accessor reads an accumulator.

What changes. The api design gains "Maintenance units and the close". A unit scheduled `OnMeta<V>` is a maintenance unit; one on a plan-stage virtual or `PassStart` sets a pass up, one on `ScheduleEnd` is the close. Its context is bound to the whole record range and no ordinary unit runs beside it, which makes it the place for a write at a record named from data, and an ordinary unit that means a change for another record appends it for a close unit to apply. It reads the appends through `AccumReaderApi`, an accessor a runner implements on the context of a maintenance unit alone, the way the `meta` accessor is gated, so no bound of `WorkUnit::Ctx` changes. The design says in so many words that the contract does not hold an ordinary unit to this, and that the sequence a close unit meets appended values in depends on the worker count after a parallel run.

How far his word reaches. It was said in the walk of kaski's canon, about kaski's mutations, and the coordinator relayed it as bearing on the api. The api gets from it the mechanism (the rank, the reader of appends, the write by position on a context that holds the whole range). The rule itself, that a simulation's changes go through mutations and only maintenance units write in place, is the consumer's to hold, and the core design topic has the same division for loimu's richer modes (`:653-655`). The first review asked for exactly this split.

`OnMeta<V>` is added to the api design's list of schedule conditions (just above `:366`), which named `Always` and `On<V>` only.

What is not done. `write` is not taken away from an ordinary unit. Every positional unit in the suites calls it, and the brief's item 9 asks that the existing parts keep working. It stays `unsafe` for everyone, and the design says a consumer that forbids in-place writes outside its maintenance units keeps its ordinary units in crates that forbid `unsafe`. The stricter contract, `write` existing only on a maintenance context by the same gating, would match his word more closely and would break every positional unit.

The second review found the contract short of his word at this point: he says "Special contracts exist f or work units that are maintenance (can write in place", and the revision gives a maintenance context the reader of appends and no write an ordinary unit lacks. The three forms that could close it were question ticket `which_write_in_place_a_maintenance_unit_has_that_an_ordinary` (7f93b9f3e621) [a: a safe checked write on a maintenance context, beside the unsafe one (recommended) | b: none, write stays unsafe everywhere | c: write only on a maintenance context]. His answer of 13:20: "This is for the kaski impl and use of hilavitkutin. Don't thin natively need that. Unless we do an abstraction and contract for the mutation behaviour of kaski, then I suppose we'll need the closers. The intent, in the coordinator's words and mine: hilavitkutin does not natively need a write of its own for maintenance units; a unit is a special case by its data being written in place, and not by a contract on the unit; the intended case under the mutation paradigm is writing through queues, which is either a second write buffer or queued operations drained at the close; and which part is hilavitkutin's and which kaski's is open. ## How each form holds the pillars

His words of 13 November bound every change to hilavitkutin: it may be "added and extended and changed" while it does not compromise "full, exhaustive typestate, contracts first, all machinery and logic runs on contracts alone, people impl its parts and the engine runs it via the contracts", with "optimisations first and foremost, always", started simpler and deepened later, and nothing "a drop looser in typestate or strictness with no std, no alloc, unless behind a feature that is entirely opt in".

The value function. In the types: each read bounded on the read list, the return total over the write list. Contract: `EachApi::map`, `Readable`, `Writable`, and `RecordOp` under `WorkUnit`. Optimisation: the function is pure over values, so the engine is free in the sequence of records, the thread and in composing units; in this revision it runs one gather, call and scatter per record and fuses only one-column maps.

Members and wrappers. In the types: a wrapper is a type in the list, `Reach` only readable and `Written` and `Differs` only writable, the reach a const parameter, an offset past it a compile error, and the positional `write` resolved through the member, so the rule a unit declared is the one its write runs, monomorphised. Contract: `Member`, with `AccessSet` over members, and `WritesColumn` with the context's bridge under `WriteAt`. Optimisation: the plan knows a cross-record read and a change rule at build, which is what a boundary, a halo and a skip need.

The buffered column. In the types: the marker picks the storage at registration, the mode is a sealed type parameter and the boundary's branch on it a constant, a read and a write are bounded on the unit's own lists as for any store, and the positional accessors do not resolve for it. Not in the types: that every writer of an `Exchange` column writes every record holds by the value function being the only way in, and no bound states it. Contract: `StoreDispatch` for the marker, `Readable` and `Writable` over it, `BufferMode`. Optimisation: readers and the writer of one store run at once with no edge between them, a field steps with no copy under `Exchange`, and a store nobody changed costs nothing at the boundary; the copy under `Snapshot` is whole for now.

Record counts. Nothing changes, so nothing is loosened: one count, one contiguous range per fiber.

The accumulator. In the types: the marker picks the storage at registration and each accessor is bounded on its own marker, so a wrong access fails at the call. Contract: `StoreDispatch<Accum<T>>` and the accessor bounds, as in source. Optimisation: none gained or lost.

The shared list. As in the first writing: the same sealed list and marker membership, `Holds` and `HoldsAll` over it.
