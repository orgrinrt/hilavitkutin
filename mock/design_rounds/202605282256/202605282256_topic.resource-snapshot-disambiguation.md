# Topic — disambiguate ResourceSnapshot semantics (HILA-RUNTIME-B2, #335)

**Date:** 2026-05-28
**Phase:** TOPIC
**Scope:** delete the placeholder `ResourceSnapshot<const N>` + `Slot` + `ResourceCache`; reconcile the stale DESIGN signature for the typed phase-bounded view; route the dispatch-time stack-caching idea to its real home (dispatch codegen).
**Source topics:** round 202605101036 topic 8 (resource-resolution, axis A); the engine-dispatch build plan `mock/research/202605282100_engine-dispatch-build-plan.md` (Phase A).

This is the first round of the engine-dispatch arc. The arc makes `Scheduler::run` real end to end. The build spine is dependency-ordered: the data plane (Phase B) is the keystone everything reads and writes, and it cannot be built cleanly while two unrelated things share the name `ResourceSnapshot`. This round removes that contradiction so the data plane has one clear meaning to build against.

The name `ResourceSnapshot` currently denotes two unrelated ideas. The engine crate ships a placeholder `ResourceSnapshot<const N>`: a fixed-size stack array of `Slot` (a `UFixed<64,0>` payload) with a sibling `ResourceCache<'a, R, N>` wrapper and a round-trip test. Its module doc describes a dispatch-time optimization (cache accessed resources to a stack-local array before a morsel loop so LLVM proves the stack does not alias the column buffers, then run the loop with the resources in registers). The locked design (round 202605101036 topic 8 axis A) describes something else entirely under the same name: `ResourceSnapshot<'phase, R>`, a read-only typed view captured at a phase barrier, lifetime-invariant and phase-bounded, observed by `AdaptWu` at `ScheduleEnd` to derive next-frame predictions. One name, two concepts, neither matching the other.

The placeholder is dead scaffolding. Grep finds no engine call site: only its own definition, the `ResourceCache` wrapper (also unused), the re-exports in `resource/mod.rs`, and one round-trip test. It is not on any dispatch path. Under the pre-1.0 no-legacy-shims rule it is deleted outright, not deprecated.

The locked design's typed view is the surviving meaning of `ResourceSnapshot`, but its DESIGN signature is stale. `hilavitkutin-api/DESIGN.md.tmpl` documents `ResourceSnapshot<'phase, R: BuilderInput<Dispatch = ResourceDispatch>>` with an `inner: Pin<&'phase R::Owned>` field. Neither `ResourceDispatch` nor `BuilderInput::Owned` exists: the round 202605101036 topic 2 builder reshape replaced per-kind dispatch routers with `StoreDispatch` / `UnitDispatch` / `KitDispatch` / `PlatformDispatch` / `RunCfgDispatch`, and `BuilderInput` carries only `Init` and `Dispatch` associated types. The signature predates the reshape. Its concrete form must be re-derived against the real `BuilderInput` contract, and that re-derivation depends on how a registered store exposes its scheduler-owned storage, which is the Phase B data-plane design. So the typed view ships with the data plane (HILA-RUNTIME-C6), not in this round. This round corrects the DESIGN so it stops presenting a stale signature as a shipping contract.
