# GATE-2 E4: run_parallel meta-pipeline parity

**Date:** 2026-06-11
**Phase:** TOPIC
**Scope:** `mock/crates/hilavitkutin/src/scheduler/mod.rs` (worker mainloop, unit-outer worker, run_parallel first-call setup), new parallel meta tests
**Source topics:** findings `mock/research/202606082300_run-parallel-meta-parity-findings.md`; rounds 202606082100 (slice-2 single-core lifecycle), 202606090400 archive (slice-3 bridge); canonical Q9 `:2119-2137`, parallel core `:716-814`

## Problem

The meta pipeline (lifecycle bands, plan-band skip, the slice-3 engine-to-meta
bridge) is complete and tested on the single-core `run` path. `run_parallel`
predates none of it mechanically (the bridge threading already reached both
worker paths) but two behaviours are missing, one per path.

Truth-of-impl as of HEAD `cba715a`, sharper than the 202606082300 findings
(which predate the bridge):

1. **Phase-loop path** (`worker_main` loop over `0..gate2_nphases`,
   `run_core_phase` per phase, `waist_barrier` between): `&self.meta_block` is
   threaded into all three dispatch arms (`run_gated` and both `dispatch_core`
   arms), so `OnMeta` work units already receive `MetaRef` here. Lifecycle band
   ordering is already given: the grouping arrays come from the same rank-outer
   renumber, so meta bands are phases, and the worker-side waist barrier orders
   them across cores. `run_core_phase` dispatches with all-ones dirty (pure-RAW,
   no incremental skip), so the 202606082300 testing confound does NOT apply to
   this path. **Missing: the plan-band skip on clean frames.** The worker phase
   loop always starts at `p = 0`, so plan-band work units re-run every frame
   where single-core `dispatch_trunks` skips `0..plan_phase_count` on a clean
   frame.

2. **Unit-outer path** (`worker_accum_unit_outer`, accumulator-bearing
   carriers): each participating core rebases the accumulators to its record
   slice and dispatches the WHOLE carrier once over `[lo, hi)`. With records
   present, a meta work unit registered in such a carrier runs once per
   participating core (N times per frame, not once), and there is no cross-core
   band ordering (core 1's consumer work can run before core 0 walks a
   pass-start meta unit). The record-less arm (core 0 only) is correct by
   accident of the participation guard. **Missing: once-per-frame meta-band
   execution, ordered around the per-core consumer slice work.**

Already correct for parallel (no work needed): `pass_count` and
`virtual_epoch` advance once per frame in `run_parallel` before
`frame_publish`, while every worker is parked; workers read them under the
publish/await happens-before. The `MetaBlock` `Cell` is sound under the same
discipline: the main thread writes it only between frames, workers only read
it during a frame.

## Proposed mechanism

### Phase-loop path: worker plan-band skip (a `dispatch_trunks` mirror)

At the first `run_parallel` (grouping setup, workers not yet spawned), also
compute the leading plan-band phase count into a new `gate2_plan_phases`
field (the grouping side already exposes `plan_phase_count`). Workers read
`s.first_frame` as the frame's plan-dirty signal (single-core slice-2 takes
`plan_dirty = first_frame`; `run_parallel` clears `first_frame` after
`frame_await_done`, between frames, so the value is stable per frame under the
same happens-before as `virtual_epoch`). The worker phase loop starts at
`gate2_plan_phases` instead of `0` on a clean frame. Interior waist count
shrinks accordingly (the barrier only fires between phases the loop visits, so
no expected-count change: every worker runs the same loop bounds).

### Unit-outer path: designated-core meta bands around the slice work

Band-split the unit-outer frame on the existing primitives, no new type-level
machinery:

1. **Core 0 runs the leading meta bands** (plan band, skipped on clean frames,
   then the remaining pre-consumer bands) via the same `dispatch_core`
   empty-morsel walk `run_core_phase` uses on record-less frames, one call per
   meta phase `p in start..consumer_band_start`. Other cores wait at a
   `waist_barrier`.
2. **All cores run the consumer band over their record slices**: the existing
   rebase + whole-carrier walk, except gated to the consumer band so meta
   units do not ride the per-core slice walk. Gating reuses the phase-mask
   walk (`run_gated` with the consumer-band unit mask over the rebased
   bindings, the slice as a single morsel range), which is behaviourally the
   current `run` call plus a mask.
3. **Barrier, then core 0 runs the trailing band** (schedule-end) the same
   way as step 1. The barrier's release/acquire publishes the consumer work to
   the designated core's epilogue band, and the frame-done barrier publishes
   the epilogue to the main thread.

A carrier with no meta units degenerates to the current behaviour (zero
leading/trailing meta phases, no extra barriers wanted: the steps are
conditional on the band counts, so the all-consumer fast path stays
byte-identical).

This requires `worker_accum_unit_outer` (or its caller) to gain the
`RunTrunkDispatch` + `BundleMasks` bounds `worker_main` already carries
(mechanical), plus consumer-band start/end derived from the grouping at
first-call setup (fields next to `gate2_plan_phases`).

### Observability / tests (TDD, fail-first)

- **Phase-loop parallel test**: record-bearing, accumulator-free carrier with
  a plan-band meta unit that writes a per-frame marker into a column, plus a
  consumer unit. Frame 1: plan marker present. Frame 2 (clean): plan band
  skipped, marker not rewritten. Observable because `run_core_phase` applies
  no incremental skip.
- **Unit-outer parallel test**: meta + accumulator carrier mirroring
  `gate2_meta_metrics` but driven through `run_parallel` on a multi-core pool
  with records: assert the meta units appended exactly once per frame (not
  once per core), the order (pass-start before consumer appends, schedule-end
  after), and the `OnMeta<ScheduleEnd>` hook reads the frame's `pass_count`
  through the bridge.
