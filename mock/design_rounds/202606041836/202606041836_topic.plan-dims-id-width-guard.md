# Topic: reject a PlanDims that exceeds the phase/trunk id width

**Date:** 2026-06-04
**Scope:** hilavitkutin engine (`plan/mod.rs`, `plan/steps.rs`) + hilavitkutin-api (`dispatch_codegen.rs`). A loud guard against a misconfigured `PlanDims`. No behaviour change for `DefaultPlanDims`.
**Source topics:** #641 (the deferred hard bound-check the `compute_execution_plan` comment at `plan/mod.rs` names), continuing the strict-by-design plan-projection hardening of round 202606041802.

`PlanDims` is a documented consumer override point: `dims.rs` states "consumers override `PlanDims` to size the engine to their workload". The phase and trunk ids are fixed-width, though: `PhaseId` wraps `Uint<5>` (addresses 32 distinct phases, indices 0 through 31) and `TrunkId` wraps `Uint<6>` (addresses 64 trunks). `DefaultPlanDims` aligns its capacities to those widths (`Phases = Dim<32>`, `Trunks = Dim<64>`), so the default can never exceed what the ids can name.

A consumer who overrides `PlanDims` with a wider phase or trunk capacity (say `Phases = Dim<40>`) gets a silent corruption: `compute_waists` caps the phase count at the declared capacity (40), and the projection then constructs `PhaseId::from_index(32..39)` via `Uint::<5>::from_raw(32..39)`, writing index values past the 5-bit range. Two phases collide on a wrapped id, or an id names a slot the type cannot address. Nothing errors; the plan reports success with corrupt ids.

## The silent surface

`compute_execution_plan` (`plan/mod.rs`) projects the waist phase count and the per-block trunk layout into `PhaseId` / `TrunkId` slots. The id width is the real bound on how many phases/trunks the plan can name, and it is smaller than (or equal to) whatever capacity a consumer's `PlanDims` declares. When the declared capacity exceeds the id width, the high slots are unnameable and id construction wraps silently. The existing comment at `plan/mod.rs` records this as the deferred follow-up (#641): "a hard bound-check that errors past the id-width cap is a follow-up".

This is the same strict-by-design pressure as the round 202606041802 `topo_count` guard and the `column_id` exhaustive match: a silent corruption surface converted to a loud, named failure.

## Round changes

1. **Addressability consts** (`hilavitkutin-api/src/dispatch_codegen.rs`): add `PhaseId::ADDRESSABLE` and `TrunkId::ADDRESSABLE`, the count of distinct ids each fixed-width type can name (`2^5` and `2^6`), co-located with the `Uint<5>` / `Uint<6>` struct definitions so the bound tracks the id width.

2. **PlanError variants** (`plan/steps.rs`): add `PhaseCapacityExceedsIdWidth` and `TrunkCapacityExceedsIdWidth`, siblings of the existing capacity-exceeded variants (`NoTrunkAssignment`, `CoreCountExceeded`).

3. **The guard** (`plan/mod.rs`): at the top of `compute_execution_plan`, before any projection, reject a `PlanDims` whose phase capacity exceeds `PhaseId::ADDRESSABLE` or whose trunk capacity exceeds `TrunkId::ADDRESSABLE`. The check is a property of the dims type `D`, independent of the input, so it fires for any call with a misconfigured `D` (including an empty plan). `DefaultPlanDims` is aligned, so the guard never fires for it and there is no behaviour change.

## Test plan (red-first)

A custom `PlanDims` impl with `Phases = Dim<33>` (one past the `PhaseId` width) drives `compute_execution_plan`, asserting `Err(PhaseCapacityExceedsIdWidth)`; a second with `Trunks = Dim<65>` asserts `Err(TrunkCapacityExceedsIdWidth)`. Both fail before the guard exists (an empty plan over the over-wide dims returns `Ok` today via the `n == 0` early return) and pass after. A `DefaultPlanDims` call over an empty input still returns `Ok` (the guard does not false-positive on the aligned default). The existing plan / dispatch / scheduler tests stay green (the default is unchanged).

## Out of scope

- Lifting the guard to a compile-time assertion (a const check on `D::Phases::CAP <= PhaseId::ADDRESSABLE`). The runtime guard matches the task's "bound-check" framing and avoids the `generic_const_exprs` normalization risk of a post-monomorphization const assertion; a compile-time upgrade is a possible follow-up.
- Widening `PhaseId` / `TrunkId` themselves. The widths are the deliberate engine cap; this round makes exceeding them loud, it does not change them.
- The major engine tiers (#339 / #340 / #342 / #344).
