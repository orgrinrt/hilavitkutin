This topic supersedes the validation-mechanism portion of the original app-builder-formalisation topic. The Provider Kit decisions (vocabulary, consume-and-emit shape, `.install` builder method) stand. The "compile-time access-set validation via `Demand` / `Supply` / `SatisfiedBy`" decision is wrong and gets replaced.

## What changed in our understanding

The original topic decided to validate registered providers against registered WorkUnits via a parallel type-state accumulator: `SchedulerBuilder<..., D, S>` carrying a Demand list and a Supply list, gated at `.build()` by `D: SatisfiedBy<S>`. That decision was made without recognising that the engine already has the data + the trait machinery to do exactly this validation, on the existing axis.

The existing system:

- `WorkUnit::Ctx` already declares the seven `Has*` bounds (`HasColumnReader<Self::Read>`, `HasColumnWriter<Self::Write>`, `HasResourceProvider<Self::Read>`, `HasVirtualFirer<Self::Write>`, `HasEach`, `HasBatch`, `HasReduce`, plus the platform projections `HasMemoryProvider` / `HasThreadPool` / `HasClock`).
- `hilavitkutin-ctx::Context<P>` is the provider-tuple carrier. It implements the `Has*` traits when `P` contains the matching components.
- `AccessMask` / `StoreId` already track per-store registration through plan-stage analysis at runtime.

The validation we want at `.build()` is a property the compiler proves anyway when it instantiates the per-WU dispatch fn: the engine emits `dispatch_wu::<WU, Context<P>>(...)`, and that call site only compiles if `Context<P>` satisfies `WU::Ctx`'s bounds. A registered WorkUnit whose `Ctx` is unsatisfiable against the registered provider tuple `P` fails to compile at `.build()` because the dispatch fn cannot instantiate.

The `Demand` / `Supply` / `SatisfiedBy` parallel system reinvents the proof obligation that the existing trait system already discharges. It also bakes in a proof shape (per-leaf membership in a type-list) that is fundamentally weaker than what the existing `Has*`-bound mechanism proves: the existing bounds carry per-store granularity (`HasColumnReader<R>` proves the context can read every store in `R`); the type-list shape forces a parallel per-store enumeration that re-derives the same data.

## Decisions for this round (corrected)

### Provider Kits: unchanged

`ProviderKit` trait, `.install(kit)` builder method, the consume-and-emit shape, the convention that each Kit is a concrete type shipped by a provider crate (e.g. `hilavitkutin-providers`): all of these stand from the prior topic. The Kit is still the answer for "how does a provider crate ship a reusable bundle of registrations".

The trait's parameter shape stays as the api-side cross-crate-friendly form (`ProviderKit<B>` with associated `Out`); the engine's `.install<K: ProviderKit<Self>>` calls into it.

### Access-set validation: defer to existing trait machinery

No `Demand` list. No `Supply` list. No `SatisfiedBy` trait. No type-state on `SchedulerBuilder` beyond the existing const-generic sizes plus a provider-tuple parameter `P`.

Instead:

- `SchedulerBuilder<MAX_UNITS, MAX_STORES, MAX_LANES, P>` carries a provider tuple `P`. Default `P = ()`.
- `.resource::<T>(init)`, `.column::<T>()`, `.memory(p)`, `.threads(p)`, `.clock(c)` each return a builder with `P` extended by the matching component. The component type is the existing provider shape from `hilavitkutin-ctx` (a tuple element that the corresponding `Has*` trait projects onto).
- `.add::<WU>()` does not change `P`. It records the WU in a unit-list type so `.build()` can emit dispatch fn instantiations.
- `.install<K: ProviderKit<Self>>(kit)` runs the kit's chain through the same builder API, threading `P` accumulation as the kit calls `.resource` / `.column` / etc.
- `.build()` instantiates dispatch for every registered WorkUnit. Each instantiation requires `Context<P>` to satisfy `WU::Ctx`; the compiler proves it through the existing seven-`Has*`-bound resolution. Mismatch surfaces as a stock trait-bound error at the `.build()` call site, naming the unsatisfied bound and the WU.

### Builder type-state shape

```rust
pub struct SchedulerBuilder<
    const MAX_UNITS: usize,
    const MAX_STORES: usize,
    const MAX_LANES: usize,
    P = (),
    U = (),
> {
    providers: P,
    _units: PhantomData<U>,
}
```

`U` is the unit-list type-state, accumulating registered WorkUnits as the chain progresses. `.add::<WU>()` advances `U` by prepending `WU` to the tuple; `.build()` walks `U` at compile time, emitting one dispatch fn instantiation per WU.

`P` carries the actual provider values (not just types) because resources hold initial values and platform providers are owned by the scheduler. `U` is purely type-level since the scheduler doesn't store WUs as values.

### Validation surface

What the consumer sees on misconfiguration:

- Missing `MemoryProvider` for a WU that needs one: trait-bound error naming `HasMemoryProvider for Context<P>` is unsatisfied. Stock Rust diagnostic.
- WU declares `Read = (Column<X>,)` but the builder never registered `Column<X>`: the engine's `Context<P>` impl of `HasColumnReader<(Column<X>,)>` requires `Column<X>` to be in `P`'s store registry. That `Has` bound fails at the dispatch instantiation site. Stock Rust diagnostic.
- Custom diagnostic improvement (naming which WU, which provider) rides the same `#[diagnostic::on_unimplemented]` follow-up the prior topic catalogued. BACKLOG carries forward.

### Module placement

- `ProviderKit` trait stays in `hilavitkutin-api/src/kit.rs`.
- `validation.rs` (introduced by the deprecated round) is removed entirely. There is no parallel validation module.
- The seven `Has*` accessor traits stay in `hilavitkutin-api/src/context.rs` and `hilavitkutin-api/src/platform.rs` exactly as today. They are the validation mechanism; nothing replaces or wraps them.

### `app!` macro

Still deferred entirely, per the prior topic's decision. Rationale unchanged: the chainable API is sufficient until a concrete consumer surfaces a friction case.
