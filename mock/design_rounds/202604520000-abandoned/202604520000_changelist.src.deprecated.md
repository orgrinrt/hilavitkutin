## `mock/crates/hilavitkutin-api/src/`

### Add new module: `kit`

New file: `mock/crates/hilavitkutin-api/src/kit.rs`. Contents:

- `pub trait ProviderKit` exactly as the doc declares. Method body is the trait method, not a default impl.
- Module doc comment: one paragraph framing (Kits register Resource/Column/projection bundles via the same chainable builder API).
- The trait references `SchedulerBuilder<MU, MS, ML>` from the engine crate. Since `hilavitkutin-api` cannot depend on `hilavitkutin` (lint-forbidden), the trait method takes the builder by an opaque type parameter. Final shape:

  ```rust
  pub trait ProviderKit {
      type Output;
      fn install<B>(self, builder: B) -> B::Out
      where
          B: KitInstaller<Output = Self::Output>;
  }
  ```

  paired with a `pub trait KitInstaller` whose impl for `SchedulerBuilder` lives in the engine crate. This sidesteps the api-cannot-depend-on-engine constraint.

  Alternative under consideration: keep the doc-declared signature literal by re-exporting `SchedulerBuilder` from `hilavitkutin-api` via a sealed re-export trait. Decision rides the SRC iteration.

- `KitInstaller` trait (above) declared in the same module.

### Add new module: `validation`

New file: `mock/crates/hilavitkutin-api/src/validation.rs`. Contents:

- Sealed trait `pub trait Demand`. Marker for type-list nodes representing builder demands.
- Sealed trait `pub trait Supply`. Marker for type-list nodes representing builder supplies.
- Empty-list type: `pub struct Nil;`. Implements both `Demand` and `Supply`.
- Cons-list type: `pub struct Cons<H, T>(PhantomData<(H, T)>);`. Implements `Demand` and `Supply` when `H: Demand`-marker / `Supply`-marker and `T: Demand` / `Supply` respectively.
- Per-marker leaf types:
  - `pub struct DemandRead<R>(PhantomData<R>)` for WU `Read` access-set requirements.
  - `pub struct DemandWrite<W>(PhantomData<W>)` for WU `Write` access-set requirements.
  - `pub struct DemandHasMemoryProvider`, `DemandHasThreadPool`, `DemandHasClock`. Three platform-projection markers.
  - (The four iteration-projection demands `HasEach` / `HasBatch` / `HasReduce` / etc. land in the v0 surface as additional marker types named `DemandHasEach`, etc.)
  - `pub struct SupplyResource<T>(PhantomData<T>)`.
  - `pub struct SupplyColumn<T>(PhantomData<T>)`.
  - `pub struct SupplyMemory<M>(PhantomData<M>)`.
  - `pub struct SupplyThreads<P>(PhantomData<P>)`.
  - `pub struct SupplyClock<C>(PhantomData<C>)`.
- Sealed trait `pub trait SatisfiedBy<S>`. Implemented for every `Demand` list `D` such that every node in `D` is satisfied by some node in `S`. Implemented via:
  - Base case: `impl<S: Supply> SatisfiedBy<S> for Nil`.
  - Cons case: `impl<H, T, S> SatisfiedBy<S> for Cons<H, T> where H: SatisfiedByOne<S>, T: SatisfiedBy<S>`.
  - Helper trait `pub trait SatisfiedByOne<S>` with one-impl-per-pair that maps Demand leaf to Supply leaf (e.g. `DemandRead<R: Contains<X>>` satisfied by `SupplyResource<X>` or `SupplyColumn<X>`).
- Module doc comment: framing as "compile-time proof obligation construct" + cross-ref to `kit` module.
- All types have `#[non_exhaustive]` on the public surface where appropriate; the module is sealed at the trait level.

## `mock/crates/hilavitkutin/src/scheduler/mod.rs`

### Extend `SchedulerBuilder` with type-state parameters

Current shape:

```rust
pub struct SchedulerBuilder<
    const MAX_UNITS: usize,
    const MAX_STORES: usize,
    const MAX_LANES: usize,
>
```

Target shape:

```rust
pub struct SchedulerBuilder<
    const MAX_UNITS: usize,
    const MAX_STORES: usize,
    const MAX_LANES: usize,
    D = Nil,
    S = Nil,
> where D: Demand, S: Supply
```

Default values (`D = Nil`, `S = Nil`) keep existing call sites that never call `.add::<WU>()` working: empty Demand is satisfied by any Supply at `.build()` time.

### Update `Scheduler::builder()` constructor

Returns `SchedulerBuilder<MAX_UNITS, MAX_STORES, MAX_LANES, Nil, Nil>` explicitly (or relies on the defaults). Body unchanged: just `SchedulerBuilder { _phantom: PhantomData }`.

### Update each chainable method to advance type-state

Each method changes shape from `fn x(self, ...) -> Self` to `fn x(self, ...) -> SchedulerBuilder<MU, MS, ML, NewD, NewS>`. Per-method advancement table (matches the doc):

| Method | New return-type D | New return-type S |
|---|---|---|
| `.add::<WU>()` | `Cons<DemandRead<WU::Read>, Cons<DemandWrite<WU::Write>, ...projections..., D>>` | `S` |
| `.resource::<T>(init)` | `D` | `Cons<SupplyResource<T>, S>` |
| `.resource_default::<T>()` | `D` | `Cons<SupplyResource<T>, S>` |
| `.column::<T>()` | `D` | `Cons<SupplyColumn<T>, S>` |
| `.memory(provider)` | `D` | `Cons<SupplyMemory<M>, S>` |
| `.threads(pool)` | `D` | `Cons<SupplyThreads<P>, S>` |
| `.clock(clock)` | `D` | `Cons<SupplyClock<C>, S>` |

Bodies stay no-op. The change is only the return type signature; runtime behaviour is unchanged in this round.

### Implement `KitInstaller` for `SchedulerBuilder`

```rust
impl<const MU: usize, const MS: usize, const ML: usize, D: Demand, S: Supply>
    KitInstaller for SchedulerBuilder<MU, MS, ML, D, S>
{
    type Out = ...;
    type Output = ...;
    // hand off to whatever the Kit chains internally
}
```

Concrete signature settles during SRC iteration. Goal: the impl is the bridge between the api-side `ProviderKit` trait and the engine-side `SchedulerBuilder` chain methods.

### Update `.build()` to require the satisfaction proof

```rust
pub fn build(self) -> Scheduler<MAX_UNITS, MAX_STORES, MAX_LANES>
where
    D: SatisfiedBy<S>,
{
    Scheduler::default()
}
```

The `where D: SatisfiedBy<S>` clause is the gate. If a registered WU's demands are not covered by registered supplies, the trait impl resolution fails and the error surfaces at the `.build()` call site.
