# Topic: splitting a WorkUnit's declaration from its execution

**Date:** 2026-07-17
**Phase:** TOPIC
**Scope:** Lift the runner-agnostic half of `WorkUnit` (the declared read set, write set, and
scheduling hint) into a trait a non-fiber runner can consume, so a consumer that only needs to
declare and plan work does not have to adopt the column-record execution model to do it.
**Driver:** A downstream consumer (a GPU renderer) needs the declaration half and cannot honour the
execution half. The gap is real and it is ours, not theirs.
**Constraint:** No API change for existing implementors or consumers. Additive only.

## Why this is hilavitkutin's problem and not the consumer's

`WorkUnit` bundles two separable things. The first is a **declaration**: `type Read: AccessSet`,
`type Write: AccessSet`, `type Hint: SchedulingHint`. It says what a unit touches and how to price
it, and it names no runner. The second is an **execution model**: `type Ctx<'frame>` bounded on
`HasColumnReader<Self::Read>` and friends, plus `execute`. That half is specific to running
column-record work on the fiber engine.

The two are welded together today, and the weld is why a consumer with a different runner cannot use
the declaration. The specific break is `ColumnReaderApi::read` (`hilavitkutin-api/src/context.rs:112`):

```rust
unsafe fn read<T: ColumnValue, I>(&self, i: USize) -> T
```

It reads a record by index and returns it by value on the CPU. A runner whose work is recorded and
submitted rather than executed in-process cannot honour that method, and a `Ctx` that implements it
with an uncallable body is a contract satisfied by lying. The consumer's options today are all bad:
implement the trait dishonestly, or duplicate `AccessSet` and `SchedulingHint` locally and lose
every consumer of the shared vocabulary.

That is the shape `use-the-stack-not-reinvent.md` names: a consumer hitting a substrate limitation
should not write a parallel implementation, and the substrate should not force one. The declaration
is genuinely general. Only the execution model is fiber-specific. The trait says otherwise, and the
trait is wrong.

## What is proposed

A trait carrying the declaration half, parameterised by schedule, with a blanket impl that gives it
to every existing `WorkUnit` for free:

```rust
pub trait Plannable<Schedule = Always> {
    type Read: AccessSet;
    type Write: AccessSet;
    type Hint: SchedulingHint;
}

impl<W: WorkUnit<S>, S> Plannable<S> for W { /* forwards to the WorkUnit items */ }
```

`WorkUnit` is not touched. Its associated types stay where they are. Every existing implementor
compiles unchanged and gains `Plannable<S>` with no new impl block, for every schedule including
`On<V>` and `OnMeta<V>`. A consumer with its own runner writes `impl Plannable for ItsThing` and
declares reads, writes, and a hint without a `Ctx` it cannot honour.

The plan stage's inputs become expressible as `T: Plannable<S>`, which is what the plan stage
actually reads: it never calls `execute`.

## The name

`Declares` was the first suggestion and is rejected as unidiomatic. `Has*` in this crate means a
context capability (`HasClock`, `HasThreadPool`, `HasMemoryProvider`, `HasRecordCount`), so a `Has*`
name would misfile a unit-side declaration. Anything spelled `Schedul*` sits two words from the
existing `HasSchedule` and `SchedulingHint`.

`Plannable` names its consumer the way `SchedulingHint` names its consumer, takes the `-able` shape
the stack already uses for `Boundable`, `NonZeroable`, and `Replaceable`, and matches the crate's own
phrase for the stage that reads it ("plan-time DAG analysis", `context.rs:109`). Alternatives
considered and available: `Schedulable<S>`, `WorkDecl<S>`.

## The hint's extensibility, settled in the same round

`SchedulingHint` is sealed (`hint.rs:68`) and implemented only for `(U, D, S)` triples of urgency,
divisibility, and significance markers. A runner with a dimension the triple lacks cannot express it,
and unsealing would cost the engine its ability to reason about every hint shape.

The additive fix keeps the seal and adds one arm:

```rust
pub trait HintExt: 'static {}
impl<U: UrgencyValue, D: DivisibilityValue, S: SignificanceValue, X: HintExt> SchedulingHint for (U, D, S, X) {}
```

A 3-tuple and a 4-tuple are different types, so the arms cannot overlap and nothing existing changes.
The engine keeps reading urgency, divisibility, and significance, and ignores the extension. A runner
that declares an extension marker reads its own dimension. The seal still holds: `SchedulingHint` is
implemented only for tuple shapes this crate names, and `HintExt` is the one open slot inside them.

## Prior art in this crate

The blanket-plus-explicit shape is already established here, not invented by this round.
`HasSchedule` (`work_unit.rs:145..153`) is blanket-impl'd for every `WorkUnit<Always>` "so existing
Always WUs gain `HasSchedule` with no extra impl", while an `On<V>` unit adds an explicit impl, and
the doc comment records that "the two do not overlap, so the blanket and the explicit impl cohere
(proven by the 202606081700 sketch)".

`Plannable` is that pattern with the schedule lifted into the trait's parameters, which is strictly
more general: because `S` appears in the trait reference, the blanket covers every schedule at once
and no explicit impl is needed for `On<V>` at all.

## What the round must establish

Stated as checks, so the output is testable:

1. The blanket impl compiles. `S` must be constrained by the trait reference; the naive
   `impl<W: WorkUnit<S>, S> Plannable for W` fails E0207.
2. A downstream type that is not a `WorkUnit` can implement `Plannable` by hand without colliding
   with the blanket impl, across a crate boundary.
3. No existing implementor changes. The engine, `hilavitkutin-providers`, and every test compile
   untouched.
4. No existing consumer changes. A `T: WorkUnit` bound still resolves `T::Read` unambiguously.
5. The 4-tuple hint arm does not overlap the 3-tuple arm, and existing hints are unaffected.
6. The seam this opens is honest: `Plannable` names no runner, and nothing in it mentions a column,
   a record, or a device.

## Method

Sketch first, per `cl-claim-sketch-discipline.md`: the round turns on coherence and on E0207, both of
which are "does rustc actually accept this" questions and neither of which is settled by reading.
The sketch is committed before the doc CL locks.

Scope discipline: this round adds the trait and the hint arm. It does not move `AccessSet` or
`SchedulingHint` into a smaller crate, though the granular-dependency argument for doing so is real
(a consumer wanting only the declaration currently links all of `hilavitkutin-api`). That extraction
is its own round and its own question, and it is named here so it is not mistaken for an oversight.
