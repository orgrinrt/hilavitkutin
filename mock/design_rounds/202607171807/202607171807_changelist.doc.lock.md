# Doc changelist: Plannable + the hint extension slot

**Date:** 2026-07-17
**Round:** `202607171733_topic.plannable-declaration-split`
**Phase:** DOC
**Scope:** Document two additive api-surface changes in
`mock/crates/hilavitkutin-api/DESIGN.md.tmpl`: the `Plannable<Schedule>` declaration trait and the
`HintExt` extension slot on `SchedulingHint`. No existing documented shape changes.

## Scope decision recorded here (the topic said more; this narrows it)

The topic proposed landing both `Plannable` and a fully-worked hint extension. This round lands:

1. **`Plannable<Schedule>`** in full. It is the load-bearing prerequisite: a runner-agnostic
   declaration a non-fiber consumer can implement without the column-record execution model.
2. **The `HintExt` mechanism only**, not any extension markers. The 4-tuple
   `(U, D, S, X: HintExt)` arm is added so the seal has one open slot, but zero `HintExt` markers
   are defined, because no concrete hint dimension beyond urgency/divisibility/significance has a
   consumer yet. Adding invented markers now would be speculative surface with no reader. The
   mechanism is proven and ready; the content waits for a real need.

The divisibility axis already expresses "can this work be split or paused", which is the axis a
tiling-capable runner would first reach for, so the extension slot may never gain a marker. It
exists so that if a genuinely new dimension appears, it lands additively rather than by unsealing.

## CHANGE: document `Plannable<Schedule>` in the WorkUnit section

File: `mock/crates/hilavitkutin-api/DESIGN.md.tmpl`

Add, after the `## WorkUnit trait (domain 09)` block, a subsection documenting `Plannable`:

- The declaration half of a `WorkUnit`: `type Read: AccessSet`, `type Write: AccessSet`,
  `type Hint: SchedulingHint`, parameterised by `Schedule` (default `Always`).
- A blanket impl `impl<W: WorkUnit<S>, S> Plannable<S> for W` gives every `WorkUnit` the trait for
  free, for every schedule, with no per-implementor impl block.
- A non-`WorkUnit` type (a runner that records rather than executes) implements `Plannable` by hand,
  declaring what it reads and writes and how to price it, without a `Ctx` it cannot honour.
- The plan stage reads `Plannable`, never `WorkUnit::execute`, so it is generic over `Plannable`.

## CHANGE: document the `HintExt` slot in the hint prose

File: `mock/crates/hilavitkutin-api/DESIGN.md.tmpl`

Where the scheduling hint is described (the three-axis tuple), note that `SchedulingHint` stays
sealed and gains one additive arm: the 4-tuple `(U, D, S, X: HintExt)`, where `HintExt` is an open
marker trait a downstream runner implements to carry a fourth, runner-specific dimension. The engine
reads urgency, divisibility, and significance and ignores the extension. No `HintExt` markers ship
in this crate.
