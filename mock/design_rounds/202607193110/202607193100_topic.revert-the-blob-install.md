# Topic: revert the blob install from replace_value

**Date:** 2026-07-19
**Phase:** TOPIC
**Scope:** `Scheduler::replace_value` (`scheduler/mod.rs`), its test, and the design invariant that
round `202607192700` added.
**Grounded on:** op's ruling 2026-07-19, "revert it now"; `202606210600` on swap semantics; r8 band A.

Round `202607192700` gave `replace_value` an install: resolve the binding through
`Selector<V, Index>` and assign the new value through the returned pointer. It shipped and the test
passes.

It should not have. `202606210600` says a `Replaceable` swap is a "member-by-member copy of each leaf
into its column slot ... **not an in-place blob memcpy**". The install is exactly the in-place blob
write that sentence rules out.

## How it got shipped

I read that sentence, then argued out of it: the member-by-member requirement is stated for the
handle model, the handle model "has not shipped", therefore the blob write is acceptable in the
interim.

Both halves were wrong. `Decompose` with `type Leaves: StoreBundle` is at
`hilavitkutin-api/src/storage.rs:97` with a test exercising it, so the premise was false and one grep
would have shown it. And even had it been true, an unbuilt substrate for the correct shape is a
reason to build the substrate, not a licence to ship the shape the spec excludes.

## What is reverted, and what is not

The **install** goes. `replace_value` returns to marking the store dirty without writing, which is
honest about doing nothing rather than doing the wrong thing.

The **signature fix stays**. The old signature took `T` unifying to `Resource<Ra>`, a `PhantomData`
marker carrying no value; it could not express an install under any mechanism. The parameter being
the value type is correct for the member-by-member install too, since the leaves are decomposed from
the value.

The **doc invariant added last round stays** and gains the member-by-member requirement, so the
design states what the install must do before anyone writes it again.

The **test** becomes a catalogued red. It asserts the right thing, that the value reaches the data
plane, and it will pass when the decomposed install lands. Deleting it would lose the case; leaving
it green would leave a test certifying an install that is not the designed one.

## What D1 now depends on

The decomposed drain: writing each leaf into its column slot, which is #654's work
(`ColumnStorage` + SoA decomposition, in progress). The current drain reserves one record of `T` and
does a single whole-`T` write, so a decomposed install would have no per-leaf columns to write into.

D1 is therefore not a band-0 defect fix. It is a storage-model item behind #654.

## Out of scope

`replace_resource`, which has its own bound problem (#696). #654 itself.
