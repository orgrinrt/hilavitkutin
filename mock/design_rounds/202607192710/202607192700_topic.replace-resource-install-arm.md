# Topic: the install arm for replace_resource

**Date:** 2026-07-19
**Phase:** TOPIC
**Scope:** `scheduler/mod.rs:1187` `replace_resource` and `:1207` `replace_value`.
**Grounded on:** roadmap r7 band 0 item D1; op's direction on 2026-07-19 to sketch the install arm
before deciding the contract.

Both functions take `_new: T`, mark the store dirty, and drop the value. The doc says "Replace the
existing `Resource<T>` instance in the data plane with `_new`". A consumer calling either observes
the dirty flag and concludes the swap happened.

## Why the install was left unfinished

After `build()`, the scheduler holds no values. `:707` says it "holds only `Copy` pointers into the
store's reserved columns". The `Vals` list is consumed at build time, so there is no field to
assign; the install has to write through a pointer, and reaching that pointer means resolving the
binding for `T` from a type-level list.

That is not a field assignment, and it is the reason the arm reads as deferred rather than
forgotten.

## What already exists to do it

`Selector<T, Index>` (`dispatch/engine_ctx.rs:416`) is exactly this resolution:
`fn get(&self) -> ResourcePtr<T>`, implemented at `Here` on a matching `ResourceBinding<T, Tail>`
and at `There<I>` by recursing into the tail. It is the spec-free witness machinery, not the
`specialization`-dependent accessor r7 lists as forbidden, so building on it does not deepen the
dependency on a banned feature.

So the install is `Selector::<T, Index>::get(&self.bindings).as_ptr()`, then a write through it.

## The question this round exists to answer

`replace_resource` already carries `Stores: Locate<T, Index>`, where `Index` is a position in the
**Stores** access-set list. `Selector` needs a position in the **bindings** list. Whether those are
the same index space is the whole question. If they coincide, one type parameter serves both and the
signature is unchanged. If they do not, the function needs a second index parameter, which changes
the call shape for every consumer.

This is not answerable by reading, and reading is what produced five wrong conclusions in this arc
today. The round makes the change and compiles it. A trait-solver rejection is the answer just as
much as a clean build is.

## What the write itself must respect

The scheduler holds `&mut self`, so no worker is running and no reader aliases the slot. The old
value must be dropped, not leaked, so the write is an assignment through the pointer rather than a
`ptr::write`. Whether `T: Sized` and the ZST case need guarding is a detail the compile will surface.
