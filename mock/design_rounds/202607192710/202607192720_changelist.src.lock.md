## CHANGE: `replace_value` INSTALLS the value, taking the value type

File: `mock/crates/hilavitkutin/src/scheduler/mod.rs`

```rust
pub fn replace_value<V: Replaceable, Index>(&mut self, new: V)
where
    Stores: Locate<Resource<V>, Index>,
    Index: WitnessIndex,
    <Vals as BindingsFor>::Bindings: Selector<V, Index>,
```

The parameter changes from the store marker to the value type. The old signature could not have been
implemented at all: `T` unified to `Resource<Ra>`, which is `PhantomData` and carries no value, so
there was nothing to install and no body could have satisfied the doc comment. `Replaceable` moves
onto the value type accordingly.

The body resolves the slot with `Selector<V, Index>` and assigns through the pointer, so the previous
value drops rather than leaks. That mirrors the drain (`resource/bindings.rs:335-375`), which
reserves one record of `T` and performs a single whole-`T` write; the drain uses `ptr::write` because
its slot is uninitialised.

**On the contract choice.** Canon does not settle it. `202606210600` says in as many words that "swap
semantics need explicit spec", and its member-by-member language is scoped to the handle model, which
has not shipped. Three shapes were costed in the sketch. This one takes the value directly, because
the bindings are keyed by the value type and the signature should agree with the data plane it
writes; the alternatives keep a marker the install has to translate away, and reach the same call
site behind more machinery. Recorded as a reasoned pick, not a lookup, so a reviewer can redirect it
in one round.

Verification: `cargo check -p hilavitkutin` clean, no new warnings.

## CHANGE: `tests/resource_bindings.rs` GAINS the install observation

File: `mock/crates/hilavitkutin/tests/resource_bindings.rs`

Builds with `Resource::new(Ra(99))`, asserts the build value is in place, calls
`replace_value(Ra(7))`, and asserts the slot reads `Ra(7)`. Against the old body the test could not
even be written: the argument had no value to pass.

Verification: eight passing cases in that file.

## NOT CHANGED: `replace_resource`, and why

`replace_resource<T: PlanAffecting, Index>` keeps its stub, because it carries a second problem this
round should not paper over.

`PlanAffecting` has exactly one implementor in the workspace: `DefaultRunCfg`
(`hilavitkutin-api/src/run_cfg.rs:155`). It is a run-config trait, not a resource-value trait. The
function is therefore callable for one type, and that type is the run configuration rather than
anything a consumer registers as a `Resource`.

Applying the same fix means first deciding what `PlanAffecting` should range over, which is a
different question from how the install works, and the trait is sealed so consumers cannot widen it.
Fixing the install while leaving the bound as it stands would produce a function that works and still
cannot be called for its apparent purpose.

Recorded for its own round.
