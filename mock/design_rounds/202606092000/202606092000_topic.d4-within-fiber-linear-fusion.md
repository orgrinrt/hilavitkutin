# Topic: D4 within-fiber linear fusion (deep single-fiber rust-pipe)

**Date:** 202606092000
**Phase:** TOPIC
**Scope:** `hilavitkutin-api` (the opt-in `RecordOp` per-record transform contract), `hilavitkutin` engine (the `dispatch::fusion` machinery + the `Scheduler::run_fused` dispatch entry), and the `engine_vs_std` bench's `element_wise` workload (opts its stages into `RecordOp` and dispatches fused).
**Source design:** canonical consolidation spec domain 17 (the codegen flattener, rust-pipe pattern, "deep single-fiber" register residency); engine roadmap r2 §3/§7 (D4); sketches `202606091200_d4-recordop-chain-fusion`, `202606091400_d4-carrier-fold-autosynthesis`, `202606091800_d4-min-spec-transparent-dispatch`.

This round builds within-fiber linear fusion, the canonical spec's deep-single-fiber rust-pipe pattern: a fiber that is a linear RAW chain runs with its intermediate columns held register-to-register (DSE eliminates the memory traffic) instead of materialising each one. It is the second of the two mechanisms the spec names as load-bearing for single-core engine-vs-std parity (the first, dispatch devirtualisation, landed in the D1e `RunFiber` walk). It greens the `element_wise` arm of the standing #664 perf gate.

## What the canonical spec says (the oracle)

Domain 17 ("The codegen flattener, rust-pipe pattern") states that for the common case the flattener emits, per fiber: read fiber-input columns at morsel start, run a pure function pipeline with locals (no intermediate column stores), let fiber-internal columns become register-to-register with DSE skipping the memory ops, and group all output stores at the end of the loop body. It states the deep single-fiber result plainly: "the flattener eliminates store-reload between WU boundaries by reusing locals (1.00x vs 1.14x with fn-ptr composition)."

The same passage draws the boundary this round respects: "Multi-fiber scenarios already achieve 0.95-1.02x because fiber boundaries are natural materialisation points, no flattening needed." Within-fiber linear fusion is the mechanism for a deep single-fiber linear chain. A multi-fiber DAG (the `branching` diamond, whose store-disjoint branches block-diagonalise into distinct fibers) reaches parity through per-fiber compiled dispatch plus devirtualisation, a different axis, and is out of scope here.

## Scope: element_wise (linear chain), not branching (diamond)

`element_wise` is four stages in a straight RAW chain, `In -> Av -> Bv -> Cv -> Dv`, one fiber, the deep-single-fiber case. The std arm keeps the three intermediates in registers and writes only `Dv`; the engine currently materialises four columns. Closing that gap is exactly the rust-pipe register-residency the spec describes, and it is expressible as a linear fold: each stage is a pure `apply: In -> Out`, composed head-to-tail, the composed body keeping each intermediate in a local.

`branching` is a diamond, `In -> {Xv, Yv} -> Zv`, where the join reads two columns. A linear fold cannot express it (a single-input-single-output `apply` cannot carry two live intermediates into a join), and per the spec it does not need linear fusion: it is multi-fiber, where materialisation at fiber boundaries is already the parity path. Diamond / sub-DAG fusion (if a future bench shows the multi-fiber dispatch alone misses tolerance) is a distinct mechanism that needs its own feasibility sketch. This round does not touch it. So this round greens `runtime_element_wise`; `runtime_branching` and `runtime_accumulator` green via their own mechanisms.

## The mechanism (proven by the committed sketches)

Sketch `202606091200` proved register residency: an opt-in per-record pure-transform trait (`RecordOp`, `apply: In -> Out`) composed by a type-level fold (`OpChain`, `tail.run_chain(head.apply(x))`, concrete monomorphised inline calls, no fn-pointer, no `dyn`) into a normal `WorkUnit` (`ChainWu`) whose `execute` reads the chain input column, runs the pipeline with intermediates as locals, and writes only the chain output column. objdump of the two real-engine morsel-outer monomorphisations: the unfused four-stage carrier is 12 loads / 10 stores (the internal columns round-trip the arena); the fused chain is 3 loads / 3 stores, the internal columns eliminated to registers, both zero `blr`. Heterogeneous intermediate types compose cleanly.

Sketch `202606091400` proved the engine synthesises the chain from the registered carrier: a `FuseCarrier` trait with two non-overlapping structural impls (`WuCons<H, WuNil>` base, `WuCons<H, WuCons<H2, T>>` recursive, link bound `tail Chain: OpChain<In = Head::Out>`) folds `WuCons<S1, WuCons<S2, ...>>` into the `OpChain`, compiling with no E0119 (single-chain folding, no partitioning, sidesteps the coherence wall that blocked type-level fiber grouping). A static type-equality binding confirmed the fold produces exactly the hand-built chain type, and its objdump matched `202606091200` (72 instrs, 0 blr, 3 loads / 3 stores). It also walked `WuCons<ChainWu, WuNil>` via a witness-inferred `run_fiber_morsel_outer`, which is precisely the `run_fused` body.

## The dispatch entry: explicit `run_fused`, resolved by sketch

Sketch `202606091800` settled the dispatch shape. Transparent single-`run()` auto-fusion (a default dispatch impl plus a `min_specialization` override for `FuseCarrier` carriers) does not compile on the pinned nightly, for two independent reasons: the fused `ChainWu` carrier's `RunFiber` witness is unconstrained in a specializing impl (E0207, because the witness is a per-call inferred type param), and `min_specialization` rejects specializing on a `FuseCarrier`-style bound ("cannot specialize on trait", min_spec permits only always-applicable predicates). This is not feature-avoidance: min_spec was tried and cannot express it.

The resolution is an explicit inherent method `Scheduler::run_fused<W2>()`, whose projection witness `W2` is a method generic inferred at the call site (the same mechanism today's `run<W>()` uses, so no E0207, no specialization). It folds the retained `self.wu_values` via `FuseCarrier` and dispatches the folded `ChainWu` through the existing `RunFiber` walk over the scheduler bindings, mirroring `run`'s morsel-outer drive. The engine still performs the fold: the consumer registers natural separate `RecordOp` work units plus their columns and calls `run_fused`; it never hand-authors the chain. `run()` stays the general per-WU walk for non-fusible carriers (accumulators). `FuseCarrier::fuse` takes `&self` (the carrier's work-unit instances are `Copy`) so it folds the field behind `&mut self`.

## Internal-column reservation

The fused `ChainWu` reads only the chain's input column and writes only its output column; the internal columns are never touched at runtime, so register residency holds whether or not they are reserved. Eliding them from reservation (per the C7 `classify_columns` Internal classification) is a memory-and-startup optimisation, not a runtime-parity requirement, and is left as a follow-up. The `element_wise` bench keeps registering all five columns (so `Dv` is materialised for the checksum readback), and the fused dispatch keeps `Av`/`Bv`/`Cv` in registers regardless.

## Changes proposed

1. `hilavitkutin-api`: add the opt-in `RecordOp` trait (`type In: ColumnValue; type Out: ColumnValue; fn apply(&self, x: In) -> Out`). A work unit opts into fusion by implementing it alongside `WorkUnit`; a simple work unit author never sees it.
2. `hilavitkutin` engine: add `dispatch::fusion` with `OpChain` / `OpNil` / `OpCons` (the type-level chain fold), `FuseCarrier` (the carrier-to-chain fold, `fuse(&self)`), and `ChainWu<C>` (the fused `WorkUnit`, `Read = One<C::In>`, `Write = One<C::Out>`). Export the consumer-relevant names from `dispatch`.
3. `hilavitkutin` engine: add `Scheduler::run_fused<W2>()`, mirroring `run`'s morsel-outer drive, dispatching the folded `ChainWu` via `RunFiber` over the bindings.
4. `engine_vs_std` bench: `element_wise`'s four stages implement `RecordOp`; `measure` dispatches via `run_fused` (startup and runtime arms). The `WorkUnit` impls stay (the build still plans over them and reserves the columns).
5. Tests: an engine integration test proving `run_fused` over a registered linear-chain carrier produces the chained output, fail-first.

- Internal-column reservation elision (C7): follow-up memory optimisation.
