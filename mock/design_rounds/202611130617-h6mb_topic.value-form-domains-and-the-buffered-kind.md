# Topic: the value form, record domains and the frame-buffered kind

**Date:** 2026-11-13
**Phase:** TOPIC
**Round:** 202611130617-h6mb
**Scope:** `hilavitkutin-api` and its design, the engine's design where these reach it
**Source:** the first topic of this round, `202611130617-h6mb_topic.revise-the-api-in-place.md`, the map's rows 1, 4, 5, 9, 12, 21, 25, 27 and 30, and the sketch `mock/research/sketches/202611130617_value-form-and-domains/`

The first topic of the round says what enters the api and on whose word. This one records how each thing is shaped and what was weighed against it. Five things are decided here: the form an author writes a unit in, how that form and today's form enter one builder, what a record domain is, how a unit reads a neighbour, and the store kind whose reads see the last committed pass.

The shapes were tried before they were written down. The sketch named above builds them on the pinned toolchain with no feature line and no `unsafe`, runs two value-form units under two runners that walk the records in opposite directions, and records eleven refusals as compile-fail pairs. Its findings list what it does not establish, and each of those is named below where a decision leans on something the sketch did not show.

No human sat in this round, and every decision here is provisional until the lead designer reads it.

## The value form

Today `RecordOp` is one value in and one value out, opted into beside `WorkUnit` so that fusion can fold a run of maps. The map's row 1 says the form kaski's branch calls a kernel is this trait widened to lists.

Options weighed for the widened shape: writes through a handle passed in beside the reads; writes returned by value; a generated context type per unit.

Taken: the reads arrive as one product of values over the unit's read list and the writes are returned as one product over its write list. A unit cannot then leave a declared write without a value, and the body holds no handle that could outlive the call or be used twice. The return is built in the write list's sequence by a small macro. Construction by member name would read better with long lists and is filed as an idea against `notko-hlist`.

What a member's value is depends on its kind. A column or a frame-buffered member is its value type. An accumulator member is an optional value, to append or not. A virtual member is a flag, to fire or not. A resource and an extent can be read and not written in this form. An accumulator and a virtual can be written and not read.

A value-form unit names no engine type, sees no index and no morsel range, and has no associated type in which a context could be named. The sketch's fixtures 04 and 05 are those two refusals.

## How the two forms relate

`WorkUnit` stays as it is in what it can say: a unit that needs the whole morsel, a reduction, or the resource and virtual providers directly is still written in the block form. The question was how both forms enter one builder when only one of them names the engine's context.

Options weighed: a blanket implementation of `WorkUnit` for every `RecordOp`; a second registration method on the builder; the router type the unit already names in `BuilderInput::Dispatch`.

A blanket implementation would have to name the context type in the api, which is the engine's, and a unit written in both forms would overlap with it. A second method splits `.with`, which the builder design made the single entry.

Taken: the router. A block-form unit names `UnitDispatch<Self>` as today and a value-form unit names `RecordDispatch<Self>`. One api trait, `Declares`, is implemented once for each router type and gives what the plan needs of either form: the stores read, the stores written, the domain, the schedule and the hint. The unit bundle and the engine's folds bind on that trait where they bound on `WorkUnit`. A runner implements its own run trait for the api's two router types, so the api carries no runner and no runner's context. Two implementations on two distinct types cannot overlap, which is why no unstable feature is involved.

A value-form unit's schedule and hint ride on the router as defaulted parameters, `RecordDispatch<Self, On<V>>` for a unit that runs when a virtual fires. They cannot be associated types of `RecordOp` with defaults, since the api does not enable defaults for associated types, and a second blanket of `HasSchedule` over `RecordOp` would overlap the one over `WorkUnit`. The sketch does not test this part; the frozen authors of the next round carry it.

The frozen authors use the value form. A block-form unit is bound to the runner whose context it names, so a reference runner cannot run it, and the sketch's last fixture shows the compiler refusing that.

## Record domains

Today the scheduler holds one record count and every column has that many records. Row 4 asks for domains.

Options weighed for where a domain is named: on the unit; on the column; on both.

Taken: on the column, as a parameter with a default, `Column<T, D = Records>`. A column belongs to a store list already and its domain is a fact about the store. `Records` is the domain every existing column is in, so no existing line changes meaning. A unit's domain is computed from its lists and never written: every column-kind member of a unit's reads and writes names one domain, and a unit whose members name two is refused where it is declared, with a message that says so. A unit that reads and writes no column-kind member iterates `Records`.

A domain is a marker with a list of axes and a reach. The axes give the key order, first axis outermost, and with it the conversion between a record's key and its position. The reach is the list of offsets a neighbour read in that domain may name.

Extents are run-time values. Options weighed for how they arrive: an argument of `build` per domain; a store.

Taken: a store. `Extent<D>` is registered with `.with` like a resource and holds the shape of `D`. `build` loses its record count argument, and the count of `Records` is the extent registered for it. A unit may read an extent. No unit writes one in this revision, so a domain's count is fixed for the life of a built scheduler, as the single count is today. A column whose domain has no registered extent is refused at `build`.

The plan gets a record count per domain. Each unit carries its domain, a fiber never holds units of two domains, and a fiber's range and morsel window come from its domain's count. Where the plan wants one figure, for choosing an approach and for the adapt record, it takes the sum of the registered extents. That choice is a placeholder for a better cost model and is marked as one. An accumulator's capacity is the count of the largest registered domain, which is wasteful for a small domain and is left so.

## Neighbour reads

Rows 5, 9 and 12. Options weighed for where the offset and the outside value live: on the column; on the domain; on the read.

Taken: on the read. `Near<C, O, E>` is a member of a read list and means the committed value of store `C` at offset `O` from the record, or the value `E` declares where that lands past the extent. An offset is a list of shifts, each along one axis by a constant, so a diagonal is a list of two. Two readers of one column may then want different outside values, which the map's row 12 raises, and a column carries nothing for readers it has never met.

The offset is checked against the domain's reach where the type is named. The reach is on the domain because it is what the plumbing needs to know once for every reader, to size a halo or to order morsels.

A neighbour read is admitted over a frame-buffered store and over no other kind. A neighbour read of a column written in place gives a result that depends on the sequence the records are visited in, which the engine does not promise and which a morsel-driven dispatch changes freely. This is narrower than the brief's "a read of a column at a declared offset", and the changelist states it as a departure. The block form gets no neighbour read in this revision.

## The frame-buffered kind

Rows 27 and 30. `Buffered<T, D = Records>` is a store kind beside `Column`, `Resource`, `Virtual` and `Accum`. A read of it, at the record or at a neighbour, sees the side committed before the pass. A write goes to a staged side. The close of the pass swaps the two for every store written in that pass, and a store nobody wrote keeps its committed side.

Three consequences for the plan. A reader and the writer of one frame-buffered store have no read-after-write edge between them and no conflict, in either sequence. A swap counts as a change of the store when the next pass asks what is dirty. And the kind has at most one writer.

Options weighed for a second writer: the priority rule the design gives every write-write pair; refusal.

Taken: refusal at `build`, as a const assertion over the units' write masks. Under the priority rule the later writer would replace the earlier writer's staged values whole, with no reader ever between them, so the earlier unit would be dead work. The design's sentence on priority is corrected for this kind only and stands for every other. The technique is that of the sketch `202611122242_frame-view-typestate`; the refusal on the real builder gets its own compile-fail pair in the source window.

Its relation to `ResourceSnapshot`: the same idea, a read-only view of a committed state that concurrent work may read while the next state is produced, taken from resources at a phase boundary to columns at a pass boundary.

## Safe writes in the block form

Row 25. Today `write` is an `unsafe fn` and the design says the unsafety "pinky-swears" a discipline the engine proves at plan time. The plan does prove that no two units write one column in one fiber window; what the signature leaves open is the index.

Taken: `each` and `batch` hand the closure an opaque index branded with a lifetime the plumbing mints for that call. `read` and `write` take that index and are safe. The index has no public constructor, no conversion to or from a number, and cannot leave the closure. The feasibility is the sketch `202611130417_branded-morsel-index`, which sits on a branch not yet landed here.

A body that used the index as data can no longer do so. The few tests that did are given a column to read. A readable member that gives a record its own key would serve them and kaski alike, and is filed as an idea.

## What is left unoptimal

His words allow it while the contract holds, and each of these changes nothing for an author when it is lifted.

Fusion still folds only units with one column read and one column write of `Records`. `run_fused` and `run_parallel` accept a set of units only when all of them iterate `Records`, as a bound on the entry. Value-form units of any domain run under `run`. The frame-buffered kind is stored as two columns and a flag. A neighbour read computes its neighbour's position per read.

## Not decided here

The append sequence of an accumulator is not promised by the value form, and tests compare appends sorted. Whether it should be promised is not something the designs answer, and the round leaves the block form's behaviour as it is.

The intents, in my words, and separate from the quotes. The record already designs most of what this round was adding, and the round is to be written from it. A resource is read by value or by reference by its kind, settled in the types. The writing unit declares what a change is. Writers of one store are ordered by the schedule, hints first and registration last, and none is refused. A count may be fixed or replaceable, as declared. Geometry is an opt-in crate and not the api's. An ordinary unit's changes go through mutations, and in-place writes belong to maintenance units, which set a frame up and close it. The doubts he voices about whether the agents know what hilavitkutin is, and the remark on porting the canon to a registry, are kept for provenance; the second is the other seat's job and under way.

What the record gave for each, with the passages, is in the doc changelist's eight numbered changes. In short: no buffered store and no domain on the column are added; a frame-start read follows from the rank of the close band; a column's count is its storage's; the value function is what a unit hands `each`, inside the work unit; a read with a reach and a write that counts as changed only where it differs are wrappers in the access set, the route the core design topic leaves for a need the two modes do not cover.
