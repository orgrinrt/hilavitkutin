# doc changelist

Round topic `202611132229_topic.buffered-column-start.md`. The other flat topic, `202607200100_topic.b1-cap-lifting-completion.md`, is about lifting the scheduler's scratch arrays onto the plan's capacities. Nothing here touches those arrays, and it stays flat for the round that does.

The sketch this round builds from is `202611132225_buffered-start-by-type`, committed before this changelist and unchanged by it.

## Current state

The api's design registers a buffered column by its bare marker, `.with(Buffered::<T>::new())`, and says "Both of its sides start as a column starts". A column starts as reserved memory nothing has written. The design says a buffered column a unit of the first pass fills is read from the second pass on, and does not say what the first pass reads. The engine's design says the two reservations are made at plan time and says nothing of what they hold.

In the source the drain reserves both sides and writes neither, and every read through the value form in the first pass goes to the frozen side. That is review 1's finding 2: a safe call reads memory nothing wrote. The engine's tests write the frozen side through a hidden accessor before the first run.

Op settled what the column starts from on 13 November. His words and what they leave open are in the topic.

## Changes proposed

### 1. A buffered column is registered with its start, in `hilavitkutin-api/DESIGN.md.tmpl`

"Store types" gains the carrier `StagedBuffered<T, M>` and the two ways to make one. `Buffered::<T, M>::start_from(value)` is there for every element type. `Buffered::<T, M>::start()` reads the element type's own start: its trivial constructor where it has `HasTrivialCtor`, else its `Default`, and for a type with neither it does not exist. The bare marker stays what a unit names the store by and is no longer taken by the builder.

Why a carrier, and not a start the engine works out from the type. `Resource::new(value)` already hands the builder a carrier of a value, and the builder's value list already keeps one. With the same form the api decides the value where the store is named, the engine gets a value and writes it, and no tier has to be known past the constructor. A start the engine derived would need the tiers as a bound on its drain, and that bound cannot rank them.

Why the sequence is an inherent function ahead of a trait's function. The plain form, one trait with a blanket impl a tier, overlaps for a type that has both a constructor and a default, and choosing by rank between overlapping impls is specialisation, which this workspace forbids. The other forms weighed: one function generic over a tier marker, which compiles where one tier holds and stops with an ambiguity where two do, so it never picks the wrong one and never applies the sequence either; and a constructor name a tier, which follows the context crate's form most literally and leaves the sequence to the author. The form chosen applies the sequence op gave with no feature gate, and the sketch shows it with the case that fails. Its cost is that the trait `StartsFromDefault` has to be in scope where the default tier is called, and that a generic caller is answered from its own bounds.

The null bit, the first tier in op's words, is not designed. `notko` has no trait that gives a type a null value: `NicheFilled` marks the types whose all-zeros pattern is not a value of theirs, and the types that carry a null of their own say it through `Default`, which the second tier here reads. So no type loses a start for the tier's absence. What is lost is starting a store from zeroed memory with no write a record. The design carries a marker for it on ticket df2e4da2d376, filed on `notko`.

"Registration" in the same document changes its sentence on the buffered column to the two calls, with `Init = T` and `Dispatch = StoreDispatch<Buffered<T, M>>`. "Reading a store as it stood when the pass began" gains the clause that the first pass reads the value the store was registered with.

### 2. The drain writes the start to both sides, in `hilavitkutin/DESIGN.md.tmpl`

The paragraph on the two reservations says the drain takes the value out of the carrier and writes it to every record of both, and why both. The list of store carriers the builder retains gains `StagedBuffered<T, M>`.

### 3. What is not changed

`Column<T>` keeps its registration by the bare marker. It has the same hole, and the order for this round named the buffered column: ticket 9b64b95e42d1.

The conformance crate's reference runner is lent its stores by the caller, both sides of a buffered one included, so it starts from what it is lent and its design stands. The frozen author units name `Buffered` as a marker in their lists and bodies, which does not change, so no frozen file is edited and `BREAKS.toml` gains no line.

## Breaks counted

Scheduler builders, one: `.with(Buffered::<T, M>::new())` no longer compiles, and becomes `start()` or `start_from(value)`. Unit authors, none: a unit's lists and body name the marker as before.

## Proving checks owed by the source

A compile-fail arm for each wrong pairing: `start()` on an element type with neither a constructor nor a default, and the bare marker handed to `with`. A test that a type with both starts from its constructor, one that a type with a default alone starts from it, and one with an explicit value. A test in the engine that the first pass reads the start on a store nothing else wrote, under both modes, with a provider whose memory is not zero, committed red ahead of the write that makes it green. A test that a record no unit wrote in the first pass holds the start after the boundary, under `Snapshot`.
