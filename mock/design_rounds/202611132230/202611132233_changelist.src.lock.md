## CHANGE: a buffered column is registered with its start
Files: `mock/crates/hilavitkutin-api/src/store.rs`, `mock/crates/hilavitkutin-api/src/lib.rs`, `mock/crates/hilavitkutin-api/src/prelude.rs`, `mock/crates/hilavitkutin-api/tests/buffered_start.rs`, `mock/crates/hilavitkutin-api/tests/trybuild.rs`, `mock/crates/hilavitkutin-api/tests/trybuild/buffered_marker_registered.rs`, `mock/crates/hilavitkutin-api/tests/trybuild/buffered_marker_registered.stderr`.
Section 1 of the doc changelist. `StagedBuffered<T, M>` holds the start value, with `Init = T` and `Dispatch = StoreDispatch<Buffered<T, M>>`. `Buffered::start_from` returns it for every element type. `Buffered::start` is an inherent function under `T: HasTrivialCtor`, and `StartsFromDefault` gives the same name to `Buffered<T, M>` where `T: Default`, so a type with both starts from its constructor and a type with neither has no `start`. `BuilderInput for Buffered<T, M>` is deleted, and the marker keeps `new` for a unit's body.

`start_from` is a `const fn`, and `start` is one where the element type's constructor is const. `StartsFromDefault::start` is not: a const `Default` sits behind `const_default`, which has no row in the workspace's table of vetted features, so the crate may not enable it. Ticket b4df1365a3f7 asks for the vetting. The trait is in the crate's prelude, because the default tier is found only where the trait is in scope, and a caller that names `Buffered` through the prelude would otherwise meet a refusal that tells it to derive what it has already derived.

`tests/buffered_start.rs` holds the constructor tier, the default tier, a type with both under both modes, the default of such a type by the trait's own path, the explicit value, a start made in a constant, and the carrier's `Dispatch` and `Init`. The two refusals are held in two places. The bare marker handed to a builder is a trybuild fixture. `start` on a type with neither is a `compile_fail` doctest on `Buffered::start` with the error code named: the compiler's message there points into the checkout of `notko` by its path on the machine and a line number, which a `.stderr` file cannot hold from one machine to the next.

## CHANGE: the drain writes the start to both sides
Files: `mock/crates/hilavitkutin/src/resource/bindings/mod.rs`, `mock/crates/hilavitkutin/src/resource/bindings/column.rs`, `mock/crates/hilavitkutin/src/dispatch/engine_ctx/map.rs`, `mock/crates/hilavitkutin/tests/buffered_start.rs`, `mock/crates/hilavitkutin/tests/buffered_column.rs`, `mock/crates/hilavitkutin/tests/stable_provider/mod.rs`.
Section 2 of the doc changelist. The value-list arms of `BindingsFor` and `DrainStores` that were headed by `Buffered<T, M>` are headed by `StagedBuffered<T, M>`, and `Markers` still names the marker, as the resource's arm does. The drain takes the value out of the carrier, reserves as before, and writes the value to every record of the frozen and of the live reservation through `ColumnBinding::start_from`. The write takes the records as `MaybeUninit<T>`, so nothing is read ahead of it. A reservation of no bytes is written through as a slice of no records or of records of no size, which touches no memory, so the function has no branch on either.

The compare of a write against the frozen side in `map.rs` is unchanged. Its safety comment now says what makes the read one of a value.

Two commits, in the sequence the doc changelist asks for. `559f3933` has the carrier and the arms with the drain taking the value and not writing it, and at it the tests that read a start are red: eight of the nine of `tests/buffered_start.rs` and the twelve of `tests/buffered_column.rs` whose start is not zero. `77d64d10` has the write, and both files are green.

`tests/buffered_start.rs` builds every scheduler over memory that is `0xA5` at every byte, through `StableProvider::filled`, and writes no side by hand. Its first test holds the premise: a plain column nobody filled reads as the poison. Under both modes it then holds that the first pass reads an explicit start, a constructor's and a default's, the default being zero, which is the start that memory which happens to be zero would pass for, and that both sides hold the start after a pass nothing wrote. The last test has a unit write the store in the first window it is handed and in no other, and holds that every record after the boundary is the write or the start, with some of each. With the write made to the frozen side alone, those eight tests fail.

In `tests/buffered_column.rs` every registration of a buffered column names its start. Where a test filled the frozen side by hand with one value, the start is that value and the fill is gone. Where the fill differs from record to record, or is of the live side to show a boundary did not run, the fill stays, over a start of zero. `a_value_equal_to_the_frozen_one_still_lands_on_the_live_side` is the first review's `probe_partial_equal`, in the tree since the round that answered that review, and it keeps both of its fills: a start is one value, and the probe needs a frozen side that differs by record.
