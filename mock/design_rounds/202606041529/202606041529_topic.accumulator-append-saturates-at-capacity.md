# Topic: accumulator append saturates at capacity

**Date:** 2026-06-04
**Phase:** TOPIC
**Scope:** hilavitkutin engine (`mock/crates/hilavitkutin`). Post-review fix on branch `feat/hilavitkutin-accumulator-columns`, atop round `202606041800`.
**Source topics:** the accumulator-columns round (`202606041800`, its Fork D); the PR #120 local review finding.

The accumulator-columns round landed the append surface but shipped the append unchecked: `resolve_append` writes at `base + live` and advances the live length unconditionally. Round `202606041800`'s Fork D decided the opposite: "a frame appending past `record_count` saturates at capacity (a checked bound), acceptable single-core-first." The code and the locked design disagreed, and the unchecked write is a genuine soundness footgun: a WorkUnit's appends are not bounded by the plan the way a column write's morsel index is, so a WorkUnit appending in a loop with no engine-enforced limit walks off the reserved buffer.

This round brings the code in line with Fork D: the append checks the live length against the reserved capacity and saturates (drops the append, leaves the live length at capacity) instead of writing out of bounds.

## The change

1. `AccumBinding<T, Tail>` records the reserved capacity (`cap: USize`, equal to the build-time `record_count` this round) alongside the base pointer and the live-length cell.
2. `AccumColPtr<'frame, T>` carries the capacity so the append accessor can check it; `AccumSelector::get` reads it from the binding.
3. `ResolveAccumAppend::resolve_append` returns early when the live length has reached the capacity, so the write and the advance never run past the buffer. `resolve_len` is unchanged.
4. The `SAFETY` comments and the `append` doc wording move from "the caller's contract keeps `live` within capacity" to "the append saturates at capacity," matching Fork D.

## Test plan (red-first)

Extend `tests/accum_dispatch.rs` with a saturation case: build an accumulator with a capacity smaller than the number of appends a WorkUnit issues, run, and assert the live length stops at the capacity and the buffer holds exactly the first `capacity` values in append order (the overflow appends dropped, no out-of-bounds write). Red before the clamp lands: the unchecked append writes past the reserved buffer; with the clamp, the overflow appends are no-ops.

## Out of scope (unchanged from round 202606041800)

- The PassEnd persistence drain that reads `[0, live_length)` (#344 / #134).
- A distinct per-accumulator capacity dimension (capacity equals `record_count` this round).
- A multi-core atomic live-length.
