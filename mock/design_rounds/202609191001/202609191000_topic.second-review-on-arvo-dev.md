## The items

### One: the engine's spawn-site gate has no committed check

The previous round forced `OnePointerClosure::<F>::FITS` inside `spawn_one_pointer` in `scheduler/run_parallel.rs`, and showed it working by widening the engine closure by hand. Nothing committed fails if the `let () =` goes, or if a later edit calls `pool.spawn` directly somewhere else in the engine. The api doctests prove the gate refuses a wide closure; they say nothing about whether the engine uses the gate. The check that would catch both is a lint in `mock/lints/`: in the `hilavitkutin` crate, every `.spawn(` call sits inside `spawn_one_pointer`, and `spawn_one_pointer` forces `OnePointerClosure` before it spawns. A lint rather than a cfg-widened build, because it reads the source that ships and needs no second build of the engine, and because a gotcha found here becomes a lint.

### A: the thread-count rule was deleted to match the code

`mock/PRINCIPLES.md.tmpl`, Pre-allocated thread pool, said `Threads = min(physical_cores, parallelisable_width + 1)`. The founding spec carries the same rule (`202604200055/202603181200_topic.hilavitkutin-design-consolidation.md`, the thread-count paragraph: the "+1" is the convergence thread). The previous round deleted it while moving the pool to the consumer. The ruling moved who spawns and who pins; it did not touch how many workers the engine uses, so the deletion let the code overrule the design. The rule comes back restated against what the engine now controls: the closures it hands out, `min(runnable worker count, parallelisable_width + 1)`, where the parallelisable width is the most trunks any phase carries (the engine design's `max_trunks_per_phase`). `run_parallel` hands out one closure per clamped worker regardless of the plan, so it does not honour the rule: a `FIXME:` at that site, and a catalogue test stating the bound.

### B: the zero-worker behaviour was decided where the design was silent

The previous round's sentence in the engine design, "at zero the engine still hands the executor one closure", settles a question nobody ratified. Three answers exist and each does something different to the frame's done-wait, `frame_await_done`, which returns once the done counter equals the expected worker count:

If the engine refuses, `run_parallel` returns an error before publishing a frame, and `frame_await_done` is never reached.

If it runs inline on the caller, the calling thread runs core 0's worker body itself, and the done-wait counts one arrival, its own.

If it hands out one closure, the done-wait expects one arrival from the executor. Where the executor reported zero because it has no thread to run anything on, the closure never runs and the done-wait never returns.

The design states the three and marks the question provisional, waiting on op. The code keeps its current behaviour, and its test and the changelist call it provisional.
