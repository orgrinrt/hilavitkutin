# overflow-review-fixes

**Date:** 2026-11-13
**Phase:** TOPIC
**Scope:** the review of round 202611130402 on `work/overflow-is-a-value`: `run_fused`'s missing reset, the `run_parallel` merge dropping the leading bands' records, the prefix claim under parallel, `AccumRefused::new`, `RunCfg::Err`, the mutant feature's fence, and the generated documents.

## Current state

Round 202611130402 made an over-capacity accumulator append a value. Its review found four defects and four smaller ones.

`run` and `run_parallel` reset every accumulator's live length and `wanted` at frame start; `run_fused` does not, yet it returns the frame's verdict. A refusing `run` followed by `run_fused` therefore reports the old refusal for a frame that appended nothing, and the design's "every run entry resets" is false.

Under `run_parallel` each core appends into its region at `base + lo_c`. The leading meta bands run on the main thread before the publish and append at `[0, len)` of the shared binding. The regions overlap those records, and the merge compacts from position 0 and overwrites them, so they leave both the live length and `wanted`, and the run returns `Ok`: a silent drop (ticket 521dedc08497, older than the refusal round).

The api design and the `resolve_append` comments say the accepted records are the prefix the frame asked for first. Under `run_parallel` each region keeps its own sticky refusal, so one core can refuse while another still accepts.

`AccumRefused::new` is public while the api design says only the engine builds a value. `RunCfg::Err` is no longer read by anything. The `mutant-truncating-append` feature sits in a shipping manifest with nothing stopping an all-features build. The two changelists of round 202611130402 name it 202611130358. `docs/HILAVITKUTIN.md` and `docs/API.md` were not regenerated.

## Changes proposed

1. `run_fused` resets the accumulators at frame start, like the other two entries, and the reset's doc is true for all three.
2. The per-core region of each accumulator starts after the records the leading bands already accepted: core c appends at `len + lo_c`, clipped to the capacity, and the merge compacts from `len` rather than 0. The leading bands' records survive and count. The last regions lose that much room, which the region-skew gap (ticket 9979e2632a6a) already covers, and a region with no room refuses rather than drops. The merged `wanted` saturates.
3. The rule for the accepted records is stated per region: on one thread the accepted records are a prefix of the appends; under `run_parallel` each region keeps its own prefix, so the bytes kept depend on the worker count while the `AccumRefused` value does not.
4. `AccumRefused` is a plain record of two parts; the design stops claiming only the engine can build one.
5. `RunCfg::Err` is removed.
6. The mutant feature refuses to build unless a second, deliberate switch is set for the mutant check.
7. The two changelists name round 202611130402, and the generated documents are regenerated.
