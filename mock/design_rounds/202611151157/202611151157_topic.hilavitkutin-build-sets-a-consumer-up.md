# hilavitkutin-build-sets-a-consumer-up

Op, 15 November 2026: "Also the kaski hilavitkutin-build integration fails and that has to be a hilavitkutin-build error. It should automatically do all the additions and all the proxying and generating the wrapper and all. Why is it not doing any of that automatically"

Op, 15 November 2026, on the per-crate build scripts: "Can't the build script be one instance the other crates just point their build script path to? Why do they manually all repeat shit? Do they differ anywhere? I think a few prototypes each crate chooses between as their build script is the real way this ought to work. Or something even better. Duplicated and disjoint drifting manual shit is exactly what our principles forbid in full"

The intent in the first: a workspace takes `hilavitkutin-build` in one step, and every piece of wiring follows from it with nothing written or kept by hand. In the second: no build script is written or kept per crate; a crate picks one of a few shared prototypes and nothing drifts. The rest of both quotes is the vehicle op sketched, kept for provenance.

## What a consumer does by hand today

A `hilavitkutin-build` build-dependency in each member, spelled as an ssh git dependency because hilavitkutin is private. A `build.rs` in each crate. The wrapper at `.cargo/hilavitkutin-rustc-wrapper`, committed as the text `write_wrapper` writes, made executable, named as `build.rustc-workspace-wrapper` in `.cargo/config.toml`, and held to that text by a test of the consumer's own. hilavitkutin itself does the same: fourteen byte-identical `build.rs` files and `mock/.cargo/`. kaski has twenty-five identical copies of the deterministic script, seven identical copies of its shader build script, and one script, `kaski-sim`'s, that is the deterministic script and a commit stamp together.

The "proxying" in op's words maps to what puts the crate's flags on rustc: cargo runs every workspace rustc through the wrapper. The ssh spelling of the dependency is the other half of what a consumer must get right by hand. Neither consumer has a `[patch]` section for `hilavitkutin-build`, and kaski's arvo proxy is the vector arithmetic stand-in of its workflow canon, unrelated to the build.

## The build script cannot be found by name alone

`build = "../../build/<prototype>.rs"` in a member's manifest builds, and the script reruns only when its directives say (sketch `mock/research/sketches/shared-build-script/`). `cargo package` refuses a build script outside the package, so a crate that is published cannot point there; a `build.rs` symlink to the same file packages with its content. The directive `cargo::rerun-if-changed=build.rs` that `write_directives` writes names a file that a crate pointing at a shared script does not have.

## The vehicle

A crate names the prototype it takes, `[package.metadata.hilavitkutin-build] prototype = "<name>"`, and holds no script of its own: its `build.rs` is a symbolic link to `<mock>/build/<file>`, which packages with the file's content and has no relative path for `#[path]` to break. `default` and `deterministic` are `hilavitkutin-build`'s own prototypes, an enum `Prototype` in the crate, and their files `<mock>/build/hilavitkutin-<name>.rs` are generated from it. Any other name is a prototype the project keeps at `<mock>/build/<name>.rs`, for a script that does more than configure.

A lint pack beside the crate, `hilavitkutin-build-pack`, carries the rest, and a workspace takes it by naming it under `[lint-crates]`. Its maker tool, `mock hilavitkutin-build`, writes everything that follows from the choices: the prototype files, every member's link, the member's build-dependency, the workspace's dependency on `hilavitkutin-build` spelled over ssh, the wrapper at the repository's `.cargo/hilavitkutin-rustc-wrapper` with its executable bit, and `build.rustc-workspace-wrapper` in `.cargo/config.toml`. Its lint holds the tree to the same plan and refuses a build script copied into a crate where a prototype would do. The tool and the lint compute one plan, so what one writes the other accepts.

`write_directives` asks cargo to rerun the script when `RUSTC_WORKSPACE_WRAPPER` changes, the one input it reads that can change between builds of one profile, instead of naming a `build.rs` the crate may not have.
