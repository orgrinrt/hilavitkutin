## What is on this branch that the landing left out

Everything the deprecated source changelist of round `202611131112` claimed under "a swap installs the value" and "the plan band is entered on the first frame or on a plan-dirty bit", and the swap text its doc changelist first carried:

1. `replace_value` and `replace_resource` take the value type and a pointer witness and write the whole value into the slot the build filled.
2. `replace_resource` sets a plan-dirty bit, and `run` and `run_parallel` open the frame on the plan band when it is the first frame or a bit was set.
3. `PlanAffecting` is an open marker on value types, and a type cannot be both plan-affecting and `Replaceable`.
4. The tests that observe all of that, and the test that was ignored on `dev` for want of the install, unignored.
5. The swap cost and swap band benches, whose results are on `dev` already.
6. The swap paragraphs and the swap-method section in the engine's design text, the exclusivity paragraph in the api's, and the corrected method name in the kit's.

The opening of `PlanAffecting` has a ruling of its own, A2-3 of 19 July (`mock/research/seed/governance.md`, item 6; `mock/research/seed/storage.md`, the section on replaceability). It rides here all the same, because on `dev` the swap methods take the store marker and an open marker on value types has nothing to attach to until they take the value.

## What the second reviewer found in the swap itself

Four things, none of which the July round had caught, and all of which this round takes up since the code is open anyway:

1. `run` and `run_parallel` each spell the same block that consumes the plan-dirty bits and publishes the decision. One function should do it.
2. `run_fused` never consumes the bits, so a plan-affecting swap followed by a fused frame leaves its bit standing for the next unfused one.
3. The plan-dirty bit is keyed by the store's position and clamped to the last slot, with a comment saying the signal is never dropped. With a capacity of zero plan-affecting resources there is no last slot and the bit is dropped.
4. The catalogued test for the aliasing of a swap between two parallel frames had a bare `panic!` for a body.

## What the answer changes

The ticket offers four answers. If the specification is ratified as it stands, this branch lands as it is. If it is ratified with changes, the changes are made here first. If it is to wait longer, the branch waits. If the swap is refused, the branch is dropped and the discard on `dev` gets its own design. In none of the four does anything on `dev` have to be taken back out, which is the point of holding it here.
