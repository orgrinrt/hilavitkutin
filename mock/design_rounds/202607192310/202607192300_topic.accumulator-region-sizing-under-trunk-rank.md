# Topic: does an accumulator survive a multi-trunk parallel phase

**Date:** 2026-07-19
**Phase:** TOPIC
**Scope:** the interaction between accumulator region sizing and dispatch ownership in
`run_parallel`.
**Grounded on:** sketch `mock/research/sketches/202607192200_r1-participation-without-record-slices/`,
roadmap r7 R1a.

R1a proposes moving worker participation off the per-core record slice and onto the trunk-rank walk.
Tracing what that costs turned up a constraint the sketch had not seen, and it is worth settling by
experiment rather than by argument.

## The constraint

The accumulator's per-core region is sized from the record slice. `scheduler/mod.rs:970-971` takes
`region = hi - lo` and calls `rebase_accums(lo, region)`. That is sound under record-slice ownership
because a core appends at most once per record and only walks records in `[lo, hi)`, so its region
is exactly large enough. `tests/gate2_accumulator.rs` states the same design in its module doc.

Under trunk-rank ownership the walk is different. The ordinary branch runs `start = 0; while start
< total`, so a core walks **every** record for the trunks it owns. `gate2_accumulator.rs` also notes
that "the plan proved this unit the exclusive appender", so exactly one WU appends to a given
accumulator, it sits in exactly one trunk, and exactly one core owns that trunk. That core would
append up to `total` times into a region of roughly `total / ncores`.

## What is actually unknown

Whether that configuration can occur. The N-way dispatch branch only applies when the phase has a
single trunk (`tphase.0 == 1`). A single-trunk phase is also what canon reserves head+tail
convergence for, and `plan/fiber.rs:118` speaks of "one accumulator slot in a head+tail-eligible
fiber", which suggests accumulators may be confined to that shape by construction.

If they are, the region arithmetic is safe under both ownership models, R1a stays small, and the
N-way region layout is over-provisioned rather than undersized. If they are not, R1a carries a
memory-model change to the accumulator, because every core owning an appending trunk needs a
full-size region.

## Why this is a test and not an argument

Four scope estimates in the current roadmap have been wrong when checked against source, each
because a plausible reading of nearby code substituted for tracing what actually runs. The question
here has a decisive experiment available: put an accumulator WU in a phase with a second,
column-disjoint trunk, run it parallel, and observe. This round builds that and records what
happens, whichever way it goes.

## Out of scope

Changing the region sizing. Changing participation. Both wait on this answer.
