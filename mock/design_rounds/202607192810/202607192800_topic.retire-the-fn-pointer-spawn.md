# Topic: retire the function-pointer spawn

**Date:** 2026-07-19
**Phase:** TOPIC
**Scope:** `OsThreadPool::spawn_fn` and its `trampoline`, `StdThreadPool::spawn_fn`, and the BACKLOG
note that tracks their portability concern.
**Grounded on:** roadmap r7 band 1 item R2b, the spawn-marshalling entry in the audit's duplicate
list, and the D2 fix from round `202607192000`.

The audit listed spawn marshalling among the nine mechanisms with two implementations, noting the
polarity inverts between tiers: "on std the working one is dead and the live one is the no-op". D2
fixed that by making the std tier's generic `spawn` real. The consequence is that the polarity is now
uniform, and it points the other way: `spawn_fn` is the dead half on **both** tiers.

## What each piece is for

`spawn_fn(&self, f: fn())` takes a bare function pointer and smuggles it through `pthread_create`'s
`*mut c_void` argument as a `usize`. `trampoline` (`os.rs:132`) is its entry point and says so in its
own safety comment: "`raw` was produced from a `fn()` pointer in `OsThreadPool::spawn_fn`".

The generic `spawn<F: FnOnce() + Send + 'static>` is separate machinery with its own entry point,
`tramp<F>` (`os.rs:163`). It copies a pointer-sized closure by value into the argument slot, guarded
by `PtrSizedClosure::<F>::CHECK`, a compile-time size and alignment assertion. A closure too fat is a
compile error rather than a heap allocation, which is what keeps the engine path allocation-free.

Neither `spawn_fn` has a caller anywhere in the workspace, tests included.

## The design note the check surfaced

`BACKLOG.md.tmpl:190` carries a portability concern against `spawn_fn`:

> POSIX does not guarantee that `fn*` and `void*` have matching size; all Rust tier-1 targets happen
> to comply in practice, but the threading-std implementation round should switch to `Box<fn()>` or a
> static work-queue slot to be POSIX-clean.

That round has since happened, and it resolved the concern differently from either option the note
proposed. The live path never casts a function pointer: it copies a closure's bytes, and the closure
captures a data pointer. The `fn*`-versus-`void*` parity question does not arise for it, and the
size/align check makes the copy's precondition explicit rather than assumed.

So the note is resolved by supersession, not still open. Deleting the code it tracks without saying
so would leave a reader to conclude the concern was dropped rather than answered.

## Why this needed the check

`spawn_fn` clears the reachability test easily: no callers, tests included. It does not clear the
design-template test, and that is the one that catches things. A deletion that only ran the grep for
callers would have removed a symbol a template still names, and the note would have outlived the code
it describes.

## Out of scope

`tramp<F>` and the generic `spawn`, both live. The `OnceLock` MSRV note directly below in the same
BACKLOG section, which is unrelated.
