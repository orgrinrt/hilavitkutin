# Hilavitkutin engine completion: roadmap draft

This is the engine-completion roadmap of a `chart-the-path` planning routine (workspace skill `chart-the-path`). It maps the ordered steps from the true current engine state to the complete unified canonical engine. It started as the Step 5 draft and has since been through the Step 6 canonical-mirror review and the Step 8 granularity review (both recorded in the step status and the sketch plan below); it is now the finalised roadmap whose unproven steps carry a planned sketch (section 9). It proves nothing by itself: each step is marked PROVEN (with a sketch or bench citation), PARTIAL, or UNPROVEN. The UNPROVEN steps get their sketches written in Step 10, after which each step's finding folds back here. The canonical design is reached in full, not as an MVP.

It descends from three durable artifacts on this branch: the strategic synthesis (`202606060900_engine-completion-strategic-synthesis.md`), the unified-engine canon amendment (`202606061000_canon-amendment-unified-engine.md`, op's authority 2026-06-06), and the build-plan memo (`202605282100_engine-dispatch-build-plan.md`, the A->E spine this re-sequences). The canonical oracle throughout is the consolidation spec `mock/design_rounds/202604200055/202603181200_topic.hilavitkutin-design-consolidation.md`; everything else is intermediate and cross-checked.

## 0. How to read this roadmap

Each step carries a status tag:

- **PROVEN** — a committed sketch or bench already establishes the step's load-bearing premise compiles / devirtualises / runs on the pinned nightly. The citation names it. Implementation still has to happen; the premise is no longer in question.
- **PARTIAL** — shipped code does part of the step; the remainder is mechanical or wiring, with no open feasibility question.
- **UNPROVEN** — the step's premise has not been established with a sketch. It gets a TODO-sketch before its implementation round opens. The highest-risk unproven steps are flagged KEYSTONE.

The canon constraint governs every step: there is no single-core code path. The engine is one machine; core count is a plan-stage configuration parameter (R6, consolidation `:2442-2446`). Where this roadmap says "validate at 1 core," it means run the one engine configured to one core (degenerate barriers, one pool worker, strategy may resolve to sequential), never a separate single-core build. N>1 paths are written once and degenerate at N=1.

## 2. The spine, re-sequenced

The build-plan memo's A->E order holds for what remains, but A/B are done, so the work is C -> D -> E, plus a build-time layer F sequenced for benching. The canon collapses the memo's "single-core path, then parallel path" within E into one engine validated at 1 core then N cores. The dispatch shape (D) is fixed by canon to the unified per-core program; the memo's Phase D under-specified this (it assumed the FiberShape local-slice without reconciling the later cons-list-walk sketches, now settled: the per-core program is the only shape, the cons-list walk is an internal fiber-walk vehicle, not a separate dispatch).

Order: **C (complete the plan) -> D (the dispatch keystone) -> E (concurrency, degenerate-at-1-core then real-at-N, then adapt) -> F (build-time LLVM flag layer, for benching).** Within each, steps are ordered by dependency.

## 3. Phase C: complete the plan algorithm chain

### C5. Block-diagonal + Dulmage-Mendelsohn (consolidation Step 6, always run). UNPROVEN (SPLIT into C5a/C5b).
The consolidation spec makes block-diagonal + D-M a mandatory always-run plan step (`:1048-1049`, `:1349-1371`): block-diagonal detects phase structure, D-M refines it into horizontal/vertical/square components, giving phase validation, dead-end WU detection, and dead column elimination (`:1357-1367`). The dead-column-elimination output reduces the column count fed to the morsel budget (C8) and the fusion classification (C7). Today `block_diagonalise` is a structural-only stub returning `Bool::TRUE`. (Omitted from the prior draft; surfaced by the canonical-mirror review.) The granularity review split it into two distinct failure modes:

- **C5a. Block-diagonal wiring + non-trivial phase detection. PROVEN, sketch 202606061800.** `arvo_sparse::block_diagonal` returns a block_count tracking connected components: the connected diamond is 1 block; two independent fibers (0->1, 2->3) are 2 blocks (per-node IDs co-block {0,1} and {2,3} distinctly); three isolates are 3 blocks. Block detection distinguishes independent components (the trunk skeletons C6 forms) on real shapes, and the block-structure-keyed feasibility-error paths become reachable. The engine's `block_diagonalise` (plan/steps.rs:335, currently a `Bool::TRUE` stub) wraps this over the DependencyGraph via the to_csr_bidirectional adapter; the signal was available all along. Residual: the exact PlanError wiring (mechanical) and the block-diagonal-vs-D-M division of labor (block_diagonal = components/trunks, D-M = column classes per C5b), both engine wiring not feasibility questions.
- **C5b. D-M decomposition + Input/Output/Internal mapping. PROVEN, sketch 202606061700.** `dulmage_mendelsohn` produces a NON-TRIVIAL decomposition on the real gate workloads: the diamond (BranchX, BranchY -> JoinZ -> NormW) classifies as 2 sources (vertical) + 1 core (square) + 1 sink (horizontal), 3 distinct classes used; the linear accumulator gate (S1 -> Tally) as source + sink, 2 classes; an isolated node as vertical only, 1 class (negative control: D-M genuinely collapses on a trivial graph, so the non-trivial results are real, not an always-3 artifact, `class_count` is always 3 but distinct-USED varies 1/2/3). The node classes map to columns: source-read-from-outside = Input, source/core writes consumed downstream = Internal, sink writes drained = Output. The diamond yields 1 Input + 3 Internal + 1 Output. The load-bearing RISK (every workload collapses to all-square, making C7 a no-op and D4 vacuous) is REFUTED: there is a real Internal set for D4's fusion (proven 2.09x, 202606061600). The fusion path is unblocked end to end. Residual: the exact node-class -> column-class mapping algorithm in C7 (reasoned, mechanical) and C5a (block_diagonal wiring), neither an open feasibility question now.

## 4. Phase D: the dispatch keystone (the unified per-core program)

This is where the muddle was and where the canon now fixes the shape. The canonical per-core program (domain 17, `:1596-1613`) is a monomorphised function per core encoding its phases, record ranges, per-fiber devirtualised LOCAL `&[WuFn]` slices, compile-time morsel constants, and phase sync points. One shape for all core counts; one core = one program with degenerate sync. The keystone is the bridge from the runtime-computed plan (C) to this compile-time-known per-core program.

### D1. KEYSTONE: the runtime-plan -> compile-time PER-CORE PROGRAM bridge. UNPROVEN (highest risk; SPLIT into D1a/D1b/D1c).
The canonical primitive is the per-core compiled program (domain 17, `:1596-1613`): a monomorphised function per physical core encoding its phases, record ranges, per-fiber devirtualised LOCAL `&[WuFn]` slices, morsel constants, and phase sync points. The keystone is the bridge from the runtime-computed plan (C) to that per-core program. The per-fiber local slice is ONE COMPONENT baked into the per-core function, not the architectural unit (canonical-mirror correction: the prior draft over-centred on a per-fiber `FiberShape` and risked treating the fiber, not the core, as the dispatch primitive). The granularity review split this into three orthogonal feasibility risks, each with its own sketch:

- **D1b. Type-level per-fiber partition from `AccessSet` cons-lists, no GCE (Gate-2 shape). RESOLVED, sketch 202606061400 (clean accept, NOT drift).** The keystone question is settled, after a two-stage review (neutral `feature-dev:code-architect` consensus + an op-persona simulation that pushed back and forced a deeper pass). ### D4. The fusion half: scratch-backed internal columns that DSE eliminates to registers. PROVEN (decisive), sketch 202606061600.
This is what moves the #664 perf gate green. The decisive two-variant experiment (In->Av->Bv, Av internal, real engine columns + EngineCtx): variant A (unfused, Av a real arena column, S1->S2 two WUs each owning its `each` loop) objdumps 2 stores + 3 loads with Av ROUND-TRIPPING the arena, 0.173 ns/rec; variant C (fused, av a LOCAL, one WU S12) objdumps 1 store + 1 load with Av ELIMINATED (no Av memory traffic), 0.083 ns/rec. A/C = 2.09x, squarely in the #664 red band (~2.1x-4.6x, memory-bandwidth signature). Both devirtualise (0 blr). LLVM does NOT auto-fuse A into C (the round-trip survives across the two separate each-loops + arena pointer), so register residency is an ENGINE codegen decision: fuse a fiber's internal-column-linked WUs so the intermediate flows as a value, drop the Internal column. Keyed by C7's Internal classification; matches canonical domain 17 ("DSE + stores-at-end: the flattener emits the optimal loop body", :1609) and D1b's flattener-emits resolution. The bar (register residency) is met; the target shape compiles, devirtualises, and wins 2x. Residual: the mechanical auto-fusion of two consumer WUs into one fused body at codegen is an implementation task (the flattener emit job), not an open feasibility question.

## 5. Phase E: concurrency runtime, degenerate-at-1-core then real-at-N, then adapt

Per canon, this is ONE runtime that degenerates at 1 core, not a single-core path plus a parallel path. The validation milestones map to the two gates: Gate 1 = the unified engine runs correctly and benches at parity configured to 1 core (real plan, per-core-program dispatch, pool with one worker, degenerate barriers, strategy may be sequential, adapt present); Gate 2 = the same engine benches well at N cores (barriers, convergence, multi-worker distribution doing real work).

### E1. `Scheduler::run` walks phases with real morsel loops and real `RecordRange`s. PARTIAL.
Replace `RecordRange::Full` in `synthesise_core_programs` with computed half-open ranges from the morsel-size formula (C7). Get the version-stamp / poison error model right here. At 1 core this is the whole schedule on core 0 with degenerate sync; the SAME code runs the N-core distribution. Depends on D (the per-core program) being real. Bench-validate at 1 core = Gate 1.

### E2. Spawn-once parking pool mainloop. PROVEN (the model, by bench).
Workers spawn at `build()` through `ThreadPoolApi`, run a mainloop: wait on a per-worker `PoolFrame` generation atomic, on wake walk phases, arrive at `phase_barrier_arrive`, last arriver resets and `atomic_wake_all`, else `pick_tier(predicted_wait_ns)`, park at frame end. The spawn-once-park model is bench-established (phased-pool 0.68x across 2K-1M records vs spawn 15.54x at 200 records, synthesis section 4). At 1 core the pool has one worker that never waits on peers (degenerate). The mainloop wiring is the implementation; the model is proven.

### E3. Barrier generation/sense-bit fix (R4). PARTIAL.
Add a phase generation / sense bit; arrivers wait on `generation != my_generation`, not on the counter hitting zero (else a fast worker races the reset). Re-check after every possibly-spurious wake. At 1 core the barrier has one arriver (degenerate, no race); the fix matters at N>1. Known fix, no feasibility question.

### E4. Phase pipelining via progress counters, meta-WU firing. PROVEN, sketch 202606062100.
A frame loop over the real two-phase dispatch fires the four canonical meta-WU markers (PlanStage, ScheduleReady, PassStart, ScheduleEnd, run_cfg.rs) in canonical order: frame 0 (plan_dirty) fires the full PlanStage->ScheduleReady->PassStart->ScheduleEnd; reuse frames fire only PassStart->ScheduleEnd (schedule-once / reuse-across-frames canon, plan-dirty-gated). Phase pipelining via an AtomicUsize progress counter integrates: phase 0 publishes per-morsel progress (Release), phase 1's consume bound is the published progress (Acquire); the gate reached all morsels each frame, Bv correct. The self-hosting meta pipeline is feasible (the proven 202605101036 atomic shape wired into the frame loop). Residual: real multi-core overlap needs the pool mainloop (E2, bench-proven) + barrier (D1c/E3); Virtual<AnomalyFired> from AdaptWu at ScheduleEnd is E8. Neither an open feasibility question.
Fire the four meta-WorkUnits (`PlanStage` on `plan_dirty`, `ScheduleReady` after plan WUs, `PassStart` at frame top, `ScheduleEnd` after the last consumer phase). Phase pipelining via progress counters (an early sketch exists: 202605101036-progress-counter-arena). Unproven as an integrated whole against the real dispatch; the pieces are designed (build-plan Phase E) and partially sketched.

### E4b. Head+tail convergence (commutative-fiber bidirectional processing). PROVEN, sketch 202606062200.
Two cores claim records from opposite ends via a packed (low, high) cursor CAS protocol; across 50 racing rounds every record processed EXACTLY once (no overlap, no gap), all values correct, head+tail claimed exactly n total. The CAS makes the last-element contention race-free. Head+tail convergence (domain 20 :1838-1844) within a commutative fiber works at 2 cores; each core carries a baked end-designation (the per-core record-range field, domain 17 item 2, on the D1b carrier + D1c barrier already proven). At 1 core it degenerates to one range. Residual: integration into the spawn-once pool mainloop (E2, bench-proven) and engine-side range baking from the plan; the convergence PROTOCOL itself is proven correct + race-free. (Original UNPROVEN/depends-on-D1b note retained below; D1b is proven, dependency satisfied.)
Per domain 20 (`:1838-1844`): within any commutative fiber, two cores process records from opposite ends and converge. This is not just runtime behavior; the per-core compiled program must bake each core's record range as the head or tail half (domain 17 item 2, `:1603`), so D1's per-core program and E's runtime both carry it. The granularity review pinned the dependency: E4b requires the per-core program to carry a head/tail designation baked from the plan, which is the Gate-2 multi-core extension of D1b, so E4b is unblocked by D1b, not merely by "D real." At 1 core there is one range (no convergence; degenerate). Surfaced by the canonical-mirror review as an omission buried inside the prior E4.

### E5. Heterogeneous core awareness (P-core/E-core asymmetric assignment). UNPROVEN (SPLIT into E5a/E5b).
Per domain 20 (`:1810-1822`): detect core types at startup (P-cores, E-cores), thread count = `min(physical_cores, parallelisable_width + 1)`; critical-path trunks to P-cores, leaf/branch fibers to E-cores; P-cores get larger morsels, E-cores proportionally smaller (E-cores at ~40% P-core speed drag down equal distribution). This is the morsel-to-core affinity adaptive parameter (R6) made real. At 1 core it is degenerate (one core, one range). Surfaced by the canonical-mirror review as an omission; the granularity review split it:

- **E5a. P/E core-type detection. PROVEN, sketch 202606062300.** The macOS aarch64 probe reads `hw.nperflevels` (2) and `hw.perflevelN.logicalcpu` (4 P + 4 E) via `sysctlbyname`, classifies 4 P-cores (level 0) + 4 E-cores (level 1), P + E partitioning the 8 logical cores. Graceful-degrade contract holds: a single-level topology reports homogeneous (is_heterogeneous=false, e_cores=0, p_cores=total), the path non-heterogeneous / unknown hardware takes. The probe is a cfg(target_os=macos, target_arch=aarch64) platform/ hook (FFI = the documented platform-hook exception), with sibling hooks for Linux (cpufreq/devicetree) and x86 hybrid (CPUID 0x1A), all degrading to one tier when no signal exists. Residual: the Linux/x86 sibling probes (same contract, not this target) and the affinity ASSIGNMENT consuming the topology (plan-stage R6 policy, benched in E5b). Detection proven.
- **E5b. Asymmetric morsel sizing. PROVEN (Kind-2 bench), sketch 202606062400.** Proportional-to-speed record distribution lowers makespan ~1.81x vs equal distribution under simulated P/E heterogeneity (4 P-threads @ 64 iters/rec + 4 E-threads @ 192 = 3x slower, ~1M records). Equal split is bounded by the slow E-cores draining an oversized share; proportional finishes all cores together. Both cover all records once (correctness trivial, asserted). The Kind-2 fork resolves: weight shares by E5a-detected core speeds (R6 morsel-to-core affinity). macOS can't pin to P/E cores, so heterogeneity is modeled with a per-record work multiplier; the DIRECTION (proportional beats equal) is settled, the ABSOLUTE on-core delta belongs on pinned hardware / the #664 suite once the pool is real.

### E6. Validate parallel against the 1-core configuration (same `Cfg::Out` for any core count). PROVEN, sketch 202606062500.
The canon makes the 1-core configuration the correctness oracle the N-core configuration validates against: same engine, same plan algorithms, same `Cfg::Out` for any core count. This is a test/bench discipline step, not new code: run the same pipeline at 1/2/7 cores, assert identical output. Gate 2 = N-core benches well.

### E7. Dirty propagation -> incremental skip (consolidation Step 9, always-run runtime pass). PROVEN, sketch 202606062600.
Per consolidation Step 9 (`:1418-1429`): a runtime dirty-bit propagation pass (`predecessors[N] & dirty_mask`, arvo-bitmask, `:191-194`) skips clean WUs, turning the pipeline from a batch processor (re-run everything) into an incremental processor (`:864`, `:1429`). The plan already computes dirty masks at plan time (`compute_upward_rank_and_dirty`); this is the per-frame runtime consumption that skips clean WUs. Fires within the frame walk (E1) and is gated by the meta-WU loop (E4). Same at any core count. Surfaced by the canonical-mirror review as an omitted runtime step; relates to #345 (plan caching). Unproven against the real dispatch.

### E8. Adapt: observe/tune bodies with hysteresis (R5). PROVEN, sketch 202606062700.
Give each `AdaptAxis` an `observe` body folding `(ema*7 + measured) >> 3`, gated by `sample_skip`, comparing thresholds to trigger morsel re-size / per-phase config re-select / full re-plan. All adapt decisions fire between frames at `ScheduleEnd`. Add hysteresis (K-consecutive crossing, dead-band, per-trigger cooldown; re-plans rate-limited hardest) to prevent oscillation. EMA vectorisation has an early sketch (202605101036-ema-vectorisation). Adapt is the same at any core count (a plan-stage parameter tuner). Lands last.

## 6.5 Unavoidable drift and resolved non-drift

Per the chart-the-path routine, drift that may be forced for the implementation to work at all is recorded explicitly, mirrored against the canonical statement it diverges from. Two items, one genuine, one challenged and resolved as NOT drift:

- **D1 / GCE boundary (RESOLVED 2026-06-06, NOT drift; sketch 202606061400).** The conditional resolved cleanly. The question was whether the per-fiber partition feeding the per-core program is type-derived or carried. Empirically (sketch 202606061400, Tiers 1-4 + vetted-feature retries + `group_fibers` cross-check): the dispatch-structure CARRIER is type-level and devirtualises to zero `blr` (Tier 1), but the GROUPING DERIVATION is not type-level-expressible (Tier 3/4 wall on negative trait reasoning across `specialization`/`min_specialization`/`negative_impls`; and the shipped `group_fibers` boundary is a runtime out-degree/topo/spectral graph algorithm, not a pairwise predicate). The canonical domain 17 (`:1566`, `:1732-1733`) says the grouping is plan-computed and the codegen flattener EMITS the carrier "derived from the WU declarations' Read/Write sets", i.e. carry/emit, not trait-solver-derive. So the realization (flattener emits the type-level flat carrier from the runtime grouping) IS the canonical mechanism, NOT a deviation. The synthesis 2.4 "build time = the type system" hope was a hypothesis flagged there as the biggest open question; it is refuted for the grouping and confirmed for the carrier. No GCE involved at all (the blocker was negative reasoning, which GCE does not address). Neither a Step-11 escalation nor a drift record is needed; the keystone bridge (runtime order -> compile-time flat carrier) is the D1a sketch, not a drift.
- **E2 no_std parking (challenged, NOT drift).** The canonical-mirror review flagged `thread::park` (spec `:1801-1803`) as requiring `std`, forcing drift in the no_std engine. Verified against the spec directly: `:917` lists `pause + futex` as the DAY-ONE worker-parking mechanism at the ISA level, and the shipped `parking.rs` already implements raw futex / `__ulock_wait2` / `WaitOnAddress` in no_std. So the no_std parking is canonical-consistent, not drift; `thread::park` is the std-tier convenience the spec names alongside the ISA-level futex it actually mandates. The only residual is the no-OS (bare embedded) tier, which degrades to `spin_loop`; the spec already accounts for tiered targets (polka-dots is a sequential-only tier). Recorded here so a later reader does not re-introduce this as a blocking concern.
