# The asm gate over the engine's dispatch, and what it found about itself

Written 13 November 2026, over `mock/benches/src/bin/asm_gate.rs`, `mock/benches/src/disasm.rs`, `mock/benches/src/disasm_5check.rs` and `mock/benches/asm_gate_fixtures/`. The artifact is `mock/benches/asm_gate_fixtures/asm_gate_report.md`, written by the gate and regenerated byte-identical by `asm_gate --check`.

Two documents rest on the five-check gate without naming any output of it. The execution-model topic says all 26 chain dispatch functions of the bench of its day pass all five checks (`design_rounds/202604200055/202603171900_topic.execution-model.md:170-179`), and the GATE-2 deviation note says the gate passed fresh, with zero indirect calls in every dispatch body (`research/202607202200_gate2-deviation-2-evidence.md:20-27`). Neither names a report, and none was committed anywhere under `mock/benches/`. This note is the run the second claim should have pointed at, made on an x86_64 Linux container, and the report it cites is committed beside the fixtures.

Running it showed that, on this platform, the gate as it stood could not have produced either claim. It asked objdump for one symbol with `--disassemble-symbols=`, which is llvm-objdump's spelling; GNU objdump refuses it, so every target came back undisassemblable and the run failed before checking anything. Past that, check 1 matched `\tcall\t*` and `\tcallq\t*`, while GNU objdump pads the mnemonic with spaces (`call   *%rax`), so it would have counted zero indirect calls in any x86_64 body at all. Checks 2 and 3 matched Intel operand forms (`ptr [`, `[rsp,`) where objdump's default is AT&T, and check 4 looked for `, 256` where AT&T writes `$0x100`. The aarch64 forms (`blr`, `[sp,`, `#256`) were right, so a run on an aarch64 machine with llvm-objdump could have been real; which machine the deviation note's run was on is not recorded.

## What changed

`src/disasm.rs` owns reading and parsing. `disassemble` tries GNU's `--disassemble=` and llvm's `--disassemble-symbols=`, with and without the Mach-O underscore, and accepts a result only when the symbol's own header came back. `Insn::parse` splits an objdump line into mnemonic, operands and trailing comment for GNU and llvm output on x86_64 and aarch64, and the five checks read those fields instead of substrings of lines.

Check 1 now separates the two kinds of indirect call a release cdylib really has. A call through a GOT slot of an import (`call *off(%rip)  # <memset@GLIBC_2.2.5>`, or through a register that slot was loaded into and copied between) is the dynamic linker's and is reported, not counted. Everything else is a target the body read from data, which is what the check refuses. The tracking forgets a register on any write to it or to a narrower part of it (`%r13d` is `%r13`), and forgets the caller-saved registers across a call, so where it is unsure it counts the call.

The gate builds the fixtures through `mock/benches/stage.sh`, so it reads its own build and not whatever another worktree last linked into the shared target directory. It scans three kinds of target: the seven fixture wrappers, the out-of-line `Scheduler::run` and `run_fused` monos, and the `run_parallel` worker body. The worker body is std's `__rust_begin_short_backtrace` instantiated over `run_parallel`'s own closure, into which `worker_main` and `run_core_phase` inline. That closes FIXME 35e2aa2b5329, under which fixture 7 checked only the scheduler side of the parallel path.

Two refusals keep the gate honest about itself. The new fixture `asm_gate_control_stored_pointer` calls through a function pointer hidden by `black_box`, and the run fails if check 1 passes it. The run also fails if the parallel fixture is present and no worker body was found.

## What the run shows

Over the build recorded in the report (x86_64, `rustc 1.98.0-nightly (57d06900f 2026-05-27)`, GNU objdump 2.42), check 1 passes all nine engine bodies and fails the control at one call. The fixture wrappers carry between 6 and 47 import calls each through the GOT (`memset`, `memcpy`, `malloc`, `free`, `syscall` for the futex waits, `clock_gettime`), and the worker body 17.

The parallel wrapper first failed at seven calls through stored pointers, and all seven were std's, not the engine's. Three walked a table at `0x64698` whose relocations name `std::sys::thread::unix::cgroups::quota_v1::{closure#0}`, `{closure#1}` and `find_mountpoint`: that is `available_parallelism`, inlined from the bench executor's constructor. The other four were `io::Error` drops through their vtables on the same path. Fixture 7 now builds its executor and spawns through `OutOfLineSpawn`, whose constructor and `spawn` are kept out of line, so the wrapper holds the scheduler side of `run_parallel` and the readback, and passes. That the classifier found a three-entry function-pointer table inside a body it had first been handed is the best evidence it is not blind.

Checks 2, 4 and 5 now read real instructions: indexed addressing and the baked 256 appear in every engine body except the column-chain and dirty-gated wrappers, whose dispatch sits in the out-of-line `Scheduler::run` mono that has both, and no body makes a direct call to a morsel, fiber or unit helper. Check 3 fails every body, because it counts every stack-relative access in the symbol, prologue and spills of the surrounding code included, and never locates the inner loop; it says nothing in its present form (ticket 42eb704cf306).

## What the claims can lean on now

holds for: target x86_64, profile release with fat LTO and one codegen unit, the toolchain and disassembler named in the report, the seven fixture shapes at N = 256.

Within that, zero indirect calls through a stored pointer in every engine dispatch body the fixtures emit, single-core and parallel, is a committed result with a control shown failing. The 26-chain claim of the execution-model topic is about a bench of its day that this gate does not build, and stays without an artifact; it is not this run's to vouch for. An aarch64 run of the same gate would extend the predicate and is the obvious next datum.
