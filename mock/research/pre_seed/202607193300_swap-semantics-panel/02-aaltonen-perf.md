# Swap semantics panel, memo 2: cost shapes and cache behaviour

**Date:** 2026-07-19
**Author:** Sebastian Aaltonen (lens: data-oriented performance, cost shapes, what is decided by structure versus what needs a profiler)
**Scope:** the same `replace_value` / `replace_resource` surface memo 01 covered, read from the machine's side: what the swap write costs, what the collection path costs, what the plan-recompute band costs, and which of memo 01's forks are actually performance questions in disguise.

Arntzen's memo establishes the write path correctly and I have nothing to add on the soundness half. What I add is the cost model underneath it, because "sound" and "correct" say nothing about whether a swap is a memcpy of 40 bytes or a multi-kilobyte structural recompute, and the spec needs to name both.

## 1. Decided by structure (no bench needed)

**The whole-blob write is a single, small, in-place store. There is no alternative shape to bench.** At the sizes named in the brief (a few scalars to a few hundred bytes plus const-sized `Field` members), the write is one to a few cache lines. A `ptr::write` through the `Selector` witness (mirroring `engine_ctx.rs:733`'s `ptr::read`) compiles to a `memcpy` that the optimiser inlines to a handful of stores for anything under 64 bytes, and to a `rep movsb`-class loop for larger blobs, still single-digit nanoseconds either way. There is no competing write shape (member-by-member copy into per-leaf slots, which the shipped FIXME at `scheduler/mod.rs:1235` gestures at, does not exist as a layout: the storage addendum killed per-member columns outright, lines 18 to 28). A fork needs at least two candidate shapes to be bench-worthy. Here there is one, so this is structural, not an experiment.

**Old-value drop is free because there is nothing to drop.** `T: ColumnValue` is `Copy` (`engine_ctx.rs:717`), so the old bytes are simply overwritten. No destructor call, no branch on a drop flag. This closes off an entire class of swap-cost concern (a `Drop`-bearing resource would force a read-modify-drop-write sequence; `ColumnValue` forecloses it by contract).

**The scalar-snapshot discipline is perf-neutral to a swap by construction, not by luck.** The snapshot (`engine_ctx.rs:733-740`, `Project` impl) runs once per morsel loop entry, reading whatever the blob currently holds at that instant. A swap that lands between frames changes what the *next* snapshot reads; it cannot interact with an in-flight snapshot because no snapshot is in flight between frames (workers parked, per memo 01 section 1). So the swap's cost is exactly the write itself, once, with zero interaction with the hoist mechanism. The addendum's own finding (section 5, "wall-clock-neutral on M1... free insurance on any uarch where it is not") already establishes the snapshot's steady-state cost; a swap does not add a second snapshot cost, it just changes the value the next one reads.

**A collection member's swap keeping the base pointer fixed is a structural requirement, not a policy that could go either way.** `Seq<T, N: Cap>` columns are sized once at plan time (schedule-once-reuse) and never resized. A swap that wrote a different base pointer would either alias a foreign region (unsound, memo 01 item 4) or force a reallocation the schedule-once model forbids. So the only shape on the table is "write up to N' elements into the existing region, update length": there is no second candidate to bench against. What IS bench-shaped is the *cost of that write* at realistic N (below).

## 2. Bench-decided forks

**Bench D (memo 01 origin, storage addendum section 4, expert-perf memo section 2) needs restating for the swap spec, not redesigning.** As written it measures "per-morsel fetch cost vs per-record, and resize/replace cost." For the swap spec specifically, restate the replace arm as: write M' elements (M' ranging from a handful up to the full `Cap` bound) into an existing `Seq<T, N>` region between frames, then measure the next frame's first-touch cost of those elements under live-streaming. Two things matter that the original framing does not separate:

1. **The write itself.** At swap time, this is a linear write of M' * sizeof(T) bytes into already-resident, already-cache-warm memory (it was live-streamed last frame if anything read it). For M' in the tens to low hundreds of elements and T at a few bytes to a few dozen bytes, this sits comfortably inside a single L1 fill's worth of write traffic and should not be a story of its own; the real cost is whichever of the two arms below wins.
2. **The next-frame read-back.** Live-streaming means the collection is walked fresh from the column each morsel (bench-decided in the addendum, axis D: stream beats copy 2.5x past 64 MiB, parity below ~4 MiB). A swap invalidates nothing about that path structurally; it just means the values streamed are the new ones. The open question is whether the swap write itself, happening once between frames, shows up as a measurable blip in the *next* frame's morsel timing versus a frame with no swap, because it is a cold write into what may otherwise be steady-state warm memory. That is a real, small, measurable effect and worth one arm.

**Bench arm, Swap-D: cold-write-then-stream.** Inputs: a `Resource<T>` carrying a `Seq<U, N>` member, N swept at 16, 64, 256 (below, at, and above one L1 line's worth of U), U at 4, 16, 64 bytes. Two conditions per N/U pair: (baseline) frame K reads the collection with no swap since frame K-1; (swap) frame K-1 ends with a `replace_value` writing M' = N/2 elements, frame K reads. Measured: wall-clock of frame K's read-and-consume of the collection, both conditions, plus a cache-miss counter if the harness supports it (perf stat, or the disasm-line-count proxy used elsewhere in the bench pack). Signal: if the swap condition regresses more than roughly 10 to 15 percent versus baseline at any N/U pair, the spec needs to name a per-swap write-then-read cache warm-up cost as a named budget line, because it means the write is evicting lines the read then re-fetches (a real effect for large N * sizeof(U) crossing L1/L2 boundaries, per the storage addendum's own 64 MiB cliff, scaled down here to per-morsel granularity). If it does not regress, the write-budget morsel formula's write_resource_collection_sizes term already accounts for the traffic and no separate swap budget is needed.

**Whether a mutable write accessor into a collection column exists (memo 01 fork 2) has a perf half worth naming even though it is primarily a design/soundness fork.** If the eventual write-back path (the `engine_ctx.rs:722` FIXME, #344) routes collection writes through the same per-morsel Context accessor a WU uses mid-frame, versus a dedicated swap-only path that writes directly to the column outside any morsel windowing, the two shapes have different cost profiles: the WU-accessor path pays whatever per-access overhead the Context machinery carries (likely negligible, monomorphised, no vtable), while a direct swap-only path is a raw pointer write with none of that overhead. Given swaps are between-frame and infrequent relative to per-morsel reads, this fork is low-stakes: even a "worse" shape here is one write per swap, not one write per morsel. I would not spend bench budget on it until #344 lands a concrete write-back shape to measure; naming it now just flags it is not a zero-cost design question either.

## 3. Engagement with memo 01

Arntzen's soundness read of the write path (item 1, `Selector`-witnessed whole-blob write) is exactly the shape the cost model above assumes; I have no correction, only the added observation that this shape is also the *fast* shape; the sound path and the fast path coincide here because there was only ever one candidate layout once the storage addendum killed per-member decomposition. That is worth stating plainly: this is a case where "soundness forced the design" and "performance forced the design" land on the identical answer, which is the strongest kind of decided-by-structure claim a spec can make.

On item 3 (the plan-dirty wiring gap): memo 01 correctly identifies that `run()` reads `self.plan_dirty` only to suppress a warning (`:1394`) and that `replace_resource` never sets a bit in it (`:1217-1221`). From the perf side, this gap has a cost-shape consequence worth naming as a budget: **the plan recompute band, once wired, is not "cheap and can fire on every swap without a care."** `run()`'s `plan_dirty` gate (`:1416-1420`) decides whether dispatch starts at phase 0 (the plan band) or skips straight to `plan_phase_count`, meaning a plan-dirty frame runs the entire leading plan band (`OnMeta<PlanStage>` units), not a localised patch. That is categorically more expensive than the store-dirty cone re-run `replace_value` triggers (`mark_dirty` seeds only the units whose read set intersects the changed store, propagated forward over the topo-ordered carrier, `dirty_units()` around `:1284`). The doc comment memo 01 cites (per-frame swaps of app state via `replace_value` being typical) is exactly the case that must never hit the plan band; `replace_resource` swaps of `PlanAffecting` types must be rare relative to frame rate, or the plan-recompute cost dominates the frame budget. The spec should state this as an explicit asymmetry, not just a mechanism gap: `replace_value` is O(dirty cone), `replace_resource` is O(whole plan band), and a caller doing the latter every frame has misused the API regardless of correctness.

On item 2, the double-impl fork (`PlanAffecting` + `Replaceable` on one type): this is a pure soundness/API-shape question, not a perf fork. I defer to memo 01 and have nothing to add; whichever mechanism forecloses it (supertrait, negative_impls, lint) costs nothing at runtime either way, since it is a compile-time constraint.

## 4. Budgets the spec should state

1. **Swap write cost**: bounded by the resource's static size (scalars plus collection ptr+len view); no per-call variable cost beyond the blob size itself. No budget number needed beyond "O(sizeof(T))", because the blob size is const and known at plan time.
2. **Collection-member swap cost**: O(M') where M' is the element count written, plus the Swap-D cache-warmth effect if the bench above finds one. If found, name it as a per-swap write-collection budget the write_resource_collection_sizes formula term should absorb (it already counts the collection bytes toward the morsel write budget; the open question is only whether a swap's write-then-immediate-read pattern needs a separate accounting line or rides the existing term).
3. **`replace_resource` plan-recompute cost**: O(plan band size), stated explicitly as strictly more expensive than a store-dirty cone re-run, with a named caller expectation ("swap `PlanAffecting` resources rarely relative to frame rate; every-frame `PlanAffecting` swaps are a design smell, not a supported hot path"). `replace_value` carries no equivalent warning; it is the cheap, expected-every-frame path per its own doc comment.
4. **No budget needed for the scalar-snapshot interaction**: it is perf-neutral to swaps by construction (section 1), so the spec states this as a fact, not a number to measure.
