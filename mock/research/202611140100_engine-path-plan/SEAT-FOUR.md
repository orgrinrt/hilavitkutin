## The arms

Arm (a), one core for a non-commutative carrier at every worker count. Ratified canon says this in three places. `tenet::ordering_is_guaranteed_by_construction` (ratified, `ratified_from` consolidation spec `:604-607`): "a non-commutative fiber runs on a single core and is trivially ordered ... no lineariser or other ordering mechanism is needed." `tenet::a_unit_declares_whether_it_is_commutative` (ratified, `:597-602`): commutative fibers are eligible for multi-core morsel dispatch, non-commutative are "processed in a single direction only". `tenet::a_fiber_is_commutative_only_if_all_its_units_are_and_resource_accumulation_uses_per_thread_accumulators_merged_after` (ratified, `:1171-1176`): a fiber is commutative only if all its units are. Plus `tenet::each_convergence_thread_accumulates_into_its_own_stack_local_resource_and_non_commutative_accumulation_runs_sequentially` (ratified) and `tenet::records_within_a_fiber_are_independent` (ratified) for the accumulation exception. Caveat on standing: all of these are ratified "by default from the written history and not by a walk" under op's 2026-11-13 words, so they are ratified by op's blanket instruction, not by op reading them. They still govern.

Arm (b), tiling for every carrier because the merge keeps record sequence. The only canon for it is `tenet::each_core_appends_into_its_own_region_of_an_accumulator_and_the_main_thread_merges_the_regions_in_order`, which is provisional, stamped, with `written_by` "the text does not say whose it is". It says the N-way regioning "is what the design asks for on the accumulator" and says nothing about commutativity either way. A provisional row binds as best current statement and may not override a ratified row; where they meet, the ratified rows win, because the provisional row is silent on the gate and the ratified ones are explicit. The "record sequence" premise is also weaker than the row says (see Findings: unit-outer interleave).

Arm (c), nothing until the measurement returns. Op's words are the highest rung and they say the code stays. But the measurement compares walk shapes on single-trunk workloads. A commutativity gate on the accumulator carrier does not choose between head-and-tail and N-way; both candidates the bench compares sit behind the gate anyway (`tenet::a_single_trunk_phase_runs_head_and_tail_convergence_with_two_threads_from_opposite_ends`, ratified: "Skip for non-commutative resource accumulation"). So the gate is neither input nor output of that bench. Whether "the code stays" still freezes it is the ambiguity above. `tenet::a_non_canonical_mechanism_is_not_kept_because_it_beats_nothing_and_single_trunk_phases_run_serially_until_head_and_tail_is_built` (provisional, agent-written) points the other way for the phase loop and is not about accumulators.

Arm (d), something else: the gate is per carrier, not per accumulator-writing unit. The ratified row defines commutativity of a fiber as all units, and every unit of the carrier is re-run on every core's slice. A non-commutative unit that never appends (a scan, a neighbour read) is broken by slicing just as an appender is. So the gate has to read every unit in the carrier, which the plan already holds (`unit_meta.commutative`).

## My answer

The canon owes arm (a), per carrier: any non-commutative unit in the carrier sends the whole carrier to one core, at every worker count including 1 (where it is already true). Arm (b) rests on a provisional row that says nothing on the gate; it contradicts three ratified rows by omission. On timing I do not decide (c); I say what is separable. The failing test can land now and costs no code change, so op's "code stays" is not touched. The repair is a one-predicate change in `carrier_unit_outer`'s caller at `worker.rs:107` and `run_parallel.rs:253,326`, and whether op's freeze covers it is op's call. If op says it is frozen, the red test stays red and is recorded as known-red, not bent green.

Consequence to expect loudly: the default is `FALSE`, so every unit that has not declared `COMMUTATIVE` drops its carrier to one core. Existing multi-worker accumulator tests with default units will go red or silently single-core. I did not read those tests; that is the first thing to inspect before a repair.

## What commutative has to mean for (a) to be well defined

Of a unit: the declared flag (`work_unit.rs:84`), meaning the unit's effects over a record range are independent of the order of records and of which core does which range. Of a fiber: all units (ratified row above). Of a carrier: all fibers, which is the gate arm (a) needs and canon does not name; canon speaks of fibers and the carrier is the tiling's grain (the tiling slices the whole carrier, `worker.rs:228-251`). So the carrier predicate is an AND over fibers and must be stated before it is coded; the canon is silent on the word "carrier". Of an append: appends into one accumulator by a commutative unit mean the multiset of records appended is order-free, so any merge order is acceptable; a non-commutative append means the order is the record sequence. Of a fold into a resource: the combiner must be associative and commutative with an identity, and the canon's "add the two accumulators" (`each_convergence_thread...` quote) names only the additive case; no row names the combine function for a general resource fold. The flag does not carry that, so commutative-flag plus resource fold is underdetermined in canon.

## Check that would show me wrong, and the case that must fail first

Wrong if a ratified row exempts the accumulator carrier from the single-core rule, or if op's freeze applies to the accumulator path. ## Found, not asked

1. The "record sequence" claim does not hold for two appenders. The carrier is unit-outer: unit A walks its range, then unit B (`worker.rs:229-251`, `run_parallel.rs:458-461`). Single core appends A over all records then B over all records. Tiled, core 0 appends A0 B0 and core 1 appends A1 B1, so the merge gives A0 B0 A1 B1. These match only with one appender per accumulator. The api-revision design (agent work, locked with no human) claims byte-identity "when nothing was refused" and scopes only the at-most-one-append-per-record case (`origin/work/api-revision:mock/crates/hilavitkutin/DESIGN.md.tmpl:672-681`); it does not scope multi-appender order. This is a hypothesis from reading, not run; the test above, with two appenders, would settle it.
2. Read-write resources are not rebased: `per_core.rs:48-52` copies `ResourceBinding` through unchanged. On the tiled path a unit that folds into a `Resource` (the case canon calls resource accumulation, `tenet::a_fiber_has_resource_accumulation...`, ratified) writes one shared cell from every core. Canon requires a per-thread accumulator merged after; this path has none. This is a race independent of the commutativity flag.
3. Two distinct things share the word. Canon's "resource accumulation" (a unit writes a resource it also reads) is not the engine's `Accum` store (append column, `tenet::an_accumulator_is_a_column_written_by_append_and_a_fourth_store_marker`, held). The ratified skip rule is stated for the former; the tiling serves the latter. The extension of the gate to appends is by the whole-fiber rule, not by the accumulation rule. State it.
4. The stack audit (`DESIGNS.md:93-109`, agent work) proposes "an N-way split gated on the declared commutativity". That describes the non-accumulator single-trunk branch, which at this commit is not at `worker.rs:323-348`; the single-trunk path I read has since moved and I did not trace it. Unverified against HEAD and presumed wrong until checked.
5. `HeadTailConvergence` docs (`plan/fiber.rs:139`) list COMMUTATIVE as a precondition; nothing enforces it, since no code reads the flag.
