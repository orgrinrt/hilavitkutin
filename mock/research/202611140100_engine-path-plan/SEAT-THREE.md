## The point

What the code does, as fact. `COMMUTATIVE` defaults to false (`mock/crates/hilavitkutin-api/src/work_unit.rs:84`). It is copied into `inputs.commutative` (`src/plan/project.rs:162`) and into `unit_meta[u].commutative` (`src/plan/mod.rs:423`), published with the whole `unit_meta` array (`src/scheduler/plan_handle.rs:386-391`), and read by nothing in `src/`. `Fiber.head_tail` is initialised `Maybe::Isnt` (`src/plan/fiber.rs:212`) and never set. The only trigger for the tiling is `carrier_unit_outer`, which is any fiber with `morsel_local` false (`src/scheduler/run_parallel.rs:467-478`). So every accumulator carrier is tiled, and by the default every unit on it is non-commutative.

The tiling is an input record split, not only an output regioning: the same `(lo, region)` from `accum_slice` both places the region and is passed as the record range, `MorselRange::new(lo, region)` (`src/scheduler/worker.rs:194`, `:235`, `:250`). The provisional row's claim that regioning and head-and-tail "share the ceiling formula and nothing else" is false against this code.

Two cases where the tiling diverges from `run()`, read from the code, not run:

1. A unit that reads its own accumulator's length. `len` reads the projected binding's cell (`src/dispatch/engine_ctx/ctx_writers.rs:172-174`); the per-core copy starts that cell at zero (`src/resource/bindings/per_core.rs:135`). A unit appending `ctx.len()` per kept record yields 0..k under `run()` and 0..k0, 0..k1, ... under the tiling. This is the accumulator form of the canon's "writes a resource that it also reads" (founding `:1764-1766`).
2. A unit that reduces over its morsel and appends once per `execute`. `run()` gives an accumulator fiber one morsel of `[0, total)` (`src/scheduler/run.rs:275-283`); the tiling gives one per core. One value becomes W values in core order. For an additive fold the ratified row says "add the two accumulators" (founding `:1756-1758`); concatenation is the wrong merge.

Arm (a), a carrier with a non-commutative unit takes one core at every worker count. Canon: ratified `ordering_is_guaranteed_by_construction`, "Non-commutative: single-core = trivially ordered" (founding `:605`); ratified `a_unit_declares_whether_it_is_commutative`, fiber commutative only when all its units are, multi-core dispatch only for commutative (`:597-602`); ratified `:1173-1176` the same. The engine design agrees: "Non-commutative accumulation keeps the sequential single-core fallback, routed by a commutativity hint that defaults to single-core" (`mock/crates/hilavitkutin/DESIGN.md.tmpl:646-648`), and the api revision's design carries the same sentence (`:681-683`). Favoured by the canon. On the qualifier: the canon gates on the fiber's declared flag, not on whether the unit writes an accumulator. `records_within_a_fiber_are_independent` (`:609-613`) says only non-commutative accumulation can observe record order, which would motivate exempting a non-accumulating fiber, but no ratified row licenses splitting a non-commutative fiber, so the unqualified form is the one the canon states. The canon's unit of the gate is the fiber; the carrier goes to one core only because this mechanism walks the whole carrier per core with no phase loop (`worker.rs:110-126`).

Arm (b), the tiling stays whatever the units declare. Canon: no row licenses it; it contradicts `ordering_is_guaranteed_by_construction`. The provisional regioning row and `DESIGN.md.tmpl:569-573` support the regioning but say nothing about commutativity, and the same design passage keeps the fallback at `:646-648`. Disfavoured. Its premise, that an in-order merge makes the split invisible, holds only for an exclusive appender whose each append depends on its own record alone; cases 1 and 2 break it.

Arm (c), nothing changes until the measurement returns. Op's words, rung one: "Measure first", option text "the question returns with the numbers. The code stays as it is meanwhile" (`mock/research/202611130850_the-record-read-whole/OP-ANSWERS.md:349-375`). The question put to him was single-trunk phases, head-and-tail against "the N-way path in `worker.rs`", which at the time was the `tphase == 1` branch of `run_core_phase` (removed in `49ab3440`, see below). Commutativity of the accumulator tiling was never put to him. His words govern when the code moves on that question; they do not say what the tiling owes. Silent on the point; possibly binding on timing.

My answer: (d), which is (a) stated at the canon's own granularity, plus one thing the arms leave out. The tiling owes the declared commutativity of every fiber it splits: any fiber with a non-commutative unit runs on one core, and since this path cannot split a carrier into tiled and serial bands, the carrier does. For a commutative fiber the merge owed depends on what the unit accumulates: in-order concatenation for per-record appends (what ships), combine for a fold (`:1756-1758`; `MergeOp` exists at `src/plan/fiber.rs:89`, carried on `HeadTailConvergence` at `:153`, and is unread). Handed back: whether op's "the code stays as it is meanwhile" reaches the accumulator path. His words do not settle it; the repair should not land until he says.

What "commutative" has to mean. The ratified rows define it only as a declared bool on a unit, conjoined over a fiber. That is enough for (a) to be well defined: the engine reads the declaration, never infers it. What the declaration promises is not in the canon for an `Accum` append; the canon's commutativity rows speak of resource accumulation (`ru`/`rw`, founding `:1750-1766`) and predate the accumulator store, whose standing is held (`an_accumulator_is_a_column_written_by_append_and_a_fourth_store_marker`). The code comment, "writes commute across record order" (`work_unit.rs:80`), read literally makes no record-ordered appender commutative, which would serialise every accumulator carrier. The reading that makes the tiling correct is segment invariance: the unit's effect over a record range equals the record-ordered concatenation, for an append, or the declared combine, for a fold, of its effects over any contiguous segmentation, with no read of state other records wrote. The ordering row's "deterministic segments, always in record order" supports this reading; it does not state it. That gap is op's to close.

The check that would show me wrong, and the case that must fail before any repair: a test pinned at `FixedWorkers<2>` through `FixedWorkers<8>`, never host parallelism, with one accumulator carrier whose unit leaves `COMMUTATIVE` at its default and appends `ctx.len()` per kept record. It asserts the `run_parallel` buffer equals `run()` byte for byte and that one thread id ran the unit. On this code it must fail on both asserts. If the values match at W of 2 or more, my reading of `len` is wrong and (b) gains ground. If a ratified row or op's word licensing multi-core dispatch of a non-commutative fiber turns up, (a) falls. A second case, a commutative reduce appending once per `execute`, must fail the value assert today and pins the merge-operator half.
