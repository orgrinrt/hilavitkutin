# What the Mockspace Bench Harness Offers, and What hilavitkutin Uses

## Scope and method

This note describes the bench harness as it stands on mockspace `dev` at a81e195 and compares it with the bench tree of hilavitkutin on `dev` at ada51bb (`mock/benches`). Harness paths are relative to the mockspace repository root. Consumer paths are relative to `mock/`, so `benches/bench.toml:25` is `mock/benches/bench.toml` line 25. The note was written by a dispatched reader for the bench-wide job; the lines 27 to 49 of `bench-core/src/lib.rs`, 267 to 286 and 752 to 766 of `bench-harness/src/harness.rs` and 13 to 32 of `bench-harness/src/lib.rs` were opened again afterwards and say what the note says of them. Nothing was built or run. Every statement about behaviour comes from reading source, and the places where a claim rests on less than that are marked unverified.

Absence claims about the consumer come from ripgrep over `mock/benches`, restricted to `*.rs`, `*.toml` or `*.md` as stated in each subsection. Each grep family was shown to match something known to be present: `\btimed!` matched 93 files; `^\s*(title|workload|master_seed)\s*=` matched 15 lines in `benches/resource_storage/bench.toml`; `ops_per_call` matched `benches/resource_storage/kernels-shared/src/lib.rs:589`; `--mode` matched `benches/src/main.rs:278` and `benches/resource_storage/src/main.rs:217`; an alternation containing `thread::` matched the thread lines in `axis_ce`, `engine_vs_std` and nothing else. The single-trunk-convergence material was not read.

## The harness in one page

The harness is four crates plus the launcher. `bench-core` (`mockspace-bench-core`, `no_std` with a `std` feature) is what a variant links: the `Routine` trait (`bench-core/src/lib.rs:67`), the byte bridge, the `timed!` and `timed_calibrated!` macros and the C ABI struct `FfiBenchCall` (`bench-core/src/lib.rs:445`). `bench-macro` provides `#[bench_variant]`. `bench-harness` (`mockspace-bench-harness`) is the orchestrator: manifest, workload, validation, statistics, report, history. `bench-matrix` is a scaffold library for multi-cell comparisons. The launcher in `src/bench.rs` exposes `mock bench init|run|report|test|list|add` (`src/bench.rs:96-116`).

A bench is declared in `bench.toml`. Each variant is a cdylib that exports `bench_entry`, `bench_name`, `bench_abi_hash` and `bench_output_size` (`bench-macro/src/lib.rs`, the typed and routine forms). A driver binary builds, for each size, a routine bridge that knows how to build the input bytes and how big the output is. The driver re-executes itself as a worker subprocess for every (variant, cooldown, pass, mode) combination, with mode being warm or cold (`bench-harness/src/harness.rs:655-907`, shuffle at 739, modes at 752). Each worker loads exactly one cdylib, runs warmup of `runs / 5` calls (`harness.rs:362`), an optional probe, then `runs / batch_size` timed batches (`harness.rs:408`), printing one line per batch.

A run produces a CSV of batch samples and a `meta.json` (`harness.rs:916-926`), a findings markdown file, and, on the manifest-driven path only, an append-only history ledger and a findings index (`bench-harness/src/driver/mod.rs:650-740`). There are two entry points. `driver::drive_spec` runs the whole loop including preflight, the duplicate-disassembly check and cross-variant validation. `harness::run` is the lower entry that only times (`bench-harness/src/lib.rs:13-27`, `183-189`). That distinction decides much of what follows.

## Inventory, with what hilavitkutin uses

### 1. Manifest and size sweep

`bench.toml` is parsed with unknown keys refused (`bench-harness/src/config.rs:53-108`). A bench section takes `title`, `workload`, `master_seed` (an integer or a string for a full u64), `variants` or `arms`, `sizes` or `points`, `may_differ`, `required`, `threaded`, the roles `baseline`, `floor`, `delta`, a `timing` override and a `normalise` table (`config.rs:206-289`, `315`, `336`). Per-size variant lists are allowed, and `validate_roles` refuses a role naming an absent arm (`config.rs:633`). Seeds come from `master_seed` through `resolve_seeds` (`config.rs:555`).

hilavitkutin uses `title`, `workload`, `master_seed` and `[[bench.<name>.sizes]]` with `n` and `variants` (`benches/bench.toml:25-30`, 70-75, the 29 `[bench.*]` sections in total). A grep of `benches/**/*.toml` for `threaded|may_differ|required|baseline|floor|delta|timing|normalise|points|arms|validation_seeds|determinism_check_seeds` as line-leading keys found nothing. The `may_differ` decision is made in Rust instead (`benches/src/main.rs:212-216`), as a const on the bridge type.

### 2. Timing knobs and per-bench override

`[timing]` carries `passes`, `runs_per_pass`, `batch_size`, `harness_runs`, `cooldowns_ms`, `validation_seeds` and `determinism_check_seeds`. Defaults are 10, 50000, 5000, 3, `[0,100,600]`, 100 and 10 (`config.rs:517-534`). A bench or sweep can override a subset through `TimingOverride` (`config.rs:350`). `HarnessTuning` also holds `quality_seeds` (1000) and `bootstrap_iterations` (10000, informational only) (`config.rs:981`). Zero timed batches result if `runs_per_pass < batch_size` (`harness.rs:408`).

hilavitkutin sets the five basic knobs once, globally: 8, 2000, 100, 1, `[0]` for the main tree (`benches/bench.toml:768-773`) and 5, 2000, 250, 3, `[0]` for `resource_storage` (`benches/resource_storage/bench.toml:32-36`). No per-bench override and no validation-seed keys (same grep as 1).

### 3. Routine trait hooks

`Routine` defines input, output and the hooks around them: `build_input` (`bench-core/src/lib.rs:92`), `validate_output` (98), `score_output` (105), `outputs_may_differ` (117), `max_relative_error` (129), `ops_per_call` (136), `max_call_us` (144), `input_tag` (155), `build_input_bytes` (174) and `score_dimensions` (190). `Input` must be `Copy` and flat, with no pointers (`lib.rs:68-69`). `ops_per_call` feeds the throughput table in the findings (`report.rs:319-321`); `max_call_us` feeds the worker deadline (section 18 below).

hilavitkutin writes one custom Routine, `SeqAlgo<N>`, implementing `build_input` and `ops_per_call` only (`benches/resource_storage/kernels-shared/src/lib.rs:581-592`). The grep `evict_cache_range|pin_to_perf_cores|read_counter|score_output|score_dimensions|max_relative_error|input_tag|validate_output|build_input_bytes|outputs_may_differ` over `*.rs` found nothing in the consumer. `ops_per_call` appears there once (the control above). So the main tree gets throughput rows only through `ByteRoutine`'s own `ops_per_call` (`bench-core/src/byte_routine.rs:100-102`).

### 4. ByteRoutine and byte dispatch

`ByteRoutine<IN, OUT, MAY_DIFFER>` is the default routine: `Input = [u8; IN]`, `Output = [u8; OUT]`, seed-filled input (`bench-core/src/byte_routine.rs:59-107`). Its `build_input_bytes` override fills a heap `Vec` so a multi-megabyte input never lives on the stack (`byte_routine.rs:81-98`). `byte_routine_dispatch!` (`bench-core/src/lib.rs:387`) builds the size match for a hand-written driver; the generated driver does it from `[dispatch] points` and `[dispatch] out` (default 8, `config.rs:179`).

hilavitkutin uses `ByteRoutine<N, 8, MAY_DIFFER>` in a hand-written `match` over nine sizes (`benches/src/main.rs:217-243`) and eight in `resource_storage` (`benches/resource_storage/src/main.rs:176-187`). It does not use `byte_routine_dispatch!` (grep `byte_routine_dispatch` over `*.rs` returned nothing; the same pattern matched three lines in `bench-core/src/lib.rs`).

### 5. Variant crates and the `bench_variant` macro

`#[bench_variant("name", sizes = [..])]` generates the four exports and a `match` over literal sizes; an undeclared size panics with a message (`bench-macro/src/lib.rs:313`, `346-353`). A routine form, `#[bench_variant(Routine, "name", sizes = [..])]`, takes `&<R<N> as Routine>::Input`. `bench_abi_hash` (`bench-core/src/lib.rs:478`) lets the driver refuse a variant built against another struct layout; `check_output_size` refuses one whose output width differs from the routine's (`harness.rs:215-249`).

hilavitkutin uses both forms. 82 variants in `benches/variants/` use the typed form with `timed!` (for example `benches/variants/iter_gather/src/lib.rs:14-16`), and the `seq_*` variants use the routine form (`benches/resource_storage/variants/seq_live/src/lib.rs:10-19`). Each variant crate depends on `mockspace-bench-core` and `mockspace-bench-macro` at `branch = "dev"` (`benches/variants/iter_gather/Cargo.toml:15-16`).

### 6. Subprocess isolation and preflight

Each worker is a fresh process that dlopens one variant. The orchestrator reshuffles variant order per pass (`harness.rs:739`), spawns a throwaway warmup worker first (`harness.rs:685`) and applies a per-call probe that skips a variant if one call exceeds ten times `max_call_us` (`harness.rs:391`). `preflight_variant` checks the ABI hash and output size before timing (`harness.rs:163`; driver calls at `driver/mod.rs:515-532`).

hilavitkutin has the isolation, because the workers are the harness's. It does not call the driver's preflight, since `harness::run` goes straight to the orchestrator (`benches/src/main.rs:121`, `benches/resource_storage/src/main.rs:93`; grep `drive_spec|harness::drive|check_disasm|append_history|detect_regressions|run_worker_validate` over `*.rs` found nothing; control: `harness::run(` matched both lines).

### 7. Timing macros

`timed!` measures one run block per call and returns `FfiBenchCall` (`bench-core/src/lib.rs:534`). `timed_calibrated!` probes one pass, then repeats the block until a floor of 2048 ticks is cleared, capped at 2^20 repetitions, so the block runs at least twice per call (`lib.rs:500-519`, `592`).

hilavitkutin uses `timed!` in all 93 files that use a timing macro (grep `\btimed!` over `*.rs`, 93 files). `timed_calibrated|calibrate_reps` returned nothing.

### 8. Warm and cold modes

The orchestrator spawns every worker twice, warm and cold (`harness.rs:752`). Warm builds the input once per worker (`harness.rs:370`). Cold builds a fresh input and output `Vec` for every call, inside the end-to-end span (`harness.rs:494-505`). The driver reports from warm samples only; cold samples reach the CSV (`driver/mod.rs:650-675`).

hilavitkutin gets both modes in its CSVs, because the orchestrator makes them, and reports warm only (`benches/src/main.rs:114,133`, `benches/resource_storage/src/main.rs:86,104`). Nothing selects a mode.

### 9. Workload programs

`Workload` holds programs made of stages. Strategies are shuffle, chain and one-of; items are `algo_call`, `scalar_work`, `graph_work`, `branch_work`, `heavy_memory` (capped at 1024 u64 in the bridge), `light_scalar` and `domain_work` (`bench-harness/src/workload.rs`, exports at `bench-harness/src/lib.rs:147-167`). The orchestrator does not run the workload; each worker builds its own from its own `main` (`lib.rs:177-182`). The program for a seed is picked by seed modulo program count, per the consumer's own comment (`benches/resource_storage/src/main.rs:116-122`; the selection code in the harness was not located, unverified). The generated driver exposes only builtin stage names, with `default` and `realistic` programs (`src/bench_gen.rs:129-137`, `171-181`).

hilavitkutin builds its own programs in both `main`s: one `realistic` program of six stages in the main tree (`benches/src/main.rs:193-206`) and three single-program workloads in `resource_storage` (`benches/resource_storage/src/main.rs:128-156`). It passes `heavy_memory(2048)` in the heavy section (`resource_storage/src/main.rs:136`), above the 1024 cap noted in the harness. `domain_work` is unused (grep `domain_work|DomainWork` over `*.rs`, `*.toml`, `*.md`, nothing; the other terms in that alternation matched only unrelated `run_inline_*` function names, which shows the alternation worked).

### 10. Validation

Validation runs on the driver path only (`lib.rs:13-27`). Per-variant `validate_output` always runs; byte-exact cross-variant comparison is skipped when outputs may differ and uses relative tolerance when `max_relative_error` is set; a determinism pair runs per seed (`bench-harness/src/validation.rs:84`, `278`). Each variant validates in one worker subprocess started with `--mode validate`, all seeds in one process, with no deadline (`validation.rs:515-557`, `harness.rs:934-972`). A binary lacking a `--mode validate` arm makes every variant skip silently with a diagnostic (`validation.rs:196-208`). `required = true` makes a dropped variant fail the run (`driver/mod.rs` exit logic, line not recorded, unverified).

hilavitkutin does not run it. Both consumer binaries call `harness::run` and neither has a validate arm (`benches/src/main.rs:262-311`, `benches/resource_storage/src/main.rs:202-240`; grep `"validate"` over `*.rs` found nothing). The comments claiming byte-exact validation (`benches/src/main.rs:16-17`, `benches/resource_storage/bench.toml:14-15`, `benches/resource_storage/Cargo.toml:15-16`) describe the bridge type's `MAY_DIFFER` constant, which only matters when `validate` is called.

### 11. Threaded benches

`threaded = true` in a bench section (`config.rs:262`) disables the worker's self-pin (`harness.rs:284-286`), passes `--threaded` to workers (`harness.rs:770`) and to the validate worker (`harness.rs:939`). The contract, in `bench-core/src/lib.rs:27-39`, is that variant-spawned threads are unpinned, that timing is wall-clock over the run block, and that only the calling thread is instrumented.

hilavitkutin does not use it: no `threaded` key in any `bench.toml`, and no variant under `benches/variants/` or `benches/resource_storage/variants/` spawns a thread (grep `thread::|OnceLock|static mut|thread_local|LazyLock` over `*.rs` hit only `axis_ce`, `engine_vs_std` and doc lines). The consumer worker `main`s also do not parse `--threaded` (`benches/src/main.rs:262-285`), and the current `run_worker` takes it as its twelfth argument (`harness.rs:267-280`); the consumer calls it with eleven (`benches/src/main.rs:297-309`, `benches/resource_storage/src/main.rs:235-238`). Against `dev` at a81e195 that call has the wrong arity by signature comparison. Compiling it was not attempted, and no `Cargo.lock` sits in either consumer crate (`ls` found none), so `branch = "dev"` resolves to whatever dev is.

### 12. Statistics and findings report

Statistics are quintile splits, per-cooldown breakdown, lag-1 autocorrelation, bootstrap CI on the median and on paired differences, a sign test, Benjamini-Hochberg adjustment, a cost-model fit and per-input-tag stats (`bench-harness/src/analysis.rs`, public list; exported at `lib.rs:67-82`). The report writes sections for key findings, methodology, end-to-end, function-under-test, per-cooldown, a performance model when `ops_per_call` is non-zero, statistical comparison, per-pass consistency, histogram and diagnostics, and conditional sections for hardware counters and for setup-versus-iteration cost (`report.rs:254-319`, `385`, `510`, `794`). Samples are batch means (`sample.rs`, CSV header at 111-112).

hilavitkutin gets the unconditional sections through `write_report_for_routine` (`benches/src/main.rs:114,133`), for example `benches/rsb_seqd_n16777216_findings.md:1-45` including a throughput row. The methodology fields are not in a report regenerated by `--report-only` (`lib.rs:235-243`).

### 13. Roles, normalisation and highlight detectors

`baseline`, `floor` and `delta` roles and a `normalise` table (mode subtract, ratio, percent or none) shape the comparison, and 18 highlight detectors flag patterns in a run (`config.rs:315`, `bench-harness/src/summary/detectors.rs`, count from an earlier read, bodies not reopened). hilavitkutin declares none (grep in section 1). The reports show a baseline anyway (`rsb_seqd_n16777216_findings.md:4`), taken by default from the first variant.

### 14. History ledger and regression detection

The driver appends timestamp, git commit, variant, N, mode, median and CI bounds to an append-only TSV and flags a regression when the current CI low sits above the median of the CI highs of the last five entries (`bench-harness/src/history.rs:164-242`; appended in `driver/mod.rs:690-740`). It records warm mode only. hilavitkutin has a `benches/.bench_history/` directory, but its 25 files are named `fiber_theory_*`, `rcm_*`, `swap_*`, `wake_policy_*`, none of which is a bench in `benches/bench.toml`. No consumer source calls `append_history` or `detect_regressions` (grep in section 6). Whoever wrote the directory did not use the current binaries.

### 15. Disassembly duplicate check

The driver runs `objdump -d` on each variant (`otool` fallback on macOS) and warns when two `bench_entry` bodies are byte-identical (`bench-harness/src/disasm.rs`, called at `driver/mod.rs:549`). hilavitkutin does not call it. It carries its own five-check disassembly module instead (`benches/src/disasm_5check.rs:5-7`, `116`, with `benches/src/lib.rs:1-8`) and a gate binary (`benches/src/bin/asm_gate.rs`, 254 lines, not read in detail).

### 16. Hardware counters

Counters are real only with the `perf-counters` feature, on macOS aarch64, as root, through kperf; the worker enables them with `MOCKSPACE_BENCH_PERF` (`bench-harness/src/perf.rs:74`, `harness.rs:288-335`). Only instructions and cycles are wired; cache and branch misses are zero placeholders. `bench-harness/Cargo.toml:25-27` has a comment promising Linux `perf_event_open` that no code implements. hilavitkutin enables no feature on the harness (`benches/Cargo.toml:22-24`; grep `perf-counters|PerfSnapshot|MOCKSPACE_BENCH_PERF` found nothing).

### 17. Environment metadata

`collect_env_meta` gathers cpu, os, rustc, git commit with a dirty marker, timestamp, counter frequency, machine class, online cpus and 1-minute load (`bench-harness/src/env.rs`). `env_meta_to_json_with` writes only cpu, os, rustc, git commit, timestamp, counter frequency, framework and an optional build profile (`harness.rs:69-85`). Load and machine class are collected and then dropped, and nothing gates on them (grep inside `bench-harness/src` found uses only in `env.rs`). hilavitkutin's meta files carry the seven written fields without a profile (`benches/atomic_inc_strategy_n1024.meta.json`). Whether a consumer-owned driver sets `MOCKSPACE_BENCH_PROFILE` was not checked, unverified.

### 18. Build profile and `[build]`

The launcher builds with `opt-level=3`, `lto="fat"`, `codegen-units=1` through `--config` arguments (`src/bench.rs:984-998`), and a `[build]` table overrides it (`config.rs:53-108`). hilavitkutin has no `[build]` table and sets the same three values in its own `[profile.release]` in every bench crate (`benches/Cargo.toml:26-29`, `benches/engine_vs_std/Cargo.toml:29-32`, `benches/resource_storage/Cargo.toml:27-30`, `benches/variants/iter_gather/Cargo.toml:18-21`).

### 19. Nested bench tree

A member directory with its own `bench.toml`, `[sweep.<name>]` sections, `arms/<arm>/` crates, `support/` crates and glob membership under `[benchspace]` gives composed keys `<member>/<sweep>`, output under `results/` and history under `history/<bench>/` (`bench-harness/src/tree.rs`, `src/bench_docs.rs:52-89`). hilavitkutin uses the flat layout: outputs land at the bench root as `<bench>_n<N>.csv` and `.meta.json` and `_findings.md` (`benches/src/main.rs:91-92`), and `resource_storage` writes to `../` (`benches/resource_storage/src/main.rs:68-69`). No `[benchspace]` key (grep in section 1).

### 20. Matrix layer

`bench-matrix` supplies `scaffold::warm`, `cold_cycle` and `stream` (`bench-matrix/src/scaffold.rs:100`, `173`, `241`) and the `bench_matrix!` macro; `bench-harness/src/matrix.rs` holds the generator (`MatrixSpec`, `expand`, `render`, `generate`). Each `bench_entry` call runs `setup`, a first-touch pass of `ITERS = 16` (`scaffold.rs:49`), a digest pass and a calibrated loop, and reports setup, first-iteration and digest ticks in `FfiBenchCall`. hilavitkutin does not use it (grep `bench_matrix|bench-matrix|mockspace_bench_matrix|MatrixSpec|scaffold::` over `*.rs`, `*.toml`, nothing).

### 21. Driver and hooks

`drive_spec` takes a `DriverSpec` and `Hooks` (`on_init`, `after_init`, `routine_for`, `after_cell`), with flags `--only`, positional names, `--seed` and `--report-only` (`driver/mod.rs`, hooks in `driver/hooks.rs`). A hook returning fail fails the exit code. hilavitkutin writes its own loop and exit code logic instead (`benches/src/main.rs:66-184`), including a hook-like `axis_a_static_fail` driven by its disasm checks (`main.rs:64`, `145-183`).

### 22. Report-only regeneration

`--report-only` rebuilds findings from the CSV (`lib.rs:226-260`). hilavitkutin supports it in both mains (`benches/src/main.rs:41,94-119`, `benches/resource_storage/src/main.rs:34,71-91`) and builds an empty `EnvMeta` for it.

### 23. Result staging

A run writes into a staging tree and promotes it only on orderly completion; stale stages are quarantined (`driver/mod.rs:397-407`, `driver/staging`). hilavitkutin writes directly to final paths (`benches/src/main.rs:128-138`), so an interrupted run leaves partial files. The multi-run data under `benches/runs/run1` and `run2` is copied by hand, as far as the tree shows.

### 24. Docs generation

`[docgen] enabled = true` makes the docs pass write `docs/BENCHES.md`, a dot graph per benchmark and a PNG, from the history ledger (`src/bench_docs.rs:39-50`, `181-276`). hilavitkutin has no `[docgen]` (grep in section 1).

### 25. Launcher commands and test integration

`mock bench init|add|run|report|list|test` (`src/bench.rs:96-144`); `test` runs `cargo test` over every crate under the bench tree and refuses zero tests (`src/entry/test_benches.rs`); `mock test` runs that tree only when its inputs moved; `bench_rev.rs:6-24` settles all generated lockfiles on one framework commit. A consumer `Cargo.toml` makes the launcher build the consumer's own driver instead of the generated one (`src/bench.rs:166`), which hilavitkutin's `benches/Cargo.toml` does. Which commit the launcher would settle on for hilavitkutin, with no committed lockfiles, was not traced (`bench_rev.rs:21` says the branch tip is taken, unverified in detail).

### 26. Dylib hash cache and drift correction

`bench-harness/src/cache.rs` keys cached batches on dylib hash, timing knobs and workload hash and corrects drift against a baseline. It is exported (`lib.rs:83-93`) but grep over `src` and `bench-harness/src` found it referenced only in `cache.rs`, `lib.rs` and `config.rs`, so `drive_spec` does not call it. `benches/resource_storage/bench.toml:28-31` states that a `.bench_cache/` reuses unchanged variants. The harness source read does not support that statement.

### 27. Cross-benchmark meta report

`meta_report::generate` and `classify_family` (`bench-harness/src/meta_report.rs`, `lib.rs:133`) produce a cross-bench summary by name heuristics. Not called by the driver (same grep method as 26). Not used by hilavitkutin.

### 28. Quality measurement

`quality::measure` scores variants over `quality_seeds` (`bench-harness/src/quality.rs`, `lib.rs:142`). Not called by the driver, not used by hilavitkutin (grep `quality::`, nothing).

### 29. Inline bench

`run_inline` times in-binary variants for devirtualisation questions (`bench-harness/src/inline_bench.rs`, `lib.rs:132`). Library-only, and the consumer's `inline_always|inline_default|inline_never` variants are cdylib variants with the same word in their names, not users of it (`benches/variants/inline_always/src/lib.rs:19`).

### 30. Counter primitives

`read_counter` (`bench-core/src/counter.rs:43`), `counter_frequency` (86), `pin_to_perf_cores` (144, macOS only, empty elsewhere at 176) and `evict_cache_range` (191). The counter is `CNTVCT_EL0` on aarch64, `lfence; rdtsc` on x86_64 with a three-second calibration, and `Instant` as fallback. Consumers reach them only through the macros. No direct use (grep in section 3).

The inventory has 30 capabilities.

## engine_vs_std and resource_storage

`engine_vs_std` is not on the harness. Its `Cargo.toml` depends on the hilavitkutin crates, arvo and notko and has no `mockspace-*` entry (`benches/engine_vs_std/Cargo.toml:22-27`), and a grep for `mockspace|Routine|bench_core|harness::` over its `*.rs` and `*.toml` found nothing. It carries its own timing loop that takes `Instant` samples, sorts them and keeps median and minimum only (`benches/engine_vs_std/src/lib.rs:183-204`), its own iteration budget (`lib.rs:206-208`, 20 to 4000 iterations from `10_000_000 / n`), its own thread executor behind `ThreadPoolApi` that spawns a detached `std::thread` per call and reports the machine's parallelism as worker count (`benches/engine_vs_std/src/executor.rs:24-35`), its own `std::thread::scope` baselines (`benches/engine_vs_std/src/wide_parallel.rs:330-342`, `benches/engine_vs_std/src/accumulator.rs:203`), a checksum check outside the timed region (`lib.rs:25-28`), per-workload ratio ceilings (`lib.rs:306-363`) and a gate test, marked `#[ignore]` with a ticket tag (`benches/engine_vs_std/tests/perf_gate.rs:156`). It has no confidence intervals, no cooldown, no cold mode and no subprocess isolation. Sizes go up to 4,194,304 records (`lib.rs:369`).

`resource_storage` is on the harness through `harness::run`, with the manifest loader, `for_size`, routine bridges, workload programs and `write_report_for_routine` (`benches/resource_storage/src/main.rs:36-114`). It does not validate (section 10), does not set `threaded`, and keeps three things of its own: a custom Routine, `SeqAlgo<N>` (`benches/resource_storage/kernels-shared/src/lib.rs:581-592`), a Python cross-run aggregator over `runs/run*/` directories (`benches/resource_storage/aggregate.py:1-24`, role as stated in its docstring, body not read further), and the `axis_ce` crate. `axis_ce` is also off the harness: it times a thread-scoped false-sharing loop with its own `Instant` and a median of 15 samples (`benches/resource_storage/axis_ce/src/lib.rs:101-145`) and runs as `#[test]` functions (`lib.rs:153`, `188-201`), and its own header says so (`axis_ce/Cargo.toml:9-15`).

The consumer's main-tree `src/main.rs` and `src/bin/asm_gate.rs` use the harness for timing and its own `disasm_5check` module for assembly checks, as set out in section 15.

## Limits for benches over millions of records with threaded arms

### Largest input the ABI and the routine can carry

A variant receives `bench_entry(input: *const u8, output: *mut u8, n: usize)` and returns `FfiBenchCall` (`bench-core/src/lib.rs:455-456`, `445`). The input has no length parameter; its size is fixed by the routine type for that `n`. `build_input_bytes` returns a heap `Vec<u8>`, and `ByteRoutine` overrides it to avoid the stack (`byte_routine.rs:81-98`). The by-value `build_input` stays required, and the doc says it must not be called at sizes the stack cannot hold (`bench-core/src/lib.rs:74-92`). The source states no numeric ceiling. The consumer has run `ByteRoutine` bridges to 4 MiB (`benches/resource_storage/bench.toml:117-118`) and `SeqAlgo` to 16,777,216 u32 elements, which is 64 MiB, with 480 CSV rows and 120 samples per variant (`benches/rsb_seqd_n16777216.csv`, `benches/rsb_seqd_n16777216_findings.md:3`). `routine_for` lists `SeqAlgo` up to 268,435,456 (`benches/resource_storage/src/main.rs:172`), declared but not exercised in `bench.toml`. Input must be `Copy` and flat (`lib.rs:68-69`), so a pointer-bearing structure cannot be the input; the consumer's workaround is a u64 seed input with the payload built inside the variant (`kernels-shared/src/lib.rs:515-538`, called from `seq_live/src/lib.rs:15`). Each distinct size is its own monomorphisation, a literal in the macro list (`bench-macro/src/lib.rs:346-353`). Compile time and type-size behaviour for `[u8; N]` at hundreds of millions of bytes is not stated in the source read.

### Whether a variant may spawn threads

Yes. The contract allows it and measures the whole block as wall-clock (`bench-core/src/lib.rs:27-39`). `threaded = true` removes the coordinating thread's self-pin and is plumbed to workers and the validate worker (`harness.rs:284`, `770`, `939`). Spawned threads are never pinned, `pin_to_perf_cores` does nothing off macOS (`counter.rs:176`), and per-thread counters are out of scope. A thread pool may live in a process-local static keyed by `n`, built on the first call, which lands in untimed warmup (`lib.rs:41-49`).

### How variants are isolated

One cdylib per worker subprocess, one subprocess per (variant, cooldown, pass, mode) for each of `harness_runs` rounds, so the orchestrator spawns `harness_runs x passes x |cooldowns| x 2 x variants` workers per cell (`harness.rs:714-752`, product from the loop structure). Validation uses one extra worker per variant (`validation.rs:532-547`). State, threads and memory of a variant die with its process.

### Timeouts

A worker gets 300 s when no `max_call_us` is known, otherwise the larger of 5 s and `ceil(max_call_us x runs_per_pass x 3 / 1e6)` seconds, and the orchestrator kills it past that, yielding nothing for that worker (`harness.rs:759-766`). `max_call_us` is not a manifest key (`config.rs:875-876`); it comes only from `Routine::max_call_us` (`bench-core/src/lib.rs:144`, `driver/samples.rs:11-17`, `driver/mod.rs:496`). Validation workers have no deadline (`validation.rs:532-547`). By arithmetic on the cited values, 300 s over the default `runs_per_pass` of 50,000 plus 10,000 warmup calls leaves 5 ms per call, setup included, because untimed setup inside `bench_entry` counts against wall time.

### Long iterations against passes, runs_per_pass and batch_size

A sample is the mean of `batch_size` calls, and a worker produces `runs_per_pass / batch_size` of them (integer division, remainder dropped, zero if `runs_per_pass < batch_size`; `harness.rs:408`). Samples per variant per mode are `harness_runs x passes x (runs_per_pass / batch_size)`; the consumer's 3 x 5 x 8 gives the 120 seen at `rsb_seqd_n16777216_findings.md:3`. Every call, including warmup at `runs / 5` (`harness.rs:362`), executes the variant's untimed setup again unless it caches in a static. In `seq_live` that setup fills 16,777,216 elements on each of about 2,400 calls per worker (`seq_live/src/lib.rs:15`, `kernels-shared/src/lib.rs:530-534`), and its cost was not measured here. `cooldown_ms` sleeps after each batch (`harness.rs`, worker loop). `batch_k` is hardcoded to 1 in the manifest path (`config.rs:875`), so the multi-call-per-sample path at `harness.rs:432` cannot be reached from `bench.toml`.

### What the harness lacks for this shape

No manifest key for `max_call_us` or `batch_k`. No thread count or affinity control for variant-spawned threads, no per-thread counters, no pinning off macOS, no perf counters off macOS aarch64 (`perf.rs:74`; the Linux claim in `bench-harness/Cargo.toml:25-27` has no code behind it). Load and machine class are collected and not recorded or gated (`harness.rs:69-85`). No deadline on validation. No memory-use measurement was found in the files read; the rest of the crate was not grepped for it, unverified. Statistics treat each batch mean as one sample, so a threaded run block's scheduling noise appears as spread, with no separate channel.

### Where the source is silent

Maximum compile-time size of `[u8; N]` per monomorphisation. How the orchestrator's memory scales with a large `n` (the warm worker allocates it, the orchestrator side was not traced). Whether `heavy_memory` can be raised past 1024 in the generated driver. How workloads interact with a threaded variant. What cold mode costs for a multi-hundred-megabyte input beyond the per-call rebuild at `harness.rs:494-505`.
