# Build and link bench, the first cells

This note reports steps 1 to 6 of the builder's steps in the build and link bench plan (`.shared/research/202611150830_stack-path/59-the-build-and-link-bench-plan.md` in the workspace repository, section 10), as built on the branch `work/bench-build-and-link` of hilavitkutin. The plan is an agent's work and was read as a claim to test; the lead designer's words in files 58 and 60 of the same directory, and hilavitkutin's registry rows, were read as the governing record.

This revision replaces the numbers of the first note. The cells were run again on the branch `work/record-the-97-crate-point-of-build-static` under the six passes both benches declare and the guards as they stand on `dev`, and the 97-crate point of `build-static` is recorded for the first time. The three-pass numbers of the first note are no longer quoted, apart from one comparison in the section on what the cells show; their run directories stay under `mock/benches/results/`.

What exists is a generated, deterministic fixture of twelve domains at 25, 97 and 169 crates, a support crate that turns one bench call into one cargo build or one link and records what that call did, and two benches on the toolchain's own defaults: `build-static`, with incremental compilation on and off over four scenarios, and `link-static`, with the relink through cargo (quantity A) and the replay of the recorded link line (quantity B). Every timing below comes from the bench harness and is quoted beside its run directory under `mock/benches/results/`. Crate counts and byte sizes come from the call record the hooks library writes during the same harness run (`calls.tsv` in each run directory).

The fixture's `dev` profile (opt-level 1, debug 0, the LLVM backend) is not hilavitkutin's `dev`. The row `there_are_five_build_profiles_dev_dev_opt_release_profiling_and_ci` (`mock/registry/tenet/identity.toml:360`) gives hilavitkutin's `dev` Cranelift for the workspace and LLVM for its dependencies, and its `release` full pragmas. So the `build-static` and `link-static` numbers measure the toolchain's default route, not any profile hilavitkutin ships.

Nothing here configures a linker, a backend, an edge form, a C compiler or an LTO setting. Those arms wait on the hilavitkutin-build design round, as the plan's section 6 and the brief say, and the benches carry no flag table of their own.

The support crate was reworked after a review (`REVIEW.md` beside this note), and every run quoted below ran on the reworked crate.

## What was built and where

All paths are under `mock/benches/`.

1. `support/build-fixture/`: the generator. Twelve domains in three tiers (roots 0 to 3, mids 4 to 7, leaves 8 to 11), each a contract crate and `c` implementation crates, and one facade binary that composes every implementation. Mids read every root; leaves read every root and two mids; only the facade takes implementations. `c` is 1, 7 and 13 at the points 25, 97 and 169. Each implementation carries 2230 non-inlined functions (`FUNCTIONS`), and each contract four generic items (`GENERICS`). The seed is `0x6876_626c_6669_7831`. `write` refuses a tree whose digest is not the committed one (`COMMITTED`: 25 `0x426667db754199ed`, 97 `0x6053cab89e05fb7a`, 169 `0xc5bb68a50a2c7a46`) and writes a hand-made, sorted `Cargo.lock`, so the fixture builds `--offline --locked`. Tests: `tests/digest.rs` (the committed digest at every point, which is what holds the generator deterministic, and a changed seed refused) and `tests/reach.rs` (each edit site's reach, and the graph's shape, at every point).
2. `support/build-call/`: one call. Each arm and point gets `<root>/<bench>/<arm>/n<n>/` with the workspace, its own target directory, temporary directory and an empty cargo home; the arm's other points are pruned when it moves on. The pinned toolchain is resolved once through rustup, and its own `cargo` and `rustc` are then run by path. Their environment is cleared and only `PATH` is put back, so no inherited variable reaches the build: no flag or wrapper variable, no `CARGO_TARGET_<triple>_LINKER`, no `CARGO_PROFILE_*`, no `CARGO_BUILD_JOBS`, no `RUSTC`. Cargo's configuration files cannot reach it either: the cargo home is the cell's empty `home/`, and cargo runs from the filesystem root with the fixture named by `--manifest-path`, so no directory above the fixture is searched, and a configuration at the root itself refuses the call. The command line adds `-Zchecksum-freshness`, `--offline --locked`, and the target and build directories of the cell. The untimed setup first holds the disk to the cell's budget (below), then does what the scenario needs (an empty target for `clean`; a catch-up build and a new edit slot content for the edit scenarios; a catch-up build and removal of the executable and the facade's own deps for the relink; the link line printed by `rustc --print link-args -C save-temps`, stored, and its output removed for the replay, which then runs with the same cleared environment and the variables rustc's line sets). The timed block is the one cargo build or the one link process, inside the harness's `timed!`. `record` appends one line per call to the call record, and `check` holds every call of a cell to: the scenario's label; for a cargo call, a compiled count equal to the generator's prediction, and for a replay, which runs no cargo, no count at all (`-` in the record); the setup having undone what it must (`absent_before`); the output present after; exit 0; cargo never waiting on a lock; for a link, exactly the mark the arm's linker must leave, which for the `default_*` arms is `Linker: ` and the version line the toolchain's own `rust-lld` prints for `--version`, worked out at run time where the host target's description names a self-contained lld flavor, so a system lld of the same version or a second linker's string joined after it is refused, and an arm naming any other linker is refused until hilavitkutin-build gives that linker its mark (that configuration, and the cargo flags, move into hilavitkutin-build with ticket `build_call_s_target_spec_reading_linker_mark_and_cargo_flags`); and the same check line printed by the built program on every call. Tests: `tests/controls.rs` (a clean call that skips the clean, an edit by file time only, a relink and a replay that keep the executable, each refused with its reason; the honest relink's mark equal to the one worked out), `tests/marks.rs` (a missing mark, another linker's mark, another build of the same lld version, a version that only starts alike, a second linker's string joined after the right one, and an arm named for mold carrying lld's mark, each refused), `tests/record.rs`, `tests/elf.rs` (the `.comment` reader on a file cut short at every length and with each offset pointed outside it: an error, never a panic), `tests/environment.rs` (a hostile linker, `RUSTC`, jobs and profile variable, a hostile cargo home and a hostile configuration above the fixture: the call builds and links, and each breaks the same command where it reaches it), `tests/lock.rs` (the cell's build locks held while a call starts: cargo prints its `Blocking` line with stderr piped, and the call is recorded as waiting and refused), `tests/space.rs`, `tests/bounds.rs` (reads both `bench.toml` files and fails on a sweep with no row at its smallest point), `tests/passes.rs` (holds both benches to six passes, whose sign test can reach p = 0.031), `tests/linkline.rs` (a replay keeps one link line per profile and refuses a line whose `-o` is outside the target directory of the profile it replays) and `tests/cleanup.rs` (every test that builds removes its state when it ends, passing or not). The link line a replay keeps is per profile because `dev` and `release` at one point share the cell's directory.
3. `build-static/` with arms `llvm_incremental` and `llvm_non_incremental`, sweeps `clean`, `leaf`, `mid`, `root`, points 25 and 97.
4. `link-static/` with arms `default_relink` (quantity A) and `default_replay` (quantity B), sweeps `dev` at 25 and 97 and `release` at 25.
5. `bench.toml`: a workload `build` that is the call alone. `src/lib.rs`: `routine_for`, `on_init` and `after_cell` route the two benches to `build_call::hooks`, which writes `calls.tsv` into each run directory and fails the cell when `check` refuses.

The bound on a call (`support/build-call/src/routine.rs`) is three times the slower arm's first timed call of the cell, rounded up to a second, read from the table `FIRST_CALL_S` in `support/build-call/src/measured.rs` and scaled by the crate count from the nearest measured point below for a point not yet measured. The rows are from the runs of this revision, read from `samples.csv` as the first warm pass of the slower arm: at 25 crates 23 s for `clean`, 6 s for `leaf`, 7 s for `mid` and 17 s for `root` (run `20261119T150158Z-ffb57e5a`), at 97 crates 124 s, 6 s, 34 s and 88 s (runs `20261119T171604Z-fe400621` and `20261119T203124Z-4228372a`), and 1 s for `link-static` at dev 25 and release 25 (run `20261119T134226Z-07a9e9a3`). `tests/measured.rs` reads every row back from the run directory it cites and fails on a row no run directory gives. The row of `link-static` at dev 97 is the one exception: it is a placeholder marked with a FIXME and the ticket, the untimed build of the 97 crates plus the relink, 119 s, and not a timed call; the blockers describe it.

The disk budget of a cell (`support/build-call/src/space.rs`) is the largest target directory a cell of the same incremental setting left, from the table `TARGET_BYTES` in the same file: 562731084 bytes at 25 and 3893504668 at 97 with incremental on, 82479236 at 25 and 567452989 at 97 with it off, read from the call records of the runs `20261119T150158Z-ffb57e5a`, `20261119T171604Z-fe400621` and `20261119T203124Z-4228372a` and checked by `tests/measured.rs`. Before each call the setup reads the free space with `df -Pk` and refuses where the free bytes and those the cell's own target already holds are under the budget plus 1 GB, as the plan's section 8 asks. The harness runs no hook before a cell, so the refusal fails the cell instead of recording it absent (ticket `the_bench_harness_has_no_hook_before_a_cell_so_a_refused_cel`). The plan's step 4 asks for the first cell's directory by `du -sb`; the hooks library reads the same byte sum (`bytes_under`) into `target_bytes` on every call instead.

Harness: 6 passes, 1 run per pass, batch 1, one validation seed and one determinism seed. Every worker ran in both modes, warm and cold, and `samples.csv` holds both; the report reads the warm mode alone, so every median below is the harness's warm median of six samples, and every delta is the paired median delta of the report's statistical comparison with its 95 percent bootstrap interval.

With six paired samples per arm, the smallest p the sign test can give is 0.0313, which every significant cell below reaches. A cell where the interval excludes zero and the adjusted p is above 0.05 is marked as not significant.

## What the cells show

1. Isolation holds in the static form at both points: an edit to one leaf implementation compiled the implementation and the facade alone (2 crates, every one of 90 calls) at 25 and at 97, and the counts after mid and root edits are exactly the generator's reach, 7 and 19 at 25 and 25 and 73 at 97. This is the first row of the plan's section 9 table: the contract and implementation split already gives the isolation, so the edge form question narrows to the link. Measured in the harness runs.
2. The default link is a small part of a rebuild. At dev 25 the relink reads 162.10 and 186.70 ms in two runs against 3920.36 ms for an incremental and 5874.19 ms for a non-incremental leaf rebuild, and the bare replay of the link line reads 79.97 and 78.47 ms. At dev 97 the relink reads 510.24 ms against 4011.75 and 5821.77 ms for the leaf rebuilds, and the replay reads 295.63 ms. The replay is faster than the relink in every one of the five link cells, significantly in each. A relink goes through cargo and rustc on the facade and a replay does not, but no cell measured how the difference divides between them.
3. Incremental off took longer than incremental on after every edit, at both points, and each of the six deltas reaches adjusted p 0.0313: the leaf rebuild reads 2104.38 ms slower at 25 and 1823.94 ms slower at 97, the mid rebuild 5490.10 ms and 30865.36 ms slower, the root rebuild 15490.28 ms and 82818.00 ms slower.
