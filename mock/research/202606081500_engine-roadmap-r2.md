## 0. Why r2 exists

r1 framed Phase D's keystone (D1) as "construct a fiber-grouped compile-time carrier" and left the construction mechanism open (#669). The dispatch-pivot work proved the construction question is a coherence wall (you cannot type-derive the grouping) and resolved it: devirt requires the carrier's TYPE order to be a valid topo order, reached by builder-append + build-time topo-validation, with the whole-program flat schedule-mega (spec Approach E) as the GATE-1 dispatch. The full-engine re-evaluation then verified this pivot does not forfeit the spec's runtime adaptability or plugin extensibility, because R6 already splits the engine exactly this way. r2 records the resolved Phase D, the C3 split, and lifts the adaptability + extensibility axes to first-class roadmap concerns so the build honors the whole spec, not just the dispatch metric.

## 1. Governing principle (cross-cutting, applies to every step): static composition, adaptive parameters

R6 (`:2435-2446`) is the oracle for the whole arc, not just dispatch: "The WU set, DAG structure, fiber/trunk/phase topology, and monomorphised dispatch functions are all fixed at build time. This is what enables LLVM devirtualisation. No runtime WU registration, no dynamic schedules. Plan-stage parameters are adaptive: morsel sizes, record counts, per-phase strategy selection, morsel-to-core affinity. These adjust at plan time without changing the pipeline composition."

Every step is built to keep this split clean:

- **Locked at compile time (the types):** WU set, dependency DAG, topo/RCM-row order, fiber/trunk/phase topology, monomorphised dispatch. Never runtime-mutable.
- **Recomputed between frames (the parameters):** morsel sizes, per-phase configs (MAX_FUSE/BALANCED/MAX_SPLIT), core/lane affinity, record ranges, dirty masks. Fed into the static per-core program as runtime values. The three domain-22 triggers (`:2042-2048`: morsel-timing → recompute morsel sizes; phase-balance → re-select configs; record-count → full plan recompute) all stay on the parameter side.
- **`meta::PlanStage` has TWO distinct cases (distinguish them, mirror finding):** (i) parameter recompute (record-count change → recompute morsel ranges + re-select approach/configs over the SAME static WU set; runtime, no reorder); (ii) structural change (WU registration / DAG change → full recompute, but per R6 "no runtime WU registration" this is a REBUILD = a new static composition = a new monomorphisation, NOT a runtime mutation of a running engine). Case (i) is the between-frames adaptive path; case (ii) is recompile. Dispatch order + fiber grouping recompute only in case (ii), where new types are built anyway. Spec basis: `:1486-1491` ("morsel ranges, fiber grouping, trunk formation... plan stage reruns... no incremental plan maintenance"); the reruns that change grouping/order are the WU-set-change (rebuild) reruns, while record-count reruns change only morsel ranges (grouping/trunk are column-structure-derived, stable under record count).
- **The rule for every step:** if a step's "adaptivity" can be expressed as a runtime parameter fed into a static walk, it must be; only genuinely structural change (a different WU set) is a rebuild, never a runtime mutation of dispatch.

This is the lens the Step-6 canonical mirror enforces (section 9).

## 5. NEW first-class section: extensibility, two surfaces

The spec has no plugin domain (it postdates the extension layer); r1 omitted extensibility entirely. r2 makes it first-class because op flagged it as a fundamental concern. Two surfaces, neither needs runtime-mutable dispatch:

- **Surface 1, new DATA (dominant, native):** records added to existing columns flow through the same static WUs. `record_count` is an R6 adaptive parameter. Unbounded data extensibility with zero new dispatch. No roadmap work needed; it falls out of the static-composition + adaptive-params design.
- **Surface 2, new CODE (rarer, downstream):** a runtime-loaded cdylib extension's transform does NOT enter the engine's monomorphised dispatch (R6: no runtime WU registration). It integrates via a statically-registered FACADE WU that calls the extension through the `ProviderId` capability ABI (hilavitkutin-extensions). The plugin keeps its own devirt (monomorphised in the cdylib); the host keeps its own; the only indirect hop is the ABI call at the FFI seam, per-invocation or per-morsel-batch, OFF the per-record hot path. Behind the facade the plugin runs its own static sub-engine (sub-graph) or is a per-morsel pure-function capability; downstream + bench-decidable.

Roadmap status: the engine-core boundary is spec'd + shipped (no runtime WU reg; extension layer loads). The facade integration pattern is currently UNDOCUMENTED and downstream; r2 adds it as a future section + a proving sketch (section 7) so it is not an afterthought. It is NOT a GATE-1 dependency.

## 6. NEW first-class section: Approach 2 (runtime-selectable variant menu) — proven optional layer

Per op's "don't arbitrarily limit" challenge: runtime-recomputable grouping/order IS achievable devirt-free, in one form only — a bounded set of compile-time-monomorphised variants selected by a per-frame branch. PROVEN by sketch 202606081400 (dispatch_selected, two grouping variants, 275 instrs, zero blr both arms; cost = code size linear in variant count + one off-hot-path branch). Bounds: 1 baked variant (GATE-1) / N-from-menu (Approach 2, devirt) / unbounded-runtime (impossible devirt-free). It is an ADDITIVE layer on the same static foundation, addable post-GATE-1.

**Spec grounding (mirror finding, sharpens this from "could" to "the mechanism for a spec feature"):** the spec's approach selection by record count (`:1547-1562`: <10K → C/D, >10K → E) combined with domain-22's "record count changed → full plan recompute" means a pipeline running at VARIABLE record counts across frames is specified to switch dispatch approach between frames. Switching a type-baked dispatch approach at runtime without a rebuild is exactly Approach 2: precompile the relevant approaches (e.g. {C/D, E}) and branch-select per frame on the current record count. So Approach 2 is the devirt-preserving realisation of the spec's runtime approach-selection, not merely a nicety. It remains post-GATE-1 (GATE-1 = one approach, Approach E, one bench), but it is spec-grounded: a workload with strongly varying record counts needs it for full fidelity. GATE-1's single-baked choice does not foreclose it; it is additive.

## 8. op decisions — RESOLVED (AskUserQuestion, 2026-06-08)

- **(a) loimu order-sensitivity → PRIORITIZE RCM-ROW RECOVERY.** loimu's hot pipelines ARE order-sensitive. The build-time auto-RCM-order recovery is a NEAR-TERM priority, not deferred: the engine should apply the cache-optimal dispatch order itself rather than relying on the consumer registering in topo/RCM order. This adds a new proving sketch (§7-6 below) and a near-term roadmap step, ideally landed before or with the GATE-1 dispatch so GATE-1 ships auto-RCM-ordered. Note (load-bearing): the only devirt-preserving auto-recovery is via Approach-2 (precompile the RCM-ordered carrier as the selected variant), because a const-fn RCM order hits the GCE-in-generic wall and a proc-macro/build.rs cannot see resolved AccessSets. So "RCM-row recovery" and "Approach-2" are the same mechanism; prioritizing (a) prioritizes the Approach-2 substrate.
- **(b) registration constraint → TEMPORARY COMPROMISE.** The producer-before-consumer registration constraint (validated by `BuildError`) is accepted for now but explicitly PROVISIONAL: it is to be revisited and relaxed when (i) the RCM-row recovery (a) makes the engine auto-order so manual registration order stops mattering, and/or (ii) the toolchain (`generic_const_args` / const-eval maturity) can auto-reorder the carrier type. Mark it provisional everywhere it appears (D1d-a/b, C3-row); do not present it to consumers as permanent.
- **(c) greenlight → PLUGIN SKETCHES (§7-4a/b) FIRST.** Prove the facade `AccessSet`/`ContainsAll` plugin feasibility (the one remaining feasibility unknown, could wall) BEFORE starting the GATE-1 implementation. Sequence: §7-4a → §7-4b → §7-6 (RCM-row recovery, per (a)) → then the GATE-1 dispatch build. If §7-4a or §7-6 walls → Step-11 op-decision (pause for op). The GATE-1 build proceeds autonomously once those sketches clear (no wall); "plugin sketches first" sequences the build behind the sketches, it does not re-gate it on a second op review.

### §7-6 NEW sketch (from decision (a)): RCM-row recovery / auto-RCM-ordered dispatch

Shape: prove a compile-time/build-time mechanism produces the RCM-ORDERED carrier (so dispatch runs in the cache-optimal order, devirt) WITHOUT the consumer manually registering in RCM order. Premise: the engine computes RCM-row at plan/const time and the dispatch uses it devirt-free. Candidates: (i) const-fn RCM over the shipped const access masks (CarrierMasks) producing a const ORDER, used to select/emit the RCM-ordered carrier variant (Approach-2 select, proven 202606081400); (ii) a Kit/macro that emits the RCM-ordered registration. Risks (real wall potential): the const-generic-N GCE-overflow-in-generic (the 071130 gotcha) for a const `[_; N]` order; proc-macro/build.rs cannot see resolved AccessSets. Leeway: prove ONE devirt-free auto-RCM-order path, or record the wall (→ op-decision: stay on manual-registration interim + future-toolchain). **Gates the GATE-1 dispatch order quality (per (a) loimu is order-sensitive), so near-term, but the manual-registration interim (D1d) is the fallback if §7-6 walls — GATE-1 is not blocked on §7-6, only its order-optimality is.**

**§7-6 RESULT (2026-06-09, sketch `202606090300_rcm-row-recovery-guarded-walk`, commit 3eff637): WORKS, NOT a wall.** Auto-RCM IS achievable devirt-free without manual registration, via a const-position-GUARDED type-level walk. Each WU carries a const RCM position (`<W as RcmPos>::POS`, computed by const-fn RCM over the carrier masks per 202606071000 / dispatch::order; hand-assigned in the sketch to isolate the walk question); the dispatch walks the cons-list once per output slot (0..N), executing only the WU whose const POS == the current slot. A fiber registered SCRAMBLED (C, A, B) with a real RAW chain ran in correct RCM order (A, B, C) and objdumped `blr=0 bl=0` (248 instrs, 30 vectorised), under the runtime morsel loop. The key relocation: the permutation lives in a const VALUE BRANCH inside the proven non-overlapping base/step walk, NOT in an impl selector (candidate (i)/`Nth<K>` → E0119, 202606071000 Tier A2/B) and NOT in a fn-ptr slot array (→ 2 blr under the morsel loop, 202606080300). LLVM folds the const guards and inlines the executes in RCM order; no GCE const-`[_;N]` (the order is per-WU const positions, not a const array length), no proc-macro/build.rs AccessSet visibility need (the order is a const derived from in-type masks at monomorphisation). Candidate (ii) (Kit/macro emit) is unnecessary. Cost: O(N_wus²) const-folded guard-checks per morsel, fine for cache-resident small-N fibers (bench-decidable vs the plain in-order walk for unusually large fibers). **Implication for op decision (b):** the provisional manual-registration constraint can be RELAXED via this mechanism rather than waiting on `generic_const_args` toolchain maturity. The GATE-1 build can (i) ship the manual-registration interim (D1d) first and adopt the guarded walk as the auto-RCM follow-on, or (ii) adopt the guarded walk directly so GATE-1 ships auto-RCM-ordered (op call (a)'s stated preference). Both de-risked; a build-sequencing call, the guarded walk's small O(N²) overhead the only tradeoff.

## 9. The Step-6 canonical-mirror mandate (the load-bearing verification)

The second expert pass (chart-the-path Step 6) mirrors this r2 against the canonical spec with ONE primary mandate beyond the usual divergence check: **verify that NO adaptive/replan trigger anywhere in the spec requires reordering dispatch or regrouping fibers from a RUNTIME signal** (as opposed to recomputing morsel sizes / configs / affinity / ranges). The pivot rests on dispatch order + grouping being static-structure. If even one adaptive path reorders dispatch from runtime data, that path must keep order runtime-resolved (Approach 2's per-frame branch, or per-morsel-amortised indirect), and r2 must record it as a required, not optional, capability there. My read + the expert survey both say no such trigger exists (R6's adaptive list is morsel/count/strategy/affinity; domain 22's heaviest trigger recomputes morsel sizes + approach, not order). The mirror's job is to confirm that exhaustively or find the exception.

**MIRROR VERDICT (Step 6, 2026-06-08, dispatched + returned; cross-checked against my own independent read of `:1486-1491`):** CONFIRMED exhaustively. No adaptive trigger reorders the WU dispatch sequence or regroups fibers from a runtime signal. All three domain-22 triggers (`:2042-2048`) land on the parameter side; `meta::PlanStage` "DAG changes" (`:2125`) is the structural-rebuild case, not a runtime reorder; domain-21 "strategy re-selection between frames" (`:2003`) is per-phase config re-selection, not topology change. The one edge ("record count → full plan recompute") re-selects the dispatch APPROACH (C/D vs E) within the same static WU set + fiber topology, which is the Approach-2 bounded-variant-select pattern, not an in-place reorder. The pivot's static-order/grouping claim holds against the full spec.

**Recorded UNAVOIDABLE DRIFT (chart-the-path Step 7).** D1b's retirement of type-level auto-derived fiber grouping is genuine unavoidable drift, but from an IMPLIED mechanism, not a stated spec requirement. The spec's Step 8 (`:1328-1348`) says "process WUs in RCM-reordered topo order" and implies the engine computes grouping from the WU graph; it does NOT state whether grouping is type-encoded or runtime plan data. The Rust coherence wall (E0119, proven thrice) makes type-level auto-derivation impossible without forbidden `specialization`. r2's recovery (builder-append + build-time topo-validation; RCM-row as the validated/recommended order; Approach-2 for runtime-recomputable grouping variants) preserves the spec's intent (engine computes grouping; RCM drives order) without contradicting any stated requirement. This is the only drift the mirror flagged, and it diverges from an implication, not a statement.

**Minor r2 fixes the mirror flagged, now applied:** (1) §1 now distinguishes the two `meta::PlanStage` cases (parameter-recompute vs structural-rebuild); (2) §6 now records that Approach-2 is the devirt-preserving realisation of the spec's record-count approach-selection across variable record counts, not merely optional.
