# Engine state map + roadmap r5: where we are after GATE-1 merge and the GATE-2 parallel core

**Date:** 2026-06-08
**Scope:** the whole hilavitkutin engine. A re-evaluation of shipped state against the canonical design, a drift audit of the roadmap/audit corpus, and the forward chart for the remaining architectural-completeness arc (E4 self-hosting meta pipeline onward).
**Method:** chart-the-path re-run. Two neutral read-only experts (a state-mapping comprehension pass over current source, a drift-mirror pass over the roadmap docs against canonical + source) plus first-party source confirmation of the two load-bearing points. The experts agree; first-party reads confirm both.
**Canonical oracle:** `mock/design_rounds/202604200055/202603181200_topic.hilavitkutin-design-consolidation.md` (consolidation spec; R6 `:2435-2446`, dispatch `:1564-1633`, adapt `:2006-2075`, self-hosting `:2119-2139`). Citations are `:line` into that file unless another path is given.
**Supersedes for currency:** the status columns of `202606081300_full-engine-overview-and-reconciliation.md` (still correct as a feature index; its 2026-06-08 status claims are updated here against post-G2-N source). Corrects `202606072100_gate2-canonical-deviation-ledger.md` §1/§4/§9 (see the correction header landed on that file).

This document answers two questions the maintainer posed: where are we against the canonical design and the roadmaps, and where is the drift; then, what is the proven path forward. The short answer to the first: GATE-1 is merged and the GATE-2 parallel core is functionally complete, including the canonical compile-time materialised dispatch that the most recent audit doc still records as un-shipped. The short answer to the second: the next genuinely-unbuilt canonical feature is the self-hosting meta pipeline (E4), its first slice is already sketch-proven, and the remaining arc after it is adapt + perf + plugin, in that dependency order.

## 1. Where we are: shipped state against canonical

The engine is much further along than the newest audit doc reflects. The two experts independently mapped current source against the canonical feature set; the picture is consistent.

**Dispatch is the canonical compile-time materialisation, not a runtime mask.** Single-core `Scheduler::run` dispatches through `RunTrunkDispatch::dispatch` (`dispatch/trunk_dispatch.rs:126`), which at each carrier position gates on two associated consts: `IsRoot::IS` (`trunk_of(POS) == POS`, `trunk_dispatch.rs:54`) and `Member::IS` (`trunk_of(Pos::INDEX) == TRUNK`, `trunk_gate.rs:67`). Both are compile-time, DCE'd to member-only monomorphised per-trunk programs. The only runtime elements are the phase-pass index match (`PhaseAt::VAL == p`) and the per-unit dirty bit. The N-core `run_parallel` path routes workers through the same per-trunk monos via `dispatch_core` (`trunk_dispatch.rs:138`), with core ownership a runtime `rank % ncores == core` predicate, one branch per trunk-root, not per unit. This is the domain-17 compile-time-flattened dispatch the spec specifies (`:1564-1633`), with core assignment as the single correct runtime quantity.

**The GATE-2 parallel surface is functionally complete.** Spawn-once pool (`scheduler/mod.rs:1354`), sense-reversing worker-side waist barrier (`thread/barrier.rs`, called from `worker_main` so workers run all phases hot), core-pinned trunks, head+tail convergence for single-trunk phases (`scheduler/mod.rs:1528`), and the threaded accumulator unit-outer path (`worker_accum_unit_outer`) all ship. The fair perf bench (engine vs optimal multi-threaded std, equal cores) puts the engine at parity with parallel std.

**GATE-1 is merged** (PR #132 to `dev`). The plan analysis chain runs (DAG, topo, waist, RCM, components, spectral for wide blocks, fiber grouping, morsel sizing, phase configs, column classification, upward-rank, dirty). Incremental skip (`dirty_units`, `scheduler/mod.rs:1046`) ships and gates both the morsel-outer and fused paths. Within-fiber fusion (`run_fused` / `FuseCarrier`, `dispatch/fusion.rs`) ships as the rust-pipe flattener. The FiberSlot runtime shim is deleted; `NonTopologicalRegistration` + `RecommendedOrder::from_rcm_order` ship as the build-time topo gate.

**What is genuinely unbuilt or partial**, in rough dependency order:

1. **Self-hosting meta pipeline (E4), absent.** `VirtualFirerApi::fire` is a literal no-op (`dispatch/engine_ctx.rs:1054`, empty body). `On<V>` is never consulted to gate dispatch: every WU dispatches as `Always`, because `RunFiber`/`RunGatedTrunk` bound `W: WorkUnit` (= `WorkUnit<Always>`). The four meta lifecycle virtuals (PlanStage/ScheduleReady/PassStart/ScheduleEnd), `MetaAccess`, and the kernel loop do not exist (`BACKLOG.md.tmpl:50-52`). `run` is a hand-written loop, not a WU-scheduled one. This is the spec's self-hosting design (`:2119-2139`) and it is the next build target.
2. **Adapt subsystem live loop (E8), absent functional logic.** The nine adapt axis types exist as API contracts and re-export shims (`adapt/mod.rs`), but no sampling, EMA update, or replan logic runs between frames. `plan_dirty`/`plan_cache` are set and then explicitly ignored in `run` (`scheduler/mod.rs:1133`). The three domain-22 replan triggers (`:2042-2048`) have no live path. Depends on E4 (the PlanStage/ScheduleEnd fire points are where adapt hangs) and on widening `PoolFrame` from its `<1,1>` right-size to real per-core/per-phase telemetry.
3. **RCM row-order auto-application, proven but unintegrated.** The guarded-walk auto-RCM mechanism is sketch-proven (`202606090300`, zero blr) but not wired into `run`; source still requires manual topological registration (the provisional constraint from op decision (b)). `topo_order`/`topo_count` are computed and stored but ignored at dispatch, retained for this relaxation.
4. **Intra-phase pipeline parallelism + progress counters, not built.** `ProgressCounter` exists but `progress_slots` is `NonNull::dangling()`; parallelism today is trunk-disjoint across cores, a correct subset of the canonical trunk + intra-phase-pipeline + convergence model. Perf, bench-decidable.
5. **Plugin facade integration, undocumented + unsketched.** The engine-core boundary (no runtime WU registration) and the extension layer both ship; the facade-WU integration pattern is a first-class roadmap item per r2 §5 with two pending feasibility sketches (§7-4a the facade `AccessSet`/`ContainsAll` question, §7-4b the per-morsel ABI hop). Downstream, post-core.

Vestigial code to clean: `synthesise_core_programs`/`CoreProgram` (`plan/core_program.rs`, real body, no live caller since the const-gated dispatch replaced the pre-projected-program path), `assign_cores_stub`/`synthesise_core_programs_stub` (`plan/steps.rs:1090,1098`), `progress_slots` dangling plumbing. The api-side `CoreProgram` type removal is gated on the #183 schedule-introspection question.

## 2. Where the roadmaps are: drift audit

**Roadmap r2 (GATE-1 full-engine) is aligned and fully consumed.** Its Phase D path landed as described: D1d-a/b/c (append builder + build-time topo validation + RCM recommended order), D1e-a/b (type-level walk threaded into `run`, shim deleted), C3-row (provisional manual-registration constraint with the §7-6 guarded-walk relaxation proven). D4 fusion, D6 ASM gate, E7 dirty-skip all ship. No r2 claim contradicts current source. Its remaining open items are the plugin sketches (§7-4a/b) and the RCM-row integration, both correctly marked pending.

**Roadmaps r3 and r4 (GATE-2 dispatch mechanism) are fully consumed.** r3's walk-level types (RunTrunk/FiberCons, RunPhase/RunPipeline) and r4's const mechanism (G-a ConstMask, G-b mask collection, G-c column numbering, G-d const grouping, G-e const-gated walk + DCE) all ship (`grouping.rs`, `trunk_gate.rs`, `trunk_dispatch.rs`). r3's G2-0c (build a nested carrier type from the plan) was correctly abandoned as the forbidden-specialization wall and superseded by r4's flat const-gated carrier. r4's one flagged residual (the N-wide associated-const array fold) shipped without hitting the wall. These are historical planning docs; their "UNBUILT" markers are expected-stale, not a problem.

**The deviation ledger (`202606072100`, dated 2026-06-07) is the one document with real, misleading drift.** It was written before tasks #677-685 landed and three of its ten entries now describe a superseded build state:

- **§1 (dispatch) is stale.** It records "we shipped the runtime-mask realisation of the canonical dispatch, not the compile-time-materialised one", tagged op-blessed with a build.rs/macro escalation path. Source shows the const-gated compile-time materialisation (the escalation target) shipped instead, via G-a..G-e. The headline deviation the ledger is built around is closed. The only remaining runtime element is core ownership (`rank % ncores`), which is correct design, not a deviation.
- **§4 (barrier) is stale.** It records "main thread serialises phases, workers park between phases". Source shows the worker-side sense-reversing `waist_barrier`: one publish/await per frame, workers run all phases hot. The canonical worker-side barrier the ledger listed as the escalation shipped.
- **§9 (threaded accumulator) is stale.** It records the unit-outer accumulator path as "out of scope in the threaded executor". Source shows `worker_accum_unit_outer` shipped (the §9 round). The bench red arm may persist; the implementation gap is closed.

The ledger's other entries hold: §2 (Pin placement), §3 (PoolFrame right-size), §5 (parking, aligned), §6 (spawn smuggle), §7 (raw aliasing under discipline), §8 (intra-phase pipeline not-built, aligned), §10 (inline scratch) are accurate. The ledger also never recorded the `VirtualFirerApi` no-op as a standing gap, which is the actual next-build item.

**Disposition:** the deviation ledger gets a correction header pointing here (audit-trail preserving, like the perf-finding correction), not a rewrite. The full-engine overview's status columns are refreshed by §1 above.

## 3. The forward chart: proven and sketch-status per step

The remaining canonical arc is architectural completeness plus perf, on top of a functionally-complete parallel execution core. Dependency order:

**E4: self-hosting meta pipeline. In flight (round 202606081200), the keystone.** It makes virtuals real and the scheduler self-hosting. Three slices:

- **E4 slice 1: virtual firing + `On<V>` dispatch gating.** SKETCH-PROVEN. `202606081400_e4-schedule-gated-walk` WORKS: a companion `Scheduled { type Sched: ScheduleGate }` assoc-type trait recovers each WU's Schedule unambiguously, and `<W::Sched as ScheduleGate>::should_run(fired)` dispatches the gate at compile time (Always const-folds to `true`; On<V> is a flag read), composing with the const-gated member walk like the dirty bit. Mixed Always/On<V> carriers compile in one cons walk. The src CL is the immediate next implementation step: add `Scheduled`+`ScheduleGate` to the api, generalise the `RunFiber`/`RunGatedTrunk` `W: WorkUnit` bound, add the domain-10 fired-flag store (epoch-based, spec `:685-714`) + the real `VirtualFirerApi` impl replacing the no-op. Leeway pinned: the exact firing semantics (per-(virtual,consumer) bits, epoch reset, clear-on-dispatch, same-pass vs next-pass) are the src-CL design grounded in `:685-714`, layered on the proven trait mechanism.
- **E4 slice 2: four meta virtuals + MetaAccess + self-hosting kernel.** The kernel loop shape is sketch-proven (`202606062100`, per the overview §6). Slice 2 composes that with slice-1's firing: fire PlanStage at lifecycle points, gate the meta resources (Dag, ExecutionPlan, LaneAssignment, SchedulerMetrics) behind `MetaAccess`, drive the ~50-line kernel (`:2119-2137`). SKETCH GAP: the `MetaAccess` gating of meta resources (proving a meta-WU reads ExecutionPlan through a gated accessor without polluting the consumer access analysis) is not separately sketched; fold a focused sketch into the slice-2 round if the api shape is not obvious from the existing Resource accessor.
- **E4 slice 3: consumer `On<meta::ScheduleEnd>` hooks + phase-overlap pipelining + the domain-22 adapt hook point.** Composition of slices 1-2 plus the intra-phase pipeline (item 4 below). **E4 slice 3 and E8 below are one connected arc, not two isolated steps** (critical-review finding, confirmed against spec): the spec places the adapt subsystem *inside* the meta pipeline. The replan triggers run between frames, between `ScheduleEnd` and the next `PlanStage` (`:2042-2048`), and the adapt EMA-sampling / trigger-evaluation logic is itself a set of consumer WUs gated on `meta::ScheduleEnd` (`:2006-2075`). So slice 3's `On<meta::ScheduleEnd>` hook surface IS the mechanism E8 attaches through; do not treat slice 3 as "done" before the adapt WUs exist, and work the slice-3/E8 boundary as a single arc.

**E8: adapt subsystem live loop. The continuation of E4 slice 3 (shares the `On<meta::ScheduleEnd>` attach point), plus wider PoolFrame.** EMA sampling/tuning between frames over the nine axes, the three replan triggers feeding parameter recompute into the static walk (never a reorder, per R6 and the r2 §9 mirror verdict). The decision logic is better-sketched than first stated: `202606062700_e8_adapt_hysteresis` proves the EMA + dead-band/cooldown trigger (cuts oscillation 5x), and the EMA formulation is bench-explored (`ema_formulation`, `ema_axis_h` benches). Remaining SKETCH GAP is narrower: the end-to-end *integration* wiring (a real `meta::ScheduleEnd`-gated adapt WU fires → recomputes morsel sizes/configs/affinity → feeds the static per-trunk walk on the next frame) is not sketched as one piece. Also requires widening `PoolFrame<1,1>` to real `<C,P>` telemetry (deviation §3); treat that widening as its own sub-step, it ripples to every PoolFrame construction.

**RCM row-order auto-application. Proven, independent, can land anytime.** Integrate the guarded-walk (`202606090300`) into dispatch so the engine auto-orders rather than requiring manual topological registration; relaxes the provisional constraint (op decision (b)). Impl, not feasibility; the sketch is the proof.

**Intra-phase pipeline parallelism + progress counters. Perf, bench-decidable.** Wire `progress_slots` for producer/consumer pipelining within a phase (deviation §8). Bench decides whether the trunk-disjoint subset suffices for target workloads.

**E5 P/E heterogeneity. Perf, sketches proven** (`202606062300_e5a-pe-core-detect` sysctl perflevel probe + homogeneous degrade, `202606062400_e5b-asym-morsel-bench` proportional-to-speed split 1.81x lower makespan; both confirmed present in the sketch tree): critical-path to P-core, leaf to E-core, proportional morsels. Integration on top of the parallel core.

**E6: N-vs-1 oracle. Sketch proven** (`202606062500_e6_n_vs_1_oracle`: bit-identical `Cfg::Out` at 1/2/7 cores for a commutative pipeline). The GATE-2 acceptance bench; the fair-bench harness now exists; E6 is reading it across N and recording the standing oracle.

**Plugin facade. Downstream, two feasibility sketches STARTED BUT NOT CONCLUDED** (r2 §7-4a/b). The sketch crates exist (`202606090100_facade-accessset-containsall`, `202606090200_facade-per-morsel-abi-hop`, each with `Cargo.toml` + `src/`) but neither has a `FINDINGS.md` recording its outcome, so per cl-claim-sketch-discipline they are not concluded: the feasibility verdict is unrecorded. §7-4a (the facade `AccessSet`/`ContainsAll` question) is the one genuine remaining feasibility unknown that could wall and trigger an op-decision; §7-4b (per-morsel ABI hop, host walk zero blr) is the same blr-class question that drove D1d/D1e, so not assume-low-risk without the recorded result. Concluding both (run them, record WORKS/FAILS in a FINDINGS.md) is a pre-plugin-build task.

**Cleanup. Anytime.** Remove `CoreProgram`/`synthesise_core_programs` (gated on #183 for the api type), the stubs, the dangling progress plumbing.

## 4. Strategic inflection for the maintainer

The GATE-2 parallel-execution core is functionally complete: const-gated compile-time dispatch, worker-side barriers, general DAGs, threaded accumulators, core-pinning, fair-benched parity with parallel std. What remains (E4 self-hosting meta pipeline, E8 adapt, E5 P/E, intra-phase pipeline, plugin facade) is architectural completeness and perf, not parallel-execution correctness. The maintainer could reasonably call the self-hosting meta pipeline GATE-3 and close GATE-2 now with the cleanup and a perf-variance pass (the 1M-record arm), rather than carrying E4 under the GATE-2 umbrella. This is a labelling/sequencing call, not a technical fork; the roadmap blesses E4 next either way, and the in-flight round 202606081200 proceeds. Recorded here so the call is visible, not blocking.

## 5. Bottom line

We are past the hard parts. The dispatch mechanism that the deviation ledger still frames as an unbuilt escalation is shipped and is the canonical one. The path forward is well-charted and largely sketch-proven: the full GATE-1-era E-series sketch sweep is confirmed present in the tree (`202606062100` meta-WU kernel, `062200` head+tail, `062300/062400` P/E, `062500` N-vs-1 oracle, `062600` dirty-skip, `062700` adapt hysteresis), so E4 slice-2's kernel, E5, E6, and E8's decision logic all stand on proven sketches. E4 slice 1 (the immediate next src CL) stands on the recent `202606081400` sketch. The genuine remaining sketch gaps are narrow and named: E4 slice-2 MetaAccess gating (a trait-boundary question in the same family as the prior partition walls, so worth a focused sketch), E8's end-to-end adapt-loop integration wiring (the decision logic is sketched; the firing-to-recompute-to-static-walk plumbing is not), and the plugin facade pair (§7-4a `AccessSet`/`ContainsAll`, §7-4b per-morsel ABI hop): both have sketch crates (`202606090100`/`202606090200`) but no recorded FINDINGS, so they are written-not-concluded; running them to a recorded verdict is a pre-plugin-build task, with §7-4a the one that could wall to an op-decision. No step on the path requires the dispatch structure to become runtime-mutable; every adaptive concern is a parameter fed into the static walk, exactly as R6 specifies and the r2 mirror confirmed. The single drift to correct in the record is the deviation ledger's stale §1/§4/§9, handled by the correction header.
